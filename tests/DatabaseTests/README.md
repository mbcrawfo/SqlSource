# Database tests

The projects of this folder are the tests that run against a real database: the ones where the describers' answers, the generated methods and the drivers meet a PostgreSQL or a SQL Server.  Each needs Docker running and starts its containers through Testcontainers, on the pinned images that [`TestHarness/DefaultImages.cs`](TestHarness/DefaultImages.cs) names.  They are the container projects of `tools/test-scopes.txt`, so `pre-commit-validation.sh` runs a project only when the uncommitted change can reach it ([test scopes](../../tools/README.md#test-scopes)), and CI and the nightly run cover every supported major of each engine between them ([the workflows](../../.github/workflows/README.md#nightly)).  [`tests/README.md`](../README.md) has the other test projects, the three libraries they all share and how they reference each other; [`AGENTS.md`](AGENTS.md) beside this file holds the rules of this folder.

Each project's folder and project file carry its short name, `Postgres/Postgres.csproj`, and its assembly and root namespace the prefix `SqlSource.DatabaseTests.`, which `Directory.Build.props` of this folder sets.

## The harness

`TestHarness/` is the library of this folder, `SqlSource.DatabaseTests.TestHarness`, which every project here references.  It holds the images, the start of a container, the folder of each engine's describer fixtures, the files of the end-to-end databases and the two driver-free containers, `PostgresContainer` and `SqlServerContainer`, which a project subclasses, giving its driver's `DbProviderFactory`, its image and the databases to build with their scripts in order, the first being the one that `ConnectionString`, `ExecuteAsync` and `ScalarAsync` use.  `PostgisContainer` is a `PostgresContainer` on a PostGIS image, for the NetTopologySuite tests alone: before it starts, it builds `Postgis/Dockerfile` through Testcontainers on the postgres image the subclass names, with PostGIS at the package version of its `Package`, as `sqlsource-postgis:<postgres tag>-<PostGIS version>`, `sqlsource-postgis:18.6-3.6.4` on `postgres:18.6`.  The image is kept after the run, so a later run on the same versions reuses it and Docker's cache rebuilds only a step that changed; the first build on each postgres image takes a minute or two.  It brings no driver, so the two driver-floor projects reference it too.  Its unit tests are in `tests/SqlSource.Tests/TestHarness/`, since they need no Docker.

## Running

```bash
dotnet test --project tests/DatabaseTests/Postgres
```

The first run pulls the image, and the first run of a PostgreSQL project on a postgres image builds its PostGIS image too.  `SQLSOURCE_TESTS_POSTGRES_IMAGE` and `SQLSOURCE_TESTS_SQLSERVER_IMAGE` run the two describer projects on another image, as CI does on each engine's oldest supported one:

```bash
SQLSOURCE_TESTS_POSTGRES_IMAGE=postgres:14.24 dotnet test --project tests/DatabaseTests/Postgres
```

```bash
SQLSOURCE_TESTS_SQLSERVER_IMAGE=mcr.microsoft.com/mssql/server:2017-CU31-GDR19-ubuntu-18.04 dotnet test --project tests/DatabaseTests/SqlServer
```

`Postgres.Npgsql8` and `SqlServer.SqlClient61` ignore the variables and run the default image.  A change to a describer project is run on both of its engine's images before it is pushed.

`dotnet test --solution` and the script leave `QueryMethodAllocation` out, since only the nightly runs it; [its readme](QueryMethodAllocation/README.md) has the command for one engine.

## The Npgsql 8 project

`tests/DatabaseTests/Postgres.Npgsql8` runs the write and read of `all_types` on Npgsql 8, the oldest driver that is supported, since the type map gives other C# types under it.  It is a project of its own because `tests/DatabaseTests/Postgres` cannot run on Npgsql 8: that project references the tool, which brings Npgsql 10, and a reference to 8 under it is a package downgrade.  So this one references the generator, `tests/SqlSource.Testing` and the harness alone, and pins Npgsql to 8.0.9 with `VersionOverride`, and `Npgsql.NodaTime` to 8.0.9 and NodaTime to 3.1.9, the floor that plugin needs, which central transitive pinning would otherwise raise to the end-to-end project's version.  It links `AllTypes.sql` and its sidecar from `tests/DatabaseTests/Postgres/EndToEnd/Queries/`, with the settings of the folder it is in, the end-to-end project's, the output `CodeGen` among them, so the generator builds the methods and the models that it gives under Npgsql 8.  It reads both rows of `all_types` through `ListAllTypes`' method, writes every column through `InsertEveryType`'s, with the values of row 1 and with the `NULL`s of row 2, and the columns of `InsertAllTypes` through its own, in transactions that are rolled back, and reads both rows through Dapper by the constant of `AllTypesSql`, a second claim of the file at the output `models`, all with the expectations of `AllTypesRows`.  It also links `Streaming.sql` and its sidecar, claimed by `StreamingQueries`, and its `StreamingQueryTests` collect the stream of `StreamAccounts` and break out of `StreamNumbers` partway through a million sorted numbers in a transaction that then commits, which a stream that cancelled its command would abort, since Npgsql 8 drains a disposed reader by its own code.  It also links `NodaTime.sql` and its sidecar from `EndToEnd/NodaTime/Queries/`, whose folder's settings file leaves NodaTime on, claimed by `NodaTimeQueries`, and its `NodaTimeQueryTests` write every column of `noda_values` and read it back, values, empty and unbounded ranges and `NULL`s, through the plugin on a data source that calls `UseNodaTime()`, with a copy of the end-to-end project's rows.  It also links `NetTopologySuite.sql` and its sidecar from `EndToEnd/NetTopologySuite/Queries/`, whose folder's settings file leaves NetTopologySuite on and names the database `gis`, claimed by `NetTopologySuiteQueries`, and its `NetTopologySuiteQueryTests` write every column of `spatial_values` and read it back through `Npgsql.NetTopologySuite` 8.0.9 on a data source that calls `UseNetTopologySuite()`, with NetTopologySuite pinned to 2.5.0, the floor that plugin needs, and a copy of the end-to-end project's rows and tests.  Its container, `AppContainer`, a subclass of the harness's `PostgresContainer` that its test classes share through the collection `UsesApp`, applies the schema and the seed of `app` on `EngineImage.Postgres.Default`, the default image, and ignores `SQLSOURCE_TESTS_POSTGRES_IMAGE`; `GisContainer`, a subclass of `PostgisContainer` shared through the collection `UsesGis`, does the same for `gis` on the PostGIS image built on that image.  It has no `--check`: the end-to-end project checks the sidecars it reads.

## The SqlClient 6.1 project

`tests/DatabaseTests/SqlServer.SqlClient61` runs the read and the write of `all_types` and `new_types` on Microsoft.Data.SqlClient 6.1, the oldest driver that is supported, the Npgsql 8 project's counterpart for SQL Server.  It is a project of its own because `tests/DatabaseTests/SqlServer` cannot run on 6.1: that project references the tool, which brings Microsoft.Data.SqlClient 7, and a reference to 6.1 under it is a package downgrade.  So this one references the generator, `tests/SqlSource.Testing` and the harness alone, and pins Microsoft.Data.SqlClient to 6.1.7 with `VersionOverride`, and NodaTime to 3.1.9, the oldest version that SqlSource supports, which central pinning would otherwise raise to the end-to-end project's version.  It links `AllTypes.sql`, `NewTypes.sql` and their sidecars from `tests/DatabaseTests/SqlServer/EndToEnd/Queries/`, with the settings of the folder they are in, the end-to-end project's, so the generator builds the models that it gives under 6.1, and claims each file twice: at the output `models`, for Dapper, and at `codegen`, for the methods, each output named by its claim's attribute, in one namespace, so that the two share the models.  It checks that their properties have the types and the nullability that the end-to-end project's have under 7, reads both rows of each table into them through Dapper and through the methods, and writes them back through the methods, each in a transaction that is rolled back, with the expectations of `SqlServerAllTypesRows`: every type of `all_types`, a `rowversion` in a `WHERE`, a C# enum over `tinyint`, `json` and `vector`, and the `NULL` of a `vector` that its query says cannot be null.  It also links `Streaming.sql` and its sidecar, claimed by `StreamingQueries`, and its `StreamingQueryTests` collect the stream of `StreamAccounts` and break out of `StreamNumbersThenMark` partway through a million sorted numbers, where the mark that the batch sets after the numbers shows that the command was not cancelled, since SqlClient 6.1 drains a disposed reader by its own code.  It also links `NodaTime.sql`, `NodaTimeOverrides.sql` and their sidecars from `EndToEnd/NodaTime/Queries/`, whose folder's settings file turns NodaTime on, claimed by `NodaTimeQueries`, and its `NodaTimeQueryTests` write `noda_values` and read it back through the methods, with a copy of the end-to-end project's rows and tests.  Its container, `AppContainer`, a subclass of the harness's `SqlServerContainer` that its test classes share through the collection `UsesApp`, builds `app` alone, with its schema, its seed and `new-types.sql`, on `EngineImage.SqlServer.Default`, the default image, and ignores `SQLSOURCE_TESTS_SQLSERVER_IMAGE`.  It has no `--check`: the end-to-end project checks the sidecars it reads.
