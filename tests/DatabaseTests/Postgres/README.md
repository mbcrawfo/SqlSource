# tests/DatabaseTests/Postgres

This project runs the PostgreSQL describer and the `describe` command against a real server, which Testcontainers starts in Docker.  It is also the end-to-end project of the generator, which it runs when it builds.  It proves five things: each step of the describer, from its session to the walk, with what only a server answers; every fixture case of the describer, described live and compared with its `expected.json` by `FixtureCasesTests`, which `tools/record-fixtures.sh` also runs to record them; the whole `describe` command with the real describer, in process and as the built tool; the realistic corpus, where each case is a query with a truth of which of its columns can be NULL, written by hand; and [the end-to-end project](#the-end-to-end-project), where the generator builds models from the project's own queries and from the realistic corpus's, with committed sidecars, the tool's `--check` finds those sidecars current, and every described query of `EndToEnd/` runs through its generated method on real rows, with Dapper beside the methods where the manual's Dapper recipe needs a proof.

## Running

The project needs Docker running, and its first run pulls the image.  It starts one container for the run, for the tests of the collection `UsesPostgres`, with the database `fixtures` and the schema `tests/SqlSource.Tool.Tests/Fixtures/Describers/postgres/schema.sql`, and a second database, `realistic`, for the realistic corpus below.  It also has the databases `app` and `billing` for the end-to-end tests, each built from the `schema.sql` and `seed.sql` in its folder of `tests/DatabaseTests/Postgres/EndToEnd/`.  `AllocationTests` starts a second container, of the same image, for itself alone ([below](#the-tests)).  The tests that need no server are not in the collection: `Describer/FixtureVersionTests.cs`, `Realistic/RealisticCasesTests.cs`, `Realistic/RealisticSamplesTests.cs`, `Realistic/Generation/RealisticClaimsTests.cs`, `Realistic/Generation/RealisticModelsTests.cs`, `Realistic/Generation/RealisticModelNullabilityTests.cs`, `Realistic/Generation/RealisticParametersTests.cs`, `EndToEnd/ModelShapeTests.cs` and `EndToEnd/MethodShapeTests.cs`.  An object that a test leaves on the first server has its text in `Describer/ScratchSchema.cs`, made by SQL that can run again, so it is the same whichever class runs first; one that changes what other tests see is dropped by its test in a `finally`.

```bash
dotnet test --project tests/DatabaseTests/Postgres
```

`dotnet test --solution SqlSource.slnx`, and so `pre-commit-validation.sh --full`, runs it on the default image.  A plain `pre-commit-validation.sh` runs it only when the uncommitted change can reach it, which [`tools/test-scopes.txt`](../../../tools/README.md#test-scopes) decides.

The project copies two fixture projects to its output, with the package's MSBuild files and `global.json`: `Single`, from `tests/SqlSource.Tool.Tests/Fixtures/Projects/`, and `ErrorPaths`, from `EndToEnd/ErrorPaths/`.  `DescribeCommandTests` runs the whole `describe` command in process against the container, over the fixture cases, `--check`, `--force` and `--log`, and `ToolProcessTests` starts the tool that was built in a process of its own and describes a copy of `Single`, whose `sqlsource.json` gives the dialect `postgres` and whose one file names the database `billing` by its header.  `ErrorPathTests` describes copies of `ErrorPaths`, [below](#the-end-to-end-project).

## The image

The image is `postgres:18.6`, named for the tests and the scripts in one place, `DefaultImages.Postgres` in `tests/DatabaseTests/TestHarness/DefaultImages.cs`, and repeated in `examples/PostgresExamples/docker-compose.yml`; the variable `SQLSOURCE_TESTS_POSTGRES_IMAGE`, `EngineImage.Postgres.Variable`, names another, which `EngineImage.Postgres.Image` gives the tests, and PostgreSQL 14 is the oldest that is supported, which CI runs as `postgres:14.24`:

```bash
SQLSOURCE_TESTS_POSTGRES_IMAGE=postgres:14.24 dotnet test --project tests/DatabaseTests/Postgres
```

Every database image the tests run is pinned to a major and a minor, such as `postgres:18.6`, and never to a bare major such as `postgres:18`.  The recorded fixtures carry the version of the server they were recorded against, and a bare major moves to each new minor without a word, so the tests would run a server the recordings never saw.  This holds for the default image, for the image CI runs on the oldest supported version, for the images of the nightly run, and for the image of any engine added later.  `PostgresDatabasesTests` fails, on `EngineImage.Postgres.Image`, on an image whose tag is not a major and a minor, or whose server reports another version, and `FixtureVersionTests` fails on a fixture case recorded against any version but the default image's.

Moving to a new minor is a change of its own: bump the tag, here and in `examples/PostgresExamples/docker-compose.yml`, record the fixtures again on the new image, as in the next section, write the sidecars of the end-to-end project, of the realistic cases and of the examples again, as in [writing the sidecars](#writing-the-sidecars), since each entry holds the server's version, and read the diff, all in the same pull request.  Nothing is recorded on `postgres:14.24`: moving it bumps its tag here, in `CONTRIBUTING.md`, in `.github/workflows/build.yml` and in the root `AGENTS.md`, and runs the tests on it.  The nightly run, `.github/workflows/nightly.yml`, runs the tests on every supported major between the floor and the default, on `postgres:15.19`, `postgres:16.15` and `postgres:17.11`.  Nothing is recorded on them either: moving one bumps its tag here, in `.github/workflows/nightly.yml` and in the root `AGENTS.md`, and runs the tests on it.

## The describer's fixtures

The describer's fixtures are in `tests/SqlSource.Tool.Tests/Fixtures/Describers/postgres/`: a folder for each case with its `query.sql`, the `capture.json` of describing it and the `expected.json` of its sidecar, whose `toolVersion` is `fixture` so that a new version of the tool touches no case.  A case may also hold an `issue.md`, which says where the case came from, and an `explain-settings.txt`, the settings of the planner it is described with.  `tests/SqlSource.Tool.Tests` replays each from its capture with no database, and this project describes each against the container and compares the entry, so a describer that asks something else fails the first and one that answers something else fails the second.  `FixtureCasesTests` describes each case through `FixtureCaseRuns.ShouldDescribeOrRecordAsync` of `tests/SqlSource.Tool.Testing/Fixtures/`, which compares it with the case's `expected.json` or, when `SQLSOURCE_RECORD_FIXTURES` is set, as the script below sets it, records it.  After a change to what the describer asks or answers, or to `schema.sql`, record them again and read the diff before it is committed:

```bash
tools/record-fixtures.sh postgres
```

To add a case, add its folder with a `query.sql` and run the script.  A recorded file is never edited by hand.

A case of the walk is named `walk-` and its shape, and `tests/SqlSource.Tool.Tests/Fixtures/WalkMatrixTests.cs` holds a row for each, written by hand, which fails for a `walk-` case it does not list.  To add a case that forces a join method:

1. Name it for the method, with `-hash`, `-merge` or `-nestloop` at the end.
2. Add an `explain-settings.txt` that turns the other two methods off, one `name=value` on a line, from the closed list of `PlannerSettings`: `enable_hashjoin=off` and `enable_nestloop=off` for a merge join.
3. Add its row to `Rows` of `WalkMatrixTests`, and an `InlineData` with the join's node type to `Capture_CaseNamedForAJoinMethod_WasPlannedWithIt` beside it.
4. Run the script.

`FixtureCasesTests` describes such a case with its settings, and `DescribeCommandTests` leaves it out, since a run of the command cannot turn a join method off.

## The realistic corpus

`tests/DatabaseTests/Postgres/Realistic/` holds the corpus and what reads it: the cases in `Realistic/Cases/`, each a folder with `query.sql`, `case.json` (the truth) and, when the case has models, its sidecar `query.sql.json`.  The `realistic` database is built from `tests/DatabaseTests/Postgres/Realistic/schema.sql` and `tests/DatabaseTests/Postgres/Realistic/seed.sql`.  The root of `Realistic/` holds what every layer shares: `RealisticCases`, which binds the project to its corpus, `RealisticSamples` and `RealisticDatabase`.  `RealisticCases.Corpus` is `RealisticCorpus.Postgres` of `tests/SqlSource.Tool.Testing/Realistic/`, which names the corpus's files and reads its cases through `RealisticCaseReader`, each a `RealisticCase` of that folder, whose `SkipUnlessRunsOn` and `SkipIfRefused` are how a test skips a case; `RealisticCases.Models` finds a case's models in this assembly, and `RealisticCases.Describe` describes a case on `realistic`.  A test reads a case's committed entry through `RealisticModels.EntryOf`.  What both engines' corpora share, the corpus and its cases, the checks of a sample, the claims of `RealisticQueries.cs` and `RealisticMethods.cs`, the finding of a case's models and methods, the checking and calling of a method (`RealisticCalls`), the input model of a sample, the description of a case, the columns a description must have and the arithmetic of the noise budget, is in `tests/SqlSource.Tool.Testing/Realistic/`, and its tests are in `tests/SqlSource.Tool.Tests/Realistic/`; [SQL Server's corpus](../SqlServer/README.md#the-realistic-corpus) is built on it too.  `Realistic/Describer/` holds the describer's checks over it, the description whole in `RealisticDescriptionTests` and its nullability in the classes named `RealisticNullability*`:

- `RealisticDescriptionTests` checks that a case is refused only as its `refusal` says, by that id, and that a case with models is described as its committed sidecar's entry holds, every field of it but the server's version.  That whole-entry comparison includes the provenance and the origins, which `--check` ignores;
- `RealisticNullabilitySafetyTests` checks its nullability against the truth and against the oracle that executes the query over the seed;
- `RealisticNullabilityNoiseTests` holds the count of columns that are not null and that the describer answers as nullable or unknown to a budget for each recorded major, 14 and 18, in its `Budgets`.

A case has models when neither the describer nor the generator refuses it.  Each such case is claimed twice, by a class of its own in each of two files, since no one class can claim them all: a `Path` that names a folder searches none of the folders below it, and the attribute is not `AllowMultiple`.  `Realistic/Generation/RealisticQueries.cs` claims it at `Models`, and `Realistic/Generation/RealisticMethods.cs` claims it a second time at `CodeGen`, so that the project holds its models and its method.  The two classes are in one namespace, so that they share the models.  `Realistic/Cases/sqlsource.json` gives those queries the logical database `realistic` and the type override `"timestamptz": "default"`, which takes out the project's `System.DateTimeOffset` for `timestamptz`, so that the corpus is read by the base type map.  Each case's sidecar is written by `tools/describe-end-to-end.sh`, as [the end-to-end project's](#writing-the-sidecars) are, and `CheckTests` finds it current.  `Realistic/Generation/` holds the checks of the generated models:

- `RealisticClaimsTests` reads the classes of `RealisticQueries.cs` and `RealisticMethods.cs` from their source, through `RealisticClaims`, and fails on a case with models that is not claimed exactly once at each output, on a class of a case without models, on a claim of a folder that is not a case, and on a class at the wrong output for its file.
- `RealisticModelNullabilityTests` reads each case's compiled output model, pairs each column of the truth with the property at its position, which must be named after it, and fails on a column that can be `NULL` whose property cannot hold null.  It reads the truth and never the sidecar's nullability, so it can fail where `--check` passes.
- `RealisticDapperTests` runs each case's query over the seed through Dapper into its output model, once for each sample, in a transaction that is rolled back.  It builds the input model from the sample's literals as the server reads them and passes its values under the SQL's snake_case names in a `DynamicParameters`, since Dapper does not bind them to the model's PascalCase properties ([D-0004](../../../docs/deferred/D-0004-input-models-bound-by-the-names-of-the-sql.md)).  It fails on an error, on a row of another type and on a case that reads no row for any sample, and asserts no value, which is the oracle's business.
- `RealisticMethodTests` runs each case through its generated method over the seed, once for each sample, in a transaction that is rolled back and that every call is given, the cases with `dapper` included, and reads every row into the output model.  The input model is built as `RealisticDapperTests` builds it, but is given to the method itself, which binds each parameter by its described type.  It fails on an error, on a row of another type, on a case that reads no row for any sample and on a `NULL` read into a property that is not nullable.  That failure names each column that held a `NULL` over the seed, with its property, through a rerun of the sample by `RealisticNullabilityOracle` after the rollback.  It needs the server, and asserts no value.
- `RealisticModelRefusalTests` describes each case with `models` against the `realistic` database into a sidecar held in memory, runs the generator over its query and that sidecar at `Models`, under the repository's own settings files of the project and of `Cases/`, and fails unless the generator gives exactly one error, of the id that `models` names.  So a case that the generator comes to accept, or refuses otherwise, fails naming itself.
- `RealisticModelsTests` and `RealisticParametersTests` test how those find this project's models, a case's method (`MethodOf`) and read a case's sample on Npgsql.  The reading of a claim, the building of an input model from its values and of Dapper's arguments from the model are tested in `tests/SqlSource.Tool.Tests/Realistic/`.

`RealisticClaimsTests`, `RealisticModelNullabilityTests` and the two tests of the helpers need no server.

A change to what the describer asks or answers, or to the schema, the seed or a case, writes the cases' sidecars again with `tools/describe-end-to-end.sh`, as in [writing the sidecars](#writing-the-sidecars), and its diff is read before it is committed.  The sidecars are written on the default image and compared on PostgreSQL 14 and 18, each on the majors that run its case and that its `checkedFrom` does not leave out.  Of a refused case, only its id is compared: the arguments, the help and the server's lines of its failure are compared nowhere.

A `case.json` can also say:

- `minimumMajor`, when the case needs a later server than 14.  The checks, `--check` and the runs through Dapper and through the method leave it out on an earlier major.
- `samples`, a SQL literal for each parameter.  A check that executes the query runs it over the seed with them.
- `refusal`, the id of the failure, when the describer refuses the case.  The case then has no columns, no class and no sidecar.
- `models`, a `refusal` and a `why`, when the generator refuses the models of a case that the describer accepts, as it refuses `two-columns-named-id` with `SQLSRC255`, since its two columns `id` give one property name.  The case keeps its SQL and has no class and no sidecar, and the describer's checks still read it.  `RealisticModelRefusalTests` checks that the generator still refuses it so.
- `checkedFrom`, a `major` and a `why`, when an earlier major describes the case otherwise than its sidecar, which is written on the default image.  `--check` and the comparison with the sidecar on an earlier server then leave the case out, and no committed record then says how the earlier major describes it: `docs/tech-debt` holds that limit once, in TD-0051, and a case that has the member adds its name there.  The `major` is a recorded one above the first recorded major the case runs on, since one at or below it leaves nothing out.  One case has it today, `exists-as-column`, from 18.
- `dapper`, a `why`, when Dapper cannot send a parameter of the case: a `string` that it sends as `text` where the query compares it with an enum or a `jsonb`, for which the server has no operator.  The member leaves the case out of the run through Dapper alone: `RealisticMethodTests` runs it, since the generated method binds each PostgreSQL parameter by its described type.  Four cases have one today.

A column that can be `NULL` says why, and an `exempt` says why the seed cannot show it, so it needs a reason and belongs only on a column that can be `NULL`.  `RealisticCaseReader`, through which `RealisticCorpus` reads each case, refuses a `case.json` that breaks either.  Every folder of `Cases/` is a case.

To add a case, add its folder with a `query.sql` and a `case.json`, which holds the truth, written from the SQL and `schema.sql` and never from what the describer answers.  Add its class to both `Realistic/Generation/RealisticQueries.cs` and `Realistic/Generation/RealisticMethods.cs`, unless the describer refuses it, which its `refusal` says, or the generator does, which its `models` says.  When the case has models, and so a class, run `tools/describe-end-to-end.sh`, which writes its sidecar: the project does not build while a claimed query has none.  A case that the describer or the generator refuses has no sidecar to write.  When a column of the truth can be `NULL` and no row of `seed.sql` makes it so, add such a row to `seed.sql`, which never removes one; `exempt` is for a `NULL` no seed can show.  The noise budget is lowered in the change that lowers the noise, the test says to, and raised only in a change that adds cases.

## The end-to-end project

`EndToEnd/` is where the project uses the generator as a consumer does.  The project imports `src/SqlSource/build/SqlSource.props` and `SqlSource.targets` by path, references the generator as an analyzer, and its `sqlsource.json` sets the dialect `postgres`, the logical database `app`, the output `CodeGen`, the input model's suffix `Args` and type `record`, the collection type `IReadOnlyList` and the type override of `timestamptz` to `System.DateTimeOffset`.  It lists `SQLSRC240` in `WarningsNotAsErrors`, so that a pull request that raises `VersionPrefix` warns until the sidecars are written again.  The cases of [the realistic corpus](#the-realistic-corpus) are queries of the same project, with settings of their own.

### The databases

The container has two logical databases for `EndToEnd/`, each built from the `schema.sql` and `seed.sql` of its folder, and the realistic corpus's queries use a third, `realistic` ([above](#the-realistic-corpus)):

- `app`, in `EndToEnd/app/`: the tables `accounts` and `notes`, which a `LEFT JOIN` reads, the enums `account_status`, read as a `string`, and `note_kind`, read as a C# enum, the domain `email`, with a `CHECK`, and the domain `note_ref`, over `bigint`, of the column `notes.ref`, the extensions `citext`, `cube`, `hstore` and `ltree`, and `all_types`, with a column of every type that the type map gives a C# type for on Npgsql 8 and 10, which leaves out `cube`.  Its seed has two rows of `all_types`: row 1 with a value in every column and row 2 with `NULL` in every column but `id`.
- `billing`, in `EndToEnd/billing/`: the table `billing.invoices`, in a schema of its own.

### The tests

- `ModelShapeTests` reads the models by reflection: the name, the shape and the properties that the settings give each.  It also holds each key of the type map to the property of `InsertEveryType` or the query that writes and reads it, `MapWritten`, checked against the parameter's described type in the committed sidecar, or to why none can, `MapLeftOut`.  It needs no server.
- `MethodShapeTests` reads the generated methods by reflection: what each declares by its shape, its collection type, its suffix and its location.  It needs no server.
- `CheckTests` runs `describe --check`, through `CliRun.Real`, over the real project, with a connection to each database, `realistic` included, and finds every committed entry the same.  On a server that leaves a realistic case out, by its `minimumMajor` or its `checkedFrom`, as PostgreSQL 14 leaves out `merge-returning`, it runs twice: once over the realistic cases it checks, each named by its `query.sql`, and once over `app` and `billing` whole.
- `ErrorPathTests` describes a copy of `ErrorPaths`, a small project that is never compiled, and makes its sidecar stale, or its query one that the server refuses.
- `AccountQueryTests`, `NoteQueryTests`, `ShapeQueryTests`, `InvoiceQueryTests`, `MethodQueryTests`, `CollectionQueryTests`, `RowBufferQueryTests`, `StreamingQueryTests` and `LocationQueryTests` run each query of their files through its generated method, with its input model as the parameters, on an open connection or a closed one, and assert the values of the rows, `NULL`s included, a `rowcount`'s count, and the exception of a shape that the rows break.  A test that writes runs in a transaction that is rolled back, but for the test of `StreamingQueryTests` that breaks out of a stream in a transaction, which commits its write into a temporary table of its own connection.  `EndToEndSources` sets up a data source as the manual's recipe says.
- `StreamingQueryTests` runs the streaming methods of `StreamingQueries` and holds what their callers can rely on: the arguments are checked at the call and not at the first row, a closed connection is opened by the first `MoveNextAsync` and closed again after a loop that ends, breaks or throws, an open one stays open, a stream enumerated twice runs its query twice, an enumerator disposed before it moved opens nothing, a command run in the loop's body is refused by Npgsql with `NpgsqlOperationInProgressException`, a `break` partway through many rows leaves the connection usable and a transaction of the caller's to commit, a cancellation by the method's token or by `WithCancellation` throws an `OperationCanceledException`, and a `NULL` in a `NOT NULL` column throws an `InvalidCastException` at its row after the rows before it.  `StreamNumbersFailingHalfway` holds what an error in the rows that a `break` leaves unread does: read to the end, the stream throws the `PostgresException` of the division by zero after 499,999 rows; a `break` after 10 rows throws it from the loop, since the disposal reads the rest, and leaves the connection usable; an exception of the loop's body is replaced by it; and in a transaction the next command is refused with `25P02`, as the error aborted the transaction.
- `RunTimeTests` runs the methods with what they take at run time: a transaction whose rollback undoes the write, a `commandTimeout` that expires on `pg_sleep`, a token cancelled before the call and while the rows are read, a closed connection closed again after a return and after an exception, an open one left open in its transaction, a null parameter, and a `DateTimeOffset` at an offset and a `DateTime` of a `Kind` that Npgsql refuses before sending.
- `EveryTypeTests` writes every column of `all_types` through `InsertEveryType`'s method, with the values of row 1 and with the `NULL`s of row 2, and reads each back by `RETURNING` and by `ListAllTypes`, each in a transaction that is rolled back; writes and reads `cube` through `EchoCube`; and shows that the server refuses a string longer than its `varchar(n)`.
- `AllocationTests` measures the bytes that `GetAccountName`, `ListAccounts` and `ListClosedBefore` allocate for each call through their methods, against hand-written ADO.NET methods of the same calls, after a warm-up, in 500 pairs of calls, one of each method, each call measured on its own, and fails when the commonest difference of a pair is more than a margin of 64 bytes.  Each query has two pairs: its method of `AccountQueries`, which reads its rows into the pooled buffer, against a hand-written method that reads them into `RowBufferByHand` of `tests/DatabaseTests/TestHarness`, the same buffer by hand, and its method of `UnpooledAccountQueries`, under `no-array-pool`, against one that reads them into a `List`, so that in each pair the two make the same calls and an object that the generated method allocates on each call shows.  The numbers queries `NumbersAsList`, `NumbersAsIList`, `NumbersAsICollection` and `NumbersAsImmutableArray`, at 3 rows, are measured the same way in two pairs each, against a method that copies the rows of `RowBufferByHand` with `ToList` or `ToImmutableArray`, and, for their `NumbersNoPoolAs` twins, against one that returns a `List` as it is or drains an `ImmutableArray` builder.  The streaming `StreamAccounts` has a pair of its own, against a hand-written static local async iterator that makes the same calls, measured over a loop to the end of the stream.  Three more tests hold the pooled `NumbersAsArray`, `NumbersAsList` and `NumbersAsImmutableArray`, at 300 rows, each to allocating at least a given number of bytes less than the hand-written baseline of its result, since the pairs against `RowBufferByHand` cannot see the buffer's own cost: a `List` copied to an array, `NumbersAsArray_PerCallOfAFewHundredRows_AllocatesLessThanAListCopiedToAnArray`; a `List` grown by doubling and returned as it is, `NumbersAsList_PerCallOfAFewHundredRows_AllocatesLessThanAGrownList`; and an `ImmutableArray` builder that is drained, `NumbersAsImmutableArray_PerCallOfAFewHundredRows_AllocatesLessThanABuilder`.  So a pooled method that allocated even its largest buffer, or a result member that lost its pooling, fails its test.  It counts every thread, so it is in the collection `MeasuresAllocations`, which runs while no other test does and starts a container of its own.  What the driver allocates on some calls and not others, and what the process does on other threads in the meantime, such as sending the test platform's telemetry, is still counted in the calls it falls in, and the commonest difference leaves those pairs out ([why](../TestHarness/EndToEnd/CallAllocations.cs)).  It skips under coverage, whose collector allocates in the process on some calls and not others, so CI runs it in a step of its own without coverage ([why](../TestHarness/EndToEnd/CallAllocations.cs)).
- `DapperRecipeTests` proves what the manual's Dapper recipe says beyond the queries: the parameters it sends by its sample, `Types/TypedParameter.cs`, and by a cast in the SQL, each column of `WriteSideLeftOut` written so in a transaction that is rolled back, a C# enum sent as its number, a `DateTimeOffset` at offset 0, an `Email` read, by `NoteSql`'s constant, and sent, each through the recipe's type handler, `Types/EmailHandler.cs`, and which records Dapper fills.

`AllTypesQueryTests` reads both rows of `all_types`, every column of each, through `ListAllTypes`' method and through Dapper by `AllTypesSql`'s constant.  It writes a row with a parameter for each type that Dapper can send, through `InsertAllTypes`' method and through Dapper, and reads it back, and lists the other types in `WriteSideLeftOut`, each with what Dapper or Npgsql said, and a test fails when one of them comes to bind through Dapper.  The expectations of both rows are in `tests/DatabaseTests/TestHarness/EndToEnd/AllTypesRows.cs`, which `tests/DatabaseTests/Postgres.Npgsql8` shares to read and write the same rows on Npgsql 8.  It fails on a property with no expectation, so a column added to `all_types` adds its value in the seed, its expectation there, its parameter to `InsertEveryType`, declared `null`, and its parameter to `InsertAllTypes` or its row to `WriteSideLeftOut`; a type added to the map adds its key to `MapWritten` or `MapLeftOut` of `ModelShapeTests`.

### Writing the sidecars

Every sidecar under `EndToEnd/Queries/`, every sidecar of the realistic cases under `Realistic/Cases/`, and every sidecar of `examples/PostgresExamples`, is written by one script, never by hand:

```bash
tools/describe-end-to-end.sh
```

It starts a container of the default image and applies the schemas and seeds of `realistic`, from `Realistic/`, and of `app` and `billing`, then deletes the sidecars of the end-to-end queries and of the realistic cases and runs `describe --force` on the project.  It then does the same for the examples, on a database `examples` made from their `schema.sql`.  After PostgreSQL's part, the same run starts a second container, of SQL Server 2025, which Apple silicon runs under emulation, and rewrites SQL Server's sidecars ([its part](../SqlServer/README.md#writing-the-sidecars)).  The project does not build while a sidecar is missing or stale, so the script runs the tool from its source, not a test.  Run it after a change to a query, a schema or a seed of `EndToEnd/`, of the realistic corpus or of the examples, after a case is added to the corpus, after a move to a new minor of the default image, and in the pull request that raises `VersionPrefix` ([`docs/publishing.md`](../../../docs/publishing.md)), and read the diff before it is committed.
