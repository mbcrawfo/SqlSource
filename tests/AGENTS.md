# AGENTS.md - tests

Seven xunit projects and the two libraries they share.  [`README.md`](README.md) says what each is, which Roslyn it runs on and how they reference each other; this file is the traps.

- **A test project compiles no `.cs` file of another project, with one exception.**  Code that two test projects need is in one of the two libraries, which they reference.  The exception is `tests/SqlSource.Tests/Generator/`, whose test classes `tests/SqlSource.Tests.RoslynFloor` compiles a second time against Roslyn 4.8.0; its own `AGENTS.md` says what that asks of a test there.  `tests/SqlSource.Tests/TestLayoutTests.cs` fails on any other `Compile` item of a test project that names a file outside the project's folder, however its path is spelled, on a file of `Generator/` whose name does not end in `Tests.cs`, and on one without the line that says it is shared.
- **The two libraries, `tests/SqlSource.Testing` and `tests/SqlSource.Tool.Testing`, hold no tests.**  `tests/SqlSource.Tests.RoslynFloor` references `SqlSource.Testing`, so it stays on the pinned Roslyn with no `VersionOverride`, and what that asks of the code is in the `AGENTS.md` of `tests/SqlSource.Tests/Generator/`.  Keep the two apart: the tool raises Roslyn to a current version, which would reach RoslynFloor through one library ([why](README.md#the-projects)).  Their types stay `internal`, except `SettingLevel` of `tests/SqlSource.Testing/Generator/LevelSettings.cs`, which a public theory takes as its row.  A helper that one test project alone uses stays in that project; one that a second project comes to need moves into a library.
- **A test reads a generated model by reflection through `ModelReflection` of `tests/SqlSource.Testing`**, which orders the properties by `MetadataToken`, the order they are declared in.  `Type.GetProperties()` does not promise that order, so a test never compares it.  `tests/SqlSource.Tests/ModelReflectionTests.cs` tests the helper.
- **Every test that opens a describer opens it through `Describers.OpenAsync` of `tests/SqlSource.Tool.Testing`** (the tool's tests, `PostgresScript`, `SqlServerScript` and `FixtureReplay` among them), and none builds an `OpenRequest` but to look at it.
- **What both engines' realistic corpora share**, `RealisticCorpus`, `RealisticCase`, `RealisticCaseReader`, `RealisticSampleChecks`, `RealisticDescriptions`, `RealisticNoise`, `RealisticEngine`, `RealisticClaims`, `RealisticModels`, `RealisticCalls`, `RealisticInputs` and `RealisticDescribe`, **is in `tests/SqlSource.Tool.Testing/Realistic/`**, with its tests in `tests/SqlSource.Tool.Tests/Realistic/`; what reads a database through a driver stays in each engine's project.  Each engine's `Realistic/RealisticCases.cs` holds only the binding of its corpus, its models and its describer, and every test reads the corpus through it.
- **`tests/SqlSource.Tests.Postgres.Npgsql8` holds the write and read of `all_types` on Npgsql 8, through the methods and through Dapper, and nothing else.**  It references nothing that brings Npgsql 10, neither the tool, `tests/SqlSource.Tool.Testing` nor `tests/SqlSource.Tests.Postgres`, since a reference to 8 under 10 is a package downgrade ([why](README.md#the-npgsql-8-project)).  It links `AllTypes.sql` and its sidecar from `EndToEnd/Queries/` and commits none of its own, nor a `sqlsource.json`: the linked file takes the settings of its own folder, the end-to-end project's, so a setting changed there changes this project's models and methods.
- **`tests/SqlSource.Tests.SqlServer.SqlClient61` holds the read of `all_types` and `new_types` through Dapper, and their write and read through the methods, on Microsoft.Data.SqlClient 6.1, and nothing else.**  It references nothing that brings Microsoft.Data.SqlClient 7, neither the tool, `tests/SqlSource.Tool.Testing` nor `tests/SqlSource.Tests.SqlServer`, since a reference to 6.1 under 7 is a package downgrade ([why](README.md#the-sqlclient-61-project)).  It links `AllTypes.sql`, `NewTypes.sql` and their sidecars from `tests/SqlSource.Tests.SqlServer/EndToEnd/Queries/` and commits none of its own, nor a `sqlsource.json`: the linked files take the settings of their own folder, the end-to-end project's, so a setting changed there changes this project's models and methods, and its two claims at `models` name that output on their attribute, since the end-to-end project's is `CodeGen`.  A type that a query of those files names by a type override is in `tests/SqlSource.Testing`, as `Level` is.
- **Tests mirror the source folders.**  A test of `src/SqlSource/<Folder>/<Type>.cs` is `tests/SqlSource.Tests/<Folder>/<Type>Tests.cs`, and a test of the tool's `<Folder>/` is in `tests/SqlSource.Tool.Tests/<Folder>/`.  Namespaces follow folders, so a moved test changes its namespace.  The driver tests of `tests/SqlSource.Tests/Generator/`, such as `ModelTests`, `NpgsqlProbeTests`, `QueryTypesTests`, `ColumnMarkerTests` and `SidecarTests`, are named after types of other folders and stay in `Generator/`, which RoslynFloor compiles.  The fakes and helpers that only the tool's tests use stay at that project's root, in `SqlSource.Tool.Tests`, which every sub-folder sees without a `using`; so do the tests of `ToolHost`, of `Outcome` and of a helper.  The tests of the `Fixtures/` and `Realistic/` harnesses of `tests/SqlSource.Tool.Testing` mirror their folder there, in `tests/SqlSource.Tool.Tests/Fixtures/` and `tests/SqlSource.Tool.Tests/Realistic/`, and the tests of its other helpers stay at the root.  The split classes `PostgresSession*`, `PostgresEvents*`, `NullabilityWalk*`, `SqlServerSession*` and `SqlServerEvents*` share their cases through a static helper, `DatabaseRuns*` through `DatabaseRunsScene`, composed as `DescribeScene` is, and `SqlFileParser*` of `tests/SqlSource.Tests/Parsing/` through `ParseOf`, and no base class ([the tool's helpers](README.md#the-projects)).
- **Every test that runs the generator or its emitter states its output.**  It passes an `OutputKind` to the harness's `OutputKind?` parameter, which has no default, nor has a helper of a test class that runs the generator: `Sql`, unless the test is of what an output that needs entries does, as the tests of sidecars and of their caching are.  The harness writes it, with the run's dialect, generator parameters and `settings`, a JSON object whose entries win, into the project's settings file at `GeneratorHarness.ProjectSettingsPath`, `/sqlsource.json`, the farthest folder of every path, so a test's own file is nearer and wins; a test's own file at that path beside it is refused, and its keys go in `settings`.  It passes `null`, which writes no `output`, only when it needs the project not to set it, as a test of the default or of the output's levels does, when its own root file, which hides the project's, or its own file at that path gives the output, and says so in a comment.  A test of `TypeEmitter` sets `Output` on each file's level.  The default, `CodeGen`, needs an entry in a sidecar for each query, so a test that leaves it unsaid gets `SQLSRC209` for each file under `ansi`.  `Microsoft.CodeAnalysis` has an `OutputKind` too: a file that imports it names the generator's with `using OutputKind = SqlSource.Settings.OutputKind;`.
- **A test gives a setting in `settings:`, a folder's settings file or a marker, or in `TestProject.Settings` or an `AddSettings` file, never in a property or metadata, which neither the generator nor the tool reads.**  `SqlSourceBuildFolders` is a build input, not a setting, which any test may set; the rule holds even for a test that would show that such a property is not read.
- **`tests/SqlSource.Tests/Snapshot/Examples/*.json` are sample sidecars, valid against `schemas/sidecar-v1.schema.json`**, which `SidecarSchemaTests` checks; `tests/SqlSource.Tests/Snapshot/SidecarExamples.cs` reads them from the output folder by that path.
- **`tests/SqlSource.Tool.Tests/Fixtures/Projects/` holds projects that are never built or restored.**  They are not compiled into the test project, and a test that leaves an `obj` in the repository, or a file in a fixture, is a bug ([fixture projects](README.md#fixture-projects)).  `OddPaths` holds a folder whose name has `;`, `=`, `%`, a quote and a non-ASCII letter on purpose.
- **No test of the tool waits for a time to pick an order, or changes the test process unseen.**  A test that needs the answers of `tests/SqlSource.Tool.Testing/FakeProcessRunner.cs` in an order, or several open at once, holds them with `tests/SqlSource.Tool.Tests/ProcessGate.cs` and not with `Task.Delay`.  A test that changes the environment of the test process is in the collection `ChangesTheEnvironment`, which runs alone, and puts back what it changed.  A test starts a program through `Programs.RunAsync`, never `Process.Start`, and starts `dotnet` as `Programs.Dotnet`, the one that the tool runs, never as `"dotnet"`.  A test that waits for what a program or the server does waits through `Eventually`, whose `Patience` is the one limit, which `ProcessGate` and every caller of `Programs.RunAsync` use too, and not with a loop of `Task.Delay`.  A test that starts a program of the operating system skips with `Programs.SkipUnlessOnPath` where the program is missing, and one that needs a program that waits takes it from `Programs.Waiter`, whichever the operating system.  `tests/SqlSource.Tool.Tests/Commands/TerminationTests.cs` is the one test of the tool's project that starts the tool as a process, and `Describer/ToolProcessTests.cs` the one of each container project, `tests/SqlSource.Tests.Postgres` and `tests/SqlSource.Tests.SqlServer`: each starts it through `ToolProcess.ShouldDescribeOneQueryAsync` and so `Programs` of `tests/SqlSource.Tool.Testing`, `Programs.ToolStart`, or for the closed console `cmd /c start` with `Programs.ToolPath` and `Programs.SetToolEnvironment`, which runs the copy in the tests' output with `--roll-forward LatestMajor`, since the libraries beside that copy are of the tests' runtime, and `ToolStart` with the tests' deps file, which names SqlClient's copy for the platform where the tests' output has it.  `TerminationTests` looks for the run's folder and for nothing else in the temporary directory, where a killed MSBuild leaves the pipes of its runtime.  Its project has a target that writes a file and then waits for two minutes, so that a test sends its signal when MSBuild has a program of its own running, and a run ends only when it is told to.  Try a change to its test of a closed console by starting `nightly.yml` by hand ([why](README.md#the-projects)).
- **A run, a host and a session of the tests stand on `TestClock` of `tests/SqlSource.Tool.Testing`**, which stands still until a test moves it, unless the test brings a clock: a test that needs the machine's passes `TimeProvider.System` and says why.
- **`tests/SqlSource.Tests/Documentation/` checks the documents a user reads**, `README.md`, `src/SqlSource.Tool/README.md` and every page of `docs/manual/` (except its `AGENTS.md`): `UserDocsLinksTests` their links and anchors, and `UserDocsSamplesTests` the SQL in their fenced blocks.  `UserDocs.cs` finds those documents from `RepositoryRoot` and is the one place that knows what counts as a user document.  A fenced block opens with `sql`, and a second word says how it is parsed: a dialect, `fragment` for part of a file, or `error` for SQL that shows a mistake.  Mark a sample so; do not weaken the test.  The two readmes are packed, so their links are absolute, `https://github.com/mbcrawfo/SqlSource/blob/main/<path>`, and a test follows those too.
- **The `PackageDownload` items of Npgsql and Microsoft.Data.SqlClient in `tests/SqlSource.Testing/SqlSource.Testing.csproj` list the versions of `tests/SqlSource.Testing/Generator/NpgsqlReferences.cs` and `tests/SqlSource.Testing/Generator/SqlClientReferences.cs`.**  A mismatch builds and fails only when a test runs.
- **Allocation budgets are tests.**  `Parsing/SqlFileParserAllocationTests.cs`, `Generation/Paths/PathResolverAllocationTests.cs` and `Snapshot/Reading/SidecarReaderAllocationTests.cs` in `tests/SqlSource.Tests` hold a number of bytes, and `ChainOf_PathFarBelowItsNearestFile_AllocatesNothing` of `Generation/Chains/SettingsFileSetTests.cs` holds none.  Lower one when the code improves; never raise one to make a change pass.  Both end-to-end `EndToEnd/AllocationTests.cs` hold each generated method to a hand-written one that makes the same calls, in two pairs: the method that reads its rows into the pooled buffer against one that reads them into `RowBufferByHand` of `tests/SqlSource.Testing`, and the same query under `no-array-pool` against one that reads them into a `List`, or for an `ImmutableArray` an `ImmutableArray` builder, each pair within the same margin, SQL Server's below the smallest object.  A change to the calls a method makes changes the hand-written method with it, never the margin, and a change to the generated buffer changes `RowBufferByHand`, which `Generation/Emitting/RowBufferTests.cs` compares with it.  Three more tests on each engine hold the pooled method of each result member that copies its rows out, `ToArray`, `ToList` and `ToImmutableArray`, to a few hundred rows against a hand-written baseline of its own, a `List` + `ToArray()`, a `List` grown by doubling and returned as it is, and an `ImmutableArray` builder that is drained, which it must undercut by at least its `LeastSavingInBytesPerCall`, `LeastListSavingInBytesPerCall` or `LeastImmutableArraySavingInBytesPerCall`: each number is set from a measure, raised when the pool saves more, and never lowered to make a change pass.  A pooled result member needs such a test, since the pairs against `RowBufferByHand` use the buffer's own text and cannot see what it costs.  Both end-to-end `EndToEnd/AllocationTests.cs` measure through `CallAllocations` of `tests/SqlSource.Testing`, by the commonest difference of pairs of calls, never by a total, a median of blocks or the least of the calls, which move with what the driver and other threads allocate ([why](SqlSource.Testing/EndToEnd/CallAllocations.cs)).
- **A test holds on CI's busy runner and under coverage, not only on a quiet machine.**  The flaky failures so far each assumed that nothing else acts during the test.
  - Never let a timer keep a command running or decide an order: SQL Server ends a `WAITFOR` early when it runs short of threads.  Hold the command on something the test controls, a row lock or an application lock, and wait for the state through `Eventually` or `ProcessGate` before acting, as `RunTimeArgumentTests` and `SessionTests` of `tests/SqlSource.Tests.SqlServer` do.
  - Measure the allocations of synchronous code with `GC.GetAllocatedBytesForCurrentThread`, which coverage and other threads leave alone.  A measure of the whole process, `GC.GetTotalAllocatedBytes`, goes through `CallAllocations`, which skips under coverage or a profiler, since the collector allocates in the process on some calls and not others, and runs in a collection with `DisableParallelization` ([why](SqlSource.Testing/EndToEnd/CallAllocations.cs)).
  - A threshold or margin set from what a test measures is measured again as CI's `build` job runs it, with the whole solution running at once and with `--coverage` unless the test skips under it, as well as alone, and its comment says how it was measured.
- **`tests/SqlSource.Tool.Tests/AnalyzerReleases.Unshipped.md` lists the one descriptor the tests bring themselves**; a new one adds a row there.
- **Assertions are Shouldly's**, and test names are `Method_Scenario_Outcome`.  `.editorconfig` turns the analyzer rules off that this needs, under `[tests/**.cs]`.  `Method` is what the test calls: the C# method in full, `DescribeAsync_` and never `Describe_`, or the command or statement it runs, as the `Describe_` of `DescribeCommandTests`, which runs `describe`, and the `Explain_` of `PlanOutputTests`, which runs the server's `EXPLAIN`.  A test of a value names the value as `Method` and what it is read under as `Scenario`, as `Patience_OfEveryWait_IsTwoMinutes`.  A test that needs another current culture takes it from `CultureScope` of `tests/SqlSource.Testing`, which puts back the one it found.  A unit-test class and a container class may share a name, as the two `NpgsqlCheckTests` do: their folders tell them apart.
- **Every test class is `sealed`**, a `partial` one `public sealed partial class`.  Nothing checks it; a new class follows the rest.
- **`.github/workflows/nightly.yml` names each test project in the Test step of its `test` job.**  A new test project that needs no container is added there, or it never runs on Windows or macOS.
