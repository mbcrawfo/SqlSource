# AGENTS.md - tests

Five xunit projects and the two libraries they share.  [`README.md`](README.md) says what each is, which Roslyn it runs on and how they reference each other; this file is the traps.

- **A test project compiles no `.cs` file of another project, with one exception.**  Code that two test projects need is in one of the two libraries, which they reference.  The exception is `tests/SqlSource.Tests/Generator/`, whose test classes `tests/SqlSource.Tests.RoslynFloor` compiles a second time against Roslyn 4.8.0; its own `AGENTS.md` says what that asks of a test there.  `tests/SqlSource.Tests/TestLayoutTests.cs` fails on any other `Compile` item of a test project that names a file outside the project's folder, however its path is spelled, on a file of `Generator/` whose name does not end in `Tests.cs`, and on one without the line that says it is shared.
- **The two libraries, `tests/SqlSource.Testing` and `tests/SqlSource.Tool.Testing`, hold no tests.**  `tests/SqlSource.Tests.RoslynFloor` references `SqlSource.Testing`, so it stays on the pinned Roslyn with no `VersionOverride`, and what that asks of the code is in the `AGENTS.md` of `tests/SqlSource.Tests/Generator/`.  Keep the two apart: the tool raises Roslyn to a current version, which would reach RoslynFloor through one library ([why](README.md#the-projects)).  Their types stay `internal`.  A helper that one test project alone uses stays in that project; one that a second project comes to need moves into a library.
- **A test of `tests/SqlSource.Tests.Postgres` that needs the server is in the collection `UsesPostgres`**, which starts one container for the run through `tests/SqlSource.Tests.Postgres/PostgresContainer.cs`, the one place that names the image ([the image](SqlSource.Tests.Postgres/README.md#the-image)).  Its databases are `fixtures`, `realistic`, and `app` and `billing` for `EndToEnd/`, built from `EndToEnd/app/` and `EndToEnd/billing/`.  The tests that need none, `Describer/FixtureVersionTests.cs`, `Realistic/RealisticCasesTests.cs`, `Realistic/RealisticSamplesTests.cs`, `Realistic/Describer/RealisticDescribeTests.cs`, `Realistic/Generation/RealisticClaimsTests.cs`, `Realistic/Generation/RealisticModelsTests.cs`, `Realistic/Generation/RealisticModelNullabilityTests.cs`, `Realistic/Generation/RealisticParametersTests.cs` and `EndToEnd/ModelShapeTests.cs`, are not in it.  The project reads `tests/SqlSource.Tool.Tests/Fixtures/Describers/` from the repository, found through `RepositoryRoot`, and not from an output folder.  A test whose answer depends on the version branches on `PostgresContainer.Major`, or skips by `SkipBelow` or `SkipUnlessRecordedMajor` there, and a change here is run on both images before it is pushed, since `pre-commit-validation.sh` runs the default image alone.  A test runs one statement of its own on the database `fixtures` through `PostgresContainer.ExecuteAsync` or `ScalarAsync`; one that holds a transaction, runs several commands on one source, reads rows, binds a parameter or uses another connection keeps its own data source.  A test opens, describes and captures through `Describer/Sessions.cs`, except the tests of the live calls below a session (`ModifierCallTests`, `ExplainTests`, `RelationsCallTests`), and reads the variable of a recording through `Recording.cs`.
- **`tests/SqlSource.Tests.Postgres/Realistic/` is the realistic corpus** ([layout and procedures](SqlSource.Tests.Postgres/README.md#the-realistic-corpus)).  The checks of a later layer over the same cases, the generated models', go in a folder of their own beside `Describer/`, never into the corpus's root.  A `case.json` is never written from what the describer answers, and an `exempt` needs a reason, which `RealisticCases` enforces ([why a column says so](SqlSource.Tests.Postgres/README.md#the-realistic-corpus)).  Never edit an expectation by hand, and read the diff of a recording.  Every folder of `Cases/` holds `query.sql`, `case.json`, the expectation of each recorded major it runs on and, when the case has models, its sidecar `query.sql.json`, and no other file, which `RealisticCasesTests` checks.  That sidecar is written by `tools/describe-end-to-end.sh` alone, never by hand.  `Realistic/Generation/RealisticQueries.cs` holds one class for each case with models, which `RealisticClaimsTests` checks, and a case whose models the generator refuses says so by `models` in its `case.json`.  `Realistic/Generation/RealisticDapperTests.cs` passes Dapper the input model's values under the SQL's snake_case names in a `DynamicParameters`, never the model itself ([D-0004](../docs/deferred/D-0004-input-models-bound-by-the-names-of-the-sql.md)), and a case with a parameter that Dapper cannot send says why by `dapper` in its `case.json`, a member that phase 8 removes from every case, since its methods bind each parameter by its type.  `.editorconfig` has a section for those files, whose lines are as long as the describer's help, and `.gitattributes` keeps every file of `Cases/` at LF, since an expectation is compared byte for byte.  `Realistic/Describer/RealisticNullabilityNoiseTests.cs` has one budget in `Budgets` for each of `PostgresContainer.RecordedMajors` and no other, changed as the readme says.
- **`tests/SqlSource.Tests.Postgres/EndToEnd/` is the end-to-end project** ([what it covers](SqlSource.Tests.Postgres/README.md#the-end-to-end-project)).  Every sidecar of `EndToEnd/Queries/` is written by `tools/describe-end-to-end.sh` alone, never by hand, and `CheckTests` runs `--check` over the real project, never a copy.  A query writes its parameters in camelCase, `@accountId`, so that its input model binds through Dapper.  A Dapper test reads, asserts the values of at least one row, `NULL`s included, and takes its data source from `EndToEndSources`; a test that writes runs in a transaction that is rolled back.  `EndToEnd/ErrorPaths/` is a fixture project that the test project never compiles or describes: the `.csproj` removes it from `Compile`, `AdditionalFiles` and `None` and copies it to the output as `Fixtures/Projects/ErrorPaths/`.  A column of `all_types` changes `EndToEnd/app/schema.sql`, `EndToEnd/app/seed.sql` and `tests/SqlSource.Testing/EndToEnd/AllTypesRows.cs` together, with its parameter in `InsertAllTypes` or its row in `WriteSideLeftOut` of `EndToEnd/AllTypesQueryTests.cs`, and a change to `WriteSideLeftOut` changes the list of parameters Dapper cannot send in `docs/manual/recipes.md#models-through-dapper`.  `EndToEnd/DapperRecipeTests.cs` writes each of its columns by the recipe's remedy and proves the rest of that recipe, and `EndToEnd/Types/TypedParameter.cs` is the same code as its sample, in this repository's layout: a change to one changes the other.
- **`tests/SqlSource.Tests.Postgres.Npgsql8` holds the read of `all_types` on Npgsql 8 and nothing else.**  It references nothing that brings Npgsql 10, neither the tool, `tests/SqlSource.Tool.Testing` nor `tests/SqlSource.Tests.Postgres`, since a reference to 8 under 10 is a package downgrade ([why](README.md#the-npgsql-8-project)).  It links `AllTypes.sql` and its sidecar from `EndToEnd/Queries/` and commits none of its own.
- **Tests mirror the source folders.**  A test of `src/SqlSource/<Folder>/<Type>.cs` is `tests/SqlSource.Tests/<Folder>/<Type>Tests.cs`, and a test of the tool's `<Folder>/` is in `tests/SqlSource.Tool.Tests/<Folder>/`.  Namespaces follow folders, so a moved test changes its namespace.  The fakes and helpers that only the tool's tests use stay at that project's root, in `SqlSource.Tool.Tests`, which every sub-folder sees without a `using`; so do the tests of `ToolHost`, of `Outcome` and of a helper, those of `tests/SqlSource.Tool.Testing` included.  The split classes `PostgresSession*`, `PostgresEvents*` and `NullabilityWalk*` share their cases through a static helper and no base class ([the tool's helpers](README.md#the-projects)).
- **Every test that runs the generator or its emitter states its output.**  It passes an `OutputKind` to the harness's `OutputKind?` parameter, which has no default, nor has a helper of a test class that runs the generator: `Sql`, unless the test is of what an output that needs entries does, as the tests of sidecars and of their caching are.  It passes `null`, which leaves `SqlSourceOutput` unset, only when it needs the project not to set it, as a test of the default or of the output's levels does, and says so in a comment.  A test of `TypeEmitter` sets `Output` on the project's level.  The default, `CodeGen`, needs an entry in a sidecar for each query, so a test that leaves it unsaid gets `SQLSRC209` for each file under `ansi`.  `Microsoft.CodeAnalysis` has an `OutputKind` too: a file that imports it names the generator's with `using OutputKind = SqlSource.Settings.OutputKind;`.
- **Multi-line values in `tests/SqlSource.Tests/SqlSource.Tests.csproj` are the test.**  `SqlSourceGeneratorParameters` and `SqlSourceDialect` are written with one word on each line, in the project and on items, to prove that the package's targets trim them before the compiler reads them.  Do not put them on one line.  The project imports the real `build/SqlSource.props` and `SqlSource.targets` for the same reason.
- **`tests/SqlSource.Tests/Snapshot/Examples/*.json` are copies of the sidecar format design**, sections 4.1 and 4.2 of `docs/superpowers/specs/2026-10-07-sidecar-format-design.md`.  A change to one changes the other, and `tests/SqlSource.Tests/Snapshot/SidecarExamples.cs` reads them from the output folder by that path.
- **`tests/SqlSource.Tool.Tests/Fixtures/Projects/` holds projects that are never built or restored.**  They are not compiled into the test project, and a test that leaves an `obj` in the repository, or a file in a fixture, is a bug ([fixture projects](README.md#fixture-projects)).  `OddPaths` holds a folder whose name has `;`, `=`, `%`, a quote and a non-ASCII letter on purpose.
- **No test of the tool waits for a time to pick an order, or changes the test process unseen.**  A test that needs the answers of `tests/SqlSource.Tool.Testing/FakeProcessRunner.cs` in an order, or several open at once, holds them with `tests/SqlSource.Tool.Tests/ProcessGate.cs` and not with `Task.Delay`.  A test that changes the environment of the test process is in the collection `ChangesTheEnvironment`, which runs alone, and puts back what it changed.  A test that starts a program of the operating system skips with `Programs.SkipUnlessOnPath` where the program is missing.  `tests/SqlSource.Tool.Tests/Commands/TerminationTests.cs` is the one test of the tool's project that starts the tool as a process, and `tests/SqlSource.Tests.Postgres/Describer/ToolProcessTests.cs` the one of the container's: both start it through `Programs` of `tests/SqlSource.Tool.Testing`, `Programs.StartTool`, or for the closed console `cmd /c start` with `Programs.ToolPath` and `Programs.SetToolEnvironment`, which runs the copy in the tests' output with `--roll-forward LatestMajor`, since the libraries beside that copy are of the tests' runtime.  `TerminationTests` looks for the run's folder and for nothing else in the temporary directory, where a killed MSBuild leaves the pipes of its runtime.  Its project has a target that writes a file and then waits for two minutes, so that a test sends its signal when MSBuild has a program of its own running, and a run ends only when it is told to.  Try a change to its test of a closed console by starting `nightly.yml` by hand ([why](README.md#the-projects)).
- **`tests/SqlSource.Tests/Documentation/` checks the documents a user reads**, `README.md`, `src/SqlSource.Tool/README.md` and every page of `docs/manual/` (except its `AGENTS.md`): `UserDocsLinksTests` their links and anchors, and `UserDocsSamplesTests` the SQL in their fenced blocks.  `UserDocs.cs` finds those documents from `RepositoryRoot` and is the one place that knows what counts as a user document.  A fenced block opens with `sql`, and a second word says how it is parsed: a dialect, `fragment` for part of a file, or `error` for SQL that shows a mistake.  Mark a sample so; do not weaken the test.  The two readmes are packed, so their links are absolute, `https://github.com/mbcrawfo/SqlSource/blob/main/<path>`, and a test follows those too.
- **Allocation budgets are tests.**  `Parsing/SqlFileParserAllocationTests.cs`, `Generation/Paths/PathResolverAllocationTests.cs` and `Snapshot/Reading/SidecarReaderAllocationTests.cs` in `tests/SqlSource.Tests` hold a number of bytes.  Lower one when the code improves; never raise one to make a change pass.
- **`tests/SqlSource.Tests/Generator/CachingTests.cs` is what makes the generator's step names mean something.**  It reads each step's run reasons by its name in `TrackingNames`; a new step that does real work gets a case there.
- **`tests/SqlSource.Tests/Diagnostics/DiagnosticsDocumentTests.cs` fails when `docs/manual/diagnostics.md` and the descriptors disagree.**  `tests/SqlSource.Tool.Tests/AnalyzerReleases.Unshipped.md` lists the one descriptor the tests bring themselves; a new one adds a row there.
- **Assertions are Shouldly's**, and test names are `Method_Scenario_Outcome`.  `.editorconfig` turns the analyzer rules off that this needs, under `[tests/**.cs]`.  `Method` is what the test calls: the C# method in full, `DescribeAsync_` and never `Describe_`, or the command or statement it runs, as the `Describe_` of `DescribeCommandTests`, which runs `describe`, and the `Explain_` of `PlanOutputTests`, which runs the server's `EXPLAIN`.  A unit-test class and a container class may share a name, as the two `NpgsqlCheckTests` do: their folders tell them apart.
- **Every test class is `sealed`**, a `partial` one `public sealed partial class`.  Nothing checks it; a new class follows the rest.

> Maintenance: this file names specific files and folders.  If you rename, move, or remove them, update this file in the same commit.
