# AGENTS.md - tests

Four xunit projects and the two libraries they share.  `CONTRIBUTING.md` says what each runs and how; this file is the traps.

- **A test project compiles no `.cs` file of another project, with one exception.**  Code that two test projects need is in one of the two libraries below, which they reference.  The exception is `tests/SqlSource.Tests/Generator/`, whose test classes `tests/SqlSource.Tests.RoslynFloor` compiles a second time against Roslyn 4.8.0; its own `AGENTS.md` says what that asks of a test there.  `tests/SqlSource.Tests/TestLayoutTests.cs` fails on any other `Compile` item of a test project that names a file outside the project's folder, however its path is spelled, on a file of `Generator/` whose name does not end in `Tests.cs`, and on one without the line that says it is shared.
- **`tests/SqlSource.Testing` and `tests/SqlSource.Tool.Testing` are the libraries of the tests**, class libraries that are never run as tests, hold no tests and are never packed.  `SqlSource.Testing` references only `src/SqlSource` and holds the generator's harness (`Generator/`), `TestSidecars` (`Snapshot/`) and `RepositoryRoot`.  `tests/SqlSource.Tests.RoslynFloor` references it, so it stays on the pinned Roslyn with no `VersionOverride`, uses only API that Roslyn 4.8.0 has, and hands the compiler C# 12 at most.  `SqlSource.Tool.Testing` holds the helpers that `tests/SqlSource.Tool.Tests` and `tests/SqlSource.Tests.Postgres` share: the harness of a whole command (`CliRun`, `CliResult`, `Hosts`, `Plans`), the fakes of a process and a project (`FakeProcessRunner`, `FakeProject`, `TestProject`), the start of the built tool (`Programs`), `LogReader`, `Secrets`, the skip of a test of a password file (`PasswordFiles`), `SidecarFiles`, `TempFolder`, the named answers of a column's nullability (`NullabilityAnswers`) and PostgreSQL's type modifiers (`Typmods`), and the harness of a describer's fixtures, its case writer `FixtureCaseFiles` and `FixtureProjects` (`Fixtures/`).  They are two because the tool raises Roslyn to a current version, which would reach RoslynFloor through one library.  Their types stay `internal`: `src/SqlSource` and `src/SqlSource.Tool` grant them `InternalsVisibleTo`, and each grants it to the projects that reference it.  A helper that one test project alone uses stays in that project; one that a second project comes to need moves into a library.
- **`tests/SqlSource.Tests.Postgres` needs a server for most of its tests.**  It copies `tests/SqlSource.Tool.Tests/Fixtures/Projects/Single/` to its output, with the package's MSBuild files and `global.json`, for `FixtureProjects`.  Its tests that need the server are in the collection `UsesPostgres`, which starts one container for the run through `tests/SqlSource.Tests.Postgres/PostgresContainer.cs`, the one place that names the image; the tests that need none, `Describer/FixtureVersionTests.cs`, `Realistic/RealisticCasesTests.cs`, `Realistic/RealisticSamplesTests.cs` and `Realistic/Describer/RealisticDescribeTests.cs`, are not.  It reads `tests/SqlSource.Tool.Tests/Fixtures/Describers/` from the repository, found through `RepositoryRoot`, and not from an output folder.  `nightly.yml` leaves the project out.  CI runs every test here on the default image and again on `postgres:14.24`, and `pre-commit-validation.sh` on the default image alone: a test whose answer depends on the version branches on `PostgresContainer.Major`, or skips by `SkipBelow` or `SkipUnlessRecordedMajor` there, and a change here is run on both before it is pushed.  A test runs one statement of its own on the database `fixtures` through `PostgresContainer.ExecuteAsync` or `ScalarAsync`; one that holds a transaction, runs several commands on one source, reads rows, binds a parameter or uses another connection keeps its own data source.  A test opens, describes and captures through `Describer/Sessions.cs`, except the tests of the live calls below a session (`ModifierCallTests`, `ExplainTests`, `RelationsCallTests`), and reads the variable of a recording through `Recording.cs`.
- **`tests/SqlSource.Tests.Postgres/Realistic/` is the realistic corpus, in its own database `realistic`** (`schema.sql`, `seed.sql`; the container's `fixtures` database is the describer's fixtures).  The folder is laid out by layer: its root holds the corpus and what reads it, every layer's (`RealisticCase`, `RealisticCases`, `RealisticSamples`, `RealisticDatabase`); `Realistic/Describer/` holds the describer's checks over it, the description whole in `RealisticDescriptionTests` and its nullability in the classes named `RealisticNullability*`; and the checks of a later layer over the same cases, the generated models', go in a folder of their own beside `Describer/`, never into the corpus's root.  Each `Cases/<name>/case.json` is the truth of which columns can be NULL, written by hand from the SQL and the schema and never from what the describer answers; a column that can be NULL says why, and an `exempt` says why the seed cannot show it, so it needs a reason and belongs only on a column that can be NULL; `RealisticCases` refuses a `case.json` that breaks either.  A case that needs a later server than 14 says so in `minimumMajor` and has no expectation for an earlier major, `samples` gives a SQL literal for each parameter, with which a check that executes the query runs it over the seed, and a case the describer refuses has the failure's id in `refusal` and no columns.  `tools/record-realistic.sh` writes only the `expected-pg14.txt` and `expected-pg18.txt` of a case, never a `case.json`: do not edit an expectation by hand, and read the diff of a recording.  `.editorconfig` has a section for those files, whose lines are as long as the describer's help, and `.gitattributes` keeps every file of `Cases/` at LF, since an expectation is compared byte for byte.  `Realistic/Describer/RealisticNullabilityNoiseTests.cs` holds the count of not-null columns that the describer answers as nullable or unknown, in `Budgets` by major, with one for each of `PostgresContainer.RecordedMajors` and no other: lower one in the change that lowers the noise, and raise one only in a change that adds cases.  Every folder of `Cases/` is a case, and holds `query.sql`, `case.json` and the expectation of each recorded major it runs on, and no other file.
- **Tests mirror the source folders.**  A test of `src/SqlSource/<Folder>/<Type>.cs` is `tests/SqlSource.Tests/<Folder>/<Type>Tests.cs`, and a test of the tool's `<Folder>/` is in `tests/SqlSource.Tool.Tests/<Folder>/`; `tests/SqlSource.Tool.Tests/Commands/` holds the tests that run a whole command line.  Namespaces follow folders, so a moved test changes its namespace.  The fakes and helpers that only the tool's tests use stay at that project's root, in `SqlSource.Tool.Tests`, which every sub-folder sees without a `using`; so do the tests of `ToolHost`, of `Outcome` and of a helper, those of `tests/SqlSource.Tool.Testing` included.  `PostgresScript.cs`, `PostgresRows.cs`, `PostgresTables.cs`, `PostgresPlans.cs`, `PostgresRequests.cs` and `FakePostgresServer.cs` are among the helpers there, for the tests of `Describing/Postgres/`; `PostgresSessionCases.cs`, `PostgresEventCases.cs` and `PostgresWalkColumns.cs` hold what the classes of one subject share, those named `PostgresSession*`, `PostgresEvents*` and `NullabilityWalk*`, which a static helper serves and no base class; and `CaptureInputs.cs` is for the tests that record and replay a capture.  `tests/SqlSource.Tool.Tests/Fixtures/` holds the tests of the fixtures' harness, which is in `tests/SqlSource.Tool.Testing/Fixtures/`.
- **Multi-line values in `tests/SqlSource.Tests/SqlSource.Tests.csproj` are the test.**  `SqlSourceGeneratorParameters` and `SqlSourceDialect` are written with one word on each line, in the project and on items, to prove that the package's targets trim them before the compiler reads them.  Do not put them on one line.  The project imports the real `build/SqlSource.props` and `SqlSource.targets` for the same reason.
- **`tests/SqlSource.Tests/Snapshot/Examples/*.json` are copies of the sidecar format design**, sections 4.1 and 4.2 of `docs/superpowers/specs/2026-10-07-sidecar-format-design.md`.  A change to one changes the other, and `tests/SqlSource.Tests/Snapshot/SidecarExamples.cs` reads them from the output folder by that path.
- **`tests/SqlSource.Tool.Tests/Fixtures/Projects/` holds projects that are never built or restored.**  They are not compiled into the test project; `tests/SqlSource.Tool.Testing/Fixtures/FixtureProjects.cs` copies one out of the repository, with the package's MSBuild files and `global.json`, and the tests run the real `dotnet msbuild` on the copy.  A test that leaves an `obj` in the repository, or a file in a fixture, is a bug.  `OddPaths` holds a folder whose name has `;`, `=`, `%`, a quote and a non-ASCII letter on purpose.
- **No test of the tool waits for a time to pick an order, or changes the test process unseen.**  A test that needs the answers of `tests/SqlSource.Tool.Testing/FakeProcessRunner.cs` in an order, or several open at once, holds them with `tests/SqlSource.Tool.Tests/ProcessGate.cs` and not with `Task.Delay`.  A test that changes the environment of the test process is in the collection `ChangesTheEnvironment`, which runs alone, and puts back what it changed.  A test that starts a program of the operating system skips with `Programs.SkipUnlessOnPath` where the program is missing.  `tests/SqlSource.Tool.Tests/Commands/TerminationTests.cs` is the one test of the tool's project that starts the tool as a process, and `tests/SqlSource.Tests.Postgres/Describer/ToolProcessTests.cs` the one of the container's: both start it through `Programs` of `tests/SqlSource.Tool.Testing`, `Programs.StartTool`, or for the closed console `cmd /c start` with `Programs.ToolPath` and `Programs.SetToolEnvironment`, which runs the copy in the tests' output with `--roll-forward LatestMajor`, since the libraries beside that copy are of the tests' runtime.  `TerminationTests` looks for the run's folder and for nothing else in the temporary directory, where a killed MSBuild leaves the pipes of its runtime.  Its project has a target that writes a file and then waits for two minutes, so that a test sends its signal when MSBuild has a program of its own running, and a run ends only when it is told to.  Its test of a closed console runs on Windows alone, so `nightly.yml` is the only place that runs it: a change to it is tried by starting that workflow by hand.
- **Allocation budgets are tests.**  `Parsing/SqlFileParserAllocationTests.cs`, `Generation/Paths/PathResolverAllocationTests.cs` and `Snapshot/Reading/SidecarReaderAllocationTests.cs` in `tests/SqlSource.Tests` hold a number of bytes.  Lower one when the code improves; never raise one to make a change pass.
- **`tests/SqlSource.Tests/Generator/CachingTests.cs` is what makes the generator's step names mean something.**  It reads each step's run reasons by its name in `TrackingNames`; a new step that does real work gets a case there.
- **`tests/SqlSource.Tests/Diagnostics/DiagnosticsDocumentTests.cs` fails when `docs/diagnostics.md` and the descriptors disagree.**  `tests/SqlSource.Tool.Tests/AnalyzerReleases.Unshipped.md` lists the one descriptor the tests bring themselves; a new one adds a row there.
- **Assertions are Shouldly's**, and test names are `Method_Scenario_Outcome`.  `.editorconfig` turns the analyzer rules off that this needs, under `[tests/**.cs]`.  `Method` is what the test calls: the C# method in full, `DescribeAsync_` and never `Describe_`, or the command or statement it runs, as the `Describe_` of `DescribeCommandTests`, which runs `describe`, and the `Explain_` of `PlanOutputTests`, which runs the server's `EXPLAIN`.  A unit-test class and a container class may share a name, as the two `NpgsqlCheckTests` do: their folders tell them apart.
- **Every test class is `sealed`**, a `partial` one `public sealed partial class`.  Nothing checks it; a new class follows the rest.

> Maintenance: this file names specific files and folders.  If you rename, move, or remove them, update this file in the same commit.
