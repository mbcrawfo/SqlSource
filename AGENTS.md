# SqlSource - C# SQL Query Source Generator

## Core rules

These apply to all development in this project.

1. **Document deferred work.**  Any work that is not implemented as planned must be documented in `docs/deferred`, in the same PR that defers it.
2. **Document tech debt.**  Any problem identified and not resolved, or any intentional choice that is known to be sub-optimal, must be documented in `docs/tech-debt`, in the same PR that discovers or introduces it.
3. **Deferred minor feedback is not allowed.**  When a review gives valid but minor feedback you should not skip it.  If the fix is large enough that you hesitate to add it, ask for user input about making the change or recording it as tech debt.
4. **Keep the docs current, each in its own place.**  A change that makes one of these documents wrong updates it in the same PR.
   - **User documentation describes effects, never internals.**  `README.md`, `src/SqlSource.Tool/README.md` and `docs/manual/` say what a user writes, what they get and what they see: the effect on their queries, parameters, generated code and build, never how SqlSource does it.  They describe what works today; a feature still to come is a "Coming in a later release" callout, and the change that delivers it replaces its callouts with documentation and flips its status.  A change to behaviour a user can see updates the manual page that documents it, and `README.md` too when it changes the common path or an FAQ answer.
   - `README.md` is for the average user, who should never need to read further: what SqlSource does and why, its status, installation and the supported environments, getting started, the other ways to use it, and a short FAQ.  It links to the manual for every option and never repeats the manual's tables.  Nothing about developing or releasing the project belongs there; link to `CONTRIBUTING.md`.  It is packed as the `SqlSource` package's readme on nuget.org, and `src/SqlSource.Tool/README.md`, the tool's short page, as `SqlSource.Tool`'s, so every link in both is an absolute URL.
   - **The two packed readmes have rules of their own.**  nuget.org shows them with HTML turned off, so they hold no raw HTML and no `<a id>` line: their headings are linked by GitHub's slug, and renaming one means updating every link to it, which the link test in `tests/SqlSource.Tests/Documentation/` catches.  A feature still to come is this callout, word for word: `> **Coming in a later release.**  <One sentence on what it will do.>  See [what works today](https://github.com/mbcrawfo/SqlSource/blob/main/docs/manual/README.md#what-works-today).`  Install and update commands carry `--prerelease`, and the NuGet badge is `nuget/vpre`, until the first stable release takes them out (`docs/publishing.md`).  A `sql` sample's info string names its dialect (`sql postgres`), or says `fragment` or `error`, since a test parses it.  Never name the describer, a plan or `EXPLAIN`, a field of the sidecar, or a tech-debt or deferred id.
   - `docs/manual/` is for the user with a specific need: one part of a project configured differently, a complex query, a database's limits, a build error to look up.  Each topic has one page; the entry page, `docs/manual/README.md`, routes a reader by need, and its "What works today" table is the one record of what is delivered.
   - `docs/manual/diagnostics.md` is the manual's list of diagnostics: what each `SQLSRC` error means and how to fix it.  A change that adds, removes or changes a diagnostic updates it.  A test in `tests/SqlSource.Tests/Diagnostics/` fails when its sections and the descriptors disagree; the explanations are yours to keep true.
   - `CONTRIBUTING.md` is the developer readme.  It holds the required tools, one sentence per project, and the commands to build, test, check, pack and run, with detail in the documents it links to.  A change to a required tool, or to how the project is built, tested, checked or packed, updates it.  So does adding or removing a project.
   - `docs/architecture/` explains how the components work and hand work to each other, as the code is today, for a developer who needs to understand one before changing it.  A change that makes a page wrong updates it.  Delivering a phase of query generation replaces that phase's placeholder with a description of what was built.  A new component, such as another describer, gets its page or section in the change that adds it.
   - `tests/README.md`, `tests/SqlSource.Tests.Postgres/README.md`, `tests/SqlSource.Tests.SqlServer/README.md`, `tools/README.md` and `.github/workflows/README.md` each hold the procedures of their area.  A change to a project, script, workflow or procedure they describe updates them in the same PR.
   - **`examples/` shows what a user writes and gets.**  A change to what a user writes, gets or sees updates the example projects that show it, in the same PR, and a phase of query generation that delivers a feature adds an example of it to each example project the feature applies to.  The examples build with the solution, and their sidecars are written by `tools/describe-end-to-end.sh`.
   - `docs/publishing.md` covers the version scheme, the release procedure and the configuration outside the repository that releasing depends on.  A change to any of those updates it.
5. **Pin every test database to its version.**  A PostgreSQL image the tests run names a major and a minor, `postgres:18.6` and never `postgres:18`.  A SQL Server image names its update, `<year>-CU<n>` with `-GDR<n>` when the build has one, then `-ubuntu-<version>`, and never `-latest`, a bare year or an on-demand hotfix, and `SqlServerContainer.ImageBuilds` in `tests/SqlSource.Tests.SqlServer/SqlServerContainer.cs` holds the build its server reports.  Moving the default image of either engine records again, in the same PR, what was recorded on it.  For PostgreSQL that is `DefaultImages.Postgres` in `tests/SqlSource.Testing/DefaultImages.cs`, whose tag is also in `examples/PostgresExamples/docker-compose.yml`, the describer's fixtures, written by `tools/record-fixtures.sh postgres`, and the sidecars of the end-to-end project, of the realistic cases and of the examples, written by `tools/describe-end-to-end.sh`.  For SQL Server it is `DefaultImages.SqlServer` in the same file, with its row of `ImageBuilds`, the describer's fixtures, written by `tools/record-fixtures.sh mssql`, and the sidecars of the end-to-end project and of the realistic cases, written by `tools/describe-end-to-end.sh`.  Nothing is recorded on a floor image, and moving one changes the places that name it and runs the tests on it: `postgres:14.24` is in `.github/workflows/build.yml`, `CONTRIBUTING.md` and `tests/SqlSource.Tests.Postgres/README.md`, and `mcr.microsoft.com/mssql/server:2017-CU31-GDR19-ubuntu-18.04` in `.github/workflows/build.yml`, `CONTRIBUTING.md`, `tests/SqlSource.Tests.SqlServer/README.md` and its row of `ImageBuilds`.  See the image sections of `tests/SqlSource.Tests.Postgres/README.md` and `tests/SqlSource.Tests.SqlServer/README.md`.
6. **Every MSBuild property of the package starts with `SqlSource`.**  A property that `src/SqlSource/build/SqlSource.props` or `src/SqlSource/build/SqlSource.targets` sets, reads or shows to the compiler is named `SqlSource<Something>`, as `SqlSourceIncludeFiles` and `SqlSourceGeneratorParameters` are.  The prefix keeps the package's names apart from those of the SDK and of other packages in a consumer's project.  A property of the SDK that the files read keeps its own name and is listed in `SdkProperties` in `tests/SqlSource.Tests/Package/BuildFileTests.cs`, where a test fails on any other name without the prefix.

## Commits

Every commit must pass `./pre-commit-validation.sh`.  Nothing enforces this: no hook runs the script for you, so running it is your job, every time.

1. **Validate before you commit.**  Run `./pre-commit-validation.sh` after your last edit and fix what it reports before you commit.  A run only covers the tree it ran on; an edit made after a passing run, however small, needs another run.
2. **Never push a branch that has not passed.**  This is the rule that matters most.  Before every push, run `./pre-commit-validation.sh` on the tree exactly as it will be pushed and see it pass.  CI runs the same checks, and each engine's describer tests again on that engine's oldest supported image, which the script does not: after a change to a describer or to its tests, also run that describer's project on its floor image, `SQLSOURCE_TESTS_POSTGRES_IMAGE=postgres:14.24` for `tests/SqlSource.Tests.Postgres` and `SQLSOURCE_TESTS_SQLSERVER_IMAGE=mcr.microsoft.com/mssql/server:2017-CU31-GDR19-ubuntu-18.04` for `tests/SqlSource.Tests.SqlServer`.  A failure in CI is one you could have found locally, and it costs a full CI run, a fix, another push and another wait.  Do not push on the strength of an earlier run, of a run on another commit, or of the belief that a change is too small to break anything.
3. **Never skip a check.**  Do not commit or push past a failure, and do not edit the script to make one go away.  If a check is wrong, tell the user.
4. **It needs the full toolchain.**  The script fails when Docker is not running or when the local tools have not been restored.  Fix the environment; see `CONTRIBUTING.md`.

## Pull requests

1. **Reply to every CodeRabbit finding.**  When you act on a comment, reply in its thread with what you changed.  When you do not act on one, reply in its thread with the reason: the rule or decision it conflicts with, or why the finding does not apply.  Never leave a finding unanswered or skip one silently.
2. **Check the version before you open a pull request.**  Run `git fetch --tags origin`, then compare `VersionPrefix` in `Directory.Build.props` with the highest release tag, `git tag --list 'v*' --sort=-v:refname | head -n 1`.  If `VersionPrefix` is not greater than that tag, ask the user what the new version should be and set it in the same pull request.  When the repository has no `v*` tags there is nothing to compare.
3. **Keep a pull request to 150 files or fewer.**  CodeRabbit skips the review of a pull request that changes more than 150 files.  When a piece of work would go over, split it into pull requests that each stay under the limit and land in order, such as the design, the code, then bulk test data, whenever the parts can be reviewed on their own.  Plan the split before the work starts, not after the pull request is open.

## Reviewing maintainability

A periodic review of folder growth, AGENTS.md accuracy, comments and duplicated patterns follows the skill in `.claude/skills/reviewing-maintainability/`, which says what is fixed in the review's pull request and what is recorded in `docs/tech-debt`.

## Adding guidance for AI agents

1. Always use AGENTS.md files for AI guidance.
2. Add folder-level AGENTS.md files to give AI agents non-obvious context to work safely with the code in that folder.  Add them where there is complex code with patterns or structure that may not be clear, or where additional context is beneficial when working with the code.
3. Be brief and direct.  Do not describe what the folder "does" - focus on actionable guidance that helps navigate the code and avoid pitfalls.  Descriptions of how code works go in `docs/architecture/`, and the AGENTS.md links to them.  The ideal size is < 250 lines.  An AGENTS.md in the root of a project may be larger if necessary.
4. An AGENTS.md holds rules, not explanation.  Each rule keeps its statement and at most one sentence of reason, and a rule about how code works links to the page in `docs/architecture/` that explains it.  A rule keeps more only when an agent could not follow it safely without the reason, as with the rule that nothing a `.sql` file holds can make the describer run a statement.
5. Do not repeat source code in an AGENTS.md file - link to the actual source files instead.  Brief code snippets that demonstrate a common pattern or pitfall are acceptable.
6. Keep lists of files and folders in sync.  Once an AGENTS.md names a specific file, folder, type, function, etc. it is coupled to that name.  When you rename, move, split, or delete those things, update the AGENTS.md **in the same commit**.  Treat it as part of the change, not a follow-up.  Any AGENTS.md that lists files or folders must end with a one-line maintenance footer reminding future editors of this coupling.
7. DO NOT list child AGENTS.md files from a parent AGENTS.md or instruct agents to read them - AGENTS.md files are loaded automatically by the tooling.

> Maintenance: this file names specific files and folders.  If you rename, move, or remove them, update this file in the same commit.
