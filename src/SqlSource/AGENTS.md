# AGENTS.md - src/SqlSource

How the generator works: [`docs/architecture/generator.md`](../../docs/architecture/generator.md).

The source generator.  It is loaded into the C# compiler of whoever consumes it, which constrains what the project may target and reference.

- **`netstandard2.0` only.**  The compiler loads Roslyn components built for `netstandard2.0`.  Do not add or change target frameworks in `SqlSource.csproj`.
- **The Roslyn pin is the support floor.**  `Microsoft.CodeAnalysis.CSharp` is pinned to 4.8.0 in `Directory.Packages.props`, the compiler in the .NET 8 SDK and Visual Studio 2022 17.8.  An API added after 4.8.0 means raising the pin, which drops consumers: ask the user first, and update the support target in `README.md` in the same commit.
- **The generator tests run on two Roslyn versions.**  A test in `tests/SqlSource.Tests/Generator/` also runs on 4.8.0, so it may use only Roslyn API that 4.8.0 has and hand the compiler C# 12 at most.  [`tests/README.md`](../../tests/README.md) has the projects and the harness.
- **Language features need runtime support.**  `LangVersion` is `preview`, but `netstandard2.0` lacks the types behind some features.  One other than `init` and records (`required` members, say) needs a polyfill in `Polyfills/`, beside `IsExternalInit.cs`, in the namespace of the type it stands in for; `.editorconfig` turns IDE0130 off there.
- **No collection expression may target `ImmutableArray<T>`.**  The `System.Collections.Immutable` that Roslyn 4.8.0 brings predates support for it (CS9210).  Use `ImmutableArray.Create`, a builder or `ToImmutableArray()`.
- **Models need value equality.**  A type the pipeline caches is a record, and holds its collections in `EquatableArray<T>`, never `ImmutableArray<T>`.
- **Performance is a requirement.**  The generator runs in the compiler and the IDE, on every edit.  Allocate nothing per character or line, copy text in runs, rent buffers from `ArrayPool<T>`, and make a string only where a result needs one.  The allocation budgets are tests, and `tests/AGENTS.md` holds their rule.  A change to a hot path states its time and allocation, before and after, in its pull request, from a `Stopwatch` loop over a `Release` build, since there is no benchmark project.
- **Do not reference `System.Memory`, `System.Buffers` or `System.Collections.Immutable` directly.**  They arrive with Roslyn 4.8.0 at the versions the compiler host loads; a newer one can fail to load there.
- **Keep Roslyn references private.**  Package references here use `PrivateAssets="all"` so that nothing flows to the projects that reference the generator.

## The pipeline

`SqlSourceGenerator` wires the steps: `Initialize` calls one method for each stage, in the order of the source outputs, and its only logic is the helpers at its end; everything else is in `Generation/`.  A new step goes in the method of its stage, and a new source output where its order among the others falls.  See [the pipeline](../../docs/architecture/generator.md#the-pipeline).

- **No Roslyn object flows between steps**, except the `AdditionalText` that `FileMetadata`, `FileParseInput` (inside `FileClaim` too) and `SidecarInput` carry, compared by reference, into the step that reads the file.  Only `Generation/TargetTypeReader.cs`, the `SupportedFramework` step, `Generation/Types/NpgsqlProbe.cs`, `Generation/Types/SqlClientProbe.cs`, `Generation/Types/IDriverProbe.cs`, `Generation/Types/MappedTypeResolver.cs`, `Generation/Types/ShortNameIndex.cs`, `Generation/Types/MappedTypeWarnings.cs`, `Generation/Converters/ConverterReader.cs` and `Generation/Models/ModelNameChecker.cs`, which `TakenModelNames` and `TakenExtensionClasses` both call, touch symbols and syntax; outside the pipeline, `Diagnostics/AttributeConflictSuppressor.cs` reads them too.  A value between steps never holds an `ISymbol`, a `SyntaxNode`, a `Compilation`, a `Location` or a `Diagnostic`; carry a `LocationInfo` or `DiagnosticInfo`, and make the Roslyn object in an output step.
- **Every `Collect()` has a `Select` after it that gives an `EquatableArray<T>`**, or the step after runs on every edit.  Two collected chains may be combined before their one `Select`, as in `AllFileModels`.  The listed paths that `CaseCollisions` and `RepeatedPaths` take are the one exception.
- **Resolving a type's `Path` must not depend on the text of any file**, only on the list of paths.
- **A `.sql` file that no type claims is never read**, and its errors are never reported.  Whether one is claimed is its `FileClaim`, so a change to `ClaimedPaths` reads only a file whose answer changed.
- **A sidecar is read only when its `.sql` file is claimed, and no step after `SidecarFile` holds its text.**
- **A later step reads an entry of a sidecar only from `SidecarCheckResult.UsableEntries`**, the entries that passed every check.  The checks run once for each file, over what every type that claims it needs, so that a problem is reported once.
- **Compare paths with `SqlPath.Comparer`, after `SqlPath.Normalize`; find one with `SqlPath.IndexOf`, `SqlPath.Contains` or `SqlPath.FindInFolder`.**  Never compare a raw path, call `System.IO.Path` or touch the file system (RS1035), and never search a list with a pass over it.  `Generation/Paths/PathCollision.cs` alone compares normalised paths ordinally, since it looks for the difference of case that the comparer ignores.  See [paths](../../docs/architecture/generator.md#paths).
- **The lists of paths and of parsed files stay distinct ignoring case.**  A later file whose path differs only by case is left out, and `Generation/Paths/PathCollision.cs` reports it as `SQLSRC013` when a type claims the path.
- **The `sqlsource` tool plans a run with this code.**  A change to a member that `src/SqlSource.Tool/Planning/` calls changes what the tool describes ([the list](../../docs/architecture/generator.md#the-tool-runs-the-same-code)); `tests/SqlSource.Tool.Tests/Planning/GeneratorParityTests.cs` compares the claims of the two, and the `SQLSRC209` and `SQLSRC210`, and the order of the `SQLSRC011` and `SQLSRC014`, that both report.
- **A step whose re-runs matter has a name in `Generation/TrackingNames.cs` and a test in the `Caching*Tests` class of its step, in `tests/SqlSource.Tests/Generator/`.**  A small `Select` between two named steps may go unnamed.  A change to the pipeline keeps those tests true, or changes them on purpose.
- **A file's check, types, models' properties and models run from its `ParsedFile` node, a model in the slot of its query and role, never from a `SelectMany` of `ParsedFiles` or of the sorted `Models`; a path in `RepeatedPaths` runs from the collected `ParsedFiles` or `ModelsByFile.OfRepeatedPaths` instead.**  The compiler matches the nodes after a `SelectMany` by their place, and a repeated path's two nodes would report or add its file twice.  See [the fan-out by file](../../docs/architecture/generator.md#the-fan-out-by-file).
- **The attribute file compiles as C# 7.3; a type's file may use C# 12.**  `AttributeSource.Text` has no `#nullable` directive and no nullable annotation.  Generated code uses nothing newer than C# 12: raising the floor in `Generation/Emitting/LanguageSupport.cs` drops consumers and changes the README, as raising the Roslyn pin does.  See [floors](../../docs/architecture/generator.md#language-and-framework-floors).
- **A type's file starts with `// <auto-generated/>`, `#nullable enable` and `#pragma warning disable CS0108, CS0114`**, writes strings with `SymbolDisplay.FormatLiteral`, never as raw string literals, and uses `\n` line endings.  A model's file, from `Generation/Emitting/ModelEmitter.cs`, starts with the first two alone, and disables only the warnings of a mapped type that is obsolete or experimental.  A file of methods, from `Generation/Emitting/MethodEmitter.cs`, starts as a type's file when the methods go on the type, and with the first two alone for an extension class, and then disables only the warnings of a converter it calls or a property type it reads or binds that is obsolete or experimental, `TypeMethods.WarningIds`.  The one pragma inside a method is the `#pragma warning disable CA2100` and its `restore` around the `CommandText` of a query whose tokens build its SQL at run time, which the analyzer reports even in generated code; keep it ([why](../../docs/architecture/generator.md#query-methods)).
- **A compiler warning inside generated code is a bug.**  The driver tests collect them as `GeneratorRun.GeneratedCodeWarnings` and assert that there are none; a new kind of generated code gets a test that does the same.
- **Nothing a user can write may make the generator throw.**  An exception drops all of the generator's output (CS8785).  See [what costs every type its code](../../docs/architecture/generator.md#what-costs-every-type-its-code).
- **A generated file's name comes from `Generation/Emitting/HintName.cs`**, built from identifier values, never the text as written.
- **A new row of `Generation/Types/PostgresTypeMap.cs` needs its name in `Settings/TypeOverrides/TypeKeyNames.cs`**, which `PostgresTypeMapTests.Keys_OfTheMap_AreTheKnownPostgresNamesOfTheSettings` holds.  A new row of `Generation/Types/SqlServerTypeMap.cs` needs its name in `TypeKeyNames.KnownSqlServerNames`, which `SqlServerTypeMapTests.Keys_OfTheMap_AreTheKnownSqlServerNamesOfTheSettings` holds.  When the map learns the types of a new Npgsql major, raise `NpgsqlProbe.NewestKnownMajor`, which decides `SQLSRC248`; for a new Microsoft.Data.SqlClient major, raise `SqlClientProbe.NewestKnownMajor`, which decides `SQLSRC268`.
- **`Generation/Types/QueryTyper.cs` types a file by its engine.**  A type goes to the map of its class, `PostgresTypeMap` or `SqlServerTypeMap`, under its own driver's column, and the type override's entries are those of the file's engine, `SqlDescribableDialects.EngineOf`.  A help of `Diagnose` for one engine leaves the other's text as it is, and `OverrideLookup` makes its engine's delegate, and `QuerySettings.ResolveColumnTypes` merges the column types, once for each level of markers, never for each query or type.  See [types](../../docs/architecture/generator.md#types).
- **`ModelCollector.FindDifference` compares every member of a model that changes the C# it emits, and not the documentation.**  A member it misses lets two queries that differ share one model.  `HasArrayColumn` is the one exception, on purpose: it adds a constructor and no property, so it is OR-ed over the queries that share a model, and a query whose column is an array shares a model with one whose column a type override gives the same C# array type.
- **Nothing a token method writes may be hidden by a parameter.**  `Generation/Emitting/MethodWriter.cs` reads the state tuple by position, names the lambda's parameters with `GetUnusedName`, writes framework types from `global::` and `string` as the keyword.  A new identifier there needs the same care, and a row in both `Run_TokenWithAnAwkwardName_Compiles` of `tests/SqlSource.Tests/Generator/GeneratedSourceMethodTests.cs`, at C# 12 on the Roslyn floor too, and `Run_TokenWithAnAwkwardName_CompilesOnTheNewestCSharp` of `tests/SqlSource.Tests/Generation/Emitting/MethodWriterTests.cs`, at `LanguageVersion.Latest`.  A local of a query's method, from `Generation/Emitting/QueryMethodWriter.cs`, takes its name from `LocalNames`, and a name a token could hide gets a row in those two and in their siblings for a query's method, `Run_TokenWithAnAwkwardNameInAQueryMethod_Compiles` and `Run_TokenWithAnAwkwardNameInAQueryMethod_CompilesOnTheNewestCSharp`.
- **A `CodeGen` query's only member is its method.**  `TypeEmitter` writes no constant or token method for it, and `Generation/Methods/MethodPlanner.cs` gives no method to one that fails a check, so such a query gets neither; its models are unaffected.  See [query methods](../../docs/architecture/generator.md#query-methods).
- **A type's methods are planned from its own slice of the project.**  `Generation/Methods/MethodsInput.cs` takes the models of the type's files, its run of `ModelSet.Assignments` and its `TypeMemberNames` by a search for each, and the converters of the types that its type overrides, column types and markers chose, without their locations, so that the plan of one type runs again only when something of it changes, and `TypeOutput`'s inputs are never widened for the methods, so that a sidecar's edit writes no type's constants again.
- **The converters reach the methods alone.**  `ConverterSet` is an input of `MethodsInput`, and never of `TypeOutput` or of a step of the types or models; `MappedTypeConverters` stays apart from `MappedTypes` for the same reason, so that an edit to a converter re-runs only the methods it touches.  See [converters](../../docs/architecture/generator.md#converters).
- **The dialect is resolved for each file before the parse**, by `Generation/MSBuild/DialectSetting.cs` and `Generation/FileParseInput.cs`, as an input of the parse.  See [the dialect](../../docs/architecture/generator.md#how-the-dialect-reaches-the-parse).
- **A property or metadata reaches the generator only when `build/SqlSource.props` lists it, and metadata is listed for `SqlSourceSettingsFile`, never for `AdditionalFiles`.**  Listing `AdditionalFiles` would give every `.sql` file of a project a section of the file the compiler reads.  Every key is composed from `MSBuildSettings.PropertyPrefix` or `MSBuildSettings.MetadataPrefix`, in the generator and in the tool's `ManifestOptions`.  See [`SqlSourceSettingsFile`](../../docs/architecture/msbuild-and-manifest.md#sqlsourcesettingsfile).
- **Only stage one of the settings reaches the parse.**  A setting of stage two must never be an input of `SqlFileReader.Read`, or a change to a property would parse every file again.  `CachingParseTests` and `CachingOptionsTests` pin what each edit parses.  See [the two stages](../../docs/architecture/generator.md#the-settings-have-two-stages).
- **A value MSBuild gives is trimmed by a target, which runs before `GenerateMSBuildEditorConfigFileCore` and is never replaced by a trim outside a target.**  The compiler reads each value from one line, so an untrimmed value arrives empty or as its first word, and the generator cannot tell.  A new setting must not give white space any meaning beyond separating words.  A target that adds a `.sql` file hooks `SqlSourceTrimMetadataOfFiles`.  See [trimming](../../docs/architecture/msbuild-and-manifest.md#trimming).

## The project manifest

`SqlSourceWriteManifest` in `build/SqlSource.targets` writes the manifest for the `sqlsource` tool, and `SqlSourceImported`, which `build/SqlSource.props` sets with no condition, tells the tool that a project uses SqlSource.  See [the manifest](../../docs/architecture/msbuild-and-manifest.md#the-manifest).

- **The target hooks nothing, on purpose.**  The tool runs it by name, and no build runs it.  Do not give it `BeforeTargets`, `AfterTargets` or a condition: `tests/SqlSource.Tests/Package/BuildFileTests.cs` holds that.  Its `DependsOnTargets` is the property `SqlSourceManifestDependsOn`, set in the `PropertyGroup` at the root of the file, which the nesting `ItemGroup` of the sidecars follows; those two are the only elements at the root that are not a target.
- **The format is a contract with the tool.**  A new key, and a new name under `Property.` or `File.`, are additions and keep the version.  A change to what an existing key means, or to how a line is read, raises the version, and a reader of another version then reads nothing.  `src/SqlSource.Tool/Projects/ManifestReader.cs` is the reader.  See [the format](../../docs/architecture/msbuild-and-manifest.md#the-format).
- **A new setting of the package is a new line in the target, twice: `Property.<Name>` and `File.<Name>` in the transform**, besides its place in each of the two trims.  `BuildFileTests` fails until all are there.  A setting that is a property alone, as `SqlSourceNestedClass`, has no `File.` line and is listed in `PropertyOnly` of `BuildFileTests`.
- **A property is written through `$([MSBuild]::Escape(...))`, a property of the SDK is first put on one line with the expression of a trim, and the lines of a file are one item.**  Without them a value is split or cut, or the metadata of a file is parted from its `File` line.  `tests/SqlSource.Tool.Tests/Projects/ManifestTargetTests.cs` runs the target with the real `dotnet msbuild`.
- **The `File` and `Compile` lines stay in the order of the items.**  For a path listed twice, `src/SqlSource.Tool/Planning/ListedFiles.cs` takes the metadata of its last item that has any, as a build does.  See [reading it](../../docs/architecture/msbuild-and-manifest.md#reading-it).
- **It depends on `AddImplicitDefineConstants`, a target of the SDK, by name, and does not see a file that a hook of the build adds.**  See [known limits](../../docs/architecture/msbuild-and-manifest.md#known-limits).

## `Settings/`

Plain data and the readers of values.  See [settings](../../docs/architecture/generator.md#settings).

- **No file access, no symbols, no pipeline types, and nothing from `Parsing/`, `Generation/` or `Diagnostics/`.**  A rule shared with another folder goes in the root namespace, as `SqlIdentifier`, `DatabaseName` and `SystemSchemas` do.
- **`QuerySettings.Resolve` is the one rule that puts the levels together, with `ResolveTypeOverrides`, `ResolveColumnTypes` and `ResolveDatabase` for the three settings the attribute has no level for.**  A new setting is a nullable member of `SettingsLevel`, a line in `Over`, a member of `QuerySettings` with its default, and a `case` in `SqlMarkerScope.Read` when a marker gives it.  When another source gives it, it is also a member of `SettingId`, a line in `SettingsLevelReader.Read`, the one reader of the attribute, the properties and the metadata, a name in `MSBuildSettings` in the order of `SettingId`, and a property in the `AttributeSettings` of `TargetTypeReader`.  An `ISettingSource` only finds a raw value, as text, as the elements of an array (the generator parameters) or as the members of an object (the type override and the column types), which the reader asks for before the text; records one that is not valid, and an element or member that is not valid or repeats a key, by its index; and says its `SettingPlace`.  A reader that finds nothing returns `SettingsLevel.None`, never a new empty level.
- **A setting comes whole from the most specific level that has it, except the type override and the column types, which merge per key.**  `TypeOverrideMap.Over` merges it, in `SettingsLevel.Over` and in `QuerySettings.ResolveTypeOverrides`, and keeps an entry of `default` so that it hides the key below; `TypeOverrideMap.Find` weighs it by its place against the other entries that match a type and gives null when it wins, so never drop one before `Find`.  The type override is not part of `QuerySettings.Resolve`, which runs for each query and each claiming type: compute the type override once for each distinct level of markers.  Every array of entries holds each key once, a key being its parts' text without quotes and with escapes decoded, compared ordinally, in the order of `TypeOverrideMap`: by that text ignoring case, then ordinally; keep a key a string in its written form, quotes included, and compare keys only through `TypeOverrideMap`.  `TypeOverrideGrammar` is its one reader, of an MSBuild value, of an object's members and of a marker alike; the attribute has no level for it.  A level holds two arrays, one for each `DatabaseEngine`: `TypeOverrides`, keyed by `TypeKeys.TryNormalizePostgres`, and `SqlServerTypeOverrides`, keyed by `TypeKeys.TryNormalizeSqlServer`, and an entry is absent from the array of an engine that does not read its key.  An MSBuild value fills both; a marker fills only its file's engine's, by `SqlDescribableDialects.EngineOf`, and a key that engine does not read is `SQLSRC111`.  Code that carries a level's entries carries both arrays, as `SettingsLevel.Over`, `MappedTypeNames` and `FileTypesInput.TypeSettingsOf` do.  See [settings](../../docs/architecture/generator.md#the-type-override).
- **The column types follow the type override's rules, in `Settings/ColumnTypes/`, with one array for both engines.**  `ColumnTypeMap` merges and weighs them as `TypeOverrideMap` does the type override's, and the two share their sorted list, `Settings/SortedKeyedList.cs`, and their ranking of a place, `SettingPlaces.Specificity`, so a change to either changes both settings; so never drop a `default` before `ColumnTypeMap.Find`, and compare keys only through it; `ColumnTypeGrammar` is their one reader, and splits an MSBuild value with `TypeOverrideGrammar`'s `NextEntry` and `TrySplitEntry`, and reads every type with its `TryReadType`, so a change to those changes both settings.  See [the column types](../../docs/architecture/generator.md#the-column-types).
- **A setting a user can write is documented in `docs/manual/settings.md` alone**: a row of its table with every place it can be written and its status, and a section anchored `setting-<name>`.  A new marker also gets a row in the marker index of `docs/manual/sql-files.md`.  A new generator parameter gets its name in the Values cell of the Generator parameters row and in the table under `#setting-generator-parameters` of `settings.md`, and in the section of `SQLSRC109` in `docs/manual/diagnostics.md` and the list of parameters in `tests/SqlSource.Tests/Diagnostics/DiagnosticsDocumentTests.cs`, which checks the section against that list, and in the list and the patterns of `schemas/settings-v1.schema.json`, which `SettingsFileSchemaTests` checks against `GeneratorParameterList.Names`.  A setting accepted before the change that gives it an effect says so in its status, and that change flips it.
- **`OutputKind`, `MemberPlacement`, `ModelKind`, `CollectionKind` and `MethodPlacement` keep the numbers of the attribute's enums.**  `tests/SqlSource.Tests/Generation/AttributeSourceTests.cs` compares each pair.
- **A value from a fixed list is read by `SettingValue.TryReadChoice`**, from the names of an enum's members, so renaming a member changes what a user may write, and with it the list and the pattern of that choice in `schemas/settings-v1.schema.json`, which `SettingsFileSchemaTests` checks against the enum.

## `SettingsFiles/`

The reader of a settings file, `sqlsource.json`.  See [the settings file](../../docs/superpowers/specs/2026-10-25-settings-files-design.md#the-settings-file).

- **The reader never throws, and bounds nesting by `SidecarTokenizer.MaxDepth`.**  A user writes the file, and an exception in the generator costs every type its generated code.
- **Never hand the walk of `SettingsFileReader` a text the grammar pass has not passed.**  The walk trusts the grammar, as `SidecarCursor` does; `SettingsFileReaderRobustnessTests` holds the two together.
- **It may use `Settings/`, the tokenizer of `Snapshot/Reading/` and `Parsing/SqlDialectName.cs`, and nothing of `Generation/` or `Diagnostics/`.**  Its errors are data with a `TextSpan`, so that the build and the tool can each report them.
- **Whether a value is valid is `SettingsLevelReader`'s, never the reader's own**, and the dialect's is `SqlDialectName`'s.  A file then accepts what MSBuild accepts; `SettingsFileSource` only turns what is rejected into errors at their spans.
- **A new key is a constant of `SettingsFileKeys`, a row of its `All` and of `TypeOf`, a property of `schemas/settings-v1.schema.json`, and, for a new kind of error, a case of `SettingsFileDiagnostics`.**  The schema accepts what the reader accepts and no more.

## Diagnostics

The generator's are in `Diagnostics/SqlDiagnostics.cs`, and the errors of the `sqlsource` tool that are not the generator's own in `Diagnostics/ToolDiagnostics.cs`, two of which, `SQLSRC209` and `SQLSRC210`, the generator reports too.  See [diagnostics](../../docs/architecture/generator.md#diagnostics).

- **Every diagnostic is an error tagged `NotConfigurable` unless its descriptor says why a project may configure it, as a warning or as information; `SqlDiagnosticsTests` lists those by id.**  Each takes its category and the start of its help link from `SqlDiagnostics.Category` and `SqlDiagnostics.HelpLinkBase`.
- **Adding, removing or changing one touches four places:** the descriptor and the `All` of its class; `AnalyzerReleases.Unshipped.md`, which the build checks (rules RS2000 to RS2008); `docs/manual/diagnostics.md`, which a test checks; and, for a parser error, `SqlDiagnostics.ForParseError`.
- **Never remove or renumber an id that a release has shipped** without recording it under `### Removed Rules` in `AnalyzerReleases.Unshipped.md`.  `AnalyzerReleases.Shipped.md` says what has shipped.
- **`SQLSRC011`, `SQLSRC014`, `SQLSRC247`, `SQLSRC248`, `SQLSRC267`, `SQLSRC268` and `SQLSRC273` have no position**, so they are reported with `Location.None` in an output step and never travel as a `DiagnosticInfo`.  `SQLSRC011` is reported once for each distinct dialect value, `SQLSRC014` once for each distinct pair of setting and value, `SQLSRC247`, `SQLSRC248`, `SQLSRC267` and `SQLSRC268` once for the project, each pair by its own driver's probe and its own engine's `UsesPostgresEntries` or `UsesSqlServerEntries`, independently of the other, and `SQLSRC273` once for each engine that the collected `CodeGenEngines` of the types' methods holds and whose probe finds no driver.  The generator and the tool take the order of the first two from `Generation/MSBuild/InvalidValues.cs` and nowhere else.
- **`Diagnostics/SettingsFileDiagnostics.cs` is the one place a `SettingsFileError` becomes a diagnostic**, `SQLSRC015` to `SQLSRC020`, at the line and column of its span, for the build and the tool alike.
- **`SQLSRC901` is a suppression, not a diagnostic.**  Its `SuppressionDescriptor` is not in `SqlDiagnostics.All`, `AnalyzerReleases.Unshipped.md` or a section of `docs/manual/diagnostics.md`.  `Diagnostics/AttributeConflictSuppressor.cs` suppresses nothing but the types of `AttributeSource.GeneratedTypes` declared in the project being compiled; `tests/SqlSource.Tests/Generator/AttributeConflictTests.cs` holds both halves.
- **Write each `new DiagnosticDescriptor(...)` out in full, with a literal id.**  The release-tracking analyzer reads the arguments, and a helper that builds descriptors hides them from it.
- **An id below 100 is about the type or the project, one from 101 about a `.sql` file, and one from 200 about the snapshot or the tool** (`tests/SqlSource.Tests/Diagnostics/ToolDiagnosticsTests.cs` holds the tool's).  `SQLSRC200` to `SQLSRC280` are taken, and phase 8 takes the ids from `SQLSRC281` that its section of `docs/superpowers/specs/2026-10-07-query-generation-epic-design.md` assigns.  Add a new `SqlParseErrorKind` at the end: the parser ids follow its order.

## `Parsing/`

See [parsing](../../docs/architecture/generator.md#parsing).

- **Never build the kept form of a query's SQL for every query**: it doubles what a parse allocates.  The tokens, the parameters and the hash come from `Segments`, the SQL without comments.  See [the two forms](../../docs/architecture/generator.md#a-block-has-two-forms-of-its-sql).
- **Pure.**  No file access and no pipeline types.  Comparisons are ordinal; marker keywords and the names of generator parameters are ordinal ignoring case.
- **Every span is an offset into the file's text**; `SqlBlockText.ToSourceSpan` maps one of a block's built SQL back.
- **Quoted regions and hints are copied as written**, apart from line endings.  Trimming and blank-line removal must never reach inside one.
- **Lexemes cover the text without gaps**, and a quoted region or block comment ends with its closing delimiter: `SqlMarkerReader` and `SqlTextBuilder` depend on both.
- **The small readings of a text are in `SqlText`**, called and never copied.  `SqlText.FindLineEnd` is the one search for the end of a line in `Parsing/`; code that tests one character for a line break calls `SqlText.IsLineTerminator`, which names both terminators of SQL, `\r` and `\n`.  `Generation/Emitting/XmlDocWriter.cs` has the five of a documentation comment, another rule.
- **Dialect-sensitive choices live in `SqlDialectRules` and the readers of `Parsing/Quoting/`.**  `SqlLexer` names no dialect and no quoting form.  `Lex_Construct_IsReadByTheRulesOfTheDialect` in `tests/SqlSource.Tests/Parsing/SqlLexerTests.cs` pins every cell; changing one changes the SQL users get.
- **A reader holds no state and allocates nothing.**  A prefix it looks back at stays in the text lexeme before the region.  It reads one part of a string; whether a string goes on is the lexer's call.  See [lexemes](../../docs/architecture/generator.md#lexemes-and-the-rules-of-a-dialect).
- **A quoted region must never be able to hold a marker.**  Keep each part of a continued string a quoted region of its own, and carry nothing but the pending continuation from one lexeme to the next in `SqlLexer`.
- **A parameter is a lexeme, and `SqlParameterList` alone builds a query's list.**  A name the query declares as a local variable is left out everywhere, defaults too; `SqlDeclaredVariables` reads the file's lexemes and lexes nothing again, and walks the text only between a `DECLARE` and the end of its list, so a query without the word costs one search.  The lexer still gives such a name as a parameter lexeme.  A parameter inside a token must be in the SQL or declared (`SQLSRC118`).
- **`SqlMarkerScope` alone knows a marker's scope and value.**  A new marker is a `SqlMarkerKind`, a keyword in `SqlMarkerReader`, a row in `IsAllowedInQuery`, `IsAllowedInPreamble` or both, and a `case` in `SqlMarkerScope.Read`.  The theory `Marker_OfEveryKind_HasAKeywordAndAScope` fails until all four are there.
- **`SqlFileParser.Parser.ReadBlock` is three steps in a fixed order**: the block's markers, the query, the settings, with the `EmptyBlock` check after the first and the `InputModelWithoutParameters` check after the second.  Moving one changes which of two errors at one place comes first.  See [markers](../../docs/architecture/generator.md#markers).
- **A file's `-- dialect:` marker is found before the text after it is lexed**, by `SqlDialectMarker.Apply`, which reports nothing: `SqlFileParser` reports a marker's errors later, from the header's end that `Apply` returns.  The two must agree on what a valid marker is, so both go through `SqlDialectMarker.TryRead`.
- **A dialect's names, and those of its options, are in `SqlDialectName` only.**  `SQLSRC011`, `docs/manual/diagnostics.md` and `schemas/settings-v1.schema.json` repeat them; `SqlDialectName.Accepted` and a test keep the message in step, and `SettingsFileSchemaTests` the schema.
- **The describable dialects are in `SqlDescribableDialects` only**: `postgres` and `mssql`.  `SQLSRC209` and its section of `docs/manual/diagnostics.md` repeat them; a test holds the list to them.
- **The dialect is not a generator parameter.**  `SqlGeneratorParameterScope` holds what `-- generator:` lines give.  A setting with a value of its own, and an MSBuild property beside it, is a marker.
- **The hash has one definition, `SqlQueryHash`, and is not computed during a parse.**  A change to it, to what `SqlTextBuilder` gives for stripped SQL, to how `Parsing/Tokens/TokenScanner.cs` splits segments, to the defaults `Parsing/Tokens/SqlTokenList.cs` gives or to the order of `SqlParameterList`, makes every stored hash stale.
- **A result with errors has no blocks.**  The generator must never emit from a partly valid file.

## `Snapshot/`

See [snapshot](../../docs/architecture/generator.md#snapshot).

- **The format is a contract** with every committed sidecar and `schemas/sidecar-v1.schema.json`, recorded in `docs/superpowers/specs/2026-10-07-sidecar-format-design.md`, which says which changes need a new version.  A change to what `SidecarWriter` gives changes the format design, the schema, and the examples there and in `tests/SqlSource.Tests/Snapshot/Examples/`, in one pull request.
- **The reader never throws.**  Never hand a `SidecarCursor` a text the grammar pass has not passed, and keep a file the tool wrote tokenized twice and no more.  `Read_MistakeInAnArrayBeforeTheEngine_IsFound` in `tests/SqlSource.Tests/Snapshot/Reading/SidecarReaderTests.cs` and `Read_ReorderedFileCutShortOrDamagedAnywhere_ReturnsOneOfItsThreeStates` in `SidecarReaderRobustnessTests.cs` beside it hold the path no file of the tool takes.  See [reading a sidecar](../../docs/architecture/generator.md#reading-a-sidecar).
- **The sidecar is strict JSON**: no reader of a sidecar constructs a `SidecarTokenizer` with `lenient: true`, which `SettingsFiles/` alone uses.
- **The reader is lenient and the schema is strict.**  A new key is added to the model, to its object's list of keys and to the `switch` beside it; a key of a parameter's type to each engine's list in `SidecarTypeReader`, and a key of an entry to `SidecarReader.EntryMembers`, which the `switch` of `ReadMembers` sets.
- **Every name of a key is in `SidecarKeys`, and every value the tool writes in `SidecarValues`.**  A test compares each list of `SidecarValues` with the schema's.
- **The writer goes by the condition, not by the value**, as the remarks of `SidecarWriter` say.  It checks nothing and never throws.
- **`Snapshot/` uses `EquatableArray<T>` and `TextSpan` and nothing of `Parsing/`, `Generation/`, `Settings/` or `Diagnostics/`.**  A test holds `SidecarValues.Engine` and `Parsing/SqlDialectName.cs` together.
- **`SidecarComparer` compares what `describe --check` compares, and no more**, as section 3 of the format design lists.  A new key is not compared, unless it is a key of a type object.
