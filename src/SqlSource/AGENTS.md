# AGENTS.md - src/SqlSource

How the generator works: [`docs/architecture/generator.md`](../../docs/architecture/generator.md).

The generator is loaded into the C# compiler of whoever consumes it, which constrains what the project may target and reference.

- **`netstandard2.0` only.**  The compiler loads Roslyn components built for `netstandard2.0`.  Do not add or change target frameworks in `SqlSource.csproj`.
- **The Roslyn pin is the support floor.**  `Microsoft.CodeAnalysis.CSharp` is pinned to 4.8.0 in `Directory.Packages.props`, the compiler in the .NET 8 SDK and Visual Studio 2022 17.8.  An API added after 4.8.0 means raising the pin, which drops consumers: ask the user first, and update the support target in `README.md` in the same commit.
- **Language features need runtime support.**  `LangVersion` is `preview`, but `netstandard2.0` lacks the types behind some features.  One other than `init` and records (`required` members, say) needs a polyfill in `Polyfills/`, beside `IsExternalInit.cs`, in the namespace of the type it stands in for; `.editorconfig` turns IDE0130 off there.
- **No collection expression may target `ImmutableArray<T>`.**  The `System.Collections.Immutable` that Roslyn 4.8.0 brings predates support for it (CS9210).  Use `ImmutableArray.Create`, a builder or `ToImmutableArray()`.
- **Models need value equality.**  A type the pipeline caches is a record, and holds its collections in `EquatableArray<T>`, never `ImmutableArray<T>`.
- **Performance is a requirement.**  The generator runs in the compiler and the IDE, on every edit.  Allocate nothing per character or line, copy text in runs, rent buffers from `ArrayPool<T>`, and make a string only where a result needs one.  The allocation budgets are tests, and `tests/AGENTS.md` holds their rule.  A change to a hot path states its time and allocation, before and after, in its pull request, from a `Stopwatch` loop over a `Release` build, since there is no benchmark project.
- **Do not reference `System.Memory`, `System.Buffers` or `System.Collections.Immutable` directly.**  They arrive with Roslyn 4.8.0 at the versions the compiler host loads; a newer one can fail to load there.
- **Keep Roslyn references private.**  Package references here use `PrivateAssets="all"` so that nothing flows to the projects that reference the generator.

## The pipeline

`SqlSourceGenerator` wires the steps: `Initialize` calls one method for each stage, in the order of the source outputs, and its only logic is the helpers at its end; everything else is in `Generation/`.  A new step goes in the method of its stage, and a new source output where its order among the others falls.  See [the pipeline](../../docs/architecture/generator.md#the-pipeline).

- **No Roslyn object flows between steps**, except the `AdditionalText` that `FileParseInput` (inside `FileClaim` too) and `SidecarInput` carry, compared by reference, into the step that reads the file.  Only `Generation/TargetTypeReader.cs`, the `SupportedFramework` step, the `CompilePaths` step, which reads the syntax trees' paths and nothing else, `Generation/Types/Drivers/NpgsqlProbe.cs`, `Generation/Types/Drivers/SqlClientProbe.cs`, `Generation/Types/Drivers/IDriverProbe.cs`, `Generation/Types/MappedTypes/MappedTypeResolver.cs`, `Generation/Types/MappedTypes/ShortNameIndex.cs`, `Generation/Types/MappedTypes/MappedTypeWarnings.cs`, `Generation/Converters/ConverterReader.cs` and `Generation/Models/ModelNameChecker.cs`, which `TakenModelNames` and `TakenExtensionClasses` both call, touch symbols and syntax; outside the pipeline, `Diagnostics/AttributeConflictSuppressor.cs` reads them too.  A value between steps never holds an `ISymbol`, a `SyntaxNode`, a `Compilation`, a `Location` or a `Diagnostic`; carry a `LocationInfo` or `DiagnosticInfo`, and make the Roslyn object in an output step.
- **Every `Collect()` has a `Select` after it that gives an `EquatableArray<T>`**, or a record of them as `SettingsFileSet.Of` does, or a value with equality, as the flags of the `CodeGenEngines` step are, or the step after runs on every edit.  Two collected chains may be combined before their one `Select`, as in `AllFileModels`.  The listed paths that `CaseCollisions` and `RepeatedPaths` take are the one exception.
- **Resolving a type's `Path` must not depend on the text of any file**, only on the list of paths.
- **A `.sql` file that no type claims is never read**, and its errors are never reported.  Whether one is claimed is its `FileClaim`, so a change to `ClaimedPaths` reads only a file whose answer changed.
- **A settings file's problems are reported only when the chain of the folder of a `.sql` file or a C# file reaches it**, from `ReachedSettingsFiles`, so a broken file above a root file never fails a build, wherever the project puts `obj`, and whatever C# files its packages add.  A compile path that is not rooted, or that `BuildFolders.ReachingPaths` (by `Contains`) puts under a folder the build writes C# files or its outputs into or a NuGet package folder, which the `BuildFolders` step reads from `SqlSourceBuildFolders`, reaches nothing; a `.sql` path is never left out.  See [which files are checked](../../docs/architecture/generator.md#which-files-are-checked).
- **A sidecar is read only when its `.sql` file is claimed, and no step after `SidecarFile` holds its text.**
- **A later step reads an entry of a sidecar only from `SidecarCheckResult.UsableEntries`**, the entries that passed every check.  The checks run once for each file, over what every type that claims it needs, so that a problem is reported once.
- **Compare paths with `SqlPath.Comparer`, after `SqlPath.Normalize`; find one with `SqlPath.IndexOf`, `SqlPath.Contains` or `SqlPath.FindInFolder`, and ask whether one is under a folder with `SqlPath.IsInFolder`.**  Never compare a raw path, call `System.IO.Path` or touch the file system (RS1035), and never search a list with a pass over it.  `Generation/Paths/PathCollision.cs` alone compares normalised paths ordinally, since it looks for the difference of case that the comparer ignores.  See [paths](../../docs/architecture/generator.md#paths).
- **The lists of paths and of parsed files stay distinct ignoring case.**  A later file whose path differs only by case is left out, and `Generation/Paths/PathCollision.cs` reports it as `SQLSRC013` when a type claims the path.
- **The `sqlsource` tool plans a run with this code.**  A change to a member that `src/SqlSource.Tool/Planning/` calls changes what the tool describes ([the list](../../docs/architecture/generator.md#the-tool-runs-the-same-code)); `tests/SqlSource.Tool.Tests/Planning/GeneratorParityTests.cs` compares the claims of the two, and the `SQLSRC209` and `SQLSRC210`, and the errors of the settings files, that both report.
- **A step whose re-runs matter has a name in `Generation/TrackingNames.cs` and a test in the `Caching*Tests` class of its step, in `tests/SqlSource.Tests/Generator/`.**  A small `Select` between two named steps may go unnamed.  A change to the pipeline keeps those tests true, or changes them on purpose.
- **A file's check, types, models' properties and models run from its `ParsedFile` node, a model in the slot of its query and role, never from a `SelectMany` of `ParsedFiles` or of the sorted `Models`; a path in `RepeatedPaths` runs from the collected `ParsedFiles` or `ModelsByFile.OfRepeatedPaths` instead.**  The compiler matches the nodes after a `SelectMany` by their place, and a repeated path's two nodes would report or add its file twice.  See [the fan-out by file](../../docs/architecture/generator.md#the-fan-out-by-file).
- **The attribute file compiles as C# 7.3; a type's file may use C# 12.**  `AttributeSource.Text` has no `#nullable` directive and no nullable annotation.  Generated code uses nothing newer than C# 12: raising the floor in `Generation/Emitting/LanguageSupport.cs` drops consumers and changes the README, as raising the Roslyn pin does.  See [floors](../../docs/architecture/generator.md#language-and-framework-floors).
- **A compiler warning inside generated code is a bug.**  The driver tests collect them as `GeneratorRun.GeneratedCodeWarnings` and assert that there are none; a new kind of generated code gets a test that does the same.
- **Nothing a user can write may make the generator throw.**  An exception drops all of the generator's output (CS8785).  See [what costs every type its code](../../docs/architecture/generator.md#what-costs-every-type-its-code).
- **A generated file's name comes from `Generation/Emitting/HintName.cs`**, built from identifier values, never the text as written.
- **A `CodeGen` query's only member is its method.**  `TypeEmitter` writes no constant or token method for it, and `Generation/Methods/MethodPlanner.cs` gives no method to one that fails a check, so such a query gets neither; its models are unaffected.  See [query methods](../../docs/architecture/generator.md#query-methods).
- **A type's methods are planned from its own slice of the project.**  `Generation/Methods/MethodsInput.cs` takes the models of the type's files, its run of `ModelSet.Assignments` and its `TypeMemberNames` by a search for each, and the converters of the types that its type overrides, column types and markers chose, without their locations, so that the plan of one type runs again only when something of it changes, and `TypeOutput`'s inputs are never widened for the methods, so that a sidecar's edit writes no type's constants again.
- **The converters reach the methods alone.**  `ConverterSet` is an input of `MethodsInput`, and never of `TypeOutput` or of a step of the types or models; `MappedTypeConverters` stays apart from `MappedTypes` for the same reason, so that an edit to a converter re-runs only the methods it touches.  See [converters](../../docs/architecture/generator.md#converters).
- **The dialect is resolved for each file before the parse**, by `Generation/FileParseInput.cs` from the chain of the file's folder, `Generation/Chains/SettingsFileSet.cs`, as an input of the parse.  See [the dialect](../../docs/architecture/generator.md#how-the-dialect-reaches-the-parse).
- **The build shows the compiler one property, `SqlSourceBuildFolders`, and no item metadata; a setting is never a property or metadata of the build.**  `build/SqlSource.props` lists it, and the generator reads it through `Generation/Chains/BuildFolders.cs`.  It is no setting: `SqlSourceFindBuildFolders` in `build/SqlSource.targets` sets it whatever a project writes ([the build's folders](../../docs/architecture/msbuild-and-manifest.md#the-builds-folders)).  `BuildFileTests` holds the props to that one item.
- **Only stage one of the settings reaches the parse.**  A setting of stage two must never be an input of `SqlFileReader.Read`, or a change to it would parse every file again.  `CachingParseTests`, `CachingOptionsTests` and `CachingSettingsFileTests` pin what each edit parses.  See [the two stages](../../docs/architecture/generator.md#the-settings-have-two-stages).
- **Stage two reads a file's settings from its `FileLevel`, the chain of its folder**, and a type's nested class the chain of its C# file's folder, in `NestedClassCheck`, never one settings file alone.  One file alone would skip the files above it.  See [the two stages](../../docs/architecture/generator.md#the-settings-have-two-stages).

## `Settings/`

Plain data and the readers of values.  See [settings](../../docs/architecture/generator.md#settings).

- **`QuerySettings.Resolve` is the one rule that puts the levels together, with `ResolveTypeOverrides`, `ResolveColumnTypes` and `ResolveDatabase` for the three settings the attribute has no level for.**  A new setting is a nullable member of `SettingsLevel`, a line in `Over`, a member of `QuerySettings` with its default, and a `case` in `SqlMarkerScope.Read` when a marker gives it.  When another source gives it, it is also a member of `SettingId`, a line in `SettingsLevelReader.Read`, the one reader of the attribute and of the settings files, and a property in the `AttributeSettings` of `TargetTypeReader`.  An `ISettingSource` only finds a raw value, as text, as the elements of an array (the generator parameters, which the reader asks for before their text) or as the members of an object (the type override and the column types, which the reader reads from members alone); records one that is not valid, and an element or member that is not valid or repeats a key, by its index; and says its `SettingPlace`.  A reader that finds nothing returns `SettingsLevel.None`, never a new empty level.
- **A setting comes whole from the most specific level that has it, except the type override and the column types, which merge per key.**  `TypeOverrideMap.Over` merges it, in `SettingsLevel.Over` and in `QuerySettings.ResolveTypeOverrides`, and keeps an entry of `default` so that it hides the key below; `TypeOverrideMap.Find` weighs it by its place against the other entries that match a type and gives null when it wins, so never drop one before `Find`.  The type override is not part of `QuerySettings.Resolve`, which runs for each query and each claiming type: compute the type override once for each distinct level of markers.  Every array of entries holds each key once, a key being its parts' text without quotes and with escapes decoded, compared ordinally, in the order of `TypeOverrideMap`: by that text ignoring case, then ordinally; keep a key a string in its written form, quotes included, and compare keys only through `TypeOverrideMap`.  `TypeOverrideGrammar` is its one reader, of an object's members and of a marker alike; the attribute has no level for it.  A level holds two arrays, one for each `DatabaseEngine`: `TypeOverrides`, keyed by `TypeKeys.TryNormalizePostgres`, and `SqlServerTypeOverrides`, keyed by `TypeKeys.TryNormalizeSqlServer`, and an entry is absent from the array of an engine that does not read its key.  An object of a settings file fills both; a marker fills only its file's engine's, by `SqlDescribableDialects.EngineOf`, and a key that engine does not read is `SQLSRC111`.  Code that carries a level's entries carries both arrays, as `SettingsLevel.Over`, `MappedTypeNames` and `FileTypesInput.TypeSettingsOf` do.  See [settings](../../docs/architecture/generator.md#the-type-override).
- **A setting a user can write is documented in `docs/manual/settings.md` alone**: a row of its table with every place it can be written and its status, and a section anchored `setting-<name>`.  A new marker also gets a row in the marker index of `docs/manual/sql-files.md`.  A new generator parameter gets its name in the Values cell of the Generator parameters row and in the table under `#setting-generator-parameters` of `settings.md`, and in the section of `SQLSRC109` in `docs/manual/diagnostics.md` and the list of parameters in `tests/SqlSource.Tests/Diagnostics/DiagnosticsDocumentTests.cs`, which checks the section against that list, and in the list and the patterns of `schemas/settings-v1.schema.json`, which `SettingsFileSchemaTests` checks against `GeneratorParameterList.Names`.  A setting accepted before the change that gives it an effect says so in its status, and that change flips it.
- **`OutputKind`, `MemberPlacement`, `ModelKind`, `CollectionKind` and `MethodPlacement` keep the numbers of the attribute's enums.**  `tests/SqlSource.Tests/Generation/AttributeSourceTests.cs` compares each pair.

## `Generation/Chains/`

The settings files read, with the problems each side reports, and the chain of each folder.  See [settings files](../../docs/architecture/generator.md#settings-files).

- **A chain is built only here, for the generator and the `sqlsource` tool alike**: a file is read by `ListedSettingsFile.Read` and the chains by `SettingsFileSet.Of`.  A second builder would let a build and the tool give one folder different settings.
- **Which compile paths reach nothing is `BuildFolders.ReachingPaths` alone**, for the generator and, from a manifest, the tool: a folder is an entry of the `|`-parted `SqlSourceBuildFolders` that is rooted and ends with a separator, with the `%25`, `%7C`, `%23` and `%3B` that `build/SqlSource.targets` escapes decoded in one pass, compared segment by segment through `SqlPath.IsInFolder`, so that a value cut at a `#` or a `;` never leaves out a path the real folder does not hold; the escaping and the decoding change together, and a folder the build writes C# files into, or a NuGet package folder, that the target leaves out lets its files reach a file above the root ([why](../../docs/architecture/generator.md#which-files-are-checked)).
- **What a side reports is `SettingsFileSides.Reports` alone**: both report a problem of the file as a file; the build reports a value of any setting but `database`, the tool a value of `dialect`, `output` or `database`.

## Diagnostics

The generator's are in `Diagnostics/SqlDiagnostics.cs`, and the errors of the `sqlsource` tool that are not the generator's own in `Diagnostics/ToolDiagnostics.cs`, two of which, `SQLSRC209` and `SQLSRC210`, the generator reports too.  See [diagnostics](../../docs/architecture/generator.md#diagnostics).

- **`SQLSRC247`, `SQLSRC248`, `SQLSRC267`, `SQLSRC268` and `SQLSRC273` have no position**, so they are reported with `Location.None` in an output step and never travel as a `DiagnosticInfo`.  `SQLSRC247`, `SQLSRC248`, `SQLSRC267` and `SQLSRC268` are reported once for the project, each pair by its own driver's probe and its own engine's `UsesPostgresEntries` or `UsesSqlServerEntries`, independently of the other, and `SQLSRC273` once for each engine that the collected `CodeGenEngines` of the types' methods holds and whose probe finds no driver.
- **`Diagnostics/SettingsFileDiagnostics.cs` is the one place a `SettingsFileError` becomes a diagnostic**, `SQLSRC015` to `SQLSRC020`, at the line and column of its span, for the build and the tool alike.
- **An id below 100 is about the type or the project, one from 101 about a `.sql` file, and one from 200 about the snapshot or the tool** (`tests/SqlSource.Tests/Diagnostics/ToolDiagnosticsTests.cs` holds the tool's).  `SQLSRC200` to `SQLSRC280` are taken, and phase 7 takes the ids from `SQLSRC281` that its spec, `docs/superpowers/specs/2026-10-26-query-generation-phase-7-library-maps-design.md`, assigns.  Add a new `SqlParseErrorKind` at the end: the parser ids follow its order.

## `Parsing/`

- **Never build the kept form of a query's SQL for every query**: it doubles what a parse allocates.  The tokens, the parameters and the hash come from `Segments`, the SQL without comments.  See [the two forms](../../docs/architecture/generator.md#a-block-has-two-forms-of-its-sql).
- **The dialect is not a generator parameter.**  `SqlGeneratorParameterScope` holds what `-- generator:` lines give.  A setting with a value of its own is a marker, and a key of a settings file beside it.
- **A result with errors has no blocks.**  The generator must never emit from a partly valid file.
