# AGENTS.md - src/SqlSource/build

- **Every MSBuild property of the package starts with `SqlSource`.**  A property that `build/SqlSource.props`, `build/SqlSource.targets`, `build/SqlSource.AfterSdk.targets` or `buildMultiTargeting/SqlSource.targets` sets, reads or shows to the compiler is named `SqlSource<Something>`, as `SqlSourceIncludeFiles` and `SqlSourceBuildFolders` are.  The prefix keeps the package's names apart from those of the SDK and of other packages in a consumer's project.
- **A property of the SDK, or a variable of the environment, that the files read keeps its own name** and is listed in `SdkProperties` in `tests/SqlSource.Tests/Package/BuildFileTests.cs`, where a test fails on any other name without the prefix.
- **A target of a project that adds a `.sql` file hooks `SqlSourceListFiles` with `BeforeTargets`, and that target stays empty, with no `BeforeTargets`, first in `SqlSourceManifestDependsOn` and in the `DependsOnTargets` of `SqlSourceFindSettingsFiles`.**  The manual gives users that line, so that their file is searched above and is in the manifest; a renamed target would leave their file out of the manifest without a word, since MSBuild passes over a `BeforeTargets` of a target that does not exist.
- **The settings files are found by `SqlSourceFindSettingsFiles`, which a build runs just before `CoreCompile` from `build/SqlSource.AfterSdk.targets`.**  The props add that file to the SDK's `AfterMicrosoftNETSdkTargets`, so it runs after every `CoreCompile` hook of `Directory.Build.targets`.  See [finding the settings files](../../../docs/architecture/msbuild-and-manifest.md#finding-the-settings-files).
- **Never hook the search or `SqlSourceTrackAdditionalFiles` to a target directly**, only through `SqlSourceSettingsSearchHook`, which `build/SqlSource.AfterSdk.targets` empties.
- **The props show the compiler three properties, `SqlSourceBuildFolders`, `SqlSourceTransitivePackageAssemblies` and `SqlSourcePublicExceptions`, and no item metadata; `BuildFileTests` holds them to those three items.**  The first two are no setting: in `build/SqlSource.targets`, `SqlSourceFindBuildFolders` sets the first and `SqlSourceFindTransitivePackageAssemblies` the second, whatever a project writes.  The third is the project's own, which only the generator reads.  See [the build's folders](../../../docs/architecture/msbuild-and-manifest.md#the-builds-folders) and [the package-brought assemblies](../../../docs/architecture/msbuild-and-manifest.md#the-package-brought-assemblies).
- **The escaping of `%`, `|`, `#` and `;` in `SqlSourceFindBuildFolders` and the decoding in `Generation/Chains/BuildFolders.cs` change together.**  A folder the build writes C# files into, or a NuGet package folder, that the target leaves out lets its files reach a settings file above the root ([why](../../../docs/architecture/generator.md#which-files-are-checked)).
- **The escaping in `SqlSourceFindTransitivePackageAssemblies` and the decoding in `Generation/Types/MappedTypes/TransitivePackageAssemblies.cs` change together**, as do those of the build's folders, whose `BuildFolders.Unescape` it shares.
- **The text of the `Error` in `SqlSourceCheckCompilerVersion` and the message of `SqlDiagnostics.CompilerTooOld` change together**, `{0}` standing for `$(SqlSourceCompilerApiVersion)`.  The generator cannot load in the compiler the target reports, so only the target can say it; `BuildFileTests` holds the two equal.  See [the compiler's version](../../../docs/architecture/msbuild-and-manifest.md#the-compilers-version).

## The online build

See [the online build](../../../docs/architecture/msbuild-and-manifest.md#the-online-build).

- **The online targets hook nothing**: `SqlSourceTrackAdditionalFiles` depends on `SqlSourceDescribeOnline`, which reaches `SqlSourceRunOnline` by a dependency or a call.  A hook would run the tool where the search does not run.
- **The tool runs in `SqlSourceRunOnline` alone, once, for the first framework**, since two runs would undo each other's sidecars.  A multi-targeted project's builds, the first framework's too, call it with `SqlSourceOnlineRun=true`, never in a framework's own configuration ([why](../../../docs/architecture/msbuild-and-manifest.md#the-online-build)).
- **`buildMultiTargeting/SqlSource.targets` holds the outer build's call, and repeats the properties its condition reads with the text of `build/SqlSource.targets`**: change both, `BuildFileTests` holds them equal.
- **Never read `$(SQLSOURCE_CONNECTION)`, in any case**: MSBuild logs a variable read as a property with its value.  Test it with `IsNullOrWhiteSpace` of `GetEnvironmentVariable`.
- **Compare `SqlSourceOnlineValue` with `Equals`, never `==`**: a condition reads `yes` as `true`.
- **The texts of `SQLSRC024` to `SQLSRC027` in the targets change with their `SqlDiagnostics` descriptors**; `BuildFileTests` holds them equal.
- **`SqlSourceToolCommand` is the tests' seam for the tool**, `dotnet sqlsource` by default, and no user setting.
- **A path in the `Exec` command goes through `Regex::Replace` with `SqlSourceShellSpecial` and `SqlSourceShellEscape`**: `/bin/sh` reads `$`, `` ` ``, `"` and `\` within quotes, and `cmd` reads `%`.

## The manifest

`SqlSourceWriteManifest` in `build/SqlSource.targets` writes the manifest for the `sqlsource` tool, and `SqlSourceImported`, which `build/SqlSource.props` sets with no condition, tells the tool that a project uses SqlSource.  See [the manifest](../../../docs/architecture/msbuild-and-manifest.md#the-manifest).

- **The target hooks nothing, on purpose.**  The tool runs it by name, and the online build through `SqlSourceRunOnline`'s dependencies; a hook would make every build write it.  Do not give it `BeforeTargets`, `AfterTargets` or a condition: `BuildFileTests` holds that.
- **Its `DependsOnTargets` is the property `SqlSourceManifestDependsOn`**, set in the `PropertyGroup` at the root of the file, which the nesting `ItemGroup` of the sidecars and the `ItemGroup` of the settings files follow; those three and the online build's group are the only elements at the root that are not a target.
- **The format is a contract with the tool.**  A new key is an addition and keeps the version, since a reader passes over a key it does not know.  A change to what an existing key means, or to how a line is read, raises the version, and a reader of another version then reads nothing.  `src/SqlSource.Tool/Projects/ManifestReader.cs` is the reader.  See [the format](../../../docs/architecture/msbuild-and-manifest.md#the-format).
- **The manifest holds no setting: version 2 has no `Property.` or `File.<Name>` line, and a setting added to the package is a key of the settings file, never a line here.**  The tool reads the settings from the files of the `Settings` lines, as the generator does.  `SqlSourceBuildFolders=` is a line and no setting: the target `SqlSourceFindBuildFolders` sets it, so the manifest's `DependsOnTargets` names that target.  `BuildFileTests` holds the lines and their order.
- **The manifest lists every `AdditionalFiles` item named `sqlsource.json` as a `Settings` line.**  A settings file the compiler is given and the manifest does not list would be read by the generator and not by the tool.
- **A property is written through `$([MSBuild]::Escape(...))`, and a property of the SDK is first put on one line with `Regex::Replace` of `\s+` and `Trim()`.**  Without them a value is split or cut.  `tests/SqlSource.Tool.Tests/Projects/ManifestTargetTests.cs` runs the target with the real `dotnet msbuild`.
- **The `File` and `Compile` lines stay in the order of the items.**  For a path listed twice, `src/SqlSource.Tool/Planning/ListedFiles.cs` keeps its first spelling.  See [reading it](../../../docs/architecture/msbuild-and-manifest.md#reading-it).
- **It depends on `AddImplicitDefineConstants`, a target of the SDK, by name, and does not see a file that a hook of the build adds.**  See [known limits](../../../docs/architecture/msbuild-and-manifest.md#known-limits).
