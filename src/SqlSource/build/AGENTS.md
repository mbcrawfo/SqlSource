# AGENTS.md - src/SqlSource/build

- **Every MSBuild property of the package starts with `SqlSource`.**  A property that `build/SqlSource.props`, `build/SqlSource.targets` or `build/SqlSource.AfterSdk.targets` sets, reads or shows to the compiler is named `SqlSource<Something>`, as `SqlSourceIncludeFiles` and `SqlSourceBuildFolders` are.  The prefix keeps the package's names apart from those of the SDK and of other packages in a consumer's project.
- **A property of the SDK that the files read keeps its own name** and is listed in `SdkProperties` in `tests/SqlSource.Tests/Package/BuildFileTests.cs`, where a test fails on any other name without the prefix.
- **A target of a project that adds a `.sql` file hooks `SqlSourceListFiles` with `BeforeTargets`, and that target stays empty, with no `BeforeTargets`, first in `SqlSourceManifestDependsOn` and in the `DependsOnTargets` of `SqlSourceFindSettingsFiles`.**  The manual gives users that line, so that their file is searched above and is in the manifest; a renamed target would leave their file out of the manifest without a word, since MSBuild passes over a `BeforeTargets` of a target that does not exist.
- **The settings files are found by `SqlSourceFindSettingsFiles`, which a build runs just before `CoreCompile` from `build/SqlSource.AfterSdk.targets`.**  The props add that file to the SDK's `AfterMicrosoftNETSdkTargets`, so it runs after every `CoreCompile` hook of `Directory.Build.targets`.  See [finding the settings files](../../../docs/architecture/msbuild-and-manifest.md#finding-the-settings-files).
- **Never hook the search or `SqlSourceTrackAdditionalFiles` to a target directly**, only through `SqlSourceSettingsSearchHook`, which `build/SqlSource.AfterSdk.targets` empties.
- **The props show the compiler two properties, `SqlSourceBuildFolders` and `SqlSourceTransitivePackageAssemblies`, and no item metadata; `BuildFileTests` holds them to those two items.**  Neither is a setting: in `build/SqlSource.targets`, `SqlSourceFindBuildFolders` sets the first and `SqlSourceFindTransitivePackageAssemblies` the second, whatever a project writes.  See [the build's folders](../../../docs/architecture/msbuild-and-manifest.md#the-builds-folders) and [the package-brought assemblies](../../../docs/architecture/msbuild-and-manifest.md#the-package-brought-assemblies).
- **The escaping of `%`, `|`, `#` and `;` in `SqlSourceFindBuildFolders` and the decoding in `Generation/Chains/BuildFolders.cs` change together.**  A folder the build writes C# files into, or a NuGet package folder, that the target leaves out lets its files reach a settings file above the root ([why](../../../docs/architecture/generator.md#which-files-are-checked)).
- **The escaping in `SqlSourceFindTransitivePackageAssemblies` and the decoding in `Generation/Types/MappedTypes/TransitivePackageAssemblies.cs` change together**, as do those of the build's folders, whose `BuildFolders.Unescape` it shares.

## The manifest

`SqlSourceWriteManifest` in `build/SqlSource.targets` writes the manifest for the `sqlsource` tool, and `SqlSourceImported`, which `build/SqlSource.props` sets with no condition, tells the tool that a project uses SqlSource.  See [the manifest](../../../docs/architecture/msbuild-and-manifest.md#the-manifest).

- **The target hooks nothing, on purpose.**  The tool runs it by name, and no build runs it.  Do not give it `BeforeTargets`, `AfterTargets` or a condition: `tests/SqlSource.Tests/Package/BuildFileTests.cs` holds that.  Its `DependsOnTargets` is the property `SqlSourceManifestDependsOn`, set in the `PropertyGroup` at the root of the file, which the nesting `ItemGroup` of the sidecars and the `ItemGroup` of the settings files follow; those three are the only elements at the root that are not a target.
- **The format is a contract with the tool.**  A new key is an addition and keeps the version, since a reader passes over a key it does not know.  A change to what an existing key means, or to how a line is read, raises the version, and a reader of another version then reads nothing.  `src/SqlSource.Tool/Projects/ManifestReader.cs` is the reader.  See [the format](../../../docs/architecture/msbuild-and-manifest.md#the-format).
- **The manifest holds no setting: version 2 has no `Property.` or `File.<Name>` line, and a setting added to the package is a key of the settings file, never a line here.**  The tool reads the settings from the files of the `Settings` lines, as the generator does.  `SqlSourceBuildFolders=` is a line and no setting: the target `SqlSourceFindBuildFolders` sets it, so the manifest's `DependsOnTargets` names that target.  `BuildFileTests` holds the lines and their order.
- **The manifest lists every `AdditionalFiles` item named `sqlsource.json` as a `Settings` line.**  A settings file the compiler is given and the manifest does not list would be read by the generator and not by the tool.
- **A property is written through `$([MSBuild]::Escape(...))`, and a property of the SDK is first put on one line with `Regex::Replace` of `\s+` and `Trim()`.**  Without them a value is split or cut.  `tests/SqlSource.Tool.Tests/Projects/ManifestTargetTests.cs` runs the target with the real `dotnet msbuild`.
- **The `File` and `Compile` lines stay in the order of the items.**  For a path listed twice, `src/SqlSource.Tool/Planning/ListedFiles.cs` keeps its first spelling.  See [reading it](../../../docs/architecture/msbuild-and-manifest.md#reading-it).
- **It depends on `AddImplicitDefineConstants`, a target of the SDK, by name, and does not see a file that a hook of the build adds.**  See [known limits](../../../docs/architecture/msbuild-and-manifest.md#known-limits).
