# AGENTS.md - src/SqlSource.Tool

The `sqlsource` command, packed as the .NET tool `SqlSource.Tool`.  `tests/SqlSource.Tool.Tests` holds its tests, in folders named as the tool's, with `Commands/` for the tests that run a whole command line; its fakes and helpers are at its root, with the tests of `ToolHost`, of `Outcome` and of a helper.

- **The tool shares the generator's code and never copies it.**  It references `src/SqlSource/SqlSource.csproj` and sees its internals.  The parser, the dialect rules, the settings, the sidecar's reader and writer, the hash and the descriptors are used from there.  Code that both need goes in the generator's project, where `netstandard2.0` and Roslyn 4.8.0 bound it.
- **It targets `net8.0` with `RollForward` `Major`, and references a current Roslyn by `VersionOverride`.**  Do not raise the target: a user with only the .NET 8 SDK must be able to run it.  `tools/check-tool-install.sh` runs the packed tool on the newest runtime the machine has.
- **Everything from outside comes through `ToolHost`.**  Nothing reads `Console`, `Environment` or the current directory except `ToolHost.Create` and `Cli.Run`, which is the entry of a real run and listens for Ctrl+C, `SIGTERM` and `SIGHUP`: the first cancels the run, which ends by its own road with its exit code, and a second, while the run has not ended, lets the process be killed (`Cli.Interrupt`), since a run that waits on a database may not look at its token.  The three share one count of signals, which is raised atomically: two that come at once, each on a thread of its own, are not both the first.  For the first signal, the handler of `SIGTERM` and `SIGHUP` returns only when the run has ended, and for a second it returns at once (`Cli.Terminate`): on Windows they are the shutdown and the closed console, and the system ends the process when their handler returns, whatever it answers.  `tests/SqlSource.Tool.Tests/Commands/TerminationTests.cs` sends each signal to the tool in a process of its own, where a system has signals, and closes the tool's console on Windows; nothing can raise the shutdown of Windows, which has the same handler.  A test gives `Cli.RunAsync` a host of its own.  The clock is `ToolHost.Time`, a `TimeProvider`: the time of a log's events and how long a step took come from it and never from `DateTime` or `Stopwatch`, and a test brings `tests/SqlSource.Tool.Tests/TestClock.cs`.  What a later phase takes from outside, a database, is a new member of `ToolHost`, as the clock and the processes are.  The one thing that does not come through it is the `os` and `runtime` of the log's `run.start`, which `Cli.OpenLog` reads from `RuntimeInformation`: `docs/tech-debt/TD-0036-two-small-gaps-of-check-and-the-log.md`.
- **Every process goes through `ToolHost.Processes`**, an `IProcessRunner` of `Processes/`.  `Processes/ProcessRunner.cs` is the only code that starts one, and a test gives `tests/SqlSource.Tool.Tests/FakeProcessRunner.cs`, which answers in MSBuild's place.  A run that is cancelled kills the program with everything it started and waits, for a few seconds at most, until the program has ended, so that the folder it wrote to can be deleted: MSBuild itself writes the manifest, and nothing waits for what MSBuild started; a kill that fails never stands in for the cancellation, which would be reported as `SQLSRC200`.  A temporary folder is made in `ToolHost.TempDirectory`, and what runs at once is bounded by `ToolHost.ProcessorCount`.
- **The tool never restores and never builds a project, and writes nothing into one but its sidecars.**  `Projects/ProjectEvaluator.cs` runs `dotnet msbuild` to evaluate a project and to run the package's target `SqlSourceWriteManifest`, which writes to a file the tool named in a temporary folder of the run.  Do not add `-restore`, a target of a build, or a file under a project's folder: `tests/SqlSource.Tool.Tests/Projects/FixtureProjectTests.cs` checks that a project has no `obj` afterwards.  A sidecar is written or deleted by `Describing/SidecarStore.cs` and by nothing else.
- **MSBuild's output is parsed only as the JSON of `-getProperty` and `-getItem`.**  Everything else it prints is shown, the first twenty lines, under `SQLSRC205`, and never read: MSBuild writes in the language of the machine.  What the tool needs from a target comes in the manifest file, read by `Projects/ManifestReader.cs`; the format is the package's contract, and `src/SqlSource/AGENTS.md` has its rules.
- **A value given to MSBuild as a property goes through `Projects/MSBuildProperty.cs`.**  MSBuild splits what follows `-p:` at `;` and `,`, and a path holds either.  Each run also sets and removes the environment variables that `ProjectEvaluator` lists, with the reason beside each: among the removed are `SQLSOURCE_CONNECTION` and, by the prefix that `ProcessRequest.RemovedPrefixes` takes, the variable of every database, so that no connection reaches MSBuild, a project's targets, or what MSBuild prints under `SQLSRC205`.  Everything else of the environment reaches MSBuild, which reads it for properties: a `Configuration` there applies to the tool's runs as it does to that user's `dotnet build`, on purpose, so that the manifest is what their compiler is given.
- **`Projects/RunProjects.cs` is the one place that says which projects a run is on** and what is said of each: the unit's projects, or the ones `--project` names.  A project of a solution that does not use SqlSource is left out silently unless it was named; one that was not restored is an error everywhere.  `Projects/SolutionReader.cs` reads a solution with `Microsoft.VisualStudio.SolutionPersistence`, and the reason of `SQLSRC223` is that library's text: no test compares it.
- **An evaluation reports nothing.**  `ProjectEvaluator` runs several projects at once and gives each error as data, in a `ProjectEvaluation`, so that the caller reports them in the order of the projects.
- **A result that may fail has one shape where files meet.**  A method that another file calls and that gives one value or one reason returns an `Outcome<TValue, TFailure>` (`Outcome.cs`) and reports nothing: its caller does, as `DescribeCommand.PlanAsync` reports what `Projects/RunUnitFinder.cs` found and `Cli.OpenLog` what `RunLogFile.Open` did.  A private helper may be a `TryX`, and so may a method that gives a value or nothing and no reason, as `ConnectionArgument.TryParse`.  A result with more than two states is a record with a state, as `ProjectEvaluation`.  A step that reports several errors as it goes takes the reporter, or returns its errors as data, and is no `Outcome`.  An `Outcome` of a value that must be disposed has a `SuppressMessage` for `CA2000` on the method that makes it, as `RunLogFile.Open` has, and on no wider scope: the analyzer follows a disposable only when it is returned itself (`docs/tech-debt/TD-0041-ca2000-is-suppressed-on-the-opener-of-the-log.md`).
- **`Planning/` makes the plan of a run and reports nothing.**  `Planning/RunPlanner.cs` gives a `RunPlan` and its errors as data, in the order they are to be reported, and `DescribeCommand.cs` reports them.  The plan keeps every query of every file that a type claims: `--database` and a `.sql` path set `PlannedQuery.IsSelected` and take nothing out, because a sidecar is written only when every query of its file that needs an entry has one.  A file that no type claims is never read.
- **The plan must agree with the generator**, on which type claims which file with which output, and on each query's hash.  So `RunPlanner` calls the generator's own path resolver, readers of settings, parser and hash, through `Planning/ManifestOptions.cs` and `Planning/SqlFileText.cs`, and copies no rule.  `GeneratorParityTests` runs both over the same sources and compares the types, their `Path` and `Output`, and the files each claims; what a file's settings and a query's hash come to is held by the tests of `RunPlanner`, which reach both through the generator's code.  A path that a project lists twice has the metadata of its last item that has any, as the compiler gives it: `Planning/ListedFiles.cs`.  A rule that both need goes into the generator's project.
- **`Planning/AttributeReader.cs` reads syntax, and two arguments.**  It has no compilation: it finds `[SqlSourceGenerate]` by name and reads `Path` as a string literal and `Output` as a member of `GeneratorOutput`.  Anything else in one of those two is `SQLSRC208`, and nothing else on the attribute is read, since nothing else changes what is described.  What it misreads is `docs/tech-debt/TD-0031-attribute-reader-of-the-tool-is-syntax-only.md`.
- **A database belongs to a query that needs an entry, and to no other.**  Names are compared ignoring case, and the plan holds the first spelling.  A file that is `NotDescribable` gives its database no dialect.
- **Of the settings that are not valid, the tool reports the ones it reads**: the dialect, `SqlSourceOutput` and `SqlSourceDatabase`, under the generator's `SQLSRC011` and `SQLSRC014`, at the project file.  The build reports the rest.
- **`Describing/` is a run after its plan, in steps that stay apart.**  `Describing/DescribeRun.cs` calls them in order: `RunDecisions.cs` reads the sidecars that are there and gives each query a state; `Connections.cs` finds the connection of each selected database; `DatabaseRuns.cs` opens one session for each database and describes its queries one at a time; `FileOutcomes.cs` gives each file its outcome and its target and changes nothing; `SidecarStore.cs` applies the outcomes to the disk; `RunSummary.cs` gives the lines that end the run.  `--check` shares the run and replaces only the step that writes: `Describing/SidecarCheck.cs` compares where `SidecarStore` writes, from each selected query's described entry, and returns its differences as data.  So the step that decides must never write, the step that writes must never decide, and the step that compares does neither: what it says of a sidecar that would be deleted it takes from `FileOutcomes`.  `RunDecisions` reports no `SQLSRC221` under `--check`: a sidecar of a higher format version is a difference there, and its queries are described like any other.
- **`Describing/Describers/` is the contract a describer implements**: `IQueryDescriber`, `IDescribeSession`, `IDescribeExchange`, and the requests, failures and server information they exchange, with each result an `Outcome` of a `DescribeFailure`.  It uses nothing of the run's steps, only `Outcome`, `Reporting/` and `Logging/`, so a describer of phase 3 depends on no step of the run.  A describer's clock is `OpenRequest.Time`, which `Describing/DatabaseRuns.cs` sets from `ToolHost.Time`: a describer reads no `DateTime` and no `Stopwatch`.
- **A describer returns a failure and never throws.**  What a server or a user can cause is a `DescribeFailure`, which the run reports at the query in the format of `Describing/DescribeErrors.cs`.  An exception from one is a bug of the describer and ends the run with `SQLSRC200`.  The released tool has no describer: `ToolHost.Create` gives `DescriberRegistry.Empty`, and every query that must be described is `SQLSRC216`, until phase 3 registers PostgreSQL's.
- **Every call a describer makes to an engine goes through `IDescribeExchange`**, the one it is given in its `OpenRequest`.  The exchange has three shapes: `Describing/Describers/LiveExchange.cs` asks the engine and keeps nothing; `Describing/Capture/CapturingExchange.cs` asks another exchange and adds each call that answered to a `DescribeCapture`; `Describing/Capture/ReplayingExchange.cs` answers from a capture and never asks.  A replay finds a call by its method and by its request as `CaptureJson.KeyOf` writes it, gives the answers of a question asked twice in the capture's order, and throws `CaptureMissException` for a question with no answer left, so that a describer whose calls changed fails its fixtures and never passes silently.  A capture that holds more than was asked is no error; `ReplayingExchange.Unused` says what was left.  `ToolHost.Exchange` gives the live one; nothing in the released tool records yet.
- **A request and an answer are plain records, and nothing of the seam crosses the exchange.**  A record of a call is sealed and holds strings, integers, booleans, nullable ones, `IReadOnlyList<T>` of them and records of the same kind: no driver type, no `DateTime`, no `Exception`, no enum, no abstract base, and never an `Outcome`, a `DescribeFailure`, a `QueryDescription` or an `EquatableArray`, none of which System.Text.Json reads back.  A describer maps between its records and the seam's types on its own side.  A call that can fail on the server has an answer with an `error` member that is null on success: the failure is data, and a replay gives it again.  A request holds everything that decides the answer, and nothing of a connection: not the value, a part of it, the host or the user's name, so the request of the call that opens a session is empty.  The one exception is the driver's own message in an `error`, which `docs/tech-debt/TD-0034-redaction-of-a-describers-text-has-holes.md` records.  A name that a describer makes up and sends, a prepared statement's for one, is a counter within its session and never random: it is part of a request.  `tests/SqlSource.Tool.Tests/Describing/Capture/CallRecordTests.cs` holds every record whose name ends in `Request` or `Answer`, in the namespace of an engine's describer and in that of the tests, to the rule; a describer in a new namespace adds it to `Namespaces` there.
- **A capture is a file that outlives the version that wrote it.**  `Describing/Capture/CaptureJson.cs` writes it indented, in UTF-8, with `\n` line ends on every platform, and reads it into an `Outcome` whose failure is a sentence.  It is the `capture.json` of a fixture and, from phase 10, of a user's bug bundle, so the name of a method and the members of a record are added to and never renamed: an answer that lacks a member is read with the member's default.  `DescribeCapture.Version` rises only when a capture of the version before can no longer be read, and the reader names a version it does not know.  `CaptureJson.Options` is the one set of options for a request and an answer; the key of a call depends on it, so a change to it changes every fixture.
- **`tests/SqlSource.Tool.Tests/FakeDescriber.cs` is a describer written by these rules**, and the tests of the exchanges and of the fixture harness run through it.  Its records are in `tests/SqlSource.Tool.Tests/FakeDescriberCalls.cs` and its maps in `tests/SqlSource.Tool.Tests/FakeCalls.cs`; it carries `PostgresType` and `OtherEngineType` and throws for a `SqlServerType`.  Under a replay its `live` functions never run, so it keeps nothing in `Opened` and `Described` and its hooks do not fire.  Its one descriptor, `SQLSRC999`, exists in the tests only and is listed in `tests/SqlSource.Tool.Tests/AnalyzerReleases.Unshipped.md`, which that project needs for release tracking: a test that adds another descriptor adds its row there.  `FakeDescriber.RejectedWith` makes one from a text, whose id is no constant and has no row.  Every run of `tests/SqlSource.Tool.Tests/CliRun.cs` records through a `CapturingExchange` into `CliRun.Capture`.
- **The fixtures of a describer are in `tests/SqlSource.Tool.Tests/Fixtures/Describers/<engine>/<case>/`**, beside the engine's `schema.sql`: `query.sql`, a complete SqlSource file with exactly one query; `capture.json`, the calls of describing it as `CaptureJson` writes them; `expected.json`, a sidecar with the one entry as `SidecarWriter` writes it, with the `toolVersion` `fixture` so that a new version of the tool touches no fixture; and an optional `issue.md`.  The files are compared byte for byte and the SQL of `query.sql` is in a request, so the folder is `text eol=lf` in `.gitattributes` and has a section in `.editorconfig`.  `tests/SqlSource.Tool.Tests/Fixtures/FixtureCases.cs` finds the cases in the output folder, and `Fixtures/FixtureReplay.cs` describes one through a `ReplayingExchange`, with the connection `replay`, and gives the sidecar's text.  The folder is empty until the first describer brings its cases.
- **A connection's value goes to the describer and nowhere else.**  `OpenRequest` is the one thing that holds it for a describer, and `ConnectionArgument`, `DatabaseConnection`, `OpenRequest` and `UsageValue` each override `ToString` to leave it out: a record prints its members.  What the tool may say of a connection is where it came from, `--connection` or the name of a variable.  A describer puts the value in nothing it returns, and the run does not rely on that: every text of a describer that is printed, an exception's included, goes through `Describing/Redaction.cs`, which writes the whole value as `***`.  A failure goes through it twice: as the describer returned it, for its descriptor, which a describer may have built from a server's text, and for its server lines, which are searched joined since a value with a line break is cut over two; and as the error made of it, for everything else.  The log is held to the same: nothing hands a log a value, `Logging/LoggedArguments.cs` builds `arguments` from what `UsageCheck` read and not from the text, a describer's log is a `Logging/SessionRunLog.cs` that removes the value from every string of an event, and what the run itself writes of a database after its connection is found goes through `RunTrace.Without`.  `tests/SqlSource.Tool.Tests/Describing/RedactionTests.cs` holds the log to all of it; a new event that carries what a describer gave gets a case there.  A description that holds the value, searched as the sidecar's writer would write it (`Describing/EntrySecretCheck.cs`, called inside the guard of `Describing/DatabaseRuns.cs`), is a bug of the describer like any other: `SQLSRC200`, the run ends and no sidecar is written.  A value that the entry's text holds without the describer's part, a word of the format or the name of the database, is none the describer put there; a member of an entry that a describer gives must be left out in `EntrySecretCheck.WithoutTheDescribersPart`, or a value in it is never found, and gets a fact in `tests/SqlSource.Tool.Tests/Describing/EntrySecretCheckTests.cs`.  What that does not cover is `docs/tech-debt/TD-0034-redaction-of-a-describers-text-has-holes.md`.  `tests/SqlSource.Tool.Tests/Commands/SecretTests.cs` holds the tool to all of it; a new place that prints what a describer gave gets a case there.
- **A sidecar is written whole or not at all, through `SidecarStore`**: to a temporary file beside it that is then moved over the old one.  A run that is killed between the two leaves the temporary file, and `SidecarStore.Apply` removes it in a later run: only a name that it gives one itself, and only when the file is older than `SidecarStore.LeftoverAge` by `ToolHost.Time`, since another run may be writing the same sidecar now.  Each folder is read once, and a run that was cancelled removes no further file.  A run with a filter removes those of the sidecars whose outcome is not `FileAction.None`; a run on the whole removes those of every sidecar in the folders of its files, since the `.sql` file of one may be gone; `--check` removes none.  The file's target holds an entry for every query that needs one, each described in this run or current, where current means that the hash and the database match and that this version of the tool wrote the file: an entry from an older tool never stands beside a new one.  A file with a query that has neither is left as it was.
- **A filter narrows what a run may read and change, as well as what it describes.**  A sidecar is read and written only for a file with a selected query that needs an entry, with one exception: a run that may delete a sidecar also reads that of a file none of whose queries needs an entry, to leave one of a higher format version alone.  A sidecar is deleted only in a run with no `--project`, no `--database` and no `.sql` path, and in which the reporter holds nothing when `Describing/DescribeRun.cs` decides the outcomes: a run on a part does not know what the rest needs of a file, and the plan drops a setting or a claim it could not read, so an error can make a file look as if it needs no entry.  `Describing/DescribeRun.cs` decides both and gives `FileOutcomes.Decide` the one answer, with a function that reads the sidecar (`SidecarOnDisk.Read`): a sidecar is deleted only if one is there, the system lets the tool open it, and it is not of a higher format version, which a newer tool wrote and which is left as it is, with nothing reported.  One that the system will not let the tool open cannot be told from a newer tool's, so it is left too, as `FileAction.Unreadable`, whose outcome holds the `SQLSRC218` that says which file stays: `SidecarStore` reports it, and under `--check` `DescribeRun` does, as an error and no difference.  `tests/SqlSource.Tool.Tests/Commands/FilterRunTests.cs` holds it.  `--check` reports within the same bounds, so that it reports what `describe` with the same filters would change, and `tests/SqlSource.Tool.Tests/Commands/CheckFilterTests.cs` holds that, with one exception: under `--database` it does not report the entry of a query that is gone when the entry's database is not named, which `describe --database` still drops when it rewrites the file (`docs/tech-debt/TD-0036-two-small-gaps-of-check-and-the-log.md`).
- **A database needs a describer and a connection only when a query of it must be described.**  The connection of every selected database is looked up, since the summary says which have none, and a missing one is an error only in `DatabaseRuns`.  `SQLSOURCE_CONNECTION` is for a run with one selected database that can be described, `RunDecisions.DescribableDatabases`: one whose every selected query the plan failed is still a selected database, with its line in the summary, and is none the variable could be meant for, so `SQLSRC215` neither counts nor names it.  A query that the plan could not describe, and every query of a file that is not `Ready`, counts as failed and gets no further error.
- **`Logging/` is what a run says of itself beside its errors and its summary.**  `--log <path>` of `describe`, or else `SQLSOURCE_LOG`, names a file of JSON Lines that `Logging/RunLogFile.cs` writes: one object for each event, written and flushed as the run goes.  `Cli.OpenLog` opens it, only after `UsageCheck` and `DescribeCommand.CheckUsage` accepted the command line and System.CommandLine read the same, so a wrong command line is never logged, and only for a command line that runs `describe` (`DescribeCommand.Runs`): the help must not empty the log of the last run.  `Cli.RunAsync` closes it.  For every `describe` that runs, `Cli.InvokeAsync` makes the run's `Reporter` with its `RunTrace`, which has the log when there is one and standard output when `--verbose` was given, and only then gives the command its action (`DescribeCommand.Bind`), so that the command cannot run with another reporter; an error before that has a reporter with no trace.  `Cli.RunAsync` calls `RunCommandAsync`, whose one `try` holds three steps in this order: `ReadCommandLineAsync`, `OpenLog` and `InvokeAsync`.  The three share a `RunState` with `RunAsync`, which ends the run outside that `try`.  `InvokeAsync` replaces `RunState.Reporter`, so whatever reports after a step reads the reporter from the state then, and never from a local made before the step.  `Cli` writes `run.start`, in `OpenLog`, and `run.end`, in `End`, since the exit code and the error of an exception are known only there; `Reporter` writes a `diagnostic` event for each error, under the same lock as the console, to the trace it was made with.  Every step that has the reporter has the trace.  `Logging/RunEvents.cs` builds each other event in one place, and its caller writes it where the thing happens: a step that reports nothing, the planner, `RunDecisions`, `FileOutcomes`, `SidecarCheck`, writes no event either, and its caller does, from what it returned.  `Describing/DescribeRun.cs` hands `Cli` the counts that `run.end` ends with, from `RunSummary.Counts`, before it writes the summary, so that a summary that cannot be written does not lose them.  `arguments` of `run.start` is built from what `UsageCheck` read (`Logging/LoggedArguments.cs`), never from the text of the command line, so that the value of a `--connection` is `***` whichever way the option was written.  A write the system refuses does not end the run: the writer goes quiet, and `Cli` reports it once as `SQLSRC218` when the run ends, with exit code `1`.  `RunTrace.Say` is the one place that writes a line of `--verbose`, each to standard output and on one line, and `RunEvents` says it beside the event it belongs to, so the two never tell two stories.  `tests/SqlSource.Tool.Tests/Logging/RunLogTests.cs` and `tests/SqlSource.Tool.Tests/Describing/RedactionTests.cs` hold it.  `tests/SqlSource.Tool.Tests/Commands/VerboseTests.cs` holds the lines.
- **An event's name and its members are read by people and by phase 10's bundle.**  A member is added and never renamed, and a value is one of `Logging/LogValue.cs`'s closed set.  A describer's events have its engine before their names, which `Logging/SessionRunLog.cs` puts there.  `Logging/RunLogFile.cs` cuts a string over 1 MiB, and never ends a run.  It owns the names `event`, `time` and `truncated` at the top of a line, and writes a caller's member of one of them with an underscore before it.
- **Every error goes through `Reporting/Reporter.cs` with a descriptor of `ToolDiagnostics`**, or of `SqlDiagnostics` where the generator reports the same condition.  The descriptors are in the generator's project; its `AGENTS.md` lists the four places a new one touches.  A wrong command line is the one exception, below.
- **The exit code is `0`, `1` or `2`.**  `1` when the reporter wrote any error but `SQLSRC219`, when the command line was wrong, and when the run was cancelled.  `2` when it wrote `SQLSRC219` and nothing else: a sidecar that `--check` found out of date.  `Cli.ExitCodeOf` takes both from `Reporter.Count` and `Reporter.DifferenceCount`, so a command reports and goes on, and never returns `1` itself.  A query that could not be described is "could not check" and never `SQLSRC219`.
- **The format of an error is a contract with MSBuild and with editors.**  `<path>(<line>,<column>): error <id>: <message>`, or `<path> : error`, or `sqlsource : error`; then continuation lines, each four spaces, a label, a colon, a space and a text; then `    see:` with the descriptor's help link, last.  Only the first column tells a first line from a continuation line, so `Reporting/OneLine.cs` writes a line break as a space in every text the tool prints and did not write itself: an argument of a message, a path, a label, the name of an unknown option.  Several threads may report, so `Reporter` writes an error with one call, under a lock.  A path in a message is a full path.  No error carries a hint to a log: a `describe` that reported an error other than `SQLSRC219`, was not cancelled, and was asked for no log ends with `Cli.RunAgainLine`, once, on standard error.  A test that compares the whole of standard error of such a run ends its text with `DescribeScene.RunAgain`.
- **An exception is `SQLSRC200`**, caught in `Cli.RunCommandAsync`, the one `try` around the steps of `Cli.RunAsync`, and in `Cli.Run` when the host itself cannot be made, as when the working directory was deleted, and in one other place: `Describing/DatabaseRuns.cs` catches what a describer throws, since its message may hold a connection's value, and throws a `DescriberFaultException` that holds the same error with the value taken out, which `Cli.RunCommandAsync` reports.  `DescriberFaultException` derives from `InvalidOperationException`, since S3871 wants an exception that derives from `Exception` to be public and CA1515 allows no public type in the tool, and it never holds an inner exception, whose message may hold the value.  A session that fails to close after the body of its database ended with an exception is dropped, so that the first exception is the run's end and a cancelled run prints nothing more.  So no `catch (InvalidOperationException)` may stand between `Describing/DatabaseRuns.cs` and `Cli.RunCommandAsync`: it would swallow the fault and the run would go on.  `Reporting/UnexpectedFailure.cs` makes the error, and takes an optional function that redacts an exception's whole text before it is split into trace lines, so that a value which spans lines is replaced whole.  The stack trace is continuation lines labelled `trace`, written only when `SQLSOURCE_DEBUG` is set and not empty.
- **A wrong command line is reported by `UsageCheck.cs`, before System.CommandLine reads it, and never repeats a token's text.**  System.CommandLine's own messages repeat the token they reject, and a token can be a secret.  A line names an option the tool has, or the name of an unknown option cut at its first `=` or `:`, or a position counted from one.  Only the first unknown option is reported, and nothing after it is read.  These lines have no id and do not go through the reporter.  `tests/SqlSource.Tool.Tests/Commands/UsageCheckTests.cs` holds the rule for an option that takes a value.
- **`UsageCheck` and System.CommandLine must read a command line the same way.**  A token that one takes for the value of an option and the other for the path is printed as a path.  `Usage.cs` is what `UsageCheck` read, and `Cli` runs nothing unless System.CommandLine found the same command and the same arguments: it writes `sqlsource: the command line is not valid` instead.  `Check_EveryAcceptedCommandLine_IsReadTheSameBySystemCommandLine` holds the two together over every command line of a few tokens.  A new kind of option adds its tokens to that test's vocabulary, and an option of the tool itself to that of `Check_EveryAcceptedCommandLineOfTheTool_IsReadTheSameBySystemCommandLine`, which runs the tool's own commands and also compares the values that each reader gives an option, and a disagreement it finds is fixed in `UsageCheck`, by reading as System.CommandLine does or by rejecting more.  What is left of the risk is `docs/tech-debt/TD-0023-unknown-option-and-path-are-printed-as-given.md`.  `Cli` also runs nothing unless both readers give `--connection` the same values (`DescribeCommand.ReadsConnectionsAs`), since the log's `arguments` is redacted from one reading and the describer is handed the other.
- **A command's own rules for its values are in the command**, as `DescribeCommand.CheckUsage`, which reads `Usage.Values`: each argument and each value of an option with its position.  `Cli.ReadCommandLineAsync` calls it when `UsageCheck` found nothing.  Its lines name a position and never a token, as `UsageCheck`'s do.  It holds a value of `--database` to the rule of a database name, a value of `--connection` to `<name>=<connection string>` with each name given once, and a value of `--log` to one that is not empty or white space, which is what `--log "$UNSET"` gives.  `describe` takes several paths so that System.CommandLine accepts a `.sql` path beside the unit; `CheckUsage` holds them to one unit.  On a line with a `--connection`, an argument that holds `=` or `;` is a part of a value that the shell split, a `.sql` path too, and is reported by its position: it would be printed as a path, a `.sql` one in full by `SQLSRC212`.  A path may hold either, as a folder of `tests/SqlSource.Tool.Tests/Fixtures/Projects/OddPaths` does, so a line with no `--connection` is left as it is.
- **An option is declared so that `UsageCheck` reads it right.**  A flag has `Arity = ArgumentArity.Zero`: System.CommandLine's default for a `bool` takes an optional value, and the token after the flag would be read as that value.  An option that takes a value takes exactly one each time it is given: `ArgumentArity.ExactlyOne` when it is given once, and an array with `ArgumentArity.OneOrMore` when it may be repeated, since System.CommandLine rejects a second `ExactlyOne`.  `UsageCheck` rejects that second one itself, with `option '<name>' is given more than once`, since System.CommandLine's message repeats the value.  An option is added to `--help` in the sub-phase that gives it an effect, not before: one that is read and checked earlier is `Hidden` until then, as `--database` was in sub-phase 2.4.
- **The root is a `Command`, not a `RootCommand`**, with a `HelpOption` under three names and a `--version` whose action is the tool's own.  A `RootCommand` takes its name from the process, prints the version of the assembly the process started with, which under a test is the test host, and reads `[suggest]` as a directive.  Response files and the bundling of short options are off in `Cli`.
- **The tool writes English**, and `SatelliteResourceLanguages` keeps other languages out of the package.  A test compares no text that System.CommandLine wrote.
