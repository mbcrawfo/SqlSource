# AGENTS.md - src/SqlSource.Tool

The `sqlsource` command, packed as the .NET tool `SqlSource.Tool`.  `tests/SqlSource.Tool.Tests` holds its tests, in folders named as the tool's, with `Commands/` for the tests that run a whole command line; its fakes and helpers are at its root, with the tests of `ToolHost`, of `Outcome` and of a helper, but for the helpers of the fixtures, which are in `Fixtures/` with the test of the replay harness.  The PostgreSQL describer is also tested against a server, in `tests/SqlSource.Tests.Postgres`.

- **The tool shares the generator's code and never copies it.**  It references `src/SqlSource/SqlSource.csproj` and sees its internals.  The parser, the dialect rules, the settings, the sidecar's reader and writer, the hash and the descriptors are used from there.  Code that both need goes in the generator's project, where `netstandard2.0` and Roslyn 4.8.0 bound it.
- **It targets `net8.0` with `RollForward` `Major`, and references a current Roslyn by `VersionOverride`.**  Do not raise the target: a user with only the .NET 8 SDK must be able to run it.  `tools/check-tool-install.sh` runs the packed tool on the newest runtime the machine has.
- **Everything from outside comes through `ToolHost`.**  Nothing reads `Console`, `Environment` or the current directory except `ToolHost.Create` and `Cli.Run`, which is the entry of a real run and listens for Ctrl+C, `SIGTERM` and `SIGHUP`: the first cancels the run, which ends by its own road with its exit code, and a second, while the run has not ended, lets the process be killed (`Cli.Interrupt`), since a run that waits on a database may not look at its token.  The three share one count of signals, which is raised atomically: two that come at once, each on a thread of its own, are not both the first.  For the first signal, the handler of `SIGTERM` and `SIGHUP` returns only when the run has ended, and for a second it returns at once (`Cli.Terminate`): on Windows they are the shutdown and the closed console, and the system ends the process when their handler returns, whatever it answers.  `tests/SqlSource.Tool.Tests/Commands/TerminationTests.cs` sends each signal to the tool in a process of its own, where a system has signals, and closes the tool's console on Windows; nothing can raise the shutdown of Windows, which has the same handler.  A test gives `Cli.RunAsync` a host of its own.  The clock is `ToolHost.Time`, a `TimeProvider`: the time of a log's events and how long a step took come from it and never from `DateTime` or `Stopwatch`, and a test brings `tests/SqlSource.Tool.Tests/TestClock.cs`.  What a later phase takes from outside, a database, is a new member of `ToolHost`, as the clock and the processes are.  The one thing that does not come through it is the `os` and `runtime` of the log's `run.start`, which `Cli.OpenLog` reads from `RuntimeInformation`: `docs/tech-debt/TD-0036-two-small-gaps-of-check-and-the-log.md`.
- **Every process goes through `ToolHost.Processes`**, an `IProcessRunner` of `Processes/`.  `Processes/ProcessRunner.cs` is the only code that starts one, and a test gives `tests/SqlSource.Tool.Tests/FakeProcessRunner.cs`, which answers in MSBuild's place.  A run that is cancelled kills the program with everything it started and waits, for a few seconds at most, until the program has ended, so that the folder it wrote to can be deleted: MSBuild itself writes the manifest, and nothing waits for what MSBuild started; a kill that fails never stands in for the cancellation, which would be reported as `SQLSRC200`.  A temporary folder is made in `ToolHost.TempDirectory`, and what runs at once is bounded by `ToolHost.ProcessorCount`.
- **The tool never restores and never builds a project, and writes nothing into one but its sidecars.**  `Projects/ProjectEvaluator.cs` runs `dotnet msbuild` to evaluate a project and to run the package's target `SqlSourceWriteManifest`, which writes to a file the tool named in a temporary folder of the run.  Do not add `-restore`, a target of a build, or a file under a project's folder: `tests/SqlSource.Tool.Tests/Projects/FixtureProjectTests.cs` checks that a project has no `obj` afterwards.  A sidecar is written or deleted by `Describing/SidecarStore.cs` and by nothing else.
- **MSBuild's output is parsed only as the JSON of `-getProperty` and `-getItem`.**  Everything else it prints is shown, the first twenty lines, under `SQLSRC205`, and never read: MSBuild writes in the language of the machine.  What the tool needs from a target comes in the manifest file, read by `Projects/ManifestReader.cs`; the format is the package's contract, and `src/SqlSource/AGENTS.md` has its rules.
- **A value given to MSBuild as a property goes through `Projects/MSBuildProperty.cs`.**  MSBuild splits what follows `-p:` at `;` and `,`, and a path holds either.  Each run also sets and removes the environment variables that `ProjectEvaluator` lists, with the reason beside each: among the removed are `SQLSOURCE_CONNECTION` and, by the prefix that `ProcessRequest.RemovedPrefixes` takes, the variable of every database, so that no connection reaches MSBuild, a project's targets, or what MSBuild prints under `SQLSRC205`.  Everything else of the environment reaches MSBuild, which reads it for properties: a `Configuration` there applies to the tool's runs as it does to that user's `dotnet build`, on purpose, so that the manifest is what their compiler is given.
- **`Projects/RunProjects.cs` is the one place that says which projects a run is on** and what is said of each: the unit's projects, or the ones `--project` names.  A project of a solution that does not use SqlSource is left out silently unless it was named; one that was not restored is an error everywhere.  `Projects/SolutionReader.cs` reads a solution with `Microsoft.VisualStudio.SolutionPersistence`, and the reason of `SQLSRC223` is that library's text: no test compares it.
- **An evaluation reports nothing.**  `ProjectEvaluator` runs several projects at once and gives each error as data, in a `ProjectEvaluation`, so that the caller reports them in the order of the projects.
- **A result that may fail has one shape where files meet.**  A method that another file calls and that gives one value or one reason returns an `Outcome<TValue, TFailure>` (`Outcome.cs`) and reports nothing: its caller does, as `DescribeCommand.PlanAsync` reports what `Projects/RunUnitFinder.cs` found and `Cli.OpenLog` what `RunLogFile.Open` did.  A private helper may be a `TryX`, and so may a method that gives a value or nothing and no reason, as `ConnectionArgument.TryParse`.  A result with more than two states is a record with a state, as `ProjectEvaluation`.  A step that reports several errors as it goes takes the reporter, or returns its errors as data, and is no `Outcome`.  An `Outcome` of a value that must be disposed has a `SuppressMessage` for `CA2000` on the method that makes it, as `RunLogFile.Open` and `PostgresSession.OpenAsync` have, and on no wider scope: the analyzer follows a disposable only when it is returned itself (`docs/tech-debt/TD-0041-ca2000-is-suppressed-on-the-opener-of-the-log.md`).
- **`Planning/` makes the plan of a run and reports nothing.**  `Planning/RunPlanner.cs` gives a `RunPlan` and its errors as data, in the order they are to be reported, and `DescribeCommand.cs` reports them.  The plan keeps every query of every file that a type claims: `--database` and a `.sql` path set `PlannedQuery.IsSelected` and take nothing out, because a sidecar is written only when every query of its file that needs an entry has one.  A file that no type claims is never read.
- **The plan must agree with the generator**, on which type claims which file with which output, and on each query's hash.  So `RunPlanner` calls the generator's own path resolver, readers of settings, parser and hash, through `Planning/ManifestOptions.cs` and `Planning/SqlFileText.cs`, and copies no rule.  `GeneratorParityTests` runs both over the same sources and compares the types, their `Path` and `Output`, and the files each claims; what a file's settings and a query's hash come to is held by the tests of `RunPlanner`, which reach both through the generator's code.  A path that a project lists twice has the metadata of its last item that has any, as the compiler gives it: `Planning/ListedFiles.cs`.  A rule that both need goes into the generator's project.
- **`Planning/AttributeReader.cs` reads syntax, and two arguments.**  It has no compilation: it finds `[SqlSourceGenerate]` by name and reads `Path` as a string literal and `Output` as a member of `GeneratorOutput`.  Anything else in one of those two is `SQLSRC208`, and nothing else on the attribute is read, since nothing else changes what is described.  What it misreads is `docs/tech-debt/TD-0031-attribute-reader-of-the-tool-is-syntax-only.md`.
- **A database belongs to a query that needs an entry, and to no other.**  Names are compared ignoring case, and the plan holds the first spelling.  A file that is `NotDescribable` gives its database no dialect.
- **Of the settings that are not valid, the tool reports the ones it reads**: the dialect, `SqlSourceOutput` and `SqlSourceDatabase`, under the generator's `SQLSRC011` and `SQLSRC014`, at the project file.  The build reports the rest.
- **`Describing/` is a run after its plan, in steps that stay apart.**  `Describing/DescribeRun.cs` calls them in order: `RunDecisions.cs` reads the sidecars that are there and gives each query a state; `Connections.cs` finds the connection of each selected database; `DatabaseRuns.cs` opens one session for each database and describes its queries one at a time; `FileOutcomes.cs` gives each file its outcome and its target and changes nothing; `SidecarStore.cs` applies the outcomes to the disk; `RunSummary.cs` gives the lines that end the run.  `--check` shares the run and replaces only the step that writes: `Describing/SidecarCheck.cs` compares where `SidecarStore` writes, from each selected query's described entry, and returns its differences as data.  So the step that decides must never write, the step that writes must never decide, and the step that compares does neither: what it says of a sidecar that would be deleted it takes from `FileOutcomes`.  `RunDecisions` reports no `SQLSRC221` under `--check`: a sidecar of a higher format version is a difference there, and its queries are described like any other.
- **`Describing/Describers/` is the contract a describer implements**: `IQueryDescriber`, `IDescribeSession`, `IDescribeExchange`, and the requests, failures and server information they exchange, with each result an `Outcome` of a `DescribeFailure`.  It uses nothing of the run's steps, only `Outcome`, `Reporting/` and `Logging/`, so a describer of phase 3 depends on no step of the run.  A describer's clock is `OpenRequest.Time`, which `Describing/DatabaseRuns.cs` sets from `ToolHost.Time`: a describer reads no `DateTime` and no `Stopwatch`.
- **A describer returns a failure and never throws.**  What a server or a user can cause is a `DescribeFailure`, which the run reports at the query in the format of `Describing/DescribeErrors.cs`.  An exception from one is a bug of the describer and ends the run with `SQLSRC200`.  The released tool has no describer: `ToolHost.Create` gives `DescriberRegistry.Empty`, and every query that must be described is `SQLSRC216`, until sub-phase 3.6 registers PostgreSQL's, which is in `Describing/Postgres/`.
- **Every call a describer makes to an engine goes through `IDescribeExchange`**, the one it is given in its `OpenRequest`.  The exchange has three shapes: `Describing/Describers/LiveExchange.cs` asks the engine and keeps nothing; `Describing/Capture/CapturingExchange.cs` asks another exchange and adds each call that answered to a `DescribeCapture`; `Describing/Capture/ReplayingExchange.cs` answers from a capture and never asks.  A replay finds a call by its method and by its request as `CaptureJson.KeyOf` writes it, without its null members, gives the answers of a question asked twice in the capture's order, and throws `CaptureMissException` for a question with no answer left, so that a describer whose calls changed fails its fixtures and never passes silently.  A capture that holds more than was asked is no error; `ReplayingExchange.Unused` says what was left.  `ToolHost.Exchange` gives the live one; nothing in the released tool records yet.
- **A request and an answer are plain records, and nothing of the seam crosses the exchange.**  A record of a call is sealed and holds strings, integers, booleans, nullable ones, `IReadOnlyList<T>` of them and records of the same kind: no driver type, no `DateTime`, no `Exception`, no enum, no abstract base, and never an `Outcome`, a `DescribeFailure`, a `QueryDescription` or an `EquatableArray`, none of which System.Text.Json reads back.  A describer maps between its records and the seam's types on its own side.  A call that can fail on the server has an answer with an `error` member that is null on success: the failure is data, and a replay gives it again.  A request holds everything that decides the answer, and nothing of a connection: not the value, a part of it, the host or the user's name, so the request of the call that opens a session is empty.  The one exception is the driver's own message in an `error`, which `docs/tech-debt/TD-0034-redaction-of-a-describers-text-has-holes.md` records.  A name that a describer makes up and sends, a prepared statement's for one, is a counter within its session and never random: it is part of a request.  `tests/SqlSource.Tool.Tests/Describing/Capture/CallRecordTests.cs` holds every record whose name ends in `Request` or `Answer`, in the namespace of an engine's describer and in that of the tests, to the rule; a namespace under an engine's is read too, and a describer in a new namespace adds it to `Under` there.
- **A capture is a file that outlives the version that wrote it.**  `Describing/Capture/CaptureJson.cs` writes it indented, in UTF-8, with `\n` line ends on every platform, and reads it into an `Outcome` whose failure is a sentence.  It is the `capture.json` of a fixture and, from phase 10, of a user's bug bundle, so what a describer asks and is answered is a contract with the captures that exist.  The name of a method never changes.  A call is found by `CaptureJson.KeyOf`, which is the request without its null members, at every depth.  So a request's record may gain a member that is nullable and whose null means what the request meant before it had the member: a call that was recorded earlier answers it.  Give a new member no other meaning for null, or an old capture answers a question it was never asked.  A member that is renamed, removed or moved, a member of a value type, which is never null, and a new member where it holds a value each make a question that no older capture answers.  A null in a list is a value and stays in the key.  The key is in no file: it is made at each replay, of the recorded request and of the asked one alike, and the file holds the request whole, so what a key leaves out can widen later without a capture being recorded again, and what a file holds cannot change.  That two requests never share a key by accident rests on the rule of a record: no dictionary and nothing polymorphic.  An answer's record may gain a member, which must be nullable: an older capture is read with null there, and an unknown member of a newer one is ignored.  A null where the record says there is none, a member that is missing included, is a `CaptureMissException` that names the member (`Describing/Capture/AnswerNulls.cs`); a member of a value type that is missing is read as its default and is not found, so a new one is nullable too.  `tests/SqlSource.Tool.Tests/Describing/Capture/ReplayingExchangeTests.cs` holds each of these.  `DescribeCapture.Version` rises only when a capture of the version before can no longer be read, and the reader names a version it does not know.  `CaptureJson.Options` is the one set of options for a request and an answer; what a capture's file holds depends on it, so a change to it changes every fixture.
- **`tests/SqlSource.Tool.Tests/FakeDescriber.cs` is a describer written by these rules**, and the tests of the exchanges and of the fixture harness run through it.  Its records are in `tests/SqlSource.Tool.Tests/FakeDescriberCalls.cs` and its maps in `tests/SqlSource.Tool.Tests/FakeCalls.cs`; it carries `PostgresType` and `OtherEngineType` and throws for a `SqlServerType`.  Its `OpenAsync` has the `SuppressMessage` for `CA2000` that an `Outcome` of a disposable needs (`docs/tech-debt/TD-0041-ca2000-is-suppressed-on-the-opener-of-the-log.md`).  Under a replay its `live` functions never run, so it keeps nothing in `Opened` and `Described`, and `OnOpen`, `OnDescribe`, `BeforeDescribe`, `OpenException` and `Exceptions` do nothing; what it does outside `live` still holds: the four results of a describer with a bug, `CloseException` and `Closed`.  Its one descriptor, `SQLSRC999`, exists in the tests only and is listed in `tests/SqlSource.Tool.Tests/AnalyzerReleases.Unshipped.md`, which that project needs for release tracking: a test that adds another descriptor adds its row there.  `FakeDescriber.RejectedWith` makes one from a text, whose id is no constant and has no row.  Every run of `tests/SqlSource.Tool.Tests/CliRun.cs` records through a `CapturingExchange` into `CliRun.Capture`.
- **The fixtures of a describer are in `tests/SqlSource.Tool.Tests/Fixtures/Describers/<engine>/<case>/`**, beside the engine's `schema.sql`: `query.sql`, a complete SqlSource file with exactly one query; `capture.json`, the calls of describing it as `CaptureJson` writes them; `expected.json`, a sidecar with the one entry as `SidecarWriter` writes it, with the `toolVersion` `fixture` so that a new version of the tool touches no fixture; and an optional `issue.md`.  A case of the PostgreSQL describer may hold an `explain-settings.txt`, one `name=value` on a line, which `FixtureCase.ExplainSettings` reads and both harnesses give the describer: a case whose name ends in `-hash`, `-merge` or `-nestloop` turns the other two join methods off.  The files are compared byte for byte and the SQL of `query.sql` is in a request, so the folder is `text eol=lf` in `.gitattributes` and has a section in `.editorconfig`.  `tests/SqlSource.Tool.Tests/Fixtures/FixtureCases.cs` finds the cases in the output folder, and `Fixtures/FixtureReplay.cs` describes one through a `ReplayingExchange`, with the connection `replay`, and gives the sidecar's text.  `postgres/schema.sql` is the schema that `tests/SqlSource.Tests.Postgres` applies to its container; a change to it can move the OIDs that the captures hold, and every case is recorded again.
- **`Describing/Postgres/` is the PostgreSQL describer, and it is registered nowhere.**  `ToolHost.Create` still gives `DescriberRegistry.Empty`, and its tests alone reach it, until sub-phase 3.6 registers it.  It describes a query through one prepared statement, and `PostgresSession.DescribePreparedAsync` holds the order: `prepare`, which runs `PREPARE <name> (<declared type or unknown>, ...) AS <sql>` on the SQL that `ParameterPlaceholders.Rewrite` gave `$n` and reads `parameter_types` of `pg_prepared_statements`; `columns`, which describes `EXECUTE <name>(NULL, ...)` under `CommandBehavior.SchemaOnly` and runs nothing; `tables`, one query of `pg_class` and `pg_attribute` for every table the columns name; `types`, once, for the closure of the OIDs of the parameters, the columns and the origin attributes; the parameters typed; the columns built; `check`; for a gated query with rows, `explain`, whose plan `NullabilityWalk` walks; the table match, which asks nothing; and `deallocate` in the `finally`.  `PREPARE` is the route because it takes a declared type as written, `int`, `varchar(50)`, a domain, resolves it and checks it against every use of the parameter; Npgsql's own describe sends no types.  `types` comes after `tables` because the type of an origin attribute is where a domain is found, and the request is one.  A call is not made when it has nothing to ask: `tables` when no column names a table, `types` when there is no OID.  A statement without rows is `SidecarResultKind.None` with no columns and no provenance.
- **A column is built from three answers, each by a class of its own.**  `ColumnOrigin.Find` gives the table and the attribute of a column's `tableOid` and `attributeNumber`; a system column, `ctid`, has an attribute number below zero and no origin, and a table or an attribute that `tables` did not answer is first asked for by `ColumnOrigin.MissingFrom`, which `PostgresSession` calls before it finds the origins: another session dropped it between two calls, and the describe is `SQLSRC225` at `catalog` through `PostgresErrors.SchemaChanged`.  A type that `types` did not answer, for a parameter, a column or an origin attribute, is found by the session before the parameters are typed and is `SQLSRC225` at `resolve type` the same way.  The throws that remain, in `ColumnOrigin.Find`, `ColumnTypes`, `PostgresColumns` and `PostgresTypes`, guard a bug of the describer.  `ColumnTypes.OidOf` chooses the type: the row description flattens a domain to its base with the domain's modifier, so the column is the origin attribute's type when that is a domain whose chain of bases reaches the reported type, and the reported type otherwise; an expression over a domain says the base.  An array of a domain is not flattened and needs no origin.  `ColumnFacets.Of` reads the facets from Npgsql's `ColumnSize`, `NumericPrecision` and `NumericScale`, since Npgsql gives no modifier, by the internal name of the reported type and for no other type, so an array, which Npgsql gives its element's numbers, gets none.  Three of Npgsql's numbers are decoded: a `numeric` with a precision and no scale has the scale 0; a scale of 1024 or more is the scale less 2048, a negative one of PostgreSQL 15; and the precision 65535 of an `interval` is none.  `PostgresColumns.Build` puts them together.  A column of a pseudo-type, `record`, is `SQLSRC229` and ends the describe; a parameter of one is found first and stays `SQLSRC226` or `SQLSRC228`.
- **A column is `nullable` `false` only when the catalog says `NOT NULL`, its origin is a table that has no inheritance child and no foreign partition, and either the query is not gated or the walk proves that no outer join null-extends its relation instance** (`ColumnNullability`, `NullabilityWalk`).  No origin is `null` with `no-origin`; an origin in a view, a materialized view or a foreign table is `null` with `view`; a gated query makes every column of a table `true` with `heuristic`.  `OuterJoinGate.IsGated` is the gate: one of `LEFT`, `RIGHT`, `FULL`, `OUTER`, `ROLLUP`, `CUBE`, `GROUPING`, `OLD`, `NEW` and `MERGE` as a whole word, in any case, in a `Text` lexeme, so a string, a comment and a quoted identifier do not count and `left(name, 3)` does.  The exception is `OLD` and `NEW`, which PostgreSQL 18 resolves when quoted: a quoted identifier whose name, with `""` read as one quote, is `old` or `new` in any case counts, and so does any Unicode-escaped identifier `U&"..."`, whose escapes the tool does not decode.  `ROLLUP`, `CUBE` and `GROUPING` are the grouping sets, which put `NULL` into a `NOT NULL` grouping column with no join; `OLD`, `NEW` and `MERGE` are PostgreSQL 18's old and new row of a `RETURNING` list and the source's columns of a `MERGE ... RETURNING`, which come back `NULL` while the row description keeps the table's origin.  The gate reads the tool's lexemes, so it is as right as the lexer's reading of the text, which `docs/tech-debt/TD-0044-small-gaps-of-the-postgresql-describers-columns.md` records.  A `NOT NULL` that PostgreSQL 18 holds as not validated (`NOT VALID`) is nullable with `catalog`: `tables` reads `pg_constraint.convalidated` into `PostgresAttributeRow.NotNullValidated`, which is null on an older server.  So is a `NOT NULL` column of a table (`r`) that has or had inheritance children: `tables` reads `pg_class.relhassubclass` into `PostgresTableRow.Relhassubclass`, and before PostgreSQL 18 a child may drop a `NOT NULL` it inherited, while a query of the parent reads the child's rows.  The rule is the same on every version: it costs the parent's columns on 18, where a child cannot drop the constraint, and those of a table whose last child was dropped, whose flag PostgreSQL clears lazily.  A partition can never drop its parent's `NOT NULL`, so that rule leaves a partitioned table (`p`) out, and an answer recorded before the member existed holds null, which reads as no child.  But a foreign table may be a partition: it inherits the parent's `NOT NULL`, which nothing enforces on its remote rows, and a query of the parent reads them.  `tables` says, for a partitioned table, whether a foreign table (`f`) is anywhere in its partition tree, at any depth, by `pg_partition_tree`, into `PostgresTableRow.HasForeignPartition`, false for any other relation, and a `NOT NULL` column of a partitioned table with one is nullable with `catalog`; null, in an answer recorded before the member existed, reads as none.  `plan` is `not-needed` for a query with rows that is not gated, `walked` for a gated one whose plan the walk used, and `unavailable` for one it could not: the `reason` of `postgres.walk` says why.
- **The table match is `TableMatcher`, and it runs after everything that sets a column's nullability.**  `PostgresSession.MatchOf` calls it once for a statement with rows, after `check` and after the walk: its last check reads the `nullable` each column was given.  It is given the columns and the `ColumnOrigin` of each, which holds the relation and every attribute of it that is not dropped, as `tables` answered, and it asks the server nothing.  The checks are the values of the format's `tableMatch` in the format's order, `no-origin`, `several-tables`, `names-differ`, `columns-differ`, `order-differs`, `nullability-differs`, and the first that fails is the answer: do not reorder them, since a sidecar says which failed first.  A view, a materialized view and a foreign table may match, as a table may.  What a relation's column has, for the last check, is `ColumnNullability.Of` for a query that is not gated, so the rule of a `NOT NULL` is written once: a gated query over a table with a `NOT NULL` column is `nullability-differs`, when the walk finds that a join extends the table or cannot answer, while one whose table the join keeps matches; and a `SELECT *` from a table whose `NOT NULL` is `NOT VALID` matches.  A name is compared ordinally, as the server returned it, so an override suffix, `AS "name!"`, is `names-differ`.  The lists are compared, not the sets: a column twice is `columns-differ`.  An `INSERT ... RETURNING *` matches its table.  A statement without rows has no match and no `table-match` event; a statement with rows whose check agreed writes one, after `check` and the events of the walk.
- **The plan of a gated query is a generic one, through the prepared statement** (`PostgresLive.ExplainAsync`).  `explain` runs `BEGIN`, `SET LOCAL plan_cache_mode = force_generic_plan`, a `SET LOCAL` for each setting of the request, `EXPLAIN (VERBOSE, FORMAT JSON) EXECUTE <name>(NULL, ...)` and `ROLLBACK`, on every version.  It passes a `NULL` for each type the server resolved for the statement, a `$n` that the SQL writes itself included, since `EXPLAIN EXECUTE` refuses any other number, where `columns` passes one for each parameter of the query's list and is described whatever the number.  `EXPLAIN (GENERIC_PLAN)` of PostgreSQL 16 is not used: through Npgsql, with the parameters bound as nulls, 18.4 folded `u.id = $1` into a `Result` with `One-Time Filter: false`.  `EXPLAIN` without `ANALYZE` plans the statement and does not execute it, and disposing the transaction rolls it back when a step failed, so the session is left as it was found.  Planning evaluates an immutable function whose arguments are constants, inside that transaction, so a function wrongly marked immutable runs, and an effect outside the transaction, a sequence's for one, remains: `docs/tech-debt/TD-0047-explain-evaluates-immutable-functions.md`.  An `explain` that fails is logged and never reported: `plan` is `unavailable` and the heuristic stands.  It is asked after `check` and for a gated query with rows alone, so a query that is not gated has the capture it had.
- **The walk follows a join's sides and nothing else** (`PlanInstances`).  A child whose `Parent Relationship` is `Outer` or `Inner` is a side of a join or the one input of another node; an `InitPlan`, a `SubPlan`, a `Member` and a `Subquery` are other plans, since a CTE's plan hangs under whichever node first needs it, and their scans are no instances of this plan's joins.  A relation instance is an `Alias` on a scan of a relation, the seven node types of `PlanInstances.RelationScans`, and it is null-extended when a join on the path from the root is `Left` or `Anti` with the instance under its `Inner` child, `Right` or `Right Anti` under its `Outer`, or `Full`.  An anti join is not only a `NOT EXISTS`: the planner makes one of `a LEFT JOIN b ... WHERE b.x IS NULL`, keeps `b`'s columns in its `Output` and returns them `NULL`, as `Anti` on 14 and `Right Anti` on 18.  A `LEFT JOIN` the planner swapped is a `Right` join with the sides swapped, and one it reduced is `Inner`: the rule needs neither told apart.  A join type outside the eight of `PlanInstances.ExtendsOf`, an alias found twice, a `Grouping Sets` key or a `MixedAggregate` makes the plan unusable, and so does a root without an `Output` for every column, a `UNION ALL`'s `Append` for one.  A plain `UNION` roots as an `Aggregate` over the `Append`, has an `Output`, and is walked: its columns have no origin, and the `Member` children of the `Append` are not followed.
- **A `ModifyTable` at the root is its target, and the scan of the target under it is that same instance.**  An `UPDATE` and a `DELETE` scan their target under the `ModifyTable` with the `ModifyTable`'s own alias, on 14 and 18: read as a second instance it would be a doubled alias, and every `RETURNING` of one would be unusable.  The target is never null-extended, whatever join it is under, since the row a `RETURNING` list gives is the one the statement acted on; the source of a `MERGE` is extended as its join says.  PostgreSQL 18 prints the old and the new row as `old.id` and `new.id`, or under the names `WITH (OLD AS o, NEW AS n)` gives them, which the server refuses only when a table of the statement's top level has the name: an alias of an inner scope, the `SELECT` of an `INSERT ... SELECT` or a subquery in `FROM`, reaches the plan under the same name.  So when `OuterJoinGate.NamesOldOrNew` finds either word in the SQL, bare or as a quoted `"old"` or `"new"` in any case, or any `U&"..."` identifier, a qualified reference at a root `ModifyTable` maps only to the target's own alias, and any other keeps the heuristic.
- **An entry of `Output` is a reference or it is nothing** (`OutputReference`).  `alias.column`, each part a name PostgreSQL prints bare, lower-case letters, digits and underscores, or in double quotes with `""` for a quote; or one bare name.  Anything else is an expression and its column keeps the heuristic: `"left"((u.name)::text, 1)` starts as a quoted name does and is none.  A bare name resolves only when the root is itself a relation instance, a scan, or a `ModifyTable` with no join under it: a `Result` that replaced a scan the planner proved empty prints bare names too, beside a scan that remains, and under a `ModifyTable` too, in its `RETURNING` list.  A reference to a `Subquery Scan` or a `CTE Scan` is unmappable and is not matched to the subquery's own plan by name: that plan's `Output` is positional expressions, the subquery's column names are nowhere in it, and a column renamed to another's name would be read as the other.  A subquery the planner flattens has no such scan and is walked exactly.  `docs/tech-debt/TD-0046-the-walk-leaves-some-columns-to-the-heuristic.md` records what mapping one would take.
- **The walk degrades a column alone, and the plan whole** (`NullabilityWalk`).  An entry that cannot be mapped leaves its own column to the heuristic and the plan `walked`; a plan that cannot be used leaves every column to it and is `unavailable`.  A mapped column that nothing extends takes `ColumnNullability.Of` for a query that is not gated, so the rule of a `NOT NULL` is written once and a view's column stays `null` with `view`; one that a join extends is `true` with `outer-join`, a view's too.  A column without an origin is not looked up.  The walk never answers `false` on its own: when in doubt it is the heuristic.
- **The settings of the planner are for the tests, and the list is closed** (`PlannerSettings`).  `PostgresDescriber` takes them at construction and every `explain` of its sessions carries them; `ToolHost.Create` makes none, and when sub-phase 3.6 registers the describer it is with the constructor that takes none.  A name outside `enable_hashjoin`, `enable_mergejoin`, `enable_nestloop`, `enable_memoize` and `enable_material`, or a value that is not `on` or `off`, throws at construction and again where the text of the `SET LOCAL` is made, so nothing else reaches one.  The settings are in the request, so a capture recorded with them is replayed with them.
- **Every fixture case gives one answer on PostgreSQL 14 and on 18.**  `FixtureCasesTests` describes each case on both and compares with the one `expected.json`.  A shape the two plan differently, `ON ... AND o.id IS NULL`, which 17 and later prove false from the `NOT NULL`, is a test of `tests/SqlSource.Tests.Postgres/Describer/WalkTests.cs` with each version's answer, and not a fixture.  `tests/SqlSource.Tool.Tests/Fixtures/WalkMatrixTests.cs` holds what each `walk-*` case must give, by hand: a recording that disagrees with it is a bug to find, and the table is not changed to fit one.
- **`check` is the lexer against Npgsql** (`NpgsqlCheck`).  The describer prepares the SQL with `$n` where the tool's lexer found a parameter; generated code will send the SQL as written, and Npgsql will find the parameters.  So `PostgresLive.CheckAsync` describes `ParameterPlaceholders.AsWritten`, the SQL cut at its trailing `;`, with a parameter for each of the query's list, bound by `DataTypeName` with the type's spelled `name` and no value, and `NpgsqlCheck.Read` compares the columns it gets with the answer of `columns`, in count, names and type OIDs.  A difference, or an error, is `SQLSRC231`.  Npgsql refuses a type name it cannot bind before it sends anything, with a `NotSupportedException`, an `InvalidCastException` or, for a name that is too long, an `ArgumentException`, and refuses a text with a `;` that something follows the same way; the live function then asks for each parameter alone with `SELECT $1`, and the first that is refused is the answer's `driverError`, `SQLSRC232`, while a refusal that is no parameter's is the answer's `error`.  `SQLSRC232` is reachable from a `.sql` file: a name that needs quotes, `"char"`, a domain over a domain, a composite type or a table's row type, `regclass` and the other types of the system catalogs that Npgsql does not load, an array of a type whose name is 63 characters long, and a parameter of plain `bit`, which is spelled `"bit"`.  The check is best effort, and `docs/tech-debt/TD-0045-the-check-against-npgsql-is-best-effort.md` says what it does not see.
- **A prepared statement is session state.**  It survives a rollback, so `deallocate` is asked in a `finally`, outside any transaction, whenever `prepare` answered without an error, and not after one that failed: there is nothing to free, and the counter of the names advances all the same.  A name is `sqlsource_<n>`, counted within the session: it is part of a request, so it is the same when a capture is recorded and when it is replayed.  The error of `deallocate` is written to the log and never reported.
- **Nothing a `.sql` file holds can make the describer run a statement.**  What holds that is how the `PREPARE` is sent, and not what the tool read of it.  `PostgresConnection.ExecuteAsOneStatementAsync` sends it as an `NpgsqlBatch` of one command with no parameters, which Npgsql does not read and never splits: the server is given the whole text as one statement to parse, and it refuses a text that holds a second one, `42601: cannot insert multiple commands into a prepared statement`, before it runs anything.  The one statement the text can be is a `PREPARE`, which runs nothing.  An `NpgsqlCommand` is another thing: Npgsql splits its text at each `;` that its own lexer finds and runs every part, so `PostgresConnection.CommandAsync` is for a text that holds nothing of a user's, and the `PREPARE` never goes through it.  `check` is the second text that holds a user's SQL, and goes the same way, through `PostgresConnection.BatchOfOneAsync`, under `CommandBehavior.SchemaOnly`: with a named parameter Npgsql reads the text to place it, and refuses one with a `;` that something follows by a `NotSupportedException`, having sent nothing, which `PostgresLive.CheckAsync` answers as an error and never lets through.  Two checks stand before anything is sent and use no server.  They are the first refusal, with an error that says what is wrong, and the guarantee does not rest on them: `ParameterPlaceholders.Rewrite` refuses a text in which the lexer finds a second statement, `SQLSRC230`, and `DeclaredTypeText` reads each `-- param:` type against the grammar of a type name, `SQLSRC228`, since the type is put into the `PREPARE` as written.  The tool's lexer, Npgsql's and the server's do not always split a text alike: `SELECT 1 AS §$x$; DROP TABLE t; --$x$` is one statement to the tool, which reads `$x$` after a `§` as the start of a dollar-quoted string, and two to Npgsql and the server, which read `§$x$` as an identifier.  The type list still ends with a line break before `AS`: whatever a type's text held, the `) AS` is not on its line, so nothing in a type can reach it.  A change to either check gets a case in `tests/SqlSource.Tool.Tests/Describing/Postgres/` that shows what is refused.  A new place that puts a user's text into SQL the tool sends does it so that the driver cannot split the text, and gets a case with a canary beside `Describe_TextTheLexerAndTheServerSplitDifferently_IsAFailureAndRunsNothing` in `tests/SqlSource.Tests.Postgres/Describer/ParameterTests.cs`, and for a text that goes to `check`, one beside `NpgsqlCheckTests.CheckAsync_TextNpgsqlWouldSplit_AnswersAnErrorAndRunsNothing` in `tests/SqlSource.Tests.Postgres/Describer/NpgsqlCheckTests.cs`.
- **The connection is made inside a `live` function and nowhere else.**  `PostgresConnection` holds the connection's value, makes one `NpgsqlDataSource` for the session and one connection from it, on the first `live` call that asks, and makes every command and every batch; and the transaction of `explain`, through `PostgresConnection.BeginAsync`; under a replay none of that runs.  The `live` functions are `Describing/Postgres/PostgresLive.cs`, with the SQL the tool sends; `PostgresSession` holds what is asked, in which order, and what is made of each answer.  A data source for each session, because a plain `NpgsqlConnection` shares a type catalog by connection string for the life of the process.  It is the one file for which `.editorconfig` turns `CA2100` off.  Each `live` function catches `NpgsqlException` and returns it as its answer's `error`; a cancellation passes through; anything else is a bug.  The one exception is `PostgresLive.CheckAsync`, which also catches the `NotSupportedException`, the `InvalidCastException` and the `ArgumentException` that the driver throws before it sends anything, and answers them.  A connection string that Npgsql cannot read is an `NpgsqlException` with a fixed text and no inner exception, so that it is an answer too and the driver's quote of the value is dropped.  So is a connection that the server ended, a restart or an idle timeout for two: Npgsql closes it on the call that finds it out, which answers what the server or the driver said, and for a command on a closed connection it throws an `InvalidOperationException`.  `PostgresConnection.OpenAsync` throws an `NpgsqlException` with the text `PostgresConnection.LostConnection` in its place, so every later call of the session answers an error: a describe is `SQLSRC225`, and the `deallocate` of the `finally` logs its error and replaces no failure.  The session is not opened again.
- **The calls and their records are a contract with the captures.**  The methods are `open`, `prepare`, `columns`, `tables`, `types`, `check`, `explain` and `deallocate`, and their records are in `Describing/Postgres/PostgresCalls.cs`, with the rule of a record above.  An OID is a `long`.  A row of `types` names its members as the catalog does.  A row of `tables` names its members as the catalog does where the catalog has one word, `attnum`, `relkind`, `relhassubclass`, and `hasForeignPartition`, which is no catalog column, for what it says; a column of `columns` holds Npgsql's three numbers as it gave them, undecoded.  A change to what the describer asks changes the fixtures: record them with `tools/record-fixtures.sh` and read the diff.
- **A server's error gets its id from four things, in this order** (`PostgresErrors`): the call, since every failure of `open` is `SQLSRC224`; a position inside the type list of the `PREPARE`, which makes it the declared type's, `SQLSRC228`, with `42704` as "no such type" and anything else as "not a type name"; the SQLSTATE `42P18` or `42P08` with a `$n` of the list in the message, `SQLSRC226` and `SQLSRC227`; and anything else is `SQLSRC225` with the server's message.  `PostgresErrors.SchemaChanged` is `SQLSRC225` with no server line and `PostgresErrors.SchemaChangedHelp`, for what the server said nothing of: a table, a column or a type that went during the describe.  The server counts a position in characters of the text as sent, so the `at character` line is the position less `ParameterPlaceholders.HeadLength`, counted in runes, and points into the `$n` form of the SQL, which the `prepare` event logs.  An error of `types` has no `at character` line, since its position is in the tool's own query of the catalog.  The server accepts a pseudo-type as a parameter's type, declared or inferred, and an array of one, `cstring[]`, and says nothing: `PostgresTypes.IsPseudo` finds it after `types`, and it is `SQLSRC228` or `SQLSRC226` at the step `resolve type`; a column of a pseudo-type is `SQLSRC229` at the same step, found after the parameters.  An error of `columns` is `SQLSRC225` at the step `describe columns`, of `tables` at `catalog`, and of `check` it is `SQLSRC231` at `check parameters`; none of the three has an `at character` line, since the server counts in a text the user did not write.
- **A type's `name` is the tool's own spelling** (`PostgresTypeNames`): `format_type(oid, -1)` for a type of `pg_catalog`, with the facets written as PostgreSQL writes a modifier; the schema and the name as identifiers for any other, whatever the `search_path`; an element's name and `[]` for an array.  `format_type` of `char` is `bpchar`, and with a length the tool writes `character(n)`.  `format_type` of `bit` is `"bit"`, quoted, since plain `bit` means `bit(1)`, and with a length the tool writes `bit(n)`.  A parameter has no facets, since the protocol gives it an OID and no modifier; a column has them, from `ColumnFacets`.  What the spelling and the parameters leave open is `docs/tech-debt/TD-0043-small-gaps-of-the-postgresql-describers-parameters.md` and `docs/tech-debt/TD-0044-small-gaps-of-the-postgresql-describers-columns.md`.
- **`tests/SqlSource.Tool.Tests/PostgresScript.cs` answers the session with no server.**  A test writes each call the describer is to make, with its answer, and a `ReplayingExchange` plays them: a request the session asks otherwise has no answer and is a `CaptureMissException`, so these tests hold what is asked as well as what is made of the answers.  `tests/SqlSource.Tool.Tests/PostgresRows.cs` has rows of `types` as a server gives them.  `tests/SqlSource.Tool.Tests/PostgresTables.cs` has tables of `tables` and columns that name them.  What only a server can show, the types it infers, its errors and their positions, is in `tests/SqlSource.Tests.Postgres/Describer/`.  `tests/SqlSource.Tool.Tests/PostgresPlans.cs` writes a plan as a server would answer `explain`, a scan, a join of two nodes and a node over one, for the tests of the walk and of the session.
- **A connection's value goes to the describer and nowhere else.**  `OpenRequest` is the one thing that holds it for a describer, and `ConnectionArgument`, `DatabaseConnection`, `OpenRequest` and `UsageValue` each override `ToString` to leave it out: a record prints its members.  What the tool may say of a connection is where it came from, `--connection` or the name of a variable.  A describer puts the value in nothing it returns, and the run does not rely on that: every text of a describer that is printed, an exception's included, goes through `Describing/Redaction.cs`, which writes the whole value as `***`.  A failure goes through it twice: as the describer returned it, for its descriptor, which a describer may have built from a server's text, and for its server lines, which are searched joined since a value with a line break is cut over two; and as the error made of it, for everything else.  The log is held to the same: nothing hands a log a value, `Logging/LoggedArguments.cs` builds `arguments` from what `UsageCheck` read and not from the text, a describer's log is a `Logging/SessionRunLog.cs` that removes the value from every string of an event, and what the run itself writes of a database after its connection is found goes through `RunTrace.Without`.  `tests/SqlSource.Tool.Tests/Describing/RedactionTests.cs` holds the log to all of it; a new event that carries what a describer gave gets a case there.  A description that holds the value, searched as the sidecar's writer would write it (`Describing/EntrySecretCheck.cs`, called inside the guard of `Describing/DatabaseRuns.cs`), is a bug of the describer like any other: `SQLSRC200`, the run ends and no sidecar is written.  A value that the entry's text holds without the describer's part, a word of the format or the name of the database, is none the describer put there; a member of an entry that a describer gives must be left out in `EntrySecretCheck.WithoutTheDescribersPart`, or a value in it is never found, and gets a fact in `tests/SqlSource.Tool.Tests/Describing/EntrySecretCheckTests.cs`.  A capture has none of this: `CapturingExchange` writes an answer as the describer gave it, and only the describer's rule keeps a value out of one.  That, and what the removal does not cover, is `docs/tech-debt/TD-0034-redaction-of-a-describers-text-has-holes.md`.  `tests/SqlSource.Tool.Tests/Commands/SecretTests.cs` holds the tool to all of it; a new place that prints what a describer gave gets a case there.
- **A sidecar is written whole or not at all, through `SidecarStore`**: to a temporary file beside it that is then moved over the old one.  A run that is killed between the two leaves the temporary file, and `SidecarStore.Apply` removes it in a later run: only a name that it gives one itself, and only when the file is older than `SidecarStore.LeftoverAge` by `ToolHost.Time`, since another run may be writing the same sidecar now.  Each folder is read once, and a run that was cancelled removes no further file.  A run with a filter removes those of the sidecars whose outcome is not `FileAction.None`; a run on the whole removes those of every sidecar in the folders of its files, since the `.sql` file of one may be gone; `--check` removes none.  The file's target holds an entry for every query that needs one, each described in this run or current, where current means that the hash and the database match and that this version of the tool wrote the file: an entry from an older tool never stands beside a new one.  A file with a query that has neither is left as it was.

A sidecar is deleted only in a run with no `--project`, no `--database` and no `.sql` path, and in which the reporter holds nothing when `Describing/DescribeRun.cs` decides the outcomes: a run on a part does not know what the rest needs of a file, and the plan drops a setting or a claim it could not read, so an error can make a file look as if it needs no entry.  `Describing/DescribeRun.cs` decides both and gives `FileOutcomes.Decide` the one answer, with a function that reads the sidecar (`SidecarOnDisk.Read`): a sidecar is deleted only if one is there, the system lets the tool open it, and it is not of a higher format version, which a newer tool wrote and which is left as it is, with nothing reported. - **A database needs a describer and a connection only when a query of it must be described.**  The connection of every selected database is looked up, since the summary says which have none, and a missing one is an error only in `DatabaseRuns`.  `SQLSOURCE_CONNECTION` is for a run with one selected database that can be described, `RunDecisions.DescribableDatabases`: one whose every selected query the plan failed is still a selected database, with its line in the summary, and is none the variable could be meant for, so `SQLSRC215` neither counts nor names it.  A query that the plan could not describe, and every query of a file that is not `Ready`, counts as failed and gets no further error.
- **`Logging/` is what a run says of itself beside its errors and its summary.**  `--log <path>` of `describe`, or else `SQLSOURCE_LOG`, names a file of JSON Lines that `Logging/RunLogFile.cs` writes: one object for each event, written and flushed as the run goes.  `Cli.OpenLog` opens it, only after `UsageCheck` and `DescribeCommand.CheckUsage` accepted the command line and System.CommandLine read the same, so a wrong command line is never logged, and only for a command line that runs `describe` (`DescribeCommand.Runs`): the help must not empty the log of the last run.  `Cli.RunAsync` closes it.  For every `describe` that runs, `Cli.InvokeAsync` makes the run's `Reporter` with its `RunTrace`, which has the log when there is one and standard output when `--verbose` was given, and only then gives the command its action (`DescribeCommand.Bind`), so that the command cannot run with another reporter; an error before that has a reporter with no trace.  `Cli.RunAsync` calls `RunCommandAsync`, whose one `try` holds three steps in this order: `ReadCommandLineAsync`, `OpenLog` and `InvokeAsync`.  The three share a `RunState` with `RunAsync`, which ends the run outside that `try`.  `InvokeAsync` replaces `RunState.Reporter`, so whatever reports after a step reads the reporter from the state then, and never from a local made before the step.  `Cli` writes `run.start`, in `OpenLog`, and `run.end`, in `End`, since the exit code and the error of an exception are known only there; `Reporter` writes a `diagnostic` event for each error, under the same lock as the console, to the trace it was made with. On a line with a `--connection`, an argument that holds `=` or `;` is a part of a value that the shell split, a `.sql` path too, and is reported by its position: it would be printed as a path, a `.sql` one in full by `SQLSRC212`. - **An option is declared so that `UsageCheck` reads it right.**  A flag has `Arity = ArgumentArity.Zero`: System.CommandLine's default for a `bool` takes an optional value, and the token after the flag would be read as that value.  An option that takes a value takes exactly one each time it is given: `ArgumentArity.ExactlyOne` when it is given once, and an array with `ArgumentArity.OneOrMore` when it may be repeated, since System.CommandLine rejects a second `ExactlyOne`.  `UsageCheck` rejects that second one itself, with `option '<name>' is given more than once`, since System.CommandLine's message repeats the value.  An option is added to `--help` in the sub-phase that gives it an effect, not before: one that is read and checked earlier is `Hidden` until then, as `--database` was in sub-phase 2.4.
- **The root is a `Command`, not a `RootCommand`**, with a `HelpOption` under three names and a `--version` whose action is the tool's own.  A `RootCommand` takes its name from the process, prints the version of the assembly the process started with, which under a test is the test host, and reads `[suggest]` as a directive.  Response files and the bundling of short options are off in `Cli`.
- **The tool writes English**, and `SatelliteResourceLanguages` keeps other languages out of the package.  A test compares no text that System.CommandLine wrote.
