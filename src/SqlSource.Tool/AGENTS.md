# AGENTS.md - src/SqlSource.Tool

How the tool works: [`docs/architecture/tool.md`](../../docs/architecture/tool.md).
How the PostgreSQL describer works: [`docs/architecture/postgres-describer.md`](../../docs/architecture/postgres-describer.md) and [`docs/architecture/postgres-nullability.md`](../../docs/architecture/postgres-nullability.md).
How the SQL Server describer works: [`docs/architecture/sqlserver-describer.md`](../../docs/architecture/sqlserver-describer.md).

The `sqlsource` command, packed as the .NET tool `SqlSource.Tool`.  Its tests, and where each kind goes, are in [`tests/README.md`](../../tests/README.md).

- **The tool shares the generator's code and never copies it.**  It references `src/SqlSource/SqlSource.csproj` and sees its internals; what each folder uses of it is in [folders](../../docs/architecture/tool.md#folders).  Code that both need goes in the generator's project, where `netstandard2.0` and Roslyn 4.8.0 bound it.
- **It targets `net8.0` with `RollForward` `Major`, and references a current Roslyn by `VersionOverride`.**  Do not raise the target: a user with only the .NET 8 SDK must be able to run it.  `tools/check-tool-install.sh` runs the packed tool on the newest runtime the machine has.
- **Everything from outside comes through `ToolHost`.**  Nothing reads `Console`, `Environment`, `RuntimeInformation` or the current directory except `ToolHost.Create` and `Cli.Run`, the entry of a real run ([the host](../../docs/architecture/tool.md#the-host)).  A test gives `Cli.RunAsync` a host of its own.  The clock is `ToolHost.Time`, a `TimeProvider`: the time of a log's events and how long a step took come from it and never from `DateTime` or `Stopwatch`, and the tests stand on `tests/SqlSource.Tool.Testing/TestClock.cs`, as the default of their runs, hosts and sessions, unless a test brings a clock.  A database is reached through `ToolHost.Describers` and `ToolHost.Exchange`, and the log's file through `ToolHost.CreateFile`, which a test replaces with a stream that fails; what a later phase takes from outside is a new member of `ToolHost`, as these, the clock and the processes are.  So do the descriptions of .NET and of the system that the log's `run.start` holds, `ToolHost.Runtime` and `ToolHost.OperatingSystem`, which `tests/SqlSource.Tool.Testing/Hosts.cs` fixes.
- **A signal cancels a run once, and a second lets the process be killed.**  `Cli.Run` listens for Ctrl+C, `SIGTERM` and `SIGHUP`: the first cancels the run, which ends by its own road with its exit code, and a second, while the run has not ended, lets the process be killed (`Cli.Interrupt`).  The three share one count of signals, which is raised atomically.  For the first signal, the handler of `SIGTERM` and `SIGHUP` returns only when the run has ended, and for a second it returns at once (`Cli.Terminate`); [signals](../../docs/architecture/tool.md#signals) says why.  `tests/SqlSource.Tool.Tests/Commands/TerminationTests.cs` sends each signal to the tool in a process of its own, where a system has signals, and closes its console on Windows.
- **Every process goes through `ToolHost.Processes`**, an `IProcessRunner` of `Processes/`.  `Processes/ProcessRunner.cs` is the only code that starts one, and a test gives `tests/SqlSource.Tool.Testing/FakeProcessRunner.cs`, which answers in MSBuild's place.  A run that is cancelled kills the program with everything it started and waits, for a few seconds at most, until the program has ended ([why](../../docs/architecture/tool.md#evaluating-a-project)); a kill that fails never stands in for the cancellation, which would be reported as `SQLSRC200`.  A temporary folder is made in `ToolHost.TempDirectory`, and what runs at once is bounded by `ToolHost.ProcessorCount`.
- **The tool never restores and never builds a project, and writes nothing into one but its sidecars.**  `Projects/ProjectEvaluator.cs` only evaluates a project and runs the package's target `SqlSourceWriteManifest` into a file of the run's temporary folder ([evaluating a project](../../docs/architecture/tool.md#evaluating-a-project)).  Do not add `-restore`, a target of a build, or a file under a project's folder: `tests/SqlSource.Tool.Tests/Projects/FixtureProjectTests.cs` checks that a project has no `obj` afterwards.  A sidecar is written or deleted by `Describing/SidecarStore.cs` and by nothing else.
- **MSBuild's output is parsed only as the JSON of `-getProperty` and `-getItem`.**  Everything else it prints is shown, the first twenty lines, under `SQLSRC205`, and never read: MSBuild writes in the language of the machine.  What the tool needs from a target comes in the manifest file, read by `Projects/ManifestReader.cs`; the format is the package's contract, and `src/SqlSource/AGENTS.md` has its rules.
- **A value given to MSBuild as a property goes through `Projects/MSBuildProperty.cs`.**  MSBuild splits what follows `-p:` at `;` and `,`, and a path holds either.  An environment variable that a run sets or removes is listed in `ProjectEvaluator`, with the reason beside it.  Among the removed are `SQLSOURCE_CONNECTION` and, by the prefix that `ProcessRequest.RemovedPrefixes` takes, the variable of every database, so that no connection reaches MSBuild, a project's targets, or what MSBuild prints under `SQLSRC205`.  Everything else of the environment reaches MSBuild on purpose, so that the manifest is what the user's compiler is given ([evaluating a project](../../docs/architecture/tool.md#evaluating-a-project)).
- **`Projects/RunProjects.cs` is the one place that says which projects a run is on** and what is said of each: the unit's projects, or the ones `--project` names.  A project of a solution that does not use SqlSource is left out silently unless it was named; one that was not restored is an error everywhere.  `Projects/SolutionReader.cs` reads a solution with `Microsoft.VisualStudio.SolutionPersistence`, and the reason of `SQLSRC223` is that library's text: no test compares it.
- **An evaluation reports nothing.**  `ProjectEvaluator` runs several projects at once and gives each error as data, in a `ProjectEvaluation`, so that the caller reports them in the order of the projects.
- **A result that may fail has one shape where files meet.**  A method that another file calls and that gives one value or one reason returns an `Outcome<TValue, TFailure>` (`Outcome.cs`) and reports nothing: its caller does, as `DescribeCommand.PlanAsync` reports what `Projects/RunUnitFinder.cs` found and `Cli.OpenLog` what `RunLogFile.Open` did.  A private helper may be a `TryX`, and so may a method that gives a value or nothing and no reason, as `ConnectionArgument.TryParse`.  A result with more than two states is a record with a state, as `ProjectEvaluation`.  A step that reports several errors as it goes takes the reporter, or returns its errors as data, and is no `Outcome`.  An `Outcome` of a value that must be disposed is made with the constructor, `new Outcome<RunLogFile, ToolDiagnostic>(log)`, never with `Outcome.Of`, and carries no `SuppressMessage`: `.editorconfig` tells `CA2000` that a constructor takes ownership, as `RunLogFile.Open` and `Describing/Describers/DescriberSession.cs`'s `OpenAsync`, the opener of both describers' sessions, show ([what it costs](../../docs/architecture/tool.md#an-outcome-of-a-disposable)).
- **`Planning/` makes the plan of a run and reports nothing.**  `Planning/RunPlanner.cs` gives a `RunPlan` and its errors as data, in the order they are to be reported, and `DescribeCommand.cs` reports them ([the plan](../../docs/architecture/tool.md#the-plan)).  The plan keeps every query of every file that a type claims: `--database` and a `.sql` path set `PlannedQuery.IsSelected` and take nothing out, because a sidecar is written only when every query of its file that needs an entry has one.  A file that no type claims is never read.
- **The plan must agree with the generator**, on which type claims which file with which output, and on each query's hash.  So `RunPlanner` calls the generator's own path resolver, readers of settings, parser and hash, through `Planning/ManifestOptions.cs` and `Planning/SqlFileText.cs`, and copies no rule.  `GeneratorParityTests` and the tests of `RunPlanner` hold the two together ([the plan](../../docs/architecture/tool.md#the-plan)).  Where the compiler decides what the generator's code cannot see, as the metadata of a path that a project lists twice (`Planning/ListedFiles.cs`), the plan does as the compiler does.  A rule that both need goes into the generator's project.
- **`Planning/AttributeReader.cs` reads syntax, and two arguments.**  It has no compilation, and reads `Path` as a string literal and `Output` as a member of `GeneratorOutput`, anything else in either being `SQLSRC208`, and nothing else on the attribute, since nothing else changes what is described ([the plan](../../docs/architecture/tool.md#the-plan)).  What it misreads is `docs/tech-debt/TD-0031-attribute-reader-of-the-tool-is-syntax-only.md`.
- **A database belongs to a query that needs an entry, and to no other.**  Names are compared with `DatabaseName.Comparer`, ignoring case, and the plan holds the first spelling.  Only a `Ready` file decides its database's dialect or conflicts with it (`SQLSRC211`); a database that only other files hold keeps the dialect of the first of them.
- **Of the settings that are not valid, the tool reports the ones it reads**: the dialect, `SqlSourceOutput` and `SqlSourceDatabase`, under the generator's `SQLSRC011` and `SQLSRC014`, at the project file, in the order of `InvalidValues`, which the generator uses too.  The build reports the rest.
- **`Describing/` is a run after its plan, in steps that stay apart.**  `Describing/DescribeRun.cs` calls them in order, from `RunDecisions` to `RunSummary` ([a describe run](../../docs/architecture/tool.md#a-describe-run)).  `Describing/DatabaseRuns.cs` opens one session for a database and describes its queries one at a time ([describing](../../docs/architecture/tool.md#describing)).  `--check` shares the run and replaces only the step that writes, `SidecarStore`, with `Describing/SidecarCheck.cs`, which compares each selected query's described entry and returns its differences as data.  So the step that decides must never write, the step that writes must never decide, and the step that compares does neither: what it says of a sidecar that would be deleted it takes from `FileOutcomes`.  `RunDecisions` reports no `SQLSRC221` under `--check`: a sidecar of a higher format version is a difference there, and its queries are described like any other.
- **`Describing/Describers/` is the contract a describer implements** ([the describer contract](../../docs/architecture/postgres-describer.md#the-describer-contract)).  It uses nothing of the run's steps, only `Outcome`, `Reporting/` and `Logging/` of the tool and the generator's types, so a describer depends on no step of the run.  A describer's clock is `OpenRequest.Time`, which `Describing/DatabaseRuns.cs` sets from `ToolHost.Time`: a describer reads no `DateTime` and no `Stopwatch`.
- **A describer returns a failure and never throws** ([the describer contract](../../docs/architecture/postgres-describer.md#the-describer-contract)).  What a server or a user can cause is a `DescribeFailure`, which the run reports at the query in the format of `Describing/DescribeErrors.cs`.  An exception from one is a bug of the describer and ends the run with `SQLSRC200`.  A describer is registered in the `DescriberRegistry` of `ToolHost.Create` ([the host](../../docs/architecture/tool.md#the-host)), and a query that must be described in a dialect with none registered is `SQLSRC216`.
- **Every call a describer makes to an engine goes through `IDescribeExchange`**, the one it is given in its `OpenRequest`, so that a run can be recorded and replayed ([the exchange](../../docs/architecture/postgres-describer.md#the-exchange)).
- **A request and an answer are plain records, and nothing of the seam crosses the exchange** ([requests and answers](../../docs/architecture/postgres-describer.md#requests-and-answers)).  A record of a call is sealed and holds strings, integers, booleans, nullable ones, `IReadOnlyList<T>` of them and records of the same kind: no driver type, no `DateTime`, no `Exception`, no enum, no abstract base, no dictionary and nothing polymorphic, and never an `Outcome`, a `DescribeFailure`, a `QueryDescription` or an `EquatableArray`.  A describer maps between its records and the seam's types on its own side.  A call that can fail on the server has an answer with an `error` member that is null on success.  A request holds everything that decides the answer, and nothing of a connection: not the value, a part of it, the host or the user's name.  An answer's `error` of `open`, of a session that the server ended, or of a connection that was lost or timed out holds the engine's code of the error, PostgreSQL's SQLSTATE, where there is one, and a fixed text of the describer's own, never the driver's or the server's message, which would name them.  A driver's refusal of a query's text or of a parameter's type speaks of the query and keeps the driver's message.  A name that a describer makes up and sends is a counter within its session and never random.  `tests/SqlSource.Tool.Tests/Describing/Capture/CallRecordTests.cs` holds every record whose name ends in `Request` or `Answer`, in the namespace of an engine's describer or under it and in that of the tests, to the rule; a describer in a new namespace adds it to `Under` there.
- **A capture is a file that outlives the version that wrote it**: the `capture.json` of a fixture and, from phase 10, of a user's bug bundle, so what a describer asks and is answered is a contract with the captures that exist ([capture and replay](../../docs/architecture/postgres-describer.md#capture-and-replay)).  The name of a method never changes.  A request's record may gain a member only when it is nullable and its null means what the request meant before it had the member; give a new member no other meaning for null ([how a record may change](../../docs/architecture/postgres-describer.md#how-a-record-may-change)).  A member that is renamed, removed or moved, a member of a value type, and a new member where it holds a value each make a question that no older capture answers.  An answer's record may gain a member, which must be nullable, one of a value type too.  `tests/SqlSource.Tool.Tests/Describing/Capture/ReplayingExchangeTests.cs` holds each of these.  `DescribeCapture.Version` rises only when a capture of the version before can no longer be read.  `CaptureJson.Options` is the one set of options for a request and an answer, and a change to it changes every fixture.
- **`tests/SqlSource.Tool.Tests/FakeDescriber.cs` is a describer written by these rules**, and the tests of the exchanges and of the fixture harness run through it ([fixtures and test describers](../../docs/architecture/postgres-describer.md#fixtures-and-test-describers)).  Its `OpenAsync` makes its `Outcome` of a session with the constructor, as every opener does.
- **The fixtures of a describer are in `tests/SqlSource.Tool.Tests/Fixtures/Describers/<engine>/<case>/`**, beside the engine's `schema.sql`, and what a case holds and how one is recorded is [the PostgreSQL describer's fixtures](../../tests/SqlSource.Tests.Postgres/README.md#the-describers-fixtures), and [the SQL Server describer's](../../tests/SqlSource.Tests.SqlServer/README.md#the-describers-fixtures) for `mssql`.  A case's `query.sql` is a complete SqlSource file with exactly one query.  The files are compared byte for byte, so the folder is `text eol=lf` in `.gitattributes` and has a section in `.editorconfig`.  `postgres/schema.sql` is the schema that `tests/SqlSource.Tests.Postgres` applies to its container; a change to it can move the OIDs that the captures hold, and every case is recorded again.  A change to `mssql/schema.sql` records the SQL Server cases again.
- **`PostgresSession.DescribeAsync` holds the order of a describe**: its four checks, `prepare` first and `deallocate` in its `finally`, and `DescribePreparedAsync` the steps between them ([one describe, step by step](../../docs/architecture/postgres-describer.md#one-describe-step-by-step)).  `types` is asked once, after `tables`, because the type of an origin attribute is where a domain is found and the request is one; `spellings` once, after `types`, and a modifier of `-1` is never asked of it; `check` after the columns are built; `explain`, then `partitions`, then `relations`, then `overloads`, after `check`; and the table match last.  A call that has nothing to ask is not made.
- **A column is built from three answers, each by a class of its own** ([building parameters and columns](../../docs/architecture/postgres-describer.md#building-parameters-and-columns)).  The rows of `types` reach what reads them only as the `CheckedTypes` that `PostgresSession.CheckTypes` gives.  A table, an attribute or a type that another session dropped between two calls is `SQLSRC225` through `PostgresErrors.SchemaChanged` and never a throw; the throws that remain guard a bug of the describer.  An OID the describer names is a constant of `BuiltInTypes`.  The types that carry a modifier are `BuiltInTypes.WithModifier`, and `BuiltInTypesTests` fails for one that `TypeModifiers`, `ColumnFacets` or `PostgresTypeNames` leaves out.  `ColumnFacets.Of` serves only a capture recorded without `typeModifier`, and reads by the internal name of the reported type and for no other type.
- **A column with an origin is `nullable` `false` only when the catalog says `NOT NULL`, its origin is a table that has no inheritance child, no foreign partition and no `INSTEAD` rule, and either the query is not gated or the walk proves that no outer join null-extends its relation instance** (`ColumnNullability`, `NullabilityWalk`, [nullability](../../docs/architecture/postgres-nullability.md#nullability)).  A column of no origin is `false` only by the walk's `expression` or `set-operation` answer.  `ColumnNullability.Of` is the one place of that rule for a column with an origin: the walk and the table match call it for a query that is not gated, so the rule of a `NOT NULL` is written once.  A `NOT NULL` that PostgreSQL 18 holds as not validated (`NOT VALID`) is nullable with `catalog`.  The rule of inheritance children is the same on every version and leaves a partitioned table out, since a partition can never drop its parent's `NOT NULL`; any `INSTEAD` rule on `INSERT`, `UPDATE` or `DELETE` counts, one that returns no rows, a conditional one and a disabled one included.  The gate is `OuterJoinGate.IsGated`: its words count only in a `Text` lexeme, so a string, a comment and a quoted identifier do not, except that a quoted `"old"` or `"new"` in any case and any `U&"..."` identifier count for `OLD` and `NEW`.
- **The table match is `PostgresTableMatcher`, and it runs after everything that sets a column's nullability**, since its last check reads the `nullable` each column was given; `PostgresSession.MatchOf` calls it once, for a statement with rows, and it asks the server nothing ([matching a table](../../docs/architecture/postgres-describer.md#matching-a-table)).  The checks are the values of the format's `tableMatch` in the one order of `TableMatchChecks` (`Describing/Describers/`), and the first that fails is the answer: do not reorder them, since a sidecar says which failed first.  Names are compared ordinally, as the server returned them, and the attributes as lists, not as sets.
- **The plan of a gated query is a generic one, through the prepared statement** (`PostgresLive.ExplainAsync`, [the plan](../../docs/architecture/postgres-nullability.md#the-plan)).  `explain` runs on every version in the describe's transaction, under `force_generic_plan` and with partition pruning off as `SET LOCAL`s that it ends by rolling back to the describe's savepoint, and `EXPLAIN` is never given `ANALYZE`.  Its `EXECUTE` passes a `NULL` for each type the server resolved for the statement, since `EXPLAIN EXECUTE` refuses any other number.  `EXPLAIN (GENERIC_PLAN)` is not used, since it folded a parameter's `NULL` into the plan.  It is asked after `check`, and only for a query with rows that is gated or has a column of no origin, so a query that is neither has the capture it had.  An `explain` that fails is logged and never reported, except `26000`, a statement that is gone, which `PostgresSession.WalkAsync` reports as `SQLSRC236` at the step `explain`; an error of `partitions`, `relations` or `overloads` is logged and never reported, and every name `overloads` was asked for is then held elsewhere.  A query that is not gated is planned for its columns of no origin alone: its columns with an origin keep the catalog's answer whatever the plan says (`WalkScope.Gated`).
- **The walk follows a join's sides and nothing else** (`PlanInstances`, [the plan walk](../../docs/architecture/postgres-nullability.md#the-plan-walk)).  Every node type, relationship, join type and set-operation command it compares is a constant of `Walk/PlanVocabulary.cs`, and the sets of node types named for their purposes are built from them: they differ on purpose, `PlanInstances`' set operations holding `Recursive Union` and `NullabilityWalk.ReachesSetOperation` not, so never merge them.  `PostgresSession.WalkAsync` builds one `PlanInstancesCache` a walk, after `partitions`, for `NullabilityWalk.Run` to find the instances of each plan once.  `relations` is asked whenever a column has no origin and the plan scans a relation that `tables` did not answer, whether or not the plan has a set operation, since a reference inside an expression is proved through the table row of its relation.  Only scans reached through `Outer` or `Inner` children are instances of the plan's joins; an `InitPlan`, `SubPlan`, `Member` or `Subquery` child is another plan.  Each of these makes the plan unusable: a join type outside the eight of `PlanInstances.ExtendsOf`, an alias found twice, a `Grouping Sets` key, and a root without an `Output` entry for every column unless a column has no origin and the set-operation path takes the plan.  In a query that is not gated, a root whose reference names another column than the described one's origin makes the plan unusable too, `output-differs`, a guard that the plan and the row description agree; a gated query's plan that fails the check is read for no expression.
- **A `ModifyTable` at the root is its target, and the scan of the target under it is that same instance**, which is never null-extended ([a root `ModifyTable`](../../docs/architecture/postgres-nullability.md#a-root-modifytable)).  When `OuterJoinGate.NamesOldOrNew` finds `OLD` or `NEW` in the SQL, bare or as a quoted `"old"` or `"new"` in any case, or any `U&"..."` identifier, a qualified reference at a root `ModifyTable` maps only to the target's own alias, and any other keeps the heuristic.
- **An entry of `Output` is a reference or it is nothing** (`OutputReference`, [output entries](../../docs/architecture/postgres-nullability.md#output-entries)).  A reference to a `Subquery Scan` or a `CTE Scan` is resolved in the scanned plan by the column's origin, and never by its place or its name: the column takes the catalog's answer only when every candidate is preserved, and `outer-join` only when every one is extended.  A bare name is only ever the plan's one relation's (`PlanInstances.BareAlias`).  A column of no origin through a scan is never resolved (`docs/tech-debt/TD-0051-columns-that-cannot-be-null-are-answered-nullable.md`).
- **A column of no origin is answered from its entry of the root's `Output` as an expression, or not at all** (`PlanExpression`, its parts `Walk/PlanExpression.Nullability.cs`, `Walk/PlanExpression.Proofs.cs` and `Walk/PlanExpression.Forms.cs`, its tokens `Walk/PlanTokens.cs`, `Walk/NullabilityWalk.Expressions.cs`, [expressions](../../docs/architecture/postgres-nullability.md#expressions)), and every rule below guards against a wrong `false`.  An entry is read as a whole, never as a prefix, and only in a plan with no set operation, since an `Append` or a `SetOp` prints its first branch at the root.  A form is pinned in `tests/SqlSource.Tests.Postgres/Describer/PlanOutputTests.cs`, as 14 and 18 print it, before it is read.  `count(x)` and the other names of `CatalogOverloads` are read only when `overloads` answered that no schema other than `pg_catalog` holds them and `pg_catalog` holds none as an object that is not built in, since another schema's `count` of the argument's exact type beats the catalog's, and an overload added to `pg_catalog` is not one the table pins.  Where a join null-extends, an entry is read only at the node that computes it and only when that node is preserved.  An aggregate is read only at the grouped `Aggregate` that computes it, never inside a value a child printed.  A `COALESCE`, `GREATEST` or `LEAST` over both sides of a full join is read only at the `Full` join that computes it, over plain references, with nothing that null-extends under either side, since a node above sees each side as the join extends it.  A `SubPlan` is read as a plan of its own, and none in a statement that may name `OLD` or `NEW`; `(SubPlan n)` only as the whole column, since 14 prints every kind of subquery so.  A reference is proved only through an instance no join extends, but for that full join, and a partitioned table without a row only through every one of its partitions' rows, never from a plan with `Subplans Removed`.  An operator, a function or an aggregate other than `count(*)` and the rankings is read only by an exact signature of `TotalFunctions` or by a name of `CatalogOverloads`, a cast only within a family of `SetOperationTypes`, and any of them, a ranking and a literal's type name only when the session finds `pg_catalog` first (`PostgresSearchPath`).  A row goes in `TotalFunctions` only for one that is total, never merely strict, with the C function that implements it, which the `Catalog_Total*` tests of `PlanOutputTests` pin on 14 and 18, and a row goes in `CatalogOverloads` only for a name whose every overload in `pg_catalog` is never `NULL` under its row's condition, which `Catalog_CatalogOverloads_ArePinned` pins.
- **A set operation's column of no origin is answered from its inputs** (`Describing/Postgres/Walk/NullabilityWalk.SetOperations.cs`, [set operations](../../docs/architecture/postgres-nullability.md#set-operations)).  A `Subquery Scan` aliased `*SELECT* <k>` is followed to its branch by position only when it is itself one of the two flagged members of a 14 `SetOp`'s `Append`: the alias alone proves nothing, and a scan under the flagged member is never followed.  An `Append` proves a column only when it has a member and every member does; an `INTERSECT`'s `SetOp` when an input does, an `EXCEPT`'s when its left input does, and either below another set operation or under a cast only when every input does.  Any other `SetOp` and a `Recursive Union` never prove a column, and a node that projects passes the ordinal on only when its entry is the child's printed entry, `E`, `(E)` or `((E)::T)`, and no other entry of the child is.  A branch's value counts only when its type carries to the column's (`SetOperationTypes.Carries`), a family of `SetOperationTypes.Families` holding only types with a built-in cast each way, as `Catalog_CastFamilies_AreBuiltInBothWays` in `tests/SqlSource.Tests.Postgres/Describer/PlanOutputTests.cs` pins, and `PlanExpression.TypeOf` knows a literal's type only when `pg_catalog` is first on the path.
- **The walk degrades a column alone, and the plan whole** (`NullabilityWalk`, [how the walk degrades](../../docs/architecture/postgres-nullability.md#how-the-walk-degrades)).  A column without an origin is never mapped.  The walk never answers `false` for a column with an origin on its own: when in doubt it is the heuristic.
- **The settings of the planner are for the tests, and the list is closed** (`PlannerSettings`, [the settings of the planner](../../docs/architecture/postgres-nullability.md#the-settings-of-the-planner)).  `ToolHost.Create` registers the describer with the constructor that takes none.  A name outside the list, or a value that is not `on` or `off`, throws at construction and again where the text of the `SET LOCAL` is made, so nothing else reaches one.
- **Every fixture case gives one answer on PostgreSQL 14 and on 18** ([the walk in the fixtures](../../docs/architecture/postgres-nullability.md#the-walk-in-the-fixtures)).  A shape the two plan differently is a test of `tests/SqlSource.Tests.Postgres/Describer/WalkTests.cs` with each version's answer, and not a fixture.  `tests/SqlSource.Tool.Tests/Fixtures/WalkMatrixTests.cs` holds what each `walk-*` case must give, by hand: a recording that disagrees with it is a bug to find, and the table is not changed to fit one.
- **`check` is the lexer against Npgsql** (`NpgsqlCheck`, [the check against Npgsql](../../docs/architecture/postgres-describer.md#the-check-against-npgsql)).  The sidecar records only a `bindName` that `check` bound in this run, and `PostgresSession.CheckAsync` refuses a parameter whose type has none as `SQLSRC232` before it asks; `PostgresBindNames` computes the candidate from the catalog rows alone, whatever the `search_path`.  The tool never rewrites a user's SQL to make a parameter bindable; `docs/deferred/D-0003-custom-type-conversion.md` is the planned way past the types Npgsql cannot bind.  `BatchRewrites` and `Describing/Postgres/RowDescriptions.cs` read Npgsql by reflection: each resolves its members once and throws a named `InvalidOperationException` when one is missing, and `BatchRewritesTests` and `RowDescriptionsTests` pin the members so that an upgrade of Npgsql fails there and not in a describe ([reflection into Npgsql](../../docs/architecture/postgres-describer.md#reflection-into-npgsql)).
- **A prepared statement is session state** ([the prepared statement and the session](../../docs/architecture/postgres-describer.md#the-prepared-statement-and-the-session)).  Every call from `prepare` to `deallocate` runs in one transaction, which `PostgresConnection.BeginDescribeAsync` begins with a savepoint before the `PREPARE`, so that a pooler in transaction mode keeps the describe on one backend; `PostgresConnection.KeepPreparedAsync` then moves the savepoint after the `PREPARE`, since a rollback to a savepoint gives up the locks taken after it.  A statement survives a rollback, so `deallocate` is asked in a `finally`, inside the transaction, whenever `prepare` answered without an error, and ends the transaction; a `prepare` that answers an error ends it itself.  A call that fails on the server goes through `PostgresLive.InDescribeAsync`, which rolls back to the savepoint before it answers, so no later call meets an aborted transaction; a new call after `prepare` goes through it too.  A cancellation ends nothing, and the transaction dies with the session.  The error of `deallocate` is written to the log and never reported.  A name is `sqlsource_<n>`, counted within the session, so it is the same when a capture is recorded and when it is replayed.  A describe needs one session, and the tool refuses what is found not to keep one as `SQLSRC236`; `PostgresConnection` refuses `Multiplexing=true` before it connects.
- **Nothing a `.sql` file holds can make the describer run a statement.**  What holds that is how the `PREPARE` is sent, and not what the tool read of it.  `PostgresConnection.ExecuteAsOneStatementAsync` sends it as an `NpgsqlBatch` of one command with no parameters, which Npgsql does not read and never splits: the server is given the whole text as one statement to parse, and it refuses a text that holds a second one, `42601: cannot insert multiple commands into a prepared statement`, before it runs anything.  The one statement the text can be is a `PREPARE`, which runs nothing.  An `NpgsqlCommand` is another thing: Npgsql splits its text at each `;` that its own lexer finds and runs every part, so `PostgresConnection.CommandAsync` is for a text that holds nothing of a user's, and the `PREPARE` never goes through it.  `check` is the second text that holds a user's SQL, and goes the same way, through `PostgresConnection.BatchOfOneAsync`, under `CommandBehavior.SchemaOnly`: with a named parameter Npgsql reads the text to place it, and refuses one with a `;` that something follows by a `NotSupportedException`, having sent nothing, which `PostgresLive.CheckAsync` answers as an error and never lets through.  Four checks stand before anything is sent and use no server.  They are the first refusal, with an error that says what is wrong, and the guarantee does not rest on them: `ParameterPlaceholders.Rewrite` refuses a text in which the lexer finds a second statement, `SQLSRC230`, `StatementShape.RefusedKind` refuses a statement that `PREPARE` does not take, `SQLSRC233`, `StatementShape.PositionalParameter` refuses a `$n` that the SQL writes itself, `SQLSRC234`, and `DeclaredTypeText` reads each `-- param:` type against the grammar of a type name, `SQLSRC228`, since the type is put into the `PREPARE` as written.  The tool's lexer, Npgsql's and the server's may split a text differently, so the guarantee does not rest on the lexer: it reads a character above U+007F as part of a name, as the server does, so `SELECT 1 AS §$x$; DROP TABLE t; --$x$` is two statements to all three, but a text the lexer reads as one can still be two to the server.  The type list still ends with a line break before `AS`: whatever a type's text held, the `) AS` is not on its line, so nothing in a type can reach it.  A change to any of them gets a case in `tests/SqlSource.Tool.Tests/Describing/Postgres/` that shows what is refused.  A new place that puts a user's text into SQL the tool sends does it so that the driver cannot split the text, and gets a case with a canary beside `PrepareAsync_TextOfTwoStatements_AnswersTheServersErrorAndRunsNothing` in `tests/SqlSource.Tests.Postgres/Describer/ParameterTests.cs`, and for a text that goes to `check`, one beside `NpgsqlCheckTests.CheckAsync_TextNpgsqlWouldSplit_AnswersAnErrorAndRunsNothing` in `tests/SqlSource.Tests.Postgres/Describer/NpgsqlCheckTests.cs`.  Every text the describer sends, and how, is [why a query cannot run a statement](../../docs/architecture/postgres-describer.md#why-a-query-cannot-run-a-statement).
- **The connection is made inside a `live` function and nowhere else** ([the connection](../../docs/architecture/postgres-describer.md#the-connection)).  `PostgresConnection` holds the connection's value and the describer's log, and is the one place that makes the data source, the connection, every command, every batch and the describe's transaction; under a replay none of that runs.  The `live` functions are `Describing/Postgres/PostgresLive.cs`, with the SQL the tool sends; `PostgresSession` holds what is asked, in which order, and what is made of each answer.  Each session has a data source of its own, since a plain `NpgsqlConnection` shares a type catalog by connection string for the life of the process.  `PostgresConnection.cs` is PostgreSQL's one file for which `.editorconfig` turns `CA2100` off, as `Describing/SqlServer/SqlServerConnection.cs` is SQL Server's.  Every `live` function answers through `PostgresLive.AnswerAsync`, which catches `NpgsqlException` and returns it as its answer's `error` through `Describing/Postgres/ConnectionErrors.cs`, `ConnectionErrors.AtOpen` for `open` and `ConnectionErrors.Of` for every other call, and never keeps the driver's text itself; a cancellation passes through; anything else is a bug.  A new text that the describer throws as an `NpgsqlException` of its own goes in `PostgresConnection.OwnTexts`, or `ConnectionErrors` replaces it.  The one exception is `PostgresLive.CheckAsync`, which also catches the `NotSupportedException`, the `InvalidCastException` and the `ArgumentException` that the driver throws before it sends anything, and answers them.  What a user can cause at `open` and Npgsql does not wrap becomes an `NpgsqlException` with a fixed text and no inner exception, so that the driver's quote of the value is dropped; `PostgresConnection.OpenAsync`'s remarks list each with where Npgsql throws it, and any other type, `IOException` included, is a bug and stays `SQLSRC200`.  A connection that the server ended makes every later call of the session answer an error, and the session is not opened again.  When the log keeps anything (`IRunLog.Writes`), the driver logs through `Describing/Postgres/NpgsqlRunLogger.cs`, which forwards only the event ids it lists, writes an exception as its type alone, and keeps parameter logging off, `Log Parameters=true` of the connection string included: an update of Npgsql reads the new version's messages again before it lists an id ([the connection](../../docs/architecture/postgres-describer.md#the-connection)).
- **The calls and their records are a contract with the captures** ([the calls and their records](../../docs/architecture/postgres-describer.md#the-calls-and-their-records)).  The names of the calls are `PostgresCallNames`, which every capture records: a call is added and never renamed.  The records are in `Describing/Postgres/PostgresCalls.cs`, with the rule of a record above.  An OID is a `long`.  A member of a row is named as the catalog names it where the catalog has one word, and for what it says where it is no catalog column.  The tool's own rewrite that `check` compares with is built by `NpgsqlCheck.Read` from the query's SQL and parameters, its arguments, and is not a member of the request, so that the requests of old captures still match.  A member that came later reads null as what an older capture meant, as the page's table lists for each.  A change to what the describer asks changes the fixtures: record them with `tools/record-fixtures.sh` and read the diff.  The SQL of a catalog call runs under the user's `search_path`: write every type and function in it with `pg_catalog.`, and pair arrays with `ROWS FROM`, never `unnest(a, b)`, which works only unqualified (operators: `TD-0077`).
- **A server's error gets its id from six things, in this order** (`PostgresErrors`, [errors](../../docs/architecture/postgres-describer.md#errors)): the call, since a failure of `open` is `SQLSRC224` but for the tool's refusal of `Multiplexing=true`, `SQLSRC236`, and a server below `PostgresSession.MinimumMajorVersion` is then `SQLSRC235`; at `prepare`, `42P05`, a statement that is not listed, or a transaction that a pooler in statement mode refused, `08P01` with PgBouncer's own message (`PostgresLive.TransactionRefused`), `SQLSRC236`; the SQLSTATE `42P14`, `SQLSRC233`; a position inside the type list of the `PREPARE`, `SQLSRC228`; `42P18` or `42P08` with a `$n` of the list in the message, `SQLSRC226` and `SQLSRC227`; and anything else, `SQLSRC225`.  `42P05`, `42P14` and `26000` are matched by their SQLSTATE alone, since a message may be translated.  `StatementShape.RefusedKind` holds a list of words to refuse, never to allow, so that `SELEC 1` stays `SQLSRC225`.  An error of `check` is `SQLSRC231` only when it is a class `42` SQLSTATE or Npgsql's own refusal of the text (`textRefused`), and `SQLSRC225` otherwise; which errors are a disagreement is decided in one place, `NpgsqlCheck.Read`, and `PostgresErrors.Check` reports from its verdict.  An `at character` line counts in the user's SQL, the position less `ParameterPlaceholders.HeadLength`, and an error whose position is in a text the user did not write has none.

- **Every error goes through `Reporting/Reporter.cs` with a descriptor of `ToolDiagnostics`**, or of `SqlDiagnostics` where the generator reports the same condition.  The descriptors are in the generator's project; its `AGENTS.md` lists the four places a new one touches.  A wrong command line is the one exception, below.
- **The exit code is `0`, `1` or `2`**, as the manual's [exit codes](../../docs/manual/tool.md#exit-codes) say.  `Cli.ExitCodeOf` takes the code from `Reporter.Count` and `Reporter.DifferenceCount`, so a command reports and goes on, and never returns `1` itself.  `2` is for `SQLSRC219` alone, a sidecar that `--check` found out of date, and a query that could not be described is "could not check" and never `SQLSRC219`.
- **The format of an error is a contract with MSBuild and with editors.**  `<path>(<line>,<column>): error <id>: <message>`, or `<path> : error`, or `sqlsource : error`; then continuation lines, each four spaces, a label, a colon, a space and a text; then `    see:` with the descriptor's help link, last.  Only the first column tells a first line from a continuation line, so `Reporting/OneLine.cs` writes a line break as a space in every text the tool prints and did not write itself: an argument of a message, a path, a label, the name of an unknown option.  Several threads may report, so `Reporter` writes an error with one call, under a lock.  A path in a message is a full path, or `The path at position <n>` when its token holds `=` or `;` (`UsageValue.NamedAsPath`).  No error carries a hint to a log: a `describe` that reported an error other than `SQLSRC219`, was not cancelled, and was asked for no log ends with `Cli.RunAgainLine`, once, on standard error.  A test that compares the whole of standard error of such a run ends its text with `DescribeScene.RunAgain`.
- **An exception is `SQLSRC200`**, caught in `Cli.RunCommandAsync`, the one `try` around the steps of `Cli.RunAsync`, and in `Cli.Run` when the host itself cannot be made, and in one other place: `Describing/DatabaseRuns.cs` catches what a describer throws, since its message may hold a connection's value, and throws a `DescriberFaultException` that holds the same error with the value taken out, which `Cli.RunCommandAsync` reports ([describing](../../docs/architecture/tool.md#describing); the `trace` lines are in [the reporter](../../docs/architecture/tool.md#the-reporter)).  `DescriberFaultException` derives from `InvalidOperationException`, since S3871 wants an exception that derives from `Exception` to be public and CA1515 allows no public type in the tool, and it never holds an inner exception, whose message may hold the value.  So no `catch (InvalidOperationException)` may stand between `Describing/DatabaseRuns.cs` and `Cli.RunCommandAsync`: it would swallow the fault and the run would go on.  A session that fails to close after the body of its database ended with an exception is dropped.  `Reporting/UnexpectedFailure.cs` makes the error; an exception's text is redacted through the function it takes, whole, and never line by line.
- **A wrong command line is reported by `UsageCheck.cs`, before System.CommandLine reads it, and never repeats a token's text**, since a token can be a secret ([reading a command line](../../docs/architecture/tool.md#reading-a-command-line)).  A line names an option the tool has, or the name of an unknown option cut at its first `=` or `:` when it is within `NearName.MaxDistance` edits of a name or alias of any option of the tool, or a position counted from one.  Only the first unknown option is reported, and nothing after it is read.  These lines have no id and do not go through the reporter.  `tests/SqlSource.Tool.Tests/Commands/UsageCheckTests.cs` holds the rule for an option that takes a value.
- **`UsageCheck` and System.CommandLine must read a command line the same way.**  A token that one takes for the value of an option and the other for the path is printed as a path.  `Usage.cs` is what `UsageCheck` read, and `Cli` runs nothing unless System.CommandLine found the same command and the same arguments: it writes `sqlsource: the command line is not valid` instead.  `Check_EveryAcceptedCommandLine_IsReadTheSameBySystemCommandLine` holds the two together over every command line of a few tokens.  A new kind of option adds its tokens to that test's vocabulary, and an option of the tool itself to that of `Check_EveryAcceptedCommandLineOfTheTool_IsReadTheSameBySystemCommandLine`, which runs the tool's own commands and also compares the values that each reader gives an option, and a disagreement it finds is fixed in `UsageCheck`, by reading as System.CommandLine does or by rejecting more.  What is left of the risk is `docs/tech-debt/TD-0023-path-without-an-equals-sign-is-printed-as-given.md`.  `Cli` also runs nothing unless both readers give `--project`, `--database`, `--connection` and `--log` the same values, in the same order (`DescribeCommand.ReadsValuesAs`): `describe` reads these values, and its unit and `.sql` paths, from `Usage`, with their positions, and the log's `arguments` is redacted from it, while System.CommandLine gives the log's path.
- **A command's own rules for its values are in the command**, as `DescribeCommand.CheckUsage`, which reads `Usage.Values`: each argument and each value of an option with its position.  `Cli.ReadCommandLineAsync` calls it when `UsageCheck` found nothing.  Its lines name a position and never a token, as `UsageCheck`'s do.  What it holds each value to is in [reading a command line](../../docs/architecture/tool.md#reading-a-command-line).  On a line with a `--connection`, an argument that holds `=` or `;` is a part of a value that the shell split, a `.sql` path too, and is reported by its position: it would be printed as a path, a `.sql` one in full by `SQLSRC212`.  A path may hold either, as a folder of `tests/SqlSource.Tool.Tests/Fixtures/Projects/OddPaths` does, so a line with no `--connection` is left as it is.
- **An option is declared so that `UsageCheck` reads it right.**  A flag has `Arity = ArgumentArity.Zero`: System.CommandLine's default for a `bool` takes an optional value, and the token after the flag would be read as that value.  An option that takes a value takes exactly one each time it is given: `ArgumentArity.ExactlyOne` when it is given once, and an array with `ArgumentArity.OneOrMore` when it may be repeated, since System.CommandLine rejects a second `ExactlyOne`.  `UsageCheck` rejects that second one itself, with `option '<name>' is given more than once`, since System.CommandLine's message repeats the value.  An option is added to `--help` in the change that gives it an effect, not before: one that is read and checked earlier is `Hidden` until then, as `--database` was in sub-phase 2.4.
- **The root is a `Command`, not a `RootCommand`**, with a `HelpOption` under three names and a `--version` whose action is the tool's own; [reading a command line](../../docs/architecture/tool.md#reading-a-command-line) says why.  Response files and the bundling of short options are off in `Cli`.
- **The tool writes English**, and `SatelliteResourceLanguages` keeps other languages out of the package.  A test compares no text that System.CommandLine wrote.
- **`README.md` here is the package's short page on nuget.org**, so its links are absolute URLs: what the tool is for, how to install it, the commands a user runs most, and links to the manual and the repository's `README.md`, which is not packed into this package.  Keep it that short.  The tool's behaviour is documented in `docs/manual/tool.md`, the workflow and the command reference, where a new option, environment variable, exit code or command goes; in `docs/manual/settings.md`, for the logical database setting; and in the page of each database it describes, `docs/manual/postgresql.md` and `docs/manual/sqlserver.md`.
