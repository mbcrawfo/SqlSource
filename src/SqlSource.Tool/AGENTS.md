# AGENTS.md - src/SqlSource.Tool

How the tool works: [`docs/architecture/tool.md`](../../docs/architecture/tool.md).
How the PostgreSQL describer works: [`docs/architecture/postgres-describer.md`](../../docs/architecture/postgres-describer.md) and [`docs/architecture/postgres-nullability.md`](../../docs/architecture/postgres-nullability.md).
How the SQL Server describer works: [`docs/architecture/sqlserver-describer.md`](../../docs/architecture/sqlserver-describer.md).

The `sqlsource` command, packed as the .NET tool `SqlSource.Tool`.  Its tests, and where each kind goes, are in [`tests/README.md`](../../tests/README.md).

- **The tool shares the generator's code and never copies it.**  It references `src/SqlSource/SqlSource.csproj` and sees its internals; what each folder uses of it is in [folders](../../docs/architecture/tool.md#folders).  Code that both need goes in the generator's project, where `netstandard2.0` and Roslyn 4.8.0 bound it.
- **It targets `net8.0` with `RollForward` `Major`, and references a current Roslyn by `VersionOverride`.**  Do not raise the target: a user with only the .NET 8 SDK must be able to run it.  `tools/check-tool-install.sh` runs the packed tool on the newest runtime the machine has.
- **Everything from outside comes through `ToolHost`.**  Nothing reads `Console`, `Environment`, `RuntimeInformation` or the current directory except `ToolHost.Create` and `Cli.Run`, the entry of a real run ([the host](../../docs/architecture/tool.md#the-host)).  A test gives `Cli.RunAsync` a host of its own.  The clock is `ToolHost.Time`, a `TimeProvider`: the time of a log's events and how long a step took come from it and never from `DateTime` or `Stopwatch`, and the tests stand on `tests/SqlSource.Tool.Testing/TestClock.cs`, as the default of their runs, hosts and sessions, unless a test brings a clock.  A database is reached through `ToolHost.Describers` and `ToolHost.Exchange`, and the log's file through `ToolHost.CreateFile`, which a test replaces with a stream that fails; what a later phase takes from outside is a new member of `ToolHost`, as these, the clock and the processes are.  So do the descriptions of .NET and of the system that the log's `run.start` holds, `ToolHost.Runtime` and `ToolHost.OperatingSystem`, which `tests/SqlSource.Tool.Testing/Hosts.cs` fixes.
- **A signal cancels a run once, and a second lets the process be killed.**  `Cli.Run` listens for Ctrl+C, `SIGTERM` and `SIGHUP`: the first cancels the run, which ends by its own road with its exit code, and a second, while the run has not ended, lets the process be killed (`Cli.Interrupt`).  The three share one count of signals, which is raised atomically.  For the first signal, the handler of `SIGTERM` and `SIGHUP` returns only when the run has ended, and for a second it returns at once (`Cli.Terminate`); [signals](../../docs/architecture/tool.md#signals) says why.  `tests/SqlSource.Tool.Tests/Commands/TerminationTests.cs` sends each signal to the tool in a process of its own, where a system has signals, and closes its console on Windows.
- **Every process goes through `ToolHost.Processes`**, an `IProcessRunner` of `Processes/`.  `Processes/ProcessRunner.cs` is the only code that starts one, and a test gives `tests/SqlSource.Tool.Testing/FakeProcessRunner.cs`, which answers in MSBuild's place.  A run that is cancelled kills the program with everything it started and waits, for a few seconds at most, until the program has ended ([why](../../docs/architecture/tool.md#evaluating-a-project)); a kill that fails never stands in for the cancellation, which would be reported as `SQLSRC200`.  A temporary folder is made in `ToolHost.TempDirectory`, and what runs at once is bounded by `ToolHost.ProcessorCount`.
- **The tool never restores and never builds a project, and writes nothing into one but its sidecars.**  `Projects/ProjectEvaluator.cs` only evaluates a project and runs the package's target `SqlSourceWriteManifest` into a file of the run's temporary folder ([evaluating a project](../../docs/architecture/tool.md#evaluating-a-project)).  Do not add `-restore`, a target of a build, or a file under a project's folder: `tests/SqlSource.Tool.Tests/Projects/FixtureProjectTests.cs` checks that a project has no `obj` afterwards.  A sidecar is written or deleted by `Describing/SidecarStore.cs` and by nothing else.
- **A result that may fail has one shape where files meet.**  A method that another file calls and that gives one value or one reason returns an `Outcome<TValue, TFailure>` (`Outcome.cs`) and reports nothing: its caller does, as `DescribeCommand.PlanAsync` reports what `Projects/RunUnitFinder.cs` found and `Cli.OpenLog` what `RunLogFile.Open` did.  A private helper may be a `TryX`, and so may a method that gives a value or nothing and no reason, as `ConnectionArgument.TryParse`.  A result with more than two states is a record with a state, as `ProjectEvaluation`.  A step that reports several errors as it goes takes the reporter, or returns its errors as data, and is no `Outcome`.  An `Outcome` of a value that must be disposed is made with the constructor, `new Outcome<RunLogFile, ToolDiagnostic>(log)`, never with `Outcome.Of`, and carries no `SuppressMessage`: `.editorconfig` tells `CA2000` that a constructor takes ownership, as `RunLogFile.Open` and `Describing/Describers/DescriberSession.cs`'s `OpenAsync`, the opener of both describers' sessions, show ([what it costs](../../docs/architecture/tool.md#an-outcome-of-a-disposable)).
- **A database belongs to a query that needs an entry, and to no other.**  Names are compared with `DatabaseName.Comparer`, ignoring case, and the plan holds the first spelling.  Only a `Ready` file decides its database's dialect or conflicts with it (`SQLSRC211`); a database that only other files hold keeps the dialect of the first of them.
- **Of the settings that are not valid, the tool reports the ones it reads**: the problems of each settings file that a chain of the project's `.sql` or C# files reaches, once in a run, at their file, line and column, after the project's `SQLSRC208`: `SQLSRC015` to `SQLSRC018`, and `SQLSRC019` of `dialect`, `output` and `database` ([the plan](../../docs/architecture/tool.md#the-plan)).  The build reports the rest.  Neither the tool nor the build reads an MSBuild property or metadata for a setting.
- **The fixtures of a describer are in `tests/SqlSource.Tool.Tests/Fixtures/Describers/<engine>/<case>/`**, beside the engine's `schema.sql`, and what a case holds and how one is recorded is [the PostgreSQL describer's fixtures](../../tests/SqlSource.Tests.Postgres/README.md#the-describers-fixtures), and [the SQL Server describer's](../../tests/SqlSource.Tests.SqlServer/README.md#the-describers-fixtures) for `mssql`.  A case's `query.sql` is a complete SqlSource file with exactly one query.  The files are compared byte for byte, so the folder is `text eol=lf` in `.gitattributes` and has a section in `.editorconfig`.  `postgres/schema.sql` is the schema that `tests/SqlSource.Tests.Postgres` applies to its container; a change to it can move the OIDs that the captures hold, and every case is recorded again.  A change to `mssql/schema.sql` records the SQL Server cases again.
- **A connection's value goes to the describer and nowhere else** ([where a connection's value goes](../../docs/architecture/tool.md#where-a-connections-value-goes)).  `OpenRequest` and the connection argument of `IQueryDescriber.SecretsOf` and of `IQueryDescriber.RewriteOf` are the things that hold it for a describer, and the parts that `SecretsOf` returns and the text that `RewriteOf` returns are the only things a describer gives back that hold it or a part of it, which the run uses only to remove them and to refuse a capture.  Both are asked under a guard of the whole value alone, before anything else of the database.  `SecretsOf` reads the environment only through the `ToolHost.GetEnvironmentVariable` it is passed, for a password that the driver takes from there or from a file.  `ConnectionArgument`, `ConnectionSecret`, `DatabaseConnection`, `OpenRequest` and `UsageValue` each override `ToString` to leave it out: a record prints its members.  What the tool may say of a connection is where it came from, `--connection` or the name of a variable.
- **Every text of a describer that is printed, said under `--verbose` or logged has the secret removed, and the run does not rely on the describer's rule** ([where a connection's value goes](../../docs/architecture/tool.md#where-a-connections-value-goes)).  What is removed is a `Describing/ConnectionSecret.cs`: each whole form of the value (`ConnectionSecret.Wholes`) wherever it stands, and each part that `SecretsOf` gives only where it stands as a token (`Redaction.HoldsToken`), so that a password `test` leaves `latest_orders` alone; it drops a part shorter than `ConnectionSecret.MinimumPartLength` and one equal to the database's name or the engine's.  A printed text, an exception's included, goes through `Describing/Redaction.cs`, a failure twice: as the describer returned it, with its server lines searched joined, and as the error made of it, its formatted message included.  Nothing hands a log a value: `Logging/LoggedArguments.cs` builds `arguments` from what `UsageCheck` read, a describer's log is a `Logging/SessionRunLog.cs`, which also searches an event's strings joined (`Describing/JoinedRedaction.cs`), and what the run writes of a database after its connection is found goes through `RunTrace.Without`.  A new event that carries what a describer gave gets a case in `tests/SqlSource.Tool.Tests/Logging/RunLogRedactionTests.cs`, and a new place that prints it one in `tests/SqlSource.Tool.Tests/Commands/SecretTests.cs`.  What the removal does not cover is `docs/tech-debt/TD-0034-redaction-of-a-describers-text-has-holes.md`.
- **`Logging/` is what a run says of itself beside its errors and its summary** ([logging and reporting](../../docs/architecture/tool.md#logging-and-reporting)).  `Cli.OpenLog` opens the log only after `UsageCheck` and `DescribeCommand.CheckUsage` accepted the command line and System.CommandLine read the same, so a wrong command line is never logged, and only for a command line that runs `describe` (`DescribeCommand.Runs`): the help must not empty the log of the last run ([the steps of a run](../../docs/architecture/tool.md#the-steps-of-a-run)).  `Logging/RunLogFile.cs` writes and flushes each event as it happens, so that a stopped run leaves its log.  For every `describe` that runs, `Cli.InvokeAsync` makes the run's `Reporter` with its `RunTrace`, and only then gives the command its action (`DescribeCommand.Bind`), so that the command cannot run with another reporter.  `InvokeAsync` replaces `RunState.Reporter`, so whatever reports after a step reads the reporter from the state then, and never from a local made before the step.  `Reporter` writes a `diagnostic` event for each error, under the same lock as the console, to the trace it was made with.  Every step that has the reporter has the trace.  `Logging/RunEvents.cs` builds each event but `run.start`, `run.end` and `diagnostic` in one place, and its caller writes it where the thing happens: a step that reports nothing, the planner, `RunDecisions`, `FileOutcomes`, `SidecarCheck`, writes no event either, and its caller does, from what it returned.  `Describing/DescribeRun.cs` hands `Cli` the counts of `run.end` before it writes the summary ([why](../../docs/architecture/tool.md#the-summary)).  `arguments` of `run.start` is built from what `UsageCheck` read (`Logging/LoggedArguments.cs`), never from the text of the command line, so that a `--connection` value and a `--database` value are `***` whichever way the option was written, and an argument or a `--project` value that holds `=` or `;` is too, as a message prints no such path.  The two names are never written because `run.start` comes before the plan, which decides whether a name would be printed; the `database` events and `run.end` name the selected databases, and `connectionSource` says which got its connection from `--connection`.  `RunTrace.Say` is the one place that writes a line of `--verbose`, each to standard output and on one line, and `RunEvents` says each line, beside the event it belongs to when it has one, so the two never tell two stories.  `tests/SqlSource.Tool.Tests/Logging/RunLogTests.cs`, `tests/SqlSource.Tool.Tests/Logging/RunLogDestinationTests.cs` and `tests/SqlSource.Tool.Tests/Logging/RunLogRedactionTests.cs` hold it.  `tests/SqlSource.Tool.Tests/Commands/VerboseTests.cs` holds the lines.
- **An event's name and its members are read by people and by phase 10's bundle.**  A member is added and never renamed, and a value is one of `Logging/LogValue.cs`'s closed set.  A describer's events have its engine before their names, which `Logging/SessionRunLog.cs` puts there.  `Logging/RunLogFile.cs` cuts a string over 1 MiB, and owns the names `event`, `time` and `truncated` at the top of a line ([the log](../../docs/architecture/tool.md#the-log)).  A write that the system refuses never ends a run: `Cli` reports it once, when the run ends.
- **Every error goes through `Reporting/Reporter.cs` with a descriptor of `ToolDiagnostics`**, or of `SqlDiagnostics` where the generator reports the same condition.  The descriptors are in the generator's project; `src/SqlSource/Diagnostics/AGENTS.md` lists the four places a new one touches.  A wrong command line is the one exception, below.
- **The exit code is `0`, `1` or `2`**, as the manual's [exit codes](../../docs/manual/tool.md#exit-codes) say.  `Cli.ExitCodeOf` takes the code from `Reporter.Count` and `Reporter.DifferenceCount`, so a command reports and goes on, and never returns `1` itself.  `2` is for `SQLSRC219` alone, a sidecar that `--check` found out of date, and a query that could not be described is "could not check" and never `SQLSRC219`.
- **The format of an error is a contract with MSBuild and with editors.**  `<path>(<line>,<column>): error <id>: <message>`, or `<path> : error`, or `sqlsource : error`; then continuation lines, each four spaces, a label, a colon, a space and a text; then `    see:` with the descriptor's help link, last.  Only the first column tells a first line from a continuation line, so `Reporting/OneLine.cs` writes a line break as a space in every text the tool prints and did not write itself: an argument of a message, a path, a label, the name of an unknown option.  Several threads may report, so `Reporter` writes an error with one call, under a lock.  A path in a message is a full path, or `The path at position <n>` when its token holds `=` or `;` (`UsageValue.NamedAsPath`).  No error carries a hint to a log: a `describe` that reported an error other than `SQLSRC219`, was not cancelled, and was asked for no log ends with `Cli.RunAgainLine`, once, on standard error.  A test that compares the whole of standard error of such a run ends its text with `DescribeScene.RunAgain`.
- **An exception is `SQLSRC200`**, caught in `Cli.RunCommandAsync`, the one `try` around the steps of `Cli.RunAsync`, and in `Cli.Run` when the host itself cannot be made, and in one other place: `Describing/DatabaseRuns.cs` catches what a describer throws, since its message may hold a connection's value, and throws a `DescriberFaultException` that holds the same error with the value taken out, which `Cli.RunCommandAsync` reports ([describing](../../docs/architecture/tool.md#describing); the `trace` lines are in [the reporter](../../docs/architecture/tool.md#the-reporter)).  `DescriberFaultException` derives from `InvalidOperationException`, since S3871 wants an exception that derives from `Exception` to be public and CA1515 allows no public type in the tool, and it never holds an inner exception, whose message may hold the value.  So no `catch (InvalidOperationException)` may stand between `Describing/DatabaseRuns.cs` and `Cli.RunCommandAsync`: it would swallow the fault and the run would go on.  A session that fails to close after the body of its database ended with an exception is dropped.  `Reporting/UnexpectedFailure.cs` makes the error; an exception's text is redacted through the function it takes, whole, and never line by line.
- **A wrong command line is reported by `UsageCheck.cs`, before System.CommandLine reads it, and never repeats a token's text**, since a token can be a secret ([reading a command line](../../docs/architecture/tool.md#reading-a-command-line)).  A line names an option the tool has, or the name of an unknown option cut at its first `=` or `:` when it is within `NearName.MaxDistance` edits of a name or alias of any option of the tool, or a position counted from one.  Only the first unknown option is reported, and nothing after it is read.  These lines have no id and do not go through the reporter.  `tests/SqlSource.Tool.Tests/Commands/UsageCheckTests.cs` holds the rule for an option that takes a value.
- **`UsageCheck` and System.CommandLine must read a command line the same way.**  A token that one takes for the value of an option and the other for the path is printed as a path.  `Usage.cs` is what `UsageCheck` read, and `Cli` runs nothing unless System.CommandLine found the same command and the same arguments: it writes `sqlsource: the command line is not valid` instead.  `Check_EveryAcceptedCommandLine_IsReadTheSameBySystemCommandLine` holds the two together over every command line of a few tokens.  A new kind of option adds its tokens to that test's vocabulary, and an option of the tool itself to that of `Check_EveryAcceptedCommandLineOfTheTool_IsReadTheSameBySystemCommandLine`, which runs the tool's own commands and also compares the values that each reader gives an option, and a disagreement it finds is fixed in `UsageCheck`, by reading as System.CommandLine does or by rejecting more.  What is left of the risk is `docs/tech-debt/TD-0023-path-without-an-equals-sign-is-printed-as-given.md`.  `Cli` also runs nothing unless both readers give `--project`, `--database`, `--connection` and `--log` the same values, in the same order (`DescribeCommand.ReadsValuesAs`): `describe` reads these values, and its unit and `.sql` paths, from `Usage`, with their positions, and the log's `arguments` is redacted from it, while System.CommandLine gives the log's path.
- **A command's own rules for its values are in the command**, as `DescribeCommand.CheckUsage`, which reads `Usage.Values`: each argument and each value of an option with its position.  `Cli.ReadCommandLineAsync` calls it when `UsageCheck` found nothing.  Its lines name a position and never a token, as `UsageCheck`'s do.  What it holds each value to is in [reading a command line](../../docs/architecture/tool.md#reading-a-command-line).  On a line with a `--connection`, an argument that holds `=` or `;` is a part of a value that the shell split, a `.sql` path too, and is reported by its position: it would be printed as a path, a `.sql` one in full by `SQLSRC212`.  A path may hold either, as a folder of `tests/SqlSource.Tool.Tests/Fixtures/Projects/OddPaths` does, so a line with no `--connection` is left as it is.
- **An option is declared so that `UsageCheck` reads it right.**  A flag has `Arity = ArgumentArity.Zero`: System.CommandLine's default for a `bool` takes an optional value, and the token after the flag would be read as that value.  An option that takes a value takes exactly one each time it is given: `ArgumentArity.ExactlyOne` when it is given once, and an array with `ArgumentArity.OneOrMore` when it may be repeated, since System.CommandLine rejects a second `ExactlyOne`.  `UsageCheck` rejects that second one itself, with `option '<name>' is given more than once`, since System.CommandLine's message repeats the value.  An option is added to `--help` in the change that gives it an effect, not before: one that is read and checked earlier is `Hidden` until then, as `--database` was in sub-phase 2.4.
- **The root is a `Command`, not a `RootCommand`**, with a `HelpOption` under three names and a `--version` whose action is the tool's own; [reading a command line](../../docs/architecture/tool.md#reading-a-command-line) says why.  Response files and the bundling of short options are off in `Cli`.
- **The tool writes English**, and `SatelliteResourceLanguages` keeps other languages out of the package.  A test compares no text that System.CommandLine wrote.
- **`README.md` here is the package's short page on nuget.org**: what the tool is for, how to install it, the commands a user runs most, and links to the manual and the repository's `README.md`, which is not packed into this package.  Keep it that short.  The tool's behaviour is documented in `docs/manual/tool.md`, the workflow and the command reference, where a new option, environment variable, exit code or command goes; in `docs/manual/settings.md`, for the logical database setting; and in the page of each database it describes, `docs/manual/postgresql.md` and `docs/manual/sqlserver.md`.
