# AGENTS.md - tools

- **A check added here is added to both callers in the same commit**: `pre-commit-validation.sh` at the root and a job of `.github/workflows/build.yml`.  A check that needs only Docker goes in `lint`; one that needs the .NET SDK goes in the job whose build it shares, or in a job of its own.
- **A check's own script sets off that check in `pre-commit-validation.sh`**, as `format.sh` runs format on everything and `tools/actionlint.sh` runs actionlint, since a change to the script can change the verdict on any file it checks.  A change to `pre-commit-validation.sh` itself makes the run full, since it makes every decision.
- **A kind of file is added to `is_known_kind` in `pre-commit-validation.sh` only after the trigger of every check that reads it handles it**, since a kind that is listed no longer makes the run full, and an unlisted one does.
- **`test-scopes.txt` is read by `pre-commit-validation.sh` and by `TestScopes` of `tests/SqlSource.Repository`**, so a pattern holds no glob character but `*`, since the C# reader refuses the others ([the format](README.md#test-scopes)).
- **A container test project that is added or removed gets or loses its `project` line in `test-scopes.txt` and its `RunningProjectTests` in the same commit**, and `TestScopesFileTests` of `tests/SqlSource.Repository.Tests/Validation/` names the four that exist.
- **A new version of a linter is a change to the tag and the digest of its image in the script, and nothing else**, except that editorconfig-checker's also changes `Version` in `.editorconfig-checker.json` to match.
- **`package-install/` is a consumer, not a project of the solution.**  Do not add it to `SqlSource.slnx` or build it where it is.  A change to what a consumer sees from the generator or its MSBuild files adds a line to `package-install/Program.cs` and to `package-install/expected-output.txt` together.
- **`check-package-install.sh` copies `examples/PostgresExamples/Models/Users.sql` and its sidecar, changes the SQL of `GetUser`, and replays `tests/SqlSource.Tool.Tests/Fixtures/Bundles/postgres/select-left-join`**, so moving, renaming or changing that query or that bundle changes the script in the same commit, and `needs_packages` of `pre-commit-validation.sh` lists their files.
- **`package-install/Queries/AddedByATarget.sql` is meant to be missing from the manifest.**  Do not delete the file or loosen the manifest check to make a run pass; the check fails when the manifest lists it, so paying off the debt it shows changes the script in the same commit ([the gap](README.md#check-package-installsh)).
- **`pull-test-images.sh` is a step of `build.yml` and of the allocation and sync-async jobs of `nightly.yml`, and `build-postgis-image.sh`, through `.github/actions/postgis-image`, of each job that runs a PostGIS test, not checks, so neither is in `pre-commit-validation.sh`; `record-fixtures.sh` and `describe-end-to-end.sh` stay out of both** ([the scripts](README.md#recording-scripts)).
- All four read the default images from the lines of `tests/DatabaseTests/TestHarness/DefaultImages.cs` that declare `Postgres` and `SqlServer` (`record-fixtures.sh` only the line of the engine it records, and `build-postgis-image.sh` only `Postgres`): a change to a line's shape changes the `sed` of each script that reads it, and a script fails when its `sed` gives nothing.  The `AppContainer` of `tests/DatabaseTests/Postgres.Npgsql8` and of `tests/DatabaseTests/SqlServer.SqlClient61` runs on the constant through `EngineImage` and reads no text.
- `record-fixtures.sh` has one row for each engine in `engine_row`, and runs its class `FixtureCasesTests`, `SqlSource.DatabaseTests.Postgres.Describer` or `SqlSource.DatabaseTests.SqlServer.Describer`, with `SQLSOURCE_RECORD_FIXTURES=1`: renaming a test, its project or its variable (`FixtureCaseRuns.RecordVariable` of `tests/SqlSource.Tool.Testing/Fixtures/`), or adding an engine, changes the row in the same commit, and a test run with the variable set rewrites the recorded files.
- **`describe-end-to-end.sh` applies the files that `PostgresDatabases` of `tests/DatabaseTests/Postgres` applies, in the same order**: `schema.sql` then `seed.sql` of `tests/DatabaseTests/Postgres/Realistic/`, `EndToEnd/app/` and `EndToEnd/billing/`.  A database added, renamed or moved there changes `POSTGRES_DATABASES` in the script in the same commit, since the script names them itself.  `gis`, of `PostgisDatabases`, is `POSTGIS_DATABASE`, on the PostGIS container.
- **`build-postgis-image.sh` names the PostGIS image as `PostgisContainer.ImageOf` of `tests/DatabaseTests/TestHarness` names it**: the postgres tag, the version of `Package`, read from its line by its shape with `sed`, and the hash of the Dockerfile without its carriage returns.  A change to either changes the other in the same commit; `PostgisImageScriptTests` of `tests/DatabaseTests/Postgres` fails when they differ, since the tests would then build the image again and hide a failed build.  `describe-end-to-end.sh` builds the image through it.
- **`describe-end-to-end.sh` applies the files that `SqlServerDatabases` of `tests/DatabaseTests/SqlServer` applies on SQL Server 2025, in the same order**: `schema.sql` then `seed.sql` of `tests/DatabaseTests/SqlServer/Realistic/`, then `schema.sql`, `seed.sql` and `new-types.sql` of `EndToEnd/app/`, then `schema.sql` and `seed.sql` of `EndToEnd/billing/`.  A database or a file added, renamed or moved there changes `SQLSERVER_DATABASES` or the list of files in the script in the same commit.
- Keep the flags of `describe-end-to-end.sh`'s SQL Server part that its comments say to keep: they run the files as `SqlServerDatabases` runs them.
- **`describe-end-to-end.sh` also describes `examples/PostgresExamples` and `examples/SqlServerExamples`**, each in its engine's part, after applying its `schema.sql` to a database `examples`, under the logical database of its dialect, `postgres` or `mssql`, the default, since neither project sets a `database`.  Moving or renaming an example, adding an example project, or setting a `database` in one changes `POSTGRES_EXAMPLES` or `SQLSERVER_EXAMPLES` and its connection in the script in the same commit.
- **`mutation-test.sh` is no check and stays out of `pre-commit-validation.sh` and `build.yml`**, since a folder takes minutes and a project more than a night.  It runs Stryker from the folder of the project it mutates, with the `stryker-config.json` there.
- **A mutation run keeps the static mutants out**, since Stryker's runner reports false kills after it tests one.  Do not remove the first of the script's two runs or the check of its report ([why](README.md#the-two-runs-of-a-run)).
- **The text that `condense` of `MutationReport` writes is what `.claude/skills/reviewing-test-quality/briefs.md` teaches a reviewer to read**, and its run folder is the one `measure.sh` there fills: a change to either changes the other in the same commit ([the commands](README.md#the-test-reviews-commands)).
- **`additional-timeout` of both `stryker-config.json` files is never lowered below a minute.**  At Stryker's default a surviving mutant whose tests are slow is reported as a timeout, which counts as detected ([why](README.md#limits)).

> Maintenance: this file names specific files and folders.  If you rename, move, or remove them, update this file in the same commit.
