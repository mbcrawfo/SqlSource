# Query generation, phase 5.3: models - design

Date: 2026-10-18

Sub-phase 5.3 of the [query generation epic](2026-10-07-query-generation-epic-design.md).  It emits the input and output types of every query whose output is `Models` or `CodeGen`, from the usable sidecar entries of [sub-phase 5.1](2026-10-18-query-generation-phase-5-1-sidecars-in-the-generator-design.md) and the C# types of [sub-phase 5.2](2026-10-18-query-generation-phase-5-2-type-map-design.md).  After it a project can run its queries through Dapper or its own ADO.NET code into generated models.

It builds on 5.1 and 5.2.  Sub-phases 5.4 and 5.5 build on it.

## Intent

This is the sub-phase a user sees.  The owner's measure is that the models are reliable and that their generation does not slow a build or an edit.  Reliable means three things here: a model's shape is the query's, its nullability never claims more than the description proved, and the generated code compiles without a warning in every combination of settings a user can write.  Fast means that an edit to one file re-emits only the models whose shape changed.

The rules of the models are decided in the epic outline's Models section, and this spec adds detail without contradicting them.  The rules are quoted where a builder needs them in hand; the outline is the authority.

## Goals

1. For each query that needs an entry and has a usable one, for each type that claims its file and resolves its output to `Models` or `CodeGen`: an input model when the query has parameters, and an output model when its entry has rows.
2. Names, namespace, accessibility, shape, property order, sorting, property names and documentation as the epic's Models section decides.
3. Each model emitted once per full name, project-wide, with the shared-name rule and its error.
4. Table models from `matchesTable`, named after the table, shared by every query that matches it, turned off by `no-table-models`.
5. The `!` and `?` suffix of a column's name stripped from the property's name and applied to its nullability.
6. The settings of the models flip from "accepted; no effect yet" to their effect, in the generator and in the manual.

## Non-goals

- Execution methods, collection types, `MethodLocation`, result shapes and `async-method-suffix`.  Phase 8.  Their settings stay accepted with no effect.
- Deduplication by shape.  The epic rejects it: two queries with one shape and two names get two models.
- An attribute or marker that sets a model's accessibility, and a per-column C# type.  Out of the epic.
- A model for a query whose output is `Sql`, or whose entry is not usable.

## Anti-goals

- **A model that is less nullable than its description.**  A column whose `nullable` is `true` or `null` is nullable in C# unless its name ends in `!`.  A parameter is nullable only when its `nullable` is `true`.
- **A warning in generated code.**  Any compiler warning in a generated model is one the user cannot fix and an error under `TreatWarningsAsErrors`.  The harness's check that generated code has none applies to every model test.
- **A clash the compiler finds first.**  Every name conflict the generator can know of is the generator's diagnostic at the query, not a `CS0101` or `CS0102` in generated code.
- **One edit re-emitting every model.**  A single `RegisterSourceOutput` over all collected models would re-add every model on every edit, which the epic's technical note forbids.

## What exists today

As of the merge of sub-phases 5.1 and 5.2, which this spec assumes:

- For each claimed file, the usable entries keyed by query name, from 5.1.
- For each usable entry and query, each parameter's and column's C# type, from 5.2: its text, `global::`-qualified or a keyword, whether it is a value type, and its accessibility, with the type override applied and its errors reported.  A query with a type error gives no shapes.
- `QuerySettings` resolves the suffixes, the namespace and the model types per type and query; `GeneratorParameters` holds `SortInput`, `SortOutput` and `NoTableModels`; `SqlQuery` holds `Summary`, `InputModelName` and `OutputModelName` and no position for the two model markers.
- `TypeEmitter` writes each type's file with the header `// <auto-generated/>`, `#nullable enable` and a pragma; `XmlDocWriter` escapes documentation text; `HintName.FindAmbiguous` finds hint names that clash ignoring case.
- `TypeEmitter.SelectMembers` leaves out of a type a file with a query that clashes by name (`SQLSRC008`, `SQLSRC009`).  Such a file gives that type no models either.
- `TargetType` carries no accessibility; `TargetTypeReader` gains the type's effective accessibility.
- `SettingValue.IsQualifiedName`, which checks a model marker's name, rejects the reserved keywords alone.
- `GeneratorHarness.CreateCompilation` compiles at the default warning level, 4, so a warning of a later warning wave, such as `CS8981`, never reaches a test.

## Design

### Which models a query has

| The entry | Input model | Output model |
|----|----|----|
| `resultKind: rows`, parameters | Yes | Yes |
| `resultKind: rows`, no parameters | No | Yes |
| `resultKind: none`, parameters | Yes | No |
| `resultKind: none`, no parameters | No | No |

A result of no columns, which PostgreSQL accepts as `SELECT FROM t`, gets an output model with no properties: a positional record with an empty parameter list, or a class with no members.  The phase 8 methods need the type, and an empty one compiles.

### Names

From the epic, unchanged: `GetUser` gets `GetUserParams` and `GetUserDto`, the suffixes are `SqlSourceInputModelSuffix` and `SqlSourceOutputModelSuffix` at every level, and `-- input-model:` and `-- output-model:` give one query's names whole.  A marker's name that holds a period is a full name and ignores the namespace setting.

A table model, below, is named after its table.  A query's `-- output-model:` wins over the table's name, so a query that names its model never shares the table's.

### Namespace and accessibility

From the epic: models are namespace-level types, in the namespace of the attributed type unless `SqlSourceModelNamespace` says otherwise; a type in the global namespace gives models in the global namespace.  A model's accessibility is the claiming type's effective accessibility, at least `internal`.

When two types that emit one model, by the shared-name rule below, have different accessibilities, the model takes the wider, so that neither type's public surface loses it.

A mapped type that is less accessible than its model, an `internal` type in a `public` model, is `SQLSRC251` at the query, the id sub-phase 5.2 gives a mapped type that is not accessible.  This is where its second case is checked, since the model's accessibility is known only here.  The model is not emitted.

### Shape

From the epic: `SqlSourceInputModelType` and `SqlSourceOutputModelType` take `record`, `sealed record`, `class` or `sealed class`, default `sealed record`.

A record is positional, its parameters in the model's property order:

```csharp
/// <summary>Loads one user by id.</summary>
/// <param name="Id">The column <c>id</c>, <c>integer</c>, from <c>public.users.id</c>.  An identity column.</param>
/// <param name="Name">The column <c>name</c>, <c>character varying(100)</c>, from <c>public.users.name</c>.</param>
/// <param name="DeletedAt">The column <c>deleted_at</c>, <c>timestamp with time zone</c>, from <c>public.users.deleted_at</c>.</param>
public sealed record GetUserDto(int Id, string Name, global::System.DateTime? DeletedAt);
```

A class has a public property with `get` and `set` for each, and no constructor of its own.  A property of a non-nullable reference type is initialised with `= default!`, so that the class compiles under `#nullable enable` without `CS8618`; `required` was weighed and not taken, since it breaks every generic `new()` constraint a user's code or library may put on the model, and Dapper sets the properties by reflection either way.

Every model file has the header `TypeEmitter` writes, `// <auto-generated/>` and `#nullable enable`, and no pragma it does not need: the one it may need is sub-phase 5.2's, for a mapped type that is obsolete.

### Properties

**Order.**  From the epic: the parameters in the query's parameter list order, declared-only ones last; the columns in the select list's order.  `sort-input` and `sort-output` sort by property name, ordinal comparison.

**Names.**  From the epic: PascalCase of the column's or the parameter's name.  The rule, precisely:

1. A column's name loses one trailing `!` or `?`, which sets its nullability (below).  A parameter's name is its bare name with the case of its first appearance, as the sidecar records it.
2. The name is split at each `_`; empty parts are dropped.
3. Each part's first character is upper-cased by the invariant culture; the rest is kept as it is.  `created_at` is `CreatedAt`, `userId` is `UserId`, `ID` is `ID`, `api_v2_url` is `ApiV2Url`.
4. The parts are joined.

Then, in this order, each an error at the query that names the column or parameter and asks for an alias or a new name:

| Condition | Diagnostic |
|----|----|
| The column is PostgreSQL's name for a column with none, `?column?` | `SQLSRC253`: the column has no name |
| The result is no C# identifier: empty, starting with a digit, holding a character an identifier cannot hold | `SQLSRC254`: the name is not an identifier after PascalCase, with both forms |
| Two properties of one model have names that are equal ignoring case: `SELECT a.id, b.id`, or `user_id` beside `userId` | `SQLSRC255`: two columns or parameters give one property name, naming both |
| The name is the model's own name (`CS0542`), or one a record or `object` declares or disallows: `EqualityContract`, `Equals`, `GetHashCode`, `ToString`, `GetType`, `MemberwiseClone`, `Finalize`, `ReferenceEquals`, `PrintMembers`, `Deconstruct`, `Clone` (`CS8859`) | `SQLSRC256`: the property name is taken |

Names are compared ignoring case for `SQLSRC255` because the parameter names already are, and because Dapper matches columns to constructor parameters and properties ignoring case, so `Id` beside `ID` would map one column twice.  The list of `SQLSRC256` is the builder's to confirm against the compiler: every name that would give an error or a warning in a record or a class model.

A query with any of these errors gets neither of its models.  None of the four depends on a setting of a type, so they are found and reported per file, once, as sub-phase 5.1 reports its checks, and not once per claiming type.

**Parameter names and Dapper.**  Dapper sends a property of a parameter object only when the SQL names it as `@` and the property's name, ignoring case but not `_`.  So an input model binds through Dapper when the query writes its parameters in camelCase, `@accountId` for `AccountId`, and binds nothing when it writes `@account_id`.  The owner decided to keep the PascalCase rule and nothing more: most users will name their parameters to suit the library, and a method that gives the parameters by the SQL's names, which the review proposed, costs a call and an allocation on every query.  The manual's Dapper recipe says to write parameters in camelCase, or to build the parameters by hand, and its known issues say what happens otherwise.  The method is deferred, [D-0004](../../deferred/D-0004-input-models-bound-by-the-names-of-the-sql.md), which this spec's pull request records.  Phase 8's methods bind every parameter themselves.

**Nullability.**  A column's property is nullable when its name ends in `?`, not nullable when it ends in `!`, and otherwise nullable when its `nullable` is `true` or `null` and not nullable when it is `false`.  A parameter's property is nullable when its `nullable` is `true`.  A nullable property is the C# type with `?`: `Nullable<T>` for a value type, the annotation for a reference type.  `T?` in source is the same text for both, and sub-phase 5.2's value-type flag decides nothing here but the `= default!` of a class.

**Types.**  Each property's type is the text sub-phase 5.2 gives, qualified with `global::`, so that a model compiles in any namespace, whatever the user's `using`s and type names.

### Documentation

Every model and every property has XML documentation, through `XmlDocWriter`:

- **The model.**  The query's `-- summary:`, when it has one, then a sentence that names what the model is: the parameters of the query, or a row of the query, with the query's name and its file's name, as the constants' documentation names it; the generator has no project directory, and a full path would make a build depend on where the repository is.  A model that several queries share, below, names each, in the order below, and takes the `-- summary:` of the first.  A table model says it is a row of the table, with its schema, and names the queries that use it the same way.
- **A shared model's properties** take the documentation of the first query's columns or parameters: two queries that share a model may differ in a facet or an origin, which changes no C# and is not a conflict.
- **A property.**  The column or the parameter as the database names it, the database type's `name` as the sidecar spells it, facets included, the origin's `schema.table.column` when the column has one, and whether it is an identity or a computed column when the sidecar says `true`.  The database type and the origin are what the epic says the facets and the origin reach.
- A record documents its properties with `<param>` tags on the type, which the compiler applies to the positional properties.  A class documents each property with `<summary>`.

### One model per full name

From the epic: the generator collects every model every claiming type needs, keyed by full name, and emits each once in its own file; two queries whose models resolve to one full name get one model when their properties' names, types and nullability are identical and their effective model type and sorting are the same, and an error otherwise.  Input and output models alike.

- **The order** of the queries that give one full name is by their files' paths, then by the queries' order in a file, then by the full name of the claiming type, so that one query claimed by two types in one namespace with different model settings has a first and a later.
- **An input model and an output model of one full name**, which equal suffixes or a marker can give, are two models of one name that differ, `SQLSRC257`: an input and an output model are never shared.
- **The error**, `SQLSRC257`, is at the later of the two queries, in that order, at its `-- input-model:` or `-- output-model:` marker when it has one and at its name otherwise, and names the earlier query, and its type when the two are one query.  It names the model, the earlier query and the first difference: a property, its type, its nullability, the model type or the sorting.  The parser gains the position of each of the two markers on `SqlQuery` for it.  When the two differ, the earlier query's model is emitted and the later query has none of that kind.
- **A model's name that cannot be used**, `SQLSRC258` at the query, and the model is not emitted, so that no `CS0101` or warning reaches generated code:
  - its full name is that of a type the compilation declares outside what SqlSource generates, or of an attributed type, which SqlSource generates partly;
  - its full name is a namespace the compilation or another model has, or one of its namespace's parts is the full name of a type of the compilation or of another model: `SqlSourceModelNamespace=MyApp.Queries` beside a class `MyApp.Queries` is `CS0101` either way;
  - its name is lower-case ASCII letters alone, `usersdto`, which is `CS8981`, or a contextual keyword such as `record`.
  The checks against the compilation are one more value-equal step over `CompilationProvider` with the collected full names, which returns the names that are taken, as sub-phase 5.2's lookup of mapped types does, and is empty at once for a project with no model.
- **Two types, one file.**  Two types that claim one file in one namespace produce one `GetUserDto`.  Two types in two namespaces produce two, one in each.
- **A table model and a query's model of one name**, `users` and a query `Users`, both `UsersDto`, are two queries of one name, under the same rule.

### Table models

From the epic: a query whose entry has a `matchesTable` gets a model named after the table instead of after the query, shared by every query that matches that table, unless `no-table-models` is in effect for the query or the query has an `-- output-model:` marker.  Its name is the PascalCase of the table's name, by the rule above, with the schema's PascalCase before it when the schema is not the engine's default, `public` on PostgreSQL, and the output suffix after it: `users` is `UsersDto`, `billing.invoices` is `BillingInvoicesDto`.  No singularising.  Its namespace is the claiming type's unless `SqlSourceModelNamespace` is set.

A table whose name gives no identifier by the rule, a quoted `"order-lines"` for instance, gets no table model: the query's model is named after the query, as under `no-table-models`, and the manual says so.  This is not an error, since the table model is a convenience and the user can do nothing about the table's name but rename it.

A table model is a model like any other under the shared-name rule: two queries that match one table but differ, by a type override that one of them sets for instance, give `SQLSRC257`.

### Emission

The epic's technical note decides the shape: `Collect()` the models every type needs, dedupe them by full name in a `Select`, which is also where `SQLSRC257` and the per-model checks come from, then `SelectMany` back to one node per model, so that an edit to one file re-emits only the models whose shape changed.  Each model's hint name goes through `HintName.FindAmbiguous` together with the types' hint names, since the compiler compares them ignoring case and throws on a clash.  A model's hint name is distinct from any type's by construction, a suffix of its own, so that a model and a type of one full name cannot share a file.

The record a type gives per model holds everything the emitter needs, the properties' names, type texts, nullability and documentation, with value equality; the emitter reads no sidecar and no setting.  The builder designs the steps within that and the caching rules below, and documents them in `docs/architecture/generator.md`, replacing its "Type map and models" placeholder.

**Caching.**  An edit to one `.sql` file, or its sidecar, that changes a model re-emits only that model, and the models of other files that share its name.  A `SelectMany` compares its outputs by position, so a model added or removed re-emits the models after it in the sorted list; that cost is accepted, written in `docs/architecture/generator.md`, and pinned by a caching test so that it is not made worse unseen.  An edit to C# that leaves every attribute alone re-emits no model.  A change to a project property that no model reads, the collection type for instance, re-emits no model.  `CachingTests` pins each.

## Diagnostics

| Id | Severity | Where | About |
|----|----|----|----|
| `SQLSRC251` | Error | The query | Sub-phase 5.2's, extended: a mapped type less accessible than its model |
| `SQLSRC253` | Error | The query | A column with no name |
| `SQLSRC254` | Error | The query | A name that is no identifier after PascalCase |
| `SQLSRC255` | Error | The query | Two columns or parameters that give one property name |
| `SQLSRC256` | Error | The query | A property name that a record, a class or the model's own name takes |
| `SQLSRC257` | Error | The later query's model marker, or its name | Two models of one full name that differ, an input and an output model of one name among them |
| `SQLSRC258` | Error | The query | A model's name that a type or a namespace of the project or another model takes, or that the compiler would warn on |
| `SQLSRC259` | Error | The `-- output-model:` marker | An `-- output-model:` on a query whose entry has no rows, which the parser cannot see; the `-- input-model:` case is already a parse error |

The ids follow sub-phase 5.2's, which end at `SQLSRC252`.  If 5.2 merged with more or fewer, this sub-phase takes the next free ids in this order and the plan says so.

## Calls made in this spec

Not decided with the owner, and open to the review of this spec:

- A class model's non-nullable reference property is initialised with `= default!`, not marked `required`.
- A model shared by two types takes the wider of their accessibilities.
- Property names that differ only by case are a conflict.
- A table whose name gives no identifier falls back to the query's model, with no error.
- An output model with no properties is emitted.
- The `SQLSRC257` order is by file path, then query order, then the claiming type's full name, and the earlier query's model is the one emitted.
- An input and an output model are never shared, so one full name for both is `SQLSRC257`.
- A shared model's documentation is the first query's, and a difference of facet or origin is no conflict.
- A model's documentation names its file by name, not by a path.
- `SQLSRC258` also covers a clash with a namespace and a name the compiler warns on, and `SQLSRC259` an `-- output-model:` on a query with no rows; phase 5's range of ids grows to `SQLSRC259`.
- Adding or removing a model re-emits the models after it, an accepted cost.
- The harness compiles at the highest warning level.
