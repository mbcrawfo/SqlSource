# Query generation, phase 9: research on starting companion tools from a build

Date: 2026-11-02

An appendix of the [phase 9 design](2026-11-02-query-generation-phase-9-build-integration-design.md).  Written before the design, to answer whether a watcher that the build starts in the background is an established and reliable pattern.  It is why the design leaves the watcher for the user to start.  Its findings were gathered from public documentation, source and issue trackers on 2026-11-02 and were not run; the design's sub-phase 9.0 runs the ones it depends on.

Yes, this path is known to be brittle, and its payoff would not arrive anyway. Build tools do auto-start companion processes routinely, and Roslyn's compiler server, MSBuild node reuse, Gradle, Bazel, Nx and sccache all follow one pattern: "connect, else spawn", with an idle timeout, a version key, a kill command and an opt-out. But each of those daemons is a **disposable performance cache whose death costs only time**, and the ones nearest SqlSource's design, schema and SQL code generators, never start a watcher from a build: Prisma, pgtyped and GraphQL Codegen ship `--watch` as an explicit flag, and SQLx's maintainer-proposed daemon has stayed unbuilt since 2021. A detached `describe --watch` launched from MSBuild design-time builds would also run into four documented mechanisms: inherited pipe handles that hang `Exec` on every MSBuild before the 18.6 change wave, design-time builds that fire dozens of times per session and must stay fast, CI runners that either hang on or kill leftover processes, and Windows file locks that block tool updates. The decisive problem comes after the sidecar is written: **Visual Studio and VS Code now default to "Balanced" generator execution, which does not re-run generators when another process changes a file on disk**, and Rider has an open bug for exactly this kind of file. In the default configuration of all three IDEs, saving a `.sql` file would regenerate against the *old* sidecar, show SQLSRC244 "Entry is stale", and leave it there until the next save or build. The robust alternatives give the process's lifetime to the editor or the user, not the build: an explicit watcher with IDE recipes, an IDE extension, or the explicit describe-plus-CI-check model SqlSource already has.

## Every established auto-started daemon is a disposable cache

The .NET SDK itself is the strongest precedent for auto-starting helpers. The Csc task's build client "starts VBCSCompiler.exe and sends it the command line", but Roslyn designs the server so that a failed connection falls back to in-process compilation with no diagnostic, and "it is always safe to kill the compiler server process" ([Roslyn: Compiler Server.md](https://github.com/dotnet/roslyn/blob/main/docs/compilers/Compiler%20Server.md)). Gradle starts or reuses a daemon only on an **exact match of Gradle version, Java version and JVM arguments**, falls back to a single-use daemon on mismatch, and exits after 3 hours idle ([Gradle Daemon docs](https://docs.gradle.org/current/userguide/gradle_daemon.html)). Nx keeps one daemon per workspace, rejects messages stamped with another workspace root, stops after 3 idle hours, and is **disabled by default in CI and Docker containers** ([Nx daemon reference](https://nx.dev/docs/reference/nx-daemon)). Bazel's server defaults to `--max_idle_secs` of 10800 ([Bazel reference](https://bazel.build/versions/8.7.0/reference/command-line-reference)); sccache spawns a server on port 4226 when none answers and honours `SCCACHE_IDLE_TIMEOUT` ([sccache Configuration.md](https://docs.rs/crate/sccache/latest/source/docs/Configuration.md)).

| Daemon | Single-instance key | Idle exit | Kill / opt-out | CI stance |
|---|---|---|---|---|
| Roslyn VBCSCompiler | user + compiler location (unverified formula) | 10 min | `dotnet build-server shutdown`, `UseSharedCompilation=false` | on |
| MSBuild nodes | per build host | — | `/nodeReuse:false`, `MSBUILDDISABLENODEREUSE` | maintainers: "irrelevant on CI" |
| Gradle | version + JVM args | 3 h | `--stop`, `--no-daemon` | on (reversed earlier "off") |
| Nx | workspace root | 3 h | `nx reset`, `NX_DAEMON=false` | **off by default** |
| Bazel | output base | 3 h | `--max_idle_secs` | on |
| sccache | port | configurable | `SCCACHE_IDLE_TIMEOUT` | on, with known breakage |

Even with that design, these daemons generate a long record of failures that were mostly answered "by design" plus an opt-out. dotnet/sdk#9487, "dotnet build leaves running dotnet.exe processes after it finishes", collects random build failures from file locks on Windows, macOS, Linux, TeamCity and GitLab agents; the fixes were opt-outs and wrapper scripts that always shut the servers down, culminating in SDK 7's `--disable-build-servers` ([dotnet/sdk#9487](https://github.com/dotnet/sdk/issues/9487)). An MSBuild maintainer later said node reuse buys "a few hundred milliseconds", is irrelevant in CI, and arguably should have been opt-in ([dotnet/msbuild#1709](https://github.com/dotnet/msbuild/issues/1709)). Under Jenkins, which kills every process a job spawned, an auto-started sccache server shared by parallel jobs is killed under the other job, causing broken builds ([sccache Jenkins.md](https://docs.rs/crate/sccache/latest/source/docs/Jenkins.md)).

The SqlSource watcher differs in kind, not degree. It does not speed anything up; it **writes inputs the generator trusts**. A dead watcher means silently stale sidecars, and a stale one means sidecars written by an old tool version or an old connection string. Neither has a Roslyn-style fallback. The closest precedent for auto-starting a code generator's watcher is a third-party Dart analyzer plugin, `build_runner_hook`, which starts `build_runner watch` from the IDE's analyzer rather than the build, and still needed per-instance owner markers, PID files and a detached cleanup watchdog to avoid orphans ([pub.dev: build_runner_hook](https://pub.dev/packages/build_runner_hook)). No source surfaced any .NET package that spawns a long-lived process from MSBuild; absence is not proof, but SqlSource would be pioneering this.

## MSBuild spawning breaks on pipes, design-time frequency and CI

### Inherited pipe handles hang the build on most shipping MSBuild

`Exec` runs its command through `cmd.exe` or `sh` with no timeout by default ([Exec task docs](https://learn.microsoft.com/en-us/visualstudio/msbuild/exec-task)). Its base class, `ToolTask`, waited with the parameterless `Process.WaitForExit()`, which blocks until **every** write handle to the redirected stdout and stderr pipes closes; a grandchild that inherits them hangs the build until it exits ([dotnet/msbuild PR #13351](https://github.com/dotnet/msbuild/pull/13351)). For a watcher, that is forever. MSBuild merged a fix in March 2026 that waits at most 2 seconds for EOF, gated behind ChangeWave 18.6. That fix crashed STA-thread tasks, was reverted on the vs18.7 and vs18.8 branches, and re-landed in an STA-safe form ([PR #13917](https://github.com/dotnet/msbuild/pull/13917)); an earlier 2024 attempt had already been reverted because `Exec` lost output. The original 2018 report remains open ([dotnet/msbuild#2981](https://github.com/dotnet/msbuild/issues/2981)). No source maps the fix to SDK feature bands, so **every VS 2022 build, every .NET 8–10 SDK before 18.6, and anyone opting out of the change wave gets the hang**. GitLab Runner and Gradle hit the same pattern and fixed it by detaching the child so it inherits no streams ([gitlab-runner MR !4162](https://gitlab.com/gitlab-org/gitlab-runner/-/merge_requests/4162); [Gradle forum](https://discuss.gradle.org/t/bug-in-org-gradle-process-internal-streams-execoutputhandlerunner/2367)).

Detaching cleanly from .NET is harder than it sounds. Before .NET 11 there was "no easy, cross-platform way to start a detached process", and `nohup … &` loses the PID ([dotnet/runtime#124334](https://github.com/dotnet/runtime/issues/124334)). .NET 11 adds `ProcessStartInfo.StartDetached`, which uses `DETACHED_PROCESS` on Windows and `setsid` on Unix and points unset standard handles at the null device ([dotnet/runtime PR #126632](https://github.com/dotnet/runtime/pull/126632)), but its grandchild-survival test is skipped on Windows. Restricting which handles a child inherits, `InheritHandles`, was approved in 2020 and is still unimplemented ([dotnet/runtime#125838](https://github.com/dotnet/runtime/issues/125838)). A tool targeting .NET 10 or earlier therefore needs P/Invoke `CreateProcess` with `bInheritHandles: false`, which is exactly what MSBuild does for its own worker nodes ([NodeLauncher.cs](https://github.com/dotnet/msbuild/blob/main/src/Build/BackEnd/Components/Communications/NodeLauncher.cs)). Whether `cmd /c start /b … >NUL 2>&1` alone avoids the hang on Windows was not verified.

### Design-time builds run constantly and must stay fast

Microsoft's guidance is blunt: targets that don't contribute sources, references or options "should avoid running in DTBs", a slow design-time build lengthens project load, and a failing one breaks IntelliSense with an info bar and files opening as Miscellaneous ([project-system: design-time-builds.md](https://github.com/dotnet/project-system/blob/main/docs/design-time-builds.md)). Design-time builds run at load, on every project-file or `Directory.*` change, on configuration and branch switches, and **once per target framework**. Roslyn's BuildHost, behind VS Code's C# tooling, sets `DesignTimeBuild=true` and `SkipCompilerExecution=true` while still walking `CoreCompile` ([roslyn ProjectBuildManager.cs](https://github.com/dotnet/roslyn/blob/main/src/Workspaces/MSBuild/BuildHost/Build/ProjectBuildManager.cs)), so a target hooked before `CoreCompile` fires there too, by inference dozens to hundreds of times per session in a large solution, often concurrently. Rider is less predictable: its loading builds do not pass `BuildingInsideVisualStudio`, and its docs warn that non-standard targets may not run during loading unless listed in a setting ([Rider: Toolset and Build](https://www.jetbrains.com/help/rider/Settings_Toolset_and_Build.html)). The trigger could fire too often in VS and VS Code and not at all in Rider. C# Dev Kit 11's Build Acceleration also skips MSBuild for unchanged projects ([.NET blog](https://devblogs.microsoft.com/dotnet/faster-lighter-csharp-dev-kit/)), so a watcher that dies after a reboot may not restart until a project changes.

### CI either hangs on the watcher or kills it

The GitHub Actions runner tags job processes with `RUNNER_TRACKING_ID` and kills every tagged orphan at job end ([actions/runner JobExtension.cs](https://github.com/actions/runner/blob/main/src/Runner.Worker/JobExtension.cs)). GitLab jobs "do not complete when dockerd or any process runs in the background" ([gitlab-runner#2880](https://gitlab.com/gitlab-org/gitlab-runner/-/issues/2880)), and Azure Pipelines agents on Linux stall on background children holding step stdio ([azure-pipelines-task-lib#389](https://github.com/Microsoft/azure-pipelines-task-lib/issues/389)). The watcher is useless in CI at best and hangs the job at worst, so it must be off there automatically, as Nx does, not by a user-set environment variable.

### Locks, version skew and orphans follow the watcher home

On Windows a running tool locks its own DLLs; a locked DLL in the tool's package folder has already broken `dotnet tool install` ([dotnet/sdk#26381](https://github.com/dotnet/sdk/issues/26381)), and the MSBuild server's lifetime locks on task and generator assemblies are an open backlog item ([dotnet/msbuild#14289](https://github.com/dotnet/msbuild/issues/14289)). For a local tool, new versions land in new folders, so the sharper hazard is **version skew**: a watcher from the previous tool version keeps writing sidecars after the manifest moves on. SqlSource's tool treats a sidecar written by another tool version as not current, so an old watcher and a new `describe` run would disagree over the same files, and a sidecar format change would reach the new generator in the old format. Lifetime is the other hole: no source shows VS, MSBuild or Rider placing build processes in a kill-on-close job object, and MSBuild's only job-object use passes `createJobObjectForCurrentProcess: false` ([DetouredNodeLauncher.cs](https://github.com/dotnet/msbuild/blob/main/src/Build/BackEnd/Components/Communications/DetouredNodeLauncher.cs)). A detached watcher therefore outlives the IDE unless it polices its own liveness, the Kotlin daemon's known failure ([kotlinlang Slack](https://slack-chats.kotlinlang.org/t/13459054/u0ds33n6s-yes-unfortunately-some-sorts-of-termination-of-the)).

## Default IDE settings would not show the new sidecar

Suppose the watcher works perfectly. The IDE still has to notice. Roslyn's workspace does watch additional files on disk and swaps in new text after a 200 ms batch ([ProjectSystemProject.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/Core/Portable/Workspace/ProjectSystem/ProjectSystemProject.cs)). But in **Balanced** mode, VS's default since late 2024 ([dotnet/roslyn#75152](https://github.com/dotnet/roslyn/issues/75152)), generators re-run only after a build, when the solution finishes loading, on a workspace-status change, or when a buffer open in the editor is saved. The VS source registers no trigger for a disk change ([VisualStudioWorkspaceImpl_SourceGenerators.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/VisualStudio/Core/Def/ProjectSystem/VisualStudioWorkspaceImpl_SourceGenerators.cs)). VS Code switched to Balanced in vscode-csharp 2.122.x, re-running generators on `didSave` and on builds, which the client must trigger itself ([vscode-csharp#8970](https://github.com/dotnet/vscode-csharp/pull/8970); [dotnet/roslyn#82330](https://github.com/dotnet/roslyn/pull/82330)). Rider's RIDER-75959, open since March 2022, is that AdditionalFiles with non-standard extensions don't re-run incremental generators; JetBrains' workaround is an explicit Ctrl+S in the editor ([RIDER-75959](https://youtrack.jetbrains.com/issue/RIDER-75959)).

| IDE (default mode) | Rewritten sidecar re-runs the generator? | What does re-run it |
|---|---|---|
| Visual Studio (Balanced) | No | Build, load, in-editor save (additional files since 17.12) |
| VS Code + C# / Dev Kit (Balanced) | No | `didSave`, build start/end |
| Rider | No (`.sql.json` falls under RIDER-75959) | Rebuild, editor save, "Restart Roslyn Analyzers and Source Generators" |
| VS / VS Code in Automatic mode | Probably, within about a second (unmeasured) | Any text change |

Taken with SqlSource's own staleness check, this produces a concrete and bad user experience. The developer saves `Users.sql` in VS or VS Code. That save is a trigger, so the generator runs at once, against the sidecar the watcher has not rewritten yet. The query's hash no longer matches its entry, so the build shows **SQLSRC244 "The query has changed since its entry was written"**. A moment later the watcher writes the correct sidecar, but nothing re-triggers the generator, and the error persists until the next save or build. The feature would turn every `.sql` save into a false error, which is worse than today's "run describe" workflow. This race is inferred from the trigger list and the generator's documented hash check rather than observed, and the Roslyn team's direction since 2024, cutting background work by tying generators to saves and builds ([roslyn discussion #75048](https://github.com/dotnet/roslyn/discussions/75048)), makes it unlikely to go away.

## Robust on-save designs give the process to the editor

The survey found four established patterns, and none of them is a build-spawned watcher. **Explicit `--watch` started by the user** is the JS norm: GraphQL Codegen recommends composing `generate --watch` with the dev server and made its watcher an optional dependency "to prevent build errors in certain environments" ([GraphQL Codegen workflow](https://the-guild.dev/graphql/codegen/docs/getting-started/development-workflow)), and pgtyped, the closest analogue (DB-connected, SQL in, types out), ships `-w` for local development and one-shot mode for CI ([@pgtyped/cli](https://npmjs.com/package/@pgtyped/cli)). **IDE-owned hooks** tie the process to the editor's lifetime and consent model. A VS Code task with `runOn: "folderOpen"`, `isBackground` and a background problem matcher starts a watcher with the workspace and surfaces its errors in the Problems panel; VS Code deliberately gates it behind workspace trust and a one-time "allow automatic tasks" prompt ([VS Code Tasks](https://code.visualstudio.com/docs/debugtest/tasks)), which is the vendor treating unsolicited background processes as a consent issue. Rider File Watchers run a command per saved file, on save or frame deactivation ([Rider: File Watchers](https://www.jetbrains.com/help/rider/Using_File_Watchers.html)), which maps naturally onto a one-shot `dotnet sqlsource describe <file>`. **Incremental build targets** are the .NET norm: Grpc.Tools runs `protoc` in design-time builds, gated by timestamps, after skipping it caused stale editor errors ([Grpc.Tools implementation_notes.md](https://github.com/grpc/grpc/blob/master/src/csharp/Grpc.Tools/implementation_notes.md)). But `protoc` is a local transform; NSwag's guidance to snapshot a spec rather than fetch it at build time, because live I/O turns "a build which works today" into one that fails tomorrow ([MS Learn: NSwag MSBuild](https://learn.microsoft.com/en-us/previous-versions/visualstudio/visual-studio-2019/msbuild/tutorial-rest-api-client-msbuild)), argues against putting a database round-trip on project load. **Explicit prepare plus a committed cache plus a CI check** is where SQLx and the F# SQL type providers converged after live database access in the compiler proved slow and invisibly stale ([sqlx#1598](https://github.com/launchbadge/sqlx/issues/1598); [SQLProvider docs](https://fsprojects.github.io/SQLProvider/core/general.html)). That is SqlSource's current sidecar model.

A practical sequence follows from the IDE findings. First, ship `describe --watch` as an explicit command and document ready-to-copy recipes: a VS Code `tasks.json` folder-open background task with a problem matcher, a Rider File Watcher or run configuration, and a terminal command for Visual Studio. Second, tell users plainly that in Balanced mode the generated code catches up on their next save or build, or that switching to Automatic gives near-live updates; this is honest about the IDE limits rather than fighting them. Third, if true save-time freshness becomes a priority, the robust form is an **editor extension or language server** that describes the file on save, writes the sidecar, and then triggers regeneration. Roslyn's LSP already exposes a `workspace/_roslyn_refreshSourceGenerators` refresh ([dotnet/roslyn#82330](https://github.com/dotnet/roslyn/pull/82330)), though whether a third-party VS Code extension can invoke it is unverified. That route costs one integration per IDE, but it closes the save race, which no build-spawned process can.

### If the build-spawned watcher ships anyway

Should the team proceed, prior art sets a minimum bar. It should be **opt-in**, not opt-out. Node reuse's maintainers regret making it the default, and an environment variable is a weak switch for IDEs launched from a GUI that never sees the user's shell profile (an inference). It needs **automatic CI and container suppression**, as Nx does. MSBuild should call only a launcher that returns in milliseconds, never fails the build, and spawns the watcher with no inherited handles: `bInheritHandles: false` before .NET 11, `StartDetached` after. Single-instance enforcement belongs in the tool, keyed on the repository root plus tool version plus user, through a lock the OS releases on process death, since PID files lie after reuse. The watcher needs an idle timeout, which the surveyed daemons set between 10 minutes and 3 hours, an exit on tool-version mismatch with the manifest, a `--stop` command in the spirit of `dotnet build-server shutdown`, and a log location users can find. Even meeting all of that, the Balanced-mode race remains: the watcher would make sidecars fresh on disk without making IntelliSense fresh.

## Conclusion

The mainstream evidence on this question is mostly absence, but it points one way. Compile servers prove that build-started processes can be made survivable, at the cost of a decade of "by design" lock and CI issues, and only because their failure mode is "slower". SqlSource's failure mode is "wrong or stale generated code", and the IDE vendors have moved generator execution toward explicit saves and builds, the opposite of reacting to files written by another process. The real obstacle to on-save freshness is not starting a process but **sequencing**: the sidecar must be current before the generator runs, and only something that sees the save before or while the IDE does can guarantee that.

The useful reframe is that SqlSource already has a strong core: hashed, version-stamped sidecars, a stale-entry diagnostic, and a `--check` for CI. The cheapest high-value step is to make the inner loop explicit and well documented, an explicit `--watch` with IDE recipes, and to keep the build free of side effects. Invest in an editor extension only if users show that one save-or-build of lag is a real cost. Before deciding, it is worth measuring two unverified points on the team's own machines: how quickly Automatic mode in VS and VS Code picks up a sidecar rewritten on disk, and whether saving a `.sql` file triggers a design-time build in each IDE.
