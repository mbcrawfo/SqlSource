# TD-0048 Forward Npgsql's Messages by Event Id Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Resolve TD-0048: `NpgsqlRunLogger` forwards a driver message only when its category and event id are on a list of ids read from Npgsql 10.0.3 and known to be safe, so that a message new to a version, and everything of `Npgsql.Exception`, is dropped until someone reads it.

**Architecture:** The levels per category become a list per category of `NpgsqlEventId` constants.  A category is enabled from Debug up when it has a listed id, and never otherwise; `Log` drops an event whose id is not listed for its category before formatting it.  The `exception` member holds the exception's type alone, never its message.  A test pins the Npgsql the list was read from, so that an update fails it until the list is read again.

**Tech Stack:** C# 13, .NET 8 (`src/SqlSource.Tool`), Microsoft.Extensions.Logging, Npgsql 10.0.3, xunit v3, Shouldly.

**Spec:** [`docs/tech-debt/TD-0048-driver-levels-trust-npgsqls-messages.md`](../../tech-debt/TD-0048-driver-levels-trust-npgsqls-messages.md) (Problem and Proposed fix), deleted by this plan.

## Global Constraints

- The log must hold no host, no user, no database's own name, no application name and no password (TD-0048, Problem).
- Npgsql is pinned at `10.0.3` in `Directory.Packages.props`; the list is read from that version's `src/Npgsql/NpgsqlEventId.cs` and `src/Npgsql/LogMessages.cs` (tag `v10.0.3`).
- Keep the three container tests of `tests/SqlSource.Tests.Postgres/Describer/DescribeCommandTests.cs` unchanged: `Describe_WithLog_HoldsDriverEventsAndNoConnectionWord`, `Describe_ConnectionRefusedWithLog_IsSqlsrc224AndNothingPrintedOrLoggedHoldsTheHostOrTheUser`, `Describe_WrongPasswordWithLog_IsSqlsrc224AndNothingPrintedOrLoggedHoldsTheUserOrTheHost`.
- Changes stay in the driver loggers and their docs: td-0034 owns `Redaction`, `SessionRunLog` and `RunTrace`.
- Event shape is unchanged: `postgres.driver` with `category`, `level`, `eventId`, `message`, `exception`, in that order.
- Every commit passes `./pre-commit-validation.sh`; the Postgres describer's project also runs on `SQLSOURCE_TESTS_POSTGRES_IMAGE=postgres:14.24` before a push.

## Where the merged code differs from the item

- The item says `Npgsql.Connection`'s messages at Warning are forwarded and its exception dropped by category.  After this change no category drops by name: every forwarded event writes the exception's type alone.
- Npgsql 10.0.3 writes its messages that are not generated by `LoggerMessage` (`LogWarning(...)`, `LogDebug(...)` called directly) with event id 0.  Id 0 is shared by safe messages (`PostgresDatabaseInfo`'s "Unable to load ... types") and unsafe ones (`KerberosUsernameProvider`'s Debug message quoting the user's principal; `ErrorOrNoticeMessage`'s Warning quoting the server's text under `Npgsql.Exception`), so id 0 is never listed.  The warnings of `PostgresDatabaseInfo` about types it cannot load, forwarded today, are dropped.

## The ids allowed, and why

Read from Npgsql 10.0.3.  An id is listed when its message template holds nothing but the tool's own command text, a fixed text or a number, and the tool can cause it: the describer builds a non-multiplexed data source (`PostgresConnection.BuildSource` refuses multiplexing), runs commands and batches, runs `explain` in a transaction it rolls back, cancels through its token and closes the connection.  It never prepares through Npgsql's `Prepare`, derives parameters, copies, replicates, enlists in `System.Transactions`, waits for notifications or sets a notice handler, so those ids are left out: a reader of a new Npgsql re-reads only what is listed.

| Category | Id | Constant | Level | Message | Why it is safe |
|---|---|---|---|---|---|
| `Npgsql.Command` | 2000 | `ExecutingCommand` | Debug | `Executing command: {CommandText}` / `Executing batch: {BatchCommands}` | The tool's SQL; parameter logging stays off, so the `Parameters` variants never run |
| `Npgsql.Command` | 2001 | `CommandExecutionCompleted` | Information | `Command execution completed (duration={DurationMs}ms): {CommandText}` and the batch form | Same |
| `Npgsql.Command` | 2003 | `ExecutingInternalCommand` | Debug | `Executing internal command: {CommandText}` | Npgsql's own `COMMIT`, `ROLLBACK`, `DEALLOCATE ALL`, savepoint and two-phase commands |
| `Npgsql.Connection` | 2002 | `CancellingCommand` | Debug | `Sending PostgreSQL cancellation...` | Fixed text (written on the connection's logger, not the command's) |
| `Npgsql.Connection` | 1903 | `ExceptionWhenClosingPhysicalConnection` | Warning | `Exception while closing connector` | Fixed text; forwarded today |
| `Npgsql.Transaction` | 30000 | `StartedTransaction` | Debug | `Starting transaction` | Fixed text |
| `Npgsql.Transaction` | 30001 | `CommittedTransaction` | Debug | `Committed transaction` | Fixed text |
| `Npgsql.Transaction` | 30002 | `RolledBackTransaction` | Debug | `Rolled back transaction` | Fixed text |
| `Npgsql.Transaction` | 30200 | `ExceptionDuringTransactionDispose` | Error | `Exception while disposing transaction` | Fixed text |

Left out on purpose, at Debug or above in 10.0.3:

- `Npgsql.Connection` 1001 `OpenedConnection`, 1004 `ClosedConnection`, 1111 `OpenedPhysicalConnection`, 1113 `ClosedPhysicalConnection`: name `{Host}:{Port}/{Database}`.
- `Npgsql.Connection` 1301 `ReceivedNotice`: the server's notice text, which can name a role or a database.
- `Npgsql.Exception`: every message is id 0 (`Non-numeric position in ErrorResponse: ...`, the server's text).  None is listed, so the category is never enabled.
- Everything at id 0, as above; ids of features the tool does not use (1300, 1500, 1901, 1902, 1904, 2100-2103, 2500, 2600, 30100-30102, 31000-31010, 40000-40102, 50000-50004, 50103).
- Trace is never forwarded, as today.

The exception of a listed event is written as its type alone: its message is the server's or the socket's text (a `PostgresException` quotes the server, which can name a role or a database), which nobody has read.

## SqlClient's forwarding (phase 6.2)

`SqlClientRunListener` does not trust SqlClient the same way: it is already an allowlist by event name (`BeginExecute`, `EndExecute`) and by payload member (`objectId`, `commandText`, `compositestate`, `sqlExceptionNumber`), and writes no free-form `message`, no `dataSource` and no `database`.  `commandText` is the tool's own text.  A message a later SqlClient adds is dropped.  Nothing to change.

## Review Focus

1. A listed id written on another category than the one listed (Npgsql moves `CancellingCommand`'s logger) is dropped, not forwarded.
2. Id 0 at Warning or above on any category is dropped.
3. An exception whose message names an endpoint on a listed id writes only the type.
4. `IsEnabled` is false for `Npgsql.Exception` and an unknown category at every level, so Npgsql does not build their messages.
5. A Npgsql update fails a test until the list is read again.
