# TD-0051 scans Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove a column of no origin not null through a `Subquery Scan`, a `CTE Scan` and a `UNION`'s `*SELECT* <k>` scan, without ever placing the column by position or by name.

**Architecture:** The plan does not say which entry of the scanned plan a scan's column is, so the walk asks of every entry it could be.  The column is proved when at least one entry is proved of a type that carries to the column's and every other entry is proved too or cannot be the column by its type.  A new call, `casts`, confirms that no cast joins two families of `SetOperationTypes`, and is asked only when that fact changes an answer.

**Tech Stack:** C#, .NET 8, PostgreSQL 14 to 18, xunit, Shouldly.

**Spec:** `docs/tech-debt/TD-0051-columns-that-cannot-be-null-are-answered-nullable.md`

## Global Constraints

- A false non-null is the worst outcome: a kind that cannot be proved stays unproved and the item says so.
- Lower `Budgets` in `RealisticNullabilityNoiseTests` in the commit that proves each kind, on 14 and 18.
- `casts` is a new call of `PostgresCallNames`, carried through capture, replay, renaming, events and `tools/record-fixtures.sh postgres`.
- The SQL of the call writes every type and operator with `pg_catalog.`, and pairs its arrays with `ROWS FROM`.
- `td-0051-rest` follows: change only this unit's bullets of TD-0051.

## Where the spec and the code differ

- The spec names the subquery's column names from the server as the missing fact.  No catalog function or `EXPLAIN` option gives them.  `debug_print_parse` and `debug_print_plan` do, but they write the query's tree to the server's log, so the describer does not use them.
- So a recursive CTE stays unproved: `id` and `depth` share a type with the nullable `parent_id`, and `path` is computed from a work-table column whose type the plan does not show.  13 of the 17 columns are in reach.

## Review Focus

- An inlined SQL function hides an assignment cast to a text type, so a nullable `integer` can be a `text` column of the scan: no entry is ruled out for a column of the text family.
- A user's `CREATE CAST` between two families: the `casts` answer turns the type rule off.
- A domain's column, whose type the row description gives as its base: it is in no family and is never ruled out.
- A scan that a join null-extends, and a plain aggregate over no rows: neither is proved.
- A placeholder `NULL::type` for an unused column of the column's family: it blocks the proof.
