# TD-0053 PR 2, the plan walk - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Spell every node type, relationship, join type and set-operation command of the walk once, give each tree helper one definition, build `PlanInstances` once per walk, and drop the members only tests use, with no answer and no logged text changed.

**Architecture:** Constants in one new file of `Walk/`, the tree helpers as members of `PlanNode`, the relation-name sort in `PlanRelations`, and the per-walk cache of `PlanInstances` as its own type that `PostgresSession.WalkAsync` builds and hands to `MayAnswerFromBranches` and `Run`.

**Tech Stack:** C# (.NET), xUnit, Shouldly.

**Spec:** `docs/superpowers/specs/2026-10-17-td-0053-2-plan-walk-design.md`, under the overview `docs/superpowers/specs/2026-10-17-td-0053-postgresql-describer-patterns-design.md`.

## Global Constraints

- No fixture, `capture.json`, `expected.json` or `expected-pg*.txt` changes; nothing is re-recorded.
- The text of every log event stays as it is: `nullExtends` is `inner`, `outer`, `both` or `none`.
- The node-type sets keep their purposes: `PlanInstances`' set-operation set holds `Recursive Union`, `ReachesSetOperation` does not.
- The constants are `const string`, since patterns match them.
- Join type `Inner` and relationship `Inner` are different constants.
- `PlanPartitions.WithoutAlias` and its scanner `Closing` are PR 1's: not touched.
- `PostgresSession` changes only to wire the cache; `PostgresEvents` only at the `nullExtends` member.
- Every commit passes `./pre-commit-validation.sh`; the container tests also pass with `SQLSOURCE_TESTS_POSTGRES_IMAGE=postgres:14.24`.

## Review Focus

- A `Recursive Union` root: `MayAnswerFromBranches` stays false for it (existing `NullabilityWalkSetOperationTests` and the container tests pin the answers).
- A node built with `with { NodeType = … }`: `SubqueryChild` and `JoinChildren` are computed on read, so a copy never carries a stale child (Task 2's tests build nodes with `with`).
- A join type the walk does not know: `ExtendsOf` is null, the node logs `none` and the plan's reason is `unknown-join-type` (existing `PlanInstancesTests`).
- A walk whose `partitions` was not asked: the cache treats it as no partition, as `NoPartitions` does today (`PlanInstancesCacheTests.Of_PartitionsNotAsked_ReadsAnAppendAsASetOperation`).
- A scope whose `ColumnTypes` is empty: no column is answered from a set operation's branches (Task 6 moves the tests that left it out to `[]`).
