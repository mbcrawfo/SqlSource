## Sorting

Each hit goes in one of four kinds:

- **A, a step or assertion for some rows only:** the branch adds, drops or swaps an arrangement step, an action or an assertion for some rows, or picks which of two different checks a row gets.  This includes a `switch` or `?:` that picks between two different calls (`flag ? RunSqlServer() : Run()`) or two assertions.
- **B, an input the row gives:** a branch that only supplies an input when the row gives one (writes a file, sets a variable or a setting), or picks how or where the row's input is supplied (a `.env` file or the environment, which file holds the error), and every row then runs the same steps and assertions.
- **C, one rule over data:** a `?:`, `switch` expression or `if` that only derives a value, an expected one or one passed to the same call, as `nullable is null ? … : …`; the rows share their calls and assertions.  These are counted for the closing bullet, not listed.  A theory listed today that is of this kind leaves the list.
- **D, not a branch on the row:** a loop condition, a run-once guard every row hits the same way, a branch on an observed result rather than the row, a false match of the scan.

## Review Focus

- A theory listed today that the scan no longer finds (renamed, split or folded by phases 19-22): it must leave the list, not stay by inertia.
- A branch hidden behind a local assigned from a parameter (`var x = row.Kind == …; if (x)`): the scan follows such locals three assignments deep.
- A `switch` expression over a parameter that picks the action, not just a value: kind A, not C.
- The PostgreSQL and Npgsql 8 copies of the same theory: both are listed, under one entry if their shape is the same.
- An entry that names its branching parameter in parentheses, as the list does today, keeps doing so.
