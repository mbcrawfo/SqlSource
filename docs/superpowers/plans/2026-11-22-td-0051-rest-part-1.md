# TD-0051 rest, part 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove four more kinds of PostgreSQL column not null from what the plan already prints: an uncorrelated scalar subquery, an aggregate whose `GROUP BY` the `WHERE` fixes, the `FULL JOIN` forms the walk does not place, and a set operation's expression branch.

**Architecture:** Each kind widens one reading of `NullabilityWalk` and `PlanExpression`.  No call is added and no request changes, so captures replay as they are.

**Tech Stack:** C#, .NET 8, PostgreSQL 14 to 18, xunit, Shouldly.

**Spec:** `docs/tech-debt/TD-0051-columns-that-cannot-be-null-are-answered-nullable.md`

## Global Constraints

- A false non-null is the worst outcome: a form that cannot be proved stays unproved, and the item says so.
- A form is pinned in `PlanOutputTests`, as 14 and 18 print it, before it is read.
- Every new proof has queries that try to break it, run on a real server over rows holding `NULL`.
- Part 2 and part 3 follow in this branch's later PRs: change only this part's bullets of TD-0051.

## Where the spec and the code differ

- PostgreSQL 14 to 16 print an `InitPlan`'s value as `$k`, the same text as the statement's parameter `$k`.  So on those majors `$k` is read as an `InitPlan`'s value only when `k` is above the statement's parameter count.
- An `InitPlan` prints `EXISTS` and `ARRAY` as `(InitPlan n).col1` too, from 17 as well.  The column's type tells them apart, as for a scalar `SubPlan`: a boolean or an array is in no family.
- The spec says PostgreSQL 18 drops a fixed `GROUP BY` column from the key.  Measured, 16, 17 and 18 do, and 14 and 15 keep it.
- The spec allows a `Hashed` `Aggregate` with no key.  None was produced on 14 to 18, so only `Sorted` is read.  `planner.c` of 14 to 18 writes `parse->groupClause ? AGG_SORTED : AGG_PLAIN`, and `nodeAgg.c` returns no row for no input unless the strategy is `AGG_PLAIN`.

## Review Focus

- A statement parameter `$1` beside an `InitPlan` that returns `$1` on 14 to 16: it stays unproved.
- An `InitPlan` under the side a join extends: `($0)` at the root stays unproved.
- A `HAVING` or a `LIMIT` on the subquery, which may return no row: it stays unproved.
- A `FULL JOIN` under another join that extends it, and a reference that a join under its side extends: both stay unproved.
- A `GROUP BY ()` and a plain aggregate over no rows, which return one row of `NULL`: both stay unproved.
