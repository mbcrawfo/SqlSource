# TD-0079 items 1, 10 and 11 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove three duplications from the generator's planners: a type's usable queries are worked out in one place (item 1), a file's engine is found one way (item 10), and the method planner passes a query's context as one value instead of long lists (item 11), with no change to what is generated.

**Architecture:** A new `Generation/UsableQueries.cs` owns `FindUsableFiles` (moved from `TypeEmitter`) and `Of(TypeQueries, diagnostics)`, which yields each query of the usable files with its indices and settings; `TypeEmitter`, `TypeModels` and `MethodPlanner` call it, and the models' index-and-name match becomes `FileModels.Find`.  `MethodPlanner` uses `SqlDescribableDialects.EngineOf` alone, maps it with `DatabaseEngine.ToCodeGenEngines()` and asks `MethodDrivers.Allows(engine)`.  A private `QueryContext` carries a query's values through `MethodPlanner`, and a new `ConversionContext` is passed whole to `ConversionPlanner.Plan`.

**Tech Stack:** C# (`netstandard2.0` generator, `LangVersion` preview), xUnit v3 + Shouldly.

**Spec:** `docs/tech-debt/TD-0079-duplicated-logic-and-uneven-conventions-in-src.md`, items 1, 10 and 11 and their Proposed fix.

## Where the code differs from the spec

- **Item 10, non-describable dialects.**  `MethodPlanner.EngineOf` gives `CodeGenEngines.None` for a dialect that is neither `postgres` nor `mssql`, while `SqlDescribableDialects.EngineOf` gives PostgreSQL for every dialect but `mssql`.  Mapping the latter straight to `CodeGenEngines` would add PostgreSQL to `CodeGenEngines` for an `ansi` file whose output is `codegen` (the default) and report a new `SQLSRC273`.  Such a file never has models (`SidecarChecker` gives it `SQLSRC209` and no usable entry), so the planner skips a file whose dialect `SqlDescribableDialects.Contains` rejects, before its engine is counted; a new test pins that no `SQLSRC273` appears.
- **Item 10, `CodeGenEngines.Of`.**  A C# enum cannot have a static method, so the mapping is the extension method `DatabaseEngine.ToCodeGenEngines()` rather than `CodeGenEngines.Of(DatabaseEngine)`.
- **Item 10, `QueryTyper`.**  `QueryTyper` picks a map by the sidecar type's class because a type of an engine this version does not know has no map; that is a question about the type, not the file, and the Proposed fix does not name it.  It stays.
- **Item 1, `TypeModels`.**  `TypeModels.Of` loops over a file's models and resolves settings only for queries that have them; after the change it loops over the usable queries and finds each one's models with `FileModels.Find`, resolving settings for every query of a usable file.  `QuerySettings` is a `readonly record struct`, so the extra resolves allocate nothing; the order of the requests is the same, since models are in query order.

## Review Focus

- A file with a non-describable dialect and output `codegen` (the default) in a project without Npgsql: only `SQLSRC209`, never `SQLSRC273` (Task 2 test).
- A file left out of a type (`SQLSRC008`, `SQLSRC009`, a kept-form error) gives that type no member, no model request and no method, and its diagnostics are reported once, by the type's file (existing tests; Task 1's `UsableQueries` tests pin the left-out file's queries are absent).
- A model whose index matches a query but whose name does not is skipped, never thrown on (Task 1 test of `FileModels.Find`).
- A query whose driver is missing is planned (its name counts) but gets no converter decided and no method (existing `MethodDriverTests`).
- Two types claiming one file still report each method problem once (existing tests).
