# Query generation, phase 5.2: the PostgreSQL type map and the type override - implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each parameter and column of a usable PostgreSQL sidecar entry gets its C# type, from the base map under the referenced Npgsql and from the user's type override, with the diagnostics `SQLSRC246` to `SQLSRC252`.  No model is emitted.

**Architecture:** A pure base map in `Generation/Types/` turns a `PostgresType` into a `TypeMapping` under one of three driver columns, which a probe of the compilation chooses.  The override is a new setting, `EquatableArray<TypeOverride>` on `SettingsLevel`, read by one grammar in `Settings/` from MSBuild values and from `-- type-override:` markers, and merged per key.  One step resolves the C# types that any level names against the compilation into value-equal `MappedType` records; one node per claimed file then types each usable entry's parameters and columns, override first, base map second.

**Tech Stack:** C# on `netstandard2.0`, Roslyn incremental generators pinned to 4.8.0, xunit v3 with Shouldly, MSBuild props and targets, `PackageDownload` for the Npgsql assemblies the tests reference.

**Spec:** [`docs/superpowers/specs/2026-10-18-query-generation-phase-5-2-type-map-design.md`](../specs/2026-10-18-query-generation-phase-5-2-type-map-design.md).  Read it with this plan: its base map table, its grammar, its "Calls made" and the owner's settled decisions bind every task.  The map's rows are copied from the spec's table, never from memory.

## What 5.1 built, and where this plan follows it

5.1 merged as its spec said in every point this sub-phase touches: its ids end at `SQLSRC245`, so this sub-phase takes `SQLSRC246` to `SQLSRC252` exactly as its spec assigns.  The names this plan builds on are the merged code's: `SidecarCheckResult.UsableEntries`, the per-file `SidecarCheck` step, `FileNeeds`, `SidecarNeeds`, `TrackingNames`, `MSBuildSettings.SettingKeys`.  Where the plan departs from the spec's wording, it says so:

- **Where the query's types are reported.**  The spec says "from the per-file output of sub-phase 5.1, once per file".  5.1's output is a `RegisterSourceOutput` over the per-file `SidecarCheck` node.  The types are a new per-file node after it, `FileTypes`, with its own per-file output beside 5.1's: still once per file, and 5.1's checks are not re-reported when only a type changes.
- **The order of the diagnostics across commits.**  `SQLSRC247` and `SQLSRC248` arrive with the probe (Task 2); `SQLSRC250` to `SQLSRC252` with the resolution (Task 4); `SQLSRC246` and `SQLSRC249`, which are at the query, with the types of a query (Task 5), together with the probe tests that need them.
- **An open generic** cannot be written in the spec's grammar, whose `<>` needs an argument: `System.Collections.Generic.List<>` is an invalid value, `SQLSRC014` or `SQLSRC111`.  The resolver still gives `NotAPropertyType` for an unbound generic, which nothing can reach, and `MappedTypeTests` tests the grammar's refusal for that row.
- **The place that wrote a mapping**, which `SQLSRC250` names, is carried on each entry as a `SettingPlace`, which `ISettingSource` gains.
