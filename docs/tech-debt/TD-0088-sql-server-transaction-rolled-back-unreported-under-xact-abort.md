# TD-0088: on SQL Server under `XACT_ABORT ON`, an unreported error rolls back the caller's transaction silently

## Problem

On SQL Server, two errors reach no caller of a generated method that reads rows, as [`QueryMethodWriter`](../../src/SqlSource/Generation/Emitting/QueryMethodWriter.cs) writes it: an error that a statement after the first result set raises, which every method that reads rows loses ([TD-0085](TD-0085-sql-server-error-after-the-first-result-set-is-lost.md)), and an error that the server raises for a row that a streaming loop left unread, which SqlClient's disposal of the reader drops where Npgsql's throws it ([TD-0087](TD-0087-drained-rows-error-replaces-the-loop-bodys-exception.md)).  With `XACT_ABORT` off, as SqlClient leaves it, such an error ends its statement or its batch and the caller's transaction stays open.  Under `SET XACT_ABORT ON`, which many applications set, the error rolls the transaction back, and still nothing is thrown.  The `SqlTransaction` is then completed: its `Connection` is null after the method, a later command given it runs in autocommit, outside any transaction, with no error, and only `Commit` throws `InvalidOperationException`, "This SqlTransaction has completed; it is no longer usable.".  What the transaction did before the method is lost, and what it did after is committed statement by statement.

[`XactAbortTransaction`](../../tests/SqlSource.Tests.SqlServer/EndToEnd/XactAbortTransaction.cs) pins it on a connection that is not pooled: it makes `#outside` before it sets `XACT_ABORT ON`, begins a transaction and writes 7, and after the method holds that `Connection` is null, that a write of 8 given the transaction succeeds, that `CommitAsync` throws, and that `#outside` holds 8 alone.  [`StreamingQueryTests`](../../tests/SqlSource.Tests.SqlServer/EndToEnd/StreamingQueryTests.cs)' `StreamNumbersFailingHalfway_BreakInATransactionUnderXactAbort_RollsItBackUnreported` holds it for a `break` at row 10 of `StreamNumbersFailingHalfway`, and `StreamThenRaise_ErrorAfterTheRowsInATransactionUnderXactAbort_RollsItBackUnreported` for the `THROW` after the rows of `StreamThenRaise`.  [`MethodShapeTests`](../../tests/SqlSource.Tests.SqlServer/EndToEnd/MethodShapeTests.cs)' `ListThenRaise_ErrorAfterTheRowsInATransactionUnderXactAbort_RollsItBackUnreported` holds it for the same batch read into an array.  With `XACT_ABORT` off, `StreamNumbersFailingHalfway_BreakInATransaction_TheTransactionCommits` and `StreamThenRaise_ErrorAfterTheRowsInATransaction_TheTransactionCommits` hold that the transaction commits.  The three tests under `XACT_ABORT ON` are the cases that flip when the fix lands.

## Why it exists

A branch review found it, by a reproduction through the generated methods on SQL Server 2025, after the errors themselves were recorded as lost.  The owner chose to document it in the branch that found it, and to leave the methods as they are until the detection below, or the fix of TD-0085, is designed for every method that reads rows.

## Impact

Medium.  It needs `XACT_ABORT ON`, a transaction given to the method, and an error that SqlClient does not report: a query whose statement after its rows can fail, or a streaming loop that stops early over rows that can fail.  When it happens, it is a silent loss of data until the commit: the caller's later commands commit on their own, outside the transaction it believes it holds, and the commit's `InvalidOperationException` says nothing of the error that caused it.  The manual documents it, with its remedy, as a known issue of `docs/manual/sqlserver.md` and `docs/manual/settings.md`.

## Proposed fix

Detect the rollback in every method that reads rows, buffered and streaming, on SQL Server: after the reader is disposed, when a transaction was given and its `Connection` is null, throw an exception that says the transaction was rolled back by an error the query raised after the rows it read.  A buffered method checks after its `await using` of the reader ends; a streaming method checks after the last row and in the `finally` that a `break`, a throw or a disposal runs, and must decide, as TD-0087 does for PostgreSQL, whether an exception thrown there may replace one that the loop's body threw.  The check costs one property read and allocates nothing, which both engines' `AllocationTests` should confirm.  Flip the three tests above, and rewrite the account of the error in the streaming rows of `docs/manual/settings.md`, in the method results of `docs/manual/sqlserver.md`, and their known issues.  If TD-0085 is fixed first, by draining the later results with `NextResultAsync`, the error after the rows is thrown and only the drained rows of a streaming loop still need the check.

## Trigger

A user's report of a transaction rolled back with no error, or the fix of TD-0085 or TD-0087, which changes the same code.
