# TD-0044 - Small gaps of the PostgreSQL describer's columns

## Problem

Six things that the PostgreSQL describer records of a column are less than the server knows, or more than it promises:

- **The modifier of a type outside `pg_catalog`.**  [`ColumnFacets`](../../src/SqlSource.Tool/Describing/Postgres/ColumnFacets.cs) reads a modifier for the ten built-in types that carry one, by internal name.  A type of an extension has its own: PostGIS's `geometry(Point,4326)` is recorded as `public.geometry`, with no facet.
- **The facets of an array's element.**  A column of `character varying(10)[]` is recorded as `character varying[]`, and its `element` has no `length`.  Npgsql gives the array the numbers of its element, and the describer drops them.
- **The fields of an interval.**  `interval year to month` is recorded as `interval`, and `interval day to second(3)` as `interval(3)`.  Npgsql gives an interval's precision and nothing of its fields.
- **A foreign table says `view`.**  PostgreSQL does not enforce the constraints of a foreign table, whose `attnotnull` is a declaration about the remote, so [`ColumnNullability`](../../src/SqlSource.Tool/Describing/Postgres/ColumnNullability.cs) answers `null` for its columns, with the source `view` for want of a word of its own.
- **A domain's own modifier, for a parameter.**  A column of `email_t`, a domain over `varchar(254)`, is recorded with a `base` of `character varying(254)`, and a parameter of `email_t` with a `base` of `character varying`, with no length.  A column's facets come from the row description, which gives a domain column the domain's modifier; a parameter has no row description, and `types` does not read `pg_type.typtypmod`.
- **The gate rests on the tool's lexer agreeing with the server's.**  [`OuterJoinGate`](../../src/SqlSource.Tool/Describing/Postgres/OuterJoinGate.cs) searches the `Text` lexemes of the tool's lexer.  `SELECT o.total AS §$x$ FROM users u LEFT JOIN orders o ON o.user_id = u.id --$x$` is, to the tool, a dollar-quoted string from `$x$` to `$x$`, so no `LEFT` stands in a `Text` lexeme and the query is not gated; to the server it is an alias, a left join and a comment, the `PREPARE` succeeds, and the check agrees, since Npgsql reads as the server does.  So `total` would be `false` with `catalog`.  It needs a character that is no letter to the lexer directly before a `$tag$`.

## Why it exists

The first three: Npgsql does not expose a column's raw type modifier, only `ColumnSize`, `NumericPrecision` and `NumericScale`, which are the modifier decoded for the types Npgsql knows.  The row description holds the modifier of every column, an expression's included, and Npgsql keeps it in `FieldDescription.TypeModifier`, a public property that no public member leads to: the way to it is `NpgsqlDataReader.RowDescription`, an internal field.  The spec of sub-phase 3.3 chose the three numbers over a second describe with `KeyInfo`, which costs a query of `pg_attribute` for each query described.  The sidecar's format is not what is short, for these three and for the fifth: the [format design](../superpowers/specs/2026-10-07-sidecar-format-design.md) defines the `name` of a type as the type as the engine spells it, facets included, and PostgreSQL spells a type with its modifier as `format_type(oid, typmod)` does, `interval year to month`, `geometry(Point,4326)`, `character varying(10)[]`.  So a `name` of `interval` for such a column is the describer short of the format, and no gap of the format.  The fourth: the sidecar format's provenance values have none for a foreign table, and a new value is a change of the format.  The fifth: a parameter has no facets, since the protocol gives it an OID and no modifier, and `types` reads no `typtypmod`; a column has the domain's modifier only because Npgsql's numbers come from its row description.  The sixth: the gate was specified over the lexer's lexemes, so that a string and a comment do not count, and the query that breaks it is contrived.

## Impact

Low.  The describer is registered nowhere until sub-phase 3.6.  The first three lose detail that no planned reader needs as data: the generator's type map is keyed by `internalName`, a `geometry` is read as one whatever its modifier, a C# type has no length, the table match of sub-phase 3.4 compares no type, and a parameter has no modifier at all.  What is lost is a spelling, and several want it: phase 5 writes the database type of each member into a model's documentation; `describe --check` compares `name` as text ([`SidecarComparer`](../../src/SqlSource/Snapshot/SidecarComparer.cs)), so a column whose SRID changed passes it today; and a person reads the sidecar in review.  A tool that would compare a sidecar with a schema wants it too.  The fourth gives a foreign table's column the right answer, unknown, under a word that is not quite true.  The fifth loses the length that a domain gives a parameter, which a generated model does not read; it makes a parameter and a column of one domain differ in the sidecar.  The sixth needs a query written to be misread, which no one writes by accident; its price is a `NOT NULL` column of a left join recorded as not nullable.

One gap outlives the fix below, whatever shape the modifier is kept in: a column without an origin, of an interval with fields or of an extension's type.  Npgsql's public surface holds no modifier, so a cast from another type, a `COALESCE` or a `CASE` of such a type is recorded as today, `'1 day'::interval day to second(3)` as `interval(3)`.  Few columns are of this kind: a function's result has no modifier, and a cast to a column's own type keeps the column's origin.  Such a column and a table's column of the same type then differ in `name`, as `varchar(50)` and `varchar(100)` do today, which matters only to what compares the types of two queries.

## Proposed fix

For the first three and the fifth, the sidecar's schema does not change.  The modifier's spelling belongs in `name`, in two steps that each stand alone.  Nothing may parse `name`: the [epic outline](../superpowers/specs/2026-10-07-query-generation-epic-design.md) holds that the generator never parses a type name.

- **Step A, the second item, with what the describer holds.**  `ColumnFacets.Of` reads Npgsql's three numbers by the internal name of the reported type, so an array has none.  Read them by the element's internal name and give them to the `element` that `PostgresTypes.Build` makes: its `length`, `precision` and `scale` are set, and the array is spelled `character varying(10)[]`.  No SQL and no record of a call changes.  It settles the second item for the ten built-in types, for a column with an origin and for one without.
- **Step B, the first, the third and the fifth, from the catalog.**  `tables` reads `a.atttypmod` and `pg_catalog.format_type(a.atttypid, a.atttypmod)` into two members of `PostgresAttributeRow`, and `types` reads `t.typtypmod` and `pg_catalog.format_type(t.typbasetype, t.typtypmod)` into two of `PostgresTypeRow`.  Each member is nullable, as the rule of an answer's record asks, and null means what a capture recorded before it means: spell as today.  A column with an origin is then spelled from its attribute.  A type of `pg_catalog` takes the server's spelling, which the container tests already hold the tool's own to.  A type of another schema keeps the tool's `schema.name`, since `format_type` qualifies a type by the session's `search_path`, and gains the modifier's text: what `format_type(oid, typmod)` holds after `format_type(oid, -1)`, and for an array the same against its element's, before the `[]`.  That rule of the tail is wrong for `bit`, `character` and the time types, whose spelling `format_type` builds itself, and those are of `pg_catalog`.  A domain's `base` is built with `typtypmod` wherever the domain is built, a parameter included.  A parameter has none of Npgsql's numbers, so the facets of a built-in base are decoded from the number: the length of a `varchar` and a `bpchar` is the number less four; the length of a `bit` and a `varbit` and the precision of a time type are the number; of a `numeric`, the number less four holds the precision in its high sixteen bits and the scale in its low eleven, signed; the precision of an `interval` is the low sixteen bits, and 65535 is none.  It settles the first and the third for a column with an origin, the second for an element of an extension's type, and the fifth for a parameter and for a base of an extension's type.

A type with a modifier of its own needs no extension in the fixture schema: a base type whose input and output are `LANGUAGE internal` functions over `varcharin` and `varcharout`, with `TYPMOD_IN = varchartypmodin` and `TYPMOD_OUT = varchartypmodout`, is spelled `tagged(7)` on a plain `postgres` image.  A change to `postgres/schema.sql` moves the OIDs that the captures hold, and every case is recorded again.

The gap of a column without an origin closes only with the modifier of the row description: through Npgsql's internal field, or through a public member that Npgsql would have to add.  One query then spells any list of pairs, `format_type(o, m)` over `unnest` of the OIDs and the modifiers.

A typed member is the next step only when a reader needs the modifier as data, and it is additive whenever it comes, since a reader ignores a key it does not know: `modifier` on the PostgreSQL type, holding the type's own text of its modifier, `(Point,4326)`.  The plausible reader is phase 7's NetTopologySuite map, should it want a `Point` for a `geometry(Point,4326)` column, which Npgsql reports as a `Geometry`; a comparison of a sidecar with a schema can compare `name`.  Three other shapes were set aside.  A general map of keys, an `srid` and the like, needs a table of each extension's modifier in the tool to fill it, and a reader for keys it cannot list.  The raw number is read by no person, and by no program without the type's own decoder, which for an extension would live in the generator.  A second name for display alone leaves `name` to the driver, and `name` is the display member by the format's definition: the second member that is wanted is the one to bind by, which [TD-0045](TD-0045-the-check-against-npgsql-is-best-effort.md) records.

Verified on PostgreSQL 18 with PostGIS 3.6, on 18.4 and on 14.24, through `psql` and Npgsql 10.0.3: the catalog's numbers and spellings, for a table and a view; the modifier in the row description of an expression; that the server drops a modifier a parameter is declared with; Npgsql's members and their visibility, which are the same in 11.0.0-preview.1; the rule of the tail; the decoding, against the numbers the catalog gave; and the type made without an extension.  Not verified: an extension other than PostGIS, pgvector for one; that a column with an origin has its attribute's modifier under every plan, which was seen for a table, a view, a CTE, a subquery and a cast to the column's own type; and what `format_type` writes for a type of `pg_catalog` that another type hides on the `search_path`.

For the fourth, add a provenance value, `foreign-table`, to the format's list, which a reader keeps when it does not know it.  For the sixth, ask for the plan of every query with rows and not of the gated ones alone, since the walk of sub-phase 3.5 reads the server's own plan but is asked for only a query that the gate lets through, or let the lexer read an identifier as the server does ([TD-0004](TD-0004-lexer-misreads-dialect-specific-sql.md)).

## Trigger

For the first three and the fifth: after sub-phase 3.4 and before sub-phase 3.6.  Sub-phase 3.4 reads the answer of `tables` for the table match and records every fixture with rows again, so the two steps ride on its recording.  Sub-phase 3.6 registers the describer: until then no sidecar exists outside this repository, and after it a `name` that says more is a difference in every sidecar with such a column, and one failure of `describe --check` until the query is described again.  Past that, a user who needs the modifier of an extension's type, an array's element or a domain's parameter in the sidecar.  For the typed member, a reader that needs the modifier as data.
