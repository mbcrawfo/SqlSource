# TD-0045 - The check against Npgsql is best effort, and some types cannot be bound

## Problem

The PostgreSQL describer prepares a query with `$n` where SqlSource's lexer found a parameter, and then asks Npgsql to describe the SQL as written, to prove that Npgsql finds the same parameters ([`NpgsqlCheck`](../../src/SqlSource.Tool/Describing/Postgres/NpgsqlCheck.cs), [`PostgresLive.CheckAsync`](../../src/SqlSource.Tool/Describing/Postgres/PostgresLive.cs)).  It compares the columns of the two results.  Seven things about it are not whole:

- **A disagreement that leaves the columns alone passes.**  If the two read a `@` differently inside a predicate, and the server accepts both readings, the result has the same columns and the check says `same`.
- **Npgsql's `:name` form.**  Npgsql reads `:id` as a parameter when the command has one of that name, and SqlSource does not read the form.  A query that writes both `@id` and `:id` for one parameter is one SqlSource prepares as a syntax error, `SQLSRC225`, so the check never sees it; it is listed because the two readers differ there and nothing but the server's refusal covers it.
- **An array of a domain that is returned.**  Npgsql sends a parameter of `email_t[]` as `character varying[]`, and the server keeps the domain.  `SELECT @p AS p` is `SQLSRC231`, rightly, with a help line that speaks of a `@`.
- **An error of `check` that is no disagreement reads as one.**  The spec says an error of `check` is `SQLSRC231`, so a connection lost, or a table dropped, between `types` and `check` is reported as "Npgsql reads the parameters ... differently", with the help about a `@`.
- **Several kinds of type cannot be bound by their spelled name**, and a query with such a parameter is `SQLSRC232`: a type whose name or schema needs quotes, since Npgsql takes `My Schema.Status` and not `"My Schema"."Status"`; `"char"`, which the server gives a parameter that is compared with `pg_class.relkind`; a domain over a domain, for which Npgsql says `Writing is not supported`; a free-standing composite type and its array, for which it says the same, which is likely the commonest of all; a table's row type and its array, which Npgsql does not load; `regclass`, which `WHERE c.oid = @t::regclass` infers, and other types of the system catalogs that Npgsql does not load, `aclitem`, `txid_snapshot` and `pg_node_tree`; an array of a type whose name is 63 characters long, which Npgsql cannot spell with its schema without cutting it; and a bit string type spelled `"bit"`.  `format_type(oid, -1)` of `bit` is `"bit"`, with the quotes, since plain `bit` means `bit(1)`; the describer keeps that spelling for a bit without a length, and a parameter has no length, so every parameter of plain `bit` is spelled `"bit"`, which Npgsql refuses.  `bit varying` is bound, and so is plain `bit`: the refusal of `"bit"` is its spelling alone.  Every query with such a parameter is therefore `SQLSRC232`.
- **A refusal costs a round trip for each parameter.**  Npgsql throws one of three exceptions before it sends anything, a `NotSupportedException`, an `InvalidCastException` or, for a name that is too long, an `ArgumentException`, for a type it cannot bind as for a text it will not send, so the live function asks again for each parameter alone to tell which.
- **A name that holds a modifier is no name to bind by.**  Npgsql's `DataTypeName` cuts one parenthesis from a name without a schema and drops what follows it: `character varying(100)` is bound as `character varying`, and `timestamp(3) with time zone` as `timestamp without time zone`, the wrong type and no error.  It cuts none from a name with a schema, so `public.geometry(Point,4326)` is refused, with the NetTopologySuite plugin too, which binds `public.geometry`; and it knows nothing of the fields of an interval, so `interval year to month` is refused.  This was seen with Npgsql 10.0.3, and without the plugin with 11.0.0-preview.1 too; Npgsql 8 and 9 were not tried.  No parameter is spelled so: the protocol gives a parameter an OID and no modifier, and the server drops one that a `-- param:` marker declares, so the check binds no such name and cannot see this.  The `name` of a column, of an array's `element` and of a domain's `base` can hold a modifier, and the fix of [TD-0044](TD-0044-small-gaps-of-the-postgresql-describers-columns.md) puts the whole of it there.

## Why it exists

The check was specified as a comparison of columns because that is what a describe gives: Npgsql does not say which placeholders it found.  The spelled name is the sidecar's, chosen in sub-phase 3.2 to be what PostgreSQL writes, and Npgsql's `DataTypeName` has a syntax of its own, without quotes.  The round trips are on the path of a failure alone.  The spec of sub-phase 3.3 made every error of `check` `SQLSRC231`, since an error of the server on Npgsql's own rewrite is what a disagreement usually looks like.

## Impact

Low.  Nothing binds by `DataTypeName` until phase 8, and the describer is registered since sub-phase 3.6, so `SQLSRC231` and `SQLSRC232` can reach a user.  The first lets a query through that fails when it runs, with the driver's error and no word of SqlSource's.  The fourth tells a user who has lost a connection to look for a `@`.  The fifth refuses queries that are valid: a project whose schema has a quoted name cannot declare a parameter of one of its types, and must cast a `text` parameter in the SQL.  Of the kinds, the composite type is likely the commonest, and the bit type needs no unusual schema: every parameter of plain `bit` is refused.  The seventh costs nothing while only a parameter's own `name` is bound.  It costs a wrong type, silently, the day generated code binds by the `name` of a `base` or an `element`, which the fifth's fix would do for a domain over a domain whose base has a modifier.

## Proposed fix

For the first, compare the parameters and not only the columns: after the check's describe, read the parameter types of the statement Npgsql prepared, which the protocol's `ParameterDescription` holds, and compare their count with the query's list.  For the third, give `SQLSRC231` a second help line when what differs is a type and a parameter is an array of a domain.  For the fourth, report an error of `check` whose SQLSTATE is no syntax or name error, or that has none of the server's, as `SQLSRC225` at the step `check parameters`.  For the fifth, decide in phase 8 how generated code names a type to Npgsql, and let the sidecar hold that: a second member beside `name`, the unquoted `schema.name` form that Npgsql takes, and for `"char"` and a domain over a domain the base type's name, without its modifier, with a cast in the SQL the generator emits; the name that generated code gives Npgsql for a bit string is `bit`.  The sixth needs none.  For the seventh, generated code never binds by a name that holds a modifier: once the fix of TD-0044 puts the modifier in `name`, the name a parameter is bound by is that other member, or the name of the type without its modifier, and never the `name` of a `base` or of an `element` as it stands.

## Trigger

Phase 8, whose generated code binds a parameter by the sidecar's `name`; a user's report of `SQLSRC231` or `SQLSRC232` on a query that is valid; for the eighth, the fix of TD-0044, which puts the whole modifier of a type in `name`.
