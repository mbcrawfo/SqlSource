# TD-0051 - The PostgreSQL describer answers nullable or unknown for many columns that cannot be NULL

## Problem

The realistic corpus, [`tests/SqlSource.Tests.Postgres/Realistic/`](../../tests/SqlSource.Tests.Postgres/Realistic/), holds a truth for each column of each case, written by hand from the SQL and the schema.  Of the columns that truth says can never be `NULL`, the describer answered about half `true` or `null` when the suite landed, 94 on PostgreSQL 14 and 95 on 18 of about 200, 81 and 82 after part A of the design below, 64 and 65 after part B, and 53 and 54 after part C.  [`RealisticNullabilityNoiseTests`](../../tests/SqlSource.Tests.Postgres/Realistic/Describer/RealisticNullabilityNoiseTests.cs) holds the count of each major version, in its `Budgets` by the major, and fails when it moves either way; the cases each kind is seen in are in their committed sidecars, `query.sql.json`, but for `two-columns-named-id`, whose models the generator refuses and which has none.  The noise is of these kinds:

- **An expression that parts A and B do not answer**, which has no origin in the row description and is `null` with `no-origin`.  Part A answers `count(*)`, a window ranking, a constant, an `IS NULL` or `IS DISTINCT FROM` test, and `COALESCE`, `GREATEST`, `LEAST` or a `CASE` with an `ELSE` over such values, from the plan's `Output` ([`PlanExpression`](../../src/SqlSource.Tool/Describing/Postgres/Walk/PlanExpression.cs)), and part B answers them in a plan with an outer join where the walk follows the entry to the node that computes it and no join null-extends that node ([`NullabilityWalk`](../../src/SqlSource.Tool/Describing/Postgres/Walk/NullabilityWalk.cs)).  They leave: `count(x)` (`group-by-having`, `count-filter-statuses`, `any-ids-and-enum-array`, `category-parent-self-join`), since an aggregate `count` of another schema that takes `x`'s exact type beats `pg_catalog.count("any")` whatever the search path and prints bare, and a ranking with arguments for the same reason; a value a node takes from the side a join null-extends, which it prints in parentheses and which is read as unknown, so that a pulled-up constant there proves nothing, and a cast of such a column, `(o.note)::text`, too, since the walk follows the column as it follows any value in parentheses; a cast outside the families of numbers, of texts and of dates and times, `a.status::text` of an enum, or a domain's cast, whose cast function the text does not name; any such form that the root computes over a set operation, whose root prints the first branch; a function in a session whose `search_path` puts another schema before `pg_catalog`; a reference argument through a relation that no plain column of the query names, which `tables` was not asked for; a node that prints no `Output` on a side a join extends, which may compute any value; and `jsonb_build_object(...)` (`json-build-and-agg`), a strict function.
- **A column of no origin through a `Subquery Scan` or a `CTE Scan`** (`parameter-in-cte`, `cte-chain`, `aggregate-cte-joined-inner`, `update-from-aggregate-returning`).  The scan prints the subquery's columns in the order the query above needs them, not in the subquery's own, and the plan prints no name of the subquery's columns, so which entry of the subquery's plan the column is cannot be told; a column with an origin is found by that origin instead, which a column of no origin has none of.  Of these, a `count(*)` through the scan is noise, `ro.order_count` of `parameter-in-cte` for one; the rest are aggregates other than `count` too.  The fix would be a position the plan proves: a scan whose `Output` lists every column of the subquery, which its child's `Output` would have to show, or the subquery's column names from the server, which no call asks for today.
- **A set operation's column that part C does not answer.**  A column of a `UNION`, an `INTERSECT` or an `EXCEPT` has no origin; part C answers it `false` with `set-operation` where the inputs the operation returns rows of prove it ([`NullabilityWalk.SetOperations.cs`](../../src/SqlSource.Tool/Describing/Postgres/Walk/NullabilityWalk.SetOperations.cs)).  It leaves:
  - A recursive CTE (`recursive-category-tree`).  Its columns reach the result through a `CTE Scan`, which prints them in the order the query needs and names none of the CTE's columns, and they have no origin to find them by.
  - A `UNION` branch that the planner keeps as a `*SELECT* <k>` scan, for a cast to the result's type or a `LIMIT` (`union-all-activity-feed` `ref_id`, `union-distinct-search-ordered-limited` `id`, `union-mixed-types` `id` and `since`).  The scan's columns print in an order the plan does not prove: the planner pulls a `UNION ALL` that a subquery in `FROM`, a CTE or an inlined SQL function holds up into its query, and such a scan then prints the columns that query needs, in its order, by names the plan does not otherwise print; and on 18, where the planner drops its own leaf scan when it adds nothing, a `SetOp`'s input may be a user's subquery of the same name, through a view, an inlined SQL function or a `U&"..."` identifier.  Only a member of a 14 `SetOp`'s `Append` that carries the planner's flag is followed by position, since the flag keeps the planner's own scan there.  The fix would be the branch's column names from the server, which no call asks for.
  - A branch's cast of a reference, `(i.issued_on)::timestamp with time zone` (`union-all-activity-feed` `at`, whose branch is such a scan too), since the text does not name the cast's function.
  - A set operation under a join or one that a node above computes over, a `GROUP BY` over a `UNION ALL` subquery's `count(*)` for one.
  - A branch's value of a type outside the three families of built-in types (`SetOperationTypes`), a domain's column for one, since the planner's cast to the result's type is not printed.
  - A nullable column that a branch's `WHERE` filters to values that are not `NULL` (`union-distinct-search-ordered-limited` `label`, `o.note ILIKE @pattern`).
- **`EXISTS (...)` as a column** (`exists-as-column`), which is never `NULL`.
- **An aggregate other than `count`** that cannot be `NULL` where it is: a `sum` or a `max` of a `NOT NULL` column over a group that has a row, `array_agg` and `string_agg` of an inner join's group (`array-and-string-agg`, `group-by-having`, `cte-chain`).
- **`VALUES`** (`values-statement`, `insert-multirow-values`), whose rows the plan does not print.
- **A strict function or operator over values that are not `NULL`**, `quantity * unit_price` (`order-report-four-tables`), `date_trunc(...)` (`aggregate-cte-joined-inner`), the range intersection `r.during * tstzrange(@from, @to)` (`reservations-in-range`), and a function that never returns `NULL` where it is called, `merge_action()` (`merge-returning`).

A few columns of the corpus are noise of other kinds, which the design below does not take up: a column of a view is `null` with `view` (`view-joined-left`), and a `RETURNING` column of a nullable table column is the catalog's `true` where the statement writes a value that is not `NULL` (`insert-select-returning`, `update-from-aggregate-returning`, `data-modifying-cte-archive`).

## Why it exists

The describer answers a column from the catalog, through its origin, and from the plan's walk where a gate asks for one; an expression, a set operation's column and a column of a view have no origin, and the walk maps only references to relation instances and follows only a value whose node it can find.  Noise is safe: a column the describer cannot prove is not null is nullable, and the epic's rule is that a false nullable is a nuisance and a false non-nullable a silent wrong value.  The suite of realistic queries was built to measure the noise before any work lowers it.

## Impact

Medium.  Nothing is wrong, but on realistic SQL about a third of the properties that could be non-nullable have a `?`, each a `!` or a check a user adds by hand; it is the most visible way the describer disappoints.  The count grows with every new case of a kind above.

## Proposed fix

[`docs/superpowers/specs/2026-10-15-postgresql-nullability-noise-design.md`](../superpowers/specs/2026-10-15-postgresql-nullability-noise-design.md): part A answers expressions from the plan's `Output` (`count`, window rankings, constants, `IS NULL`, `COALESCE`, `CASE`, `GREATEST`, `LEAST`), part B is TD-0046's own fix of the walk's gaps, with the expressions it can follow under an outer join, and part C answers a set operation's column from its branches; the recursive CTE stays here, as above.  Each part lowers the budgets of 14 and 18 and updates this item to hold what remains.  What the design leaves, strict functions and operators, `EXISTS` as a column, aggregates other than `count`, `VALUES`, a column of no origin through a scan of another plan, a column of a view and a `RETURNING` column of a written value, stays here with a proposal of its own when one is found.

## Trigger

The branch's column names from the server, for a `UNION`'s leaf scan and a recursive CTE; a user's report of a model with nullable properties that need not be.
