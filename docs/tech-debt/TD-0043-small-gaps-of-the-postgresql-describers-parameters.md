# TD-0043 - Small gaps of the PostgreSQL describer's parameters

## Problem

Nine things that [`PostgresSession`](../../src/SqlSource.Tool/Describing/Postgres/PostgresSession.cs) does to describe a query's parameters are not whole, or were never tried:

- **A `$n` that the SQL writes itself.**  SqlSource's parameter is `@name`, and the lexer reads `$1` as text.  The server reads it as a parameter: `SELECT 1 FROM users WHERE id = @id AND name = $2` prepares with two types, and `SELECT @a, $1` has one parameter that the SQL names twice.  The describer types the parameters of the query's list, the first of the types the server resolved, and says nothing of the rest: the query is described as if the `$n` were not a parameter, and what the generated code then sends is the user's to get right.  Sub-phase 3.3's check of the lexer against Npgsql does not see it either: Npgsql sends `$1` for `@id` and leaves the `$2`, the server types it, and the two describes agree.
- **A reserved word as the schema of a type.**  [`PostgresTypeNames`](../../src/SqlSource.Tool/Describing/Postgres/PostgresTypeNames.cs) writes a schema and a name bare when each is lower-case letters, digits and `_`.  A schema named `user` or `order` needs quotes in SQL, and its types are spelled `user.status`.  The sidecar's `name` is what phase 8's generated code binds with.
- **A cancelled describe leaves its statement.**  `deallocate` is asked with the describe's own token, so a run that is cancelled between `prepare` and `deallocate` frees nothing.  The statement dies with its session, which the run closes next.
- **A statement whose types could not be read.**  `prepare` runs `PREPARE` and then reads `parameter_types` of `pg_prepared_statements`.  When the `PREPARE` succeeds and the read fails, `prepare` answers the error, so `deallocate` is not asked and the statement stays until the session ends; and the error is mapped as one of the `PREPARE`, so a position in it would be counted against the `PREPARE`'s text.  The one cause that is known is a connection that the server ends between the two.  It is reported as `SQLSRC225` at the step `describe parameters`, with what the server said last, `57P01`, or the driver's message, and has no position; the statement is gone with its backend, and every later call of the session answers `the connection to the server was lost`.
- **A statement that `PREPARE` does not take.**  `PREPARE` takes a `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE` or `VALUES`.  `CALL p(@a)` and `CREATE TEMP TABLE …` are valid SQL that a user may well keep in a `.sql` file, and of each the server says a syntax error at character 1, `syntax error at or near "CALL"`.  It is reported as `SQLSRC225`, as if the query were wrong.  Once the describer is registered, one such query keeps the sidecar of its file from being written, since a sidecar is written only when every query of its file that needs an entry has one.
- **A server older than PostgreSQL 14.**  The supported floor is 14, and nothing checks the version that `open` answers.  `types` reads `pg_range.rngmultitypid`, which PostgreSQL 13 does not have, so on such a server every query with a parameter is `SQLSRC225` at the step `resolve type`, with the server's `column m.rngmultitypid does not exist`: a line that quotes the tool's own query and says nowhere that the server is too old.
- **`int2vector` and `oidvector`.**  The two are base types of the category `A` with an element, which is how the describer knows an array, so a parameter of one is described as `smallint[]` or `oid[]`, of the kind `array`.  They are no arrays: their text and their lower bound are their own.  The catalog's columns have them, `pg_index.indkey` for one, and a table of a user hardly ever.
- **A proxy that pools by transaction.**  `PREPARE`, the read of `pg_prepared_statements` and `DEALLOCATE` are three round trips, and a proxy such as PgBouncer in its transaction mode may give each to another backend.  The read then finds no statement, for which the describer throws, or the `DEALLOCATE` finds none to free.  `Multiplexing=true` in a connection string may do the same within Npgsql.  Neither is tried.
- **An exception of `open` that is none of the two the describer knows.**  `open` answers an `NpgsqlException`, and the `ArgumentException` of a connection string that Npgsql cannot read.  Anything else the driver throws while it connects is a throw, `SQLSRC200`, though a user caused it: a certificate file that the connection string names and that is missing, for one.  What Npgsql throws there has not been enumerated.

## Why it exists

The first: refusing a `$n` needs the tool to tell one from a dollar-quoted string's tag and from a money literal, which the lexer does for a quote and not for a placeholder; the check of the lexer against Npgsql was hoped to see it and does not, since it compares the columns of two describes ([TD-0045](TD-0045-the-check-against-npgsql-is-best-effort.md)).  The second: the tool has no list of PostgreSQL's reserved words, which differs by version.  The third is the spec's choice: a cancelled run must not wait on a server.  The fourth: an answer has a value or an error and nothing between.  The fifth: the route of the describer is one prepared statement, which gives the types of the parameters as no other call does, and the sidecar has no entry yet for a statement that has no description.  The sixth: the describer was built and tested against 14 and 18, the two that CI runs.  The seventh: the closure tells an array by its category, as `pg_type` marks one.  The eighth and the ninth were found by the review of sub-phase 3.2, when the describer was whole and still registered nowhere: no test has a proxy, and none makes Npgsql throw on `open` anything but the two.

## Impact

Low.  The describer is registered since sub-phase 3.6, so each of these can reach a user.  The first two need a query or a schema that few projects have.  The third costs nothing: the session ends.  The fourth costs nothing in practice, since a connection that fails there has ended.  The fifth is the one that a user meets first: a project that keeps one `CALL` beside its queries gets no sidecar for that file, and an error that sends its author looking for a mistake in valid SQL.  The sixth gives a user of an old server an error on every query with a parameter that names nothing they wrote.  The seventh needs a parameter that is compared with a column of the catalog.  The eighth and the ninth are unknown in size: a pooled connection is common where a database is hosted, and a describe through one may end the run with `SQLSRC200`.

## Proposed fix

For the first, report a `$` followed by a digit in a `Text` lexeme, outside an identifier, as an error of its own at the query.  For the second, quote a name that `pg_get_keywords()` lists as reserved, asked once for a session with `open`, or always quote a name of a schema outside `pg_catalog` and `public`.  The third needs none, and the fourth none until a call is added between the `PREPARE` and the read.  For the fifth, decide what a statement that cannot be prepared is to the tool: an error of its own that says `PREPARE` does not take the statement, told by the first word of the SQL or by a syntax error at character 1 of it, and whether its query needs an entry at all, so that it does not hold back the sidecar of its file.  For the sixth, compare the version that `open` answers with the floor and fail the session with an error that names both, `SQLSRC224` or one of its own.  For the seventh, treat the two types as base types, by their OIDs, 22 and 30, or by an element together with a `typname` that does not start with `_`.  For the eighth, try the describer through PgBouncer in its transaction mode and with `Multiplexing=true`, and either hold the three calls to one backend with a transaction, document that the describer needs a session of its own, or answer the statement that is not listed as an error.  For the ninth, read what `NpgsqlDataSource.OpenConnectionAsync` throws for each keyword of a connection string that names a file or a service, and answer what a user can cause as `open`'s error.

## Trigger

Phase 8, whose generated code sends the SQL as written, for the first, and binds a parameter by the sidecar's `name`, for the second; for the fifth to the ninth, a user who meets one, since sub-phase 3.6 gave the describer to users.
