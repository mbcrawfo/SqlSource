# TD-0085: on SQL Server, an error after the first result set is lost

## Problem

A generated method that reads rows reads the first result set of its query and disposes its reader, as [`QueryMethodWriter`](../../src/SqlSource/Generation/Emitting/QueryMethodWriter.cs) writes it, and calls no `NextResultAsync`.  On SQL Server, an error that a statement after that result set raises is then reported by no call.  `StreamThenRaise`, in [`Queries/Streaming.sql`](../../tests/SqlSource.Tests.SqlServer/EndToEnd/Queries/Streaming.sql), selects the accounts, sets `CONTEXT_INFO` and runs `THROW 50000, 'after the rows', 1;`.  The two `StreamThenRaise_ErrorAfterTheRows_*` tests of [`StreamingQueryTests`](../../tests/SqlSource.Tests.SqlServer/EndToEnd/StreamingQueryTests.cs) pin what its streaming method does: it yields the three accounts, the `MoveNextAsync` that ends the loop returns `false`, `DisposeAsync` returns normally, the connection is usable after, and the mark on the session shows the batch ran as far as the `THROW`.  `ListThenRaise`, the same batch read into an array, in [`Queries/Methods.sql`](../../tests/SqlSource.Tests.SqlServer/EndToEnd/Queries/Methods.sql), loses the error too: [`MethodShapeTests`](../../tests/SqlSource.Tests.SqlServer/EndToEnd/MethodShapeTests.cs)' `ListThenRaise_ErrorAfterTheRows_ReturnsTheRowsAndIsNotThrown` pins that it returns the rows, throws nothing, and ran to the `THROW`.  `GetThenRaise` and `FindThenRaise`, the batch with the first account alone under `one` and `one-optional`, dispose their reader the same way after their second read and lose the error too: `GetThenRaise_ErrorAfterTheRow_ReturnsTheRowAndIsNotThrown` and `FindThenRaise_ErrorAfterTheRow_ReturnsTheRowAndIsNotThrown` pin that each returns the account, throws nothing, and ran to the `THROW`.  These three are the cases that flip when the fix lands, with the two of `StreamThenRaise`.  `RunThenRaise` and `CountThenRaise`, the batch under `none` and `rowcount`, which read no rows, throw the `SqlException` of `Number` 50000, as `RunThenRaise_ErrorAfterTheRows_ThrowsTheError` and `CountThenRaise_ErrorAfterTheRows_ThrowsTheError` pin.  So the error is in the batch's reply: a method that runs `ExecuteNonQueryAsync` reports it, and one that reads rows and disposes its reader does not.  The likely cause is that Microsoft.Data.SqlClient, when a reader is disposed, reads the rest of the batch and drops an error that follows the last result set it was asked for, which `NextResultAsync` would raise; the tests do not show the cause.

## Why it exists

The methods were written to read one result set, as [`D-0006`](../deferred/D-0006-multiple-result-sets-on-sql-server.md) leaves several result sets for later, and nothing tested a statement that fails after the rows until the streaming methods did.  It was found by the end-to-end tests of [streaming query methods](../superpowers/specs/2026-10-26-streaming-query-methods-design.md), whose scope is one collection type.  Reporting the error means changing every method that reads rows, buffered and streaming alike, with its generated code, its allocation tests and the manual's account of a query of several statements, which is a change of its own.

## Impact

Medium.  A query whose later statement can fail is uncommon, and the manual says that such an error is not reported, but the loss is silent: the caller sees the rows and success, while the batch stopped at the error, so a statement after it did not run and one before it, outside a transaction, stays done.  In a transaction, what becomes of it depends on the error and on `XACT_ABORT`: with it off, a `THROW`, a divide by zero or a value too large or out of range for its type leaves the statements before the error done in the transaction, which stays open, while a conversion of text that is not a valid number, date, GUID or XML rolls the transaction back; under `SET XACT_ABORT ON` nearly every error rolls it back.  A rollback undoes those statements and everything the transaction did before, with nothing thrown until `Commit`, as [TD-0088](TD-0088-sql-server-unreported-error-rolls-back-the-transaction.md) records.  It risks a wrong result in a caller that relies on a later statement of a query having run.

## Proposed fix

After the rows a method reads, and before the reader is disposed, call `NextResultAsync` with the method's token until it returns `false`, so that the driver raises an error that a later result or statement holds.  In a streaming method, do it after the last row and in the `finally` that a `break` or a disposal runs, so that a loop that ends early drains the later results too; decide whether an error raised there, during a disposal, should be thrown or kept from hiding the exception that ended the loop.  Measure the allocations of both engines' `AllocationTests` before and after, flip the SQL Server cases above, add the same cases on PostgreSQL, where Npgsql may already report such an error, flip the cases of TD-0088 that roll back after the rows, `StreamThenRaise` and `ListThenRaise` under `XACT_ABORT ON` and `StreamThenFailConversion` and `ListThenFailConversion` with it off, which then throw the error, and update the account of a query of several statements in `docs/manual/sqlserver.md`, `docs/manual/generator.md` and the streaming rows of `docs/manual/settings.md`, with the known issue of `sqlserver.md` removed.

## Trigger

A user's report of a lost error, or the work of `D-0006` on several result sets, which reads the later results anyway.
