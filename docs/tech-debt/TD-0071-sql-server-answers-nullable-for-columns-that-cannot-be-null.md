# TD-0071 - The SQL Server describer answers nullable for columns that cannot be NULL

## Problem

The realistic corpus, [`tests/DatabaseTests/SqlServer/Realistic/`](../../tests/DatabaseTests/SqlServer/Realistic/), holds a truth for each column of each case, written by hand from the SQL and the schema.  Of the columns that truth says can never be `NULL`, the describer answers 1 nullable on SQL Server 2017 (major 14) and the same 1 on 2025 (17).  [`RealisticNullabilityNoiseTests`](../../tests/DatabaseTests/SqlServer/Realistic/Describer/RealisticNullabilityNoiseTests.cs) holds the count of each major in its `Budgets` and fails when it moves either way, listing the noisy columns.

The describer keeps the server's nullability (`sys.dm_exec_describe_first_result_set`, `nullableSource` `server`) except where [the proofs of not null](../architecture/sqlserver-describer.md#proofs-of-not-null) narrow it: from the query's text, when it is one `SELECT`, a set operator whose every branch proves the column, or an `INSERT`, `UPDATE` or `DELETE` with `OUTPUT`, for `COUNT`, the ranking functions, `SUM`, `MAX` and `MIN` over a group or a frame that holds the current row, `COALESCE`, `ISNULL`, `GREATEST` and `LEAST`, `COALESCE` and `ISNULL` over a column of each side of the last `FULL JOIN`, each asked over its own side's rows, `CAST` and `CONVERT`, arithmetic, `JSON_OBJECT` and `JSON_ARRAY`, the date functions and `AT TIME ZONE`, `LAG` and `LEAD` with a default, and `CASE WHEN x IS NULL THEN e ELSE x END`, each with the server asked about its operands; a stored column that a top-level `WHERE` conjunct rejects when it is `NULL`, the optional side of a `LEFT JOIN` that such a conjunct makes inner, and a column read through a CTE whose `WHERE` does so; a column of a CTE, of one branch or of several, a recursive one included, that every branch proves, a recursive member with the CTE's own columns taken as not null; a computed column read from a table that no join can make `NULL`, by the catalog when it is `PERSISTED NOT NULL` and by its definition in `sys.computed_columns` otherwise; and, in an `OUTPUT`, a `PERSISTED NOT NULL` column of `inserted` or `deleted`, a column of `deleted` of an `UPDATE` or a `DELETE`, or of `inserted` of an `UPDATE` that its `SET` does not write, that the `WHERE` keeps from `NULL`, an `inserted` column that the `SET` writes not null, and any other item of an `UPDATE` or a `DELETE` as a `SELECT`'s item over its `FROM` and `WHERE`.  That column is of a kind those proofs do not read:

- **`COALESCE` over a column read `FOR SYSTEM_TIME`**: `price-as-of` `effective_price`, `COALESCE(pr.price, p.list_price)`.  The server names no source column for `pr.price`, so it is not shown to give one value in a row, which an argument before the proved one must.

The proofs' other limits are as narrow, and no column of the corpus reaches them: a date function that is no form, such as `DATEFROMPARTS`, `DATETRUNC`, `DATE_BUCKET`, `SWITCHOFFSET` or `TODATETIMEOFFSET`; `LAG` or `LEAD` whose offset is not an integer literal or that names a window; a `CASE` that guards a computed column, a view's column or a derived table's expression that the server answers nullable, which is read twice and may differ between the reads; a `COALESCE` with such a value, a `CASE`, a date function or a string function before its proved argument, as in `COALESCE(SUM(CASE WHEN x > 0 THEN x END), 0)`, for the same reason; a `COALESCE` over a column of another database or a linked server, read by its name, a synonym, a derived table or a CTE, since `columns` reads a source's type only in the session's database; a `COALESCE` over a column of a `UNION` or `UNION ALL` in a derived table or CTE, an `UNPIVOT` column or a column that a derived table or CTE computes, for which the server names no source column; `COALESCE(AVG(x), 0)`, since `AVG` has no type proof and counts only inside a `CAST` or `CONVERT`; a `COALESCE` or `ISNULL` over the two sides of a `FULL JOIN` that is nested or in parentheses, that a `RIGHT` or another `FULL JOIN` follows, or whose side's column only the `WHERE` keeps from `NULL`, since each side is asked without it; a computed column read through a derived table, a CTE or a view, from the optional side of an outer join, even a `LEFT JOIN` the `WHERE` makes inner, without its qualifier in a `FROM` of several sources, in parentheses, or in a statement that is not one `SELECT` but as a `PERSISTED NOT NULL` column of `inserted` or `deleted`, keeps the server's answer, since through an outer join it is `NULL` while the server still names it as the source; a computed column whose definition holds a `CAST` or `CONVERT`, whose target the server writes in brackets (`CONVERT([int], ...)`), which is no target the forms read; a filter in any other form, such as `x IN (...)`, `x BETWEEN a AND b`, `x + 1 > 0`, a condition under `OR` or a column without the qualifier its item has; a filtered computed column, view column or derived table's expression, which is read twice; a `LEFT JOIN` beside an `APPLY`, a comma, a join hint or a nested join, or filtered by a column with no qualifier; a column of a CTE read through an outer join, or through a `LEFT JOIN` the `WHERE` makes inner whose filter's column is not stored, as no column of a `UNION`, of a recursive CTE or that a CTE computes is, or that a branch reads from its own CTE through a comma, an `APPLY` or a derived table; a set operator with `*` in a branch, or whose computed column the catalog or its definition would prove; a column of a CLR type the server answers not null whose row names no stored column of a table, and that no view or inline function passes on from one, read from a table variable, a table of another database or a linked server (whose `sourceType` is not read), a multi-statement function (`TF`), whose `NOT NULL` return table would refuse the Null, or a view created `WITH VIEW_METADATA`, which browse mode 1 names as the source, given by `VALUES`, `UNPIVOT` or an expression such as `ISNULL(x, y)`, or of a set operator inside a derived table, a CTE, a view or a function, which [`ColumnProofs`](../../src/SqlSource.Tool/Describing/SqlServer/Proofs/ColumnProofs.cs) makes nullable even where every branch is of that type, since a string that a set operator converts to the type may be its Null and the server answers that not null wherever the column is read; an `OUTPUT` that reads `inserted` or `deleted` inside an expression, as `COALESCE(inserted.b, 0)`, since the server refuses a pseudo-table's column in the `SELECT` of `operands`; any column of an `INSERT`'s `OUTPUT` but a `PERSISTED NOT NULL` one, since its rows come from no `FROM`; an `UPDATE` or a `DELETE` without a `FROM` whose proof needs the server, as `SET note = ship_city`, since an operand has no rows to be asked over; a `SET` value of `DEFAULT`, which may write `NULL`, or a `SET` the reader cannot follow, `c += 1`, `@v = c = e` or a method of a CLR column, which counts as writing every column; a target the reader does not resolve, a name of several parts beside a `FROM`, a CTE or a derived table, and a view, whose columns name the view as their source and so are no stored column of the table; a `FROM` that the join chain gives up on, or with a source named `inserted` or `deleted`, which proves nothing for the whole statement; and a query with `FOR XML` or `FOR JSON`, a `MERGE`, whose `inserted` is `NULL` in a row it deletes, `WHERE CURRENT OF`, or a batch of several statements, is not read at all.

## Why it exists

The rule is to rely on the server where it is accurate and to correct it only where a proof shows it wrong, and the proofs read the forms the corpus over-reported most, from the text and the server's answer about their operands, with no model of the query's rows.  Noise is safe: a column the describer cannot prove is not null is nullable, so the generated type is wider than it needs to be and a false nullable costs a check or a `!`, where a false non-nullable is a silent wrong value.  Each kind above needs a reading of its own: a function's rule of what it returns, the rows a filter leaves, the value a `MERGE` writes, or the rows of a statement that has no `FROM`.

## Impact

Low.  Nothing is wrong, and of the corpus's columns that cannot be `NULL`, 1 of the 193 of the cases that run on 2017 and 1 of the 209 of those that run on 2025 are answered nullable.  Each that remains is a property with a `?` that a user meets as a `!` or a check added by hand, as TD-0051 is for PostgreSQL; the manual's [SQL Server limit](../../site/reference/databases/sqlserver/nullability.md#limit-columns-treated-as-nullable) says what a user can do.  The count grows with every case of a kind above.

## Proposed fix

The next kinds, each a form of [`ExpressionProofs`](../../src/SqlSource.Tool/Describing/SqlServer/Proofs/ExpressionProofs.cs) or a rule of [`ColumnProofs`](../../src/SqlSource.Tool/Describing/SqlServer/Proofs/ColumnProofs.cs) on the same reader, with a test of what it proves on a server and of the queries that try to break it in `ProofTests`, and the budget lowered in its commit:

- **More values that give one value in a row, for `COALESCE`** (`ExpressionProofs.OneValue`): a column read `FOR SYSTEM_TIME`, which needs the `FROM` read since the server names no source; a `CASE` of such values, which needs its conditions read; a column of a `UNION` or an `UNPIVOT`, which needs every branch or source column read and held to `OneValue`; and the date and string functions that are deterministic.  Each is measured on every supported major with an operand that changes, as `ValuesThatChange` of `ProofTests` does.
- **A column of another database on the same server, for `COALESCE`**: a new nullable member of the `columns` row from `OBJECT_ID(<db>.<schema>.<table>, N'U')`, with its rule in `SqlServerFields.cs`, read in `OperandsQuery.AnswersOf`.  `source_type` stays null there, as `ColumnsAsync_SourceType_IsTheBaseTypeOfASourceOfTheSessionsDatabase` of `ColumnTests` holds, and a table of a linked server stays nullable.
- **A bare `AVG`, for `COALESCE`**: the type proof of its operand in `PrimaryType`, so that `COALESCE(AVG(x), 0)` is proved.
- **A pseudo-table inside an `OUTPUT` expression**: `COALESCE(inserted.b, 0)` proved with each `p.c` of the target, `inserted` or `deleted`, answered from the visible row of `columns` of that name rather than asked, as [`ComputedProofs`](../../src/SqlSource.Tool/Describing/SqlServer/Proofs/ComputedProofs.cs) answers a definition's operand from `table`, and `inserted.c` taken as the `SET`'s value where one writes it.
- **An `UPDATE` or a `DELETE` without a `FROM`**: its operands asked over the target, `FROM <target> WHERE ...`.  The text of `operands` is only slices of the user's SQL ([`OperandsQuery`](../../src/SqlSource.Tool/Describing/SqlServer/Proofs/OperandsQuery.cs)), and an `UPDATE` has no word `FROM` to slice, so this widens that rule, with a canary in `SafetyTests`.
- **A `MERGE` that only updates**, whose `inserted` and `deleted` are rows of the target: a reader of [`OutputStatement`](../../src/SqlSource.Tool/Describing/SqlServer/Proofs/OutputStatement.cs)'s kind for a `MERGE` whose every action is `UPDATE`, its `ON` and `WHEN MATCHED AND` conditions read as a `WHERE`.

## Trigger

The owner asks to lower the noise again, a user reports a model wider than its query, or a case of a kind above is added to the corpus.
