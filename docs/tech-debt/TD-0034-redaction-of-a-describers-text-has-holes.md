# TD-0034 - What the removal of a connection's value from a describer's text does not cover

## Problem

Before a text that a describer gave is printed, [`Redaction`](../../src/SqlSource.Tool/Describing/Redaction.cs) writes each whole form of the database's connection value as `***` wherever it stands, and each secret part of it where it stands as a token.  [`ConnectionSecret`](../../src/SqlSource.Tool/Describing/ConnectionSecret.cs) holds both.  The whole forms are the value, the value trimmed, and the value as the describer's driver writes it again, which `IQueryDescriber.RewriteOf` gives.  The parts are the passwords that the describer's `SecretsOf` gives: the PostgreSQL describer's `Password` and `SSL Password`, and, when the string has no `Password`, the `PGPASSWORD` of the host's environment, or else the passwords of the password file that Npgsql would read ([`PasswordFile`](../../src/SqlSource.Tool/Describing/Postgres/PasswordFile.cs)); the SQL Server describer's `Password`.  [`DatabaseRuns`](../../src/SqlSource.Tool/Describing/DatabaseRuns.cs) applies it, to a failure's message once it is formatted too.  The log of `--log`, through [`SessionRunLog`](../../src/SqlSource.Tool/Logging/SessionRunLog.cs), and the lines of `--verbose`, through [`RunTrace`](../../src/SqlSource.Tool/Logging/RunTrace.cs), have the same removal, and the log searches the strings of an event joined too ([`JoinedRedaction`](../../src/SqlSource.Tool/Describing/JoinedRedaction.cs)).  [`EntrySecretCheck`](../../src/SqlSource.Tool/Describing/EntrySecretCheck.cs) ends the run when a describer put a whole form into an entry of a sidecar.  [`CaptureJson.Write`](../../src/SqlSource.Tool/Describing/Capture/CaptureJson.cs), given the secret, refuses a capture whose strings hold a whole form or a part, searched as the strings of a log's event are; the describers' fixtures are recorded through it, and nothing in the released tool writes a capture yet.  Both describers answer a session that could not be opened, or that ended, with the engine's code and a fixed text of their own (the `ConnectionErrors` of [PostgreSQL](../../src/SqlSource.Tool/Describing/Postgres/ConnectionErrors.cs) and of [SQL Server](../../src/SqlSource.Tool/Describing/SqlServer/ConnectionErrors.cs)), so no driver's message of a connection is passed on.  These are outside all of it:

- **A part shorter than four characters.**  `ConnectionSecret` drops a part shorter than `ConnectionSecret.MinimumPartLength`, since a token of one to three characters matches too much ordinary text.  Such a password is printed and logged wherever a message quotes it.
- **A part equal to a word the run writes of the database.**  `ConnectionSecret` drops a part that equals the database's logical name or the engine's canonical name, `postgres`, compared ordinally.  The run prints those words whatever the describer does, so hiding them hides nothing, and the password `postgres` would otherwise turn every error's `query:` line into `query: GetUser, database app, *** 16.4`.  A message that quotes such a password, `Password=postgres;`, keeps it.
- **A login's name in a message of SQL Server.**  The SQL Server describer keeps the message of a server's error of a query verbatim, since it speaks of the query, and such a message can name the login: a query whose three-part name reaches a database that the login may not open is error 916 at `parameters`, `The server principal "app_login" is not able to access the database "billing" under the current security context.`, which `SQLSRC225` prints, the log writes and a capture holds.  The removal takes out the value and the password, and not the login's name, which is no secret and is still the user's.  That is the owner's decision.
- **A server's message in a capture.**  The writer refuses a capture that holds the secret, and keeps the rest of what the server said: an `error` of a query keeps its message, detail and hint, and an answer of `open` the server's version and settings.  A message that names the host, the database or the user is written, as the log writes it.  What an `error` may keep in a capture that a user sends is not decided.  `CaptureJson.Write(DescribeCapture)`, without the secret, writes whatever a capture holds.
- **A value in pieces that neither joined search puts side by side.**  `SessionRunLog` searches the strings of an event alone, all of them joined in the order they were written, the names of members among them, and the texts of the values joined without the names.  A value whose halves are two strings with others between them in both orders, such as a member's name and the value of a later member, or two strings in the reverse order of the event, is logged.  A capture is searched for each request and each answer apart, so a value split between a request and its answer, or between two calls, is written.  The describer's rule keeps the value out of all of them; the joined search is for a describer that passes on a text cut in two.
- **A password file read whole.**  When the string has no `Password` and `PGPASSWORD` is not set, the PostgreSQL describer gives the password of every entry of the file.  With no `Passfile` and no `PGPASSFILE` it reads both default files, `.pgpass` in `HOME` and `postgresql/pgpass.conf` in `APPDATA`, each whose variable is set, whatever the system, while Npgsql reads one file and uses the one entry that matches the host, port, database and user as it resolves them.  Each of those passwords is removed, so one that equals a word of a message hides that word, as below.  A password file that can be read only once, a named pipe or the pipe of a shell's process substitution (`PGPASSFILE=<(...)`), is not read, since the describer asks for the secrets before the driver reads the file and would leave it nothing: its password is not removed.
- **A password that the driver takes from where the describer does not look.**  Npgsql also takes a password, before `PGPASSWORD`, from a provider of the data source, set with `NpgsqlDataSourceBuilder.UsePasswordProvider` or `UsePeriodicPasswordProvider`, and from the connection's `ProvidePasswordCallback`, a property of `NpgsqlConnection`.  The tool sets none of them, so no such password reaches a run today.
- **An entry is searched for the whole forms alone.**  `EntrySecretCheck` does not search for the parts.  An entry holds the names of a catalog and no driver's message, so a part found there would mostly be a name that equals a password, the password `password` beside a column `password` found through `SELECT *`, and `SQLSRC200` would end the run for a common schema.  The owner chose that over the search, so a describer that put a password into an entry would have it written to the sidecar, and printed under `--check`, in the line of `SQLSRC219` that says what the database says.
- **A value that the sidecar holds without the describer.**  `EntrySecretCheck` finds a whole form only when the entry's text holds it and the same text without the describer's part does not.  A value that equals a word of the format, the engine, or the name of the query, of its database or of a parameter is so never found in what a describer gave.  No real connection string has that shape, and the file holds such a value whatever the describer does.
- **A value that equals a word of the describer's part of an entry.**  The text without the describer's part has no column and no type, so a value that equals a key that only those have, `origin` or `nullableSource` for two, ends the run with `SQLSRC200` when a query has a column.  That fails closed, and it is what is left of a wider case: a dummy value of a test or a replay such as `postgres` does not end the run.
- **A password that equals a whole word of what is printed.**  A kept part is removed wherever it stands as a token, so a password that equals a name the server quotes, a column `password` in `column "password" does not exist` with the password `password`, prints that name as `***`.  It leaks nothing and hides a word of the message.

## Why it exists

The tool does not read a connection string itself, so it knows of a value what the describer says: the passwords its driver reads from the value and from the environment, and the text its driver writes the value as.  A form of the value other than those three is found by its passwords alone.  The token rule, the shortest part and the words of the run trade a little cover for output a user can still read: a dev password such as `test` leaves `latest_orders` alone.  The password file is read whole because the entry Npgsql uses depends on the host, port, database and user as it resolves them, and a password too many only hides a word.  The search of an entry for the whole forms alone, and a login's name left in SQL Server's messages, are the owner's decisions, for the reasons above.  What a server's message in a capture may keep is left for the phase that first writes one for a user, with a real capture to decide it on.

## Impact

Low.  A driver's message of a connection no longer reaches the output.  The container tests of `tests/DatabaseTests/Postgres` hold it: `SessionTests` checks that the failure of a wrong password, a missing database, an unreachable host and a terminated backend names neither the host nor the user, and `DescribeCommandTests` that a refused connection and a wrong password leave them out of everything printed and logged.  What is left needs a password shorter than four characters or one that equals a word the run writes, or a describer that writes a value in pieces against its rule; the rest hides a word too many or keeps a name that is no secret.  The manual's known issue in [the tool's page](../manual/tool.md#known-issues) says to search a log for the password before sharing it.  A describer's rule is to put the value, or a part of it, in nothing it returns but `SecretsOf` and `RewriteOf`, and this is the net under that rule, with these holes.

## Proposed fix

For a capture, with phase 10's first capture for a user: write it only through `CaptureJson.Write(DescribeCapture, ConnectionSecret)`, and decide on that capture what a server's message in an `error` may keep, such as its code alone, or its message once the user has read it.  For a value in pieces, search every pair of an event's strings joined, in both orders, if a describer is found to write one so.  For the password file, give the password of the entry that Npgsql would match, from the host, port, database and user as it resolves them, and read the default file of the running system alone, if a report shows a word hidden by another entry's password.  For a pipe, ask for the secrets again once the driver has read the file, if a user's report shows one.  For a password callback or provider, have `SecretsOf` give its password in the change that makes the tool set one.  Search an entry for the parts only if a describer is found to put a password in what it returns.

## Trigger

A user's report of a part of a connection in what the tool printed or logged, or of a word written as `***` that is no password of theirs.  For a capture, phase 10's `sqlsource diagnose`, which writes one for a user.
