# TD-0034 - What the removal of a connection's value from a describer's text does not cover

## Problem

Before a text that a describer gave is printed, [`Redaction`](../../src/SqlSource.Tool/Describing/Redaction.cs) writes every occurrence of the database's whole connection value as `***`.  [`DatabaseRuns`](../../src/SqlSource.Tool/Describing/DatabaseRuns.cs) applies it.  The log of `--log`, through [`SessionRunLog`](../../src/SqlSource.Tool/Logging/SessionRunLog.cs), and the lines of `--verbose`, through [`RunTrace`](../../src/SqlSource.Tool/Logging/RunTrace.cs), have the same removal, and [`EntrySecretCheck`](../../src/SqlSource.Tool/Describing/EntrySecretCheck.cs) ends the run when a describer put the whole value into an entry of a sidecar.  Six things are outside all of them:

- **A value that was changed.**  Only the whole value is found.  A driver's message that quotes the value changed, trimmed of a trailing space or line break for one, or quotes one keyword of it, is printed, said and logged, and an entry that holds it is written.  A log is a file that a user may attach to an issue, and a sidecar is committed.
- **A value that the parts of a message make together.**  The message format of a failure's descriptor and each of its arguments are searched alone, so a value that stands half in the format and half in an argument, or over two arguments, is in the message that is printed and logged.  The same holds for a value that a describer writes over two members of one event of its log.
- **A value that the sidecar holds without the describer.**  `EntrySecretCheck` finds a value only when the entry's text holds it and the same text without the describer's part does not.  A value that equals a word of the format, the engine, or the name of the query, of its database or of a parameter is so never found in what a describer gave.  No real connection string has that shape, and the file holds such a value whatever the describer does.
- **A capture.**  [`CapturingExchange`](../../src/SqlSource.Tool/Describing/Capture/CapturingExchange.cs) writes each answer as the describer gave it, and nothing searches a capture for the value.  A request holds nothing of a connection by the describer's rule, and the request that opens a session is empty, but an answer holds what the server and the driver said: a version, a setting, or the driver's own message in the `error` of a call that failed, which may name the host or the user.  Nothing in the released tool records, so no capture leaves a machine today; from phase 10 a capture is the file a user attaches to a report.
- **A value that equals a word of the describer's part of an entry.**  The text without the describer's part has no column and no type, so a value that equals a key that only those have, `origin` or `nullableSource` for two, ends the run with `SQLSRC200` when a query has a column.  That fails closed, and it is what is left of a wider case: a dummy value of a test or a replay such as `postgres` no longer ends the run.
- **The driver's own message of a session that could not be opened, or that dropped.**  The PostgreSQL describer answers `open` with what Npgsql or the server said, and that names a part of the connection that is no secret and is still the user's: `Failed to connect to 10.0.0.5:5432` holds the host and the port, and `password authentication failed for user "app"` the user's name.  It is printed under `SQLSRC224`, written to the log's `diagnostic` event, and kept in the `open` answer of a capture.  A connection that the server ends while a query is described is `SQLSRC225`: the call that finds it out answers what the server said last, `57P01: terminating connection due to administrator command` for one, or the driver's message of a socket that closed, which is of the same kind and has no SQLSTATE.  Two texts are the describer's own and hold nothing of a connection.  What Npgsql says of a connection string it cannot read is not passed on: [`PostgresConnection`](../../src/SqlSource.Tool/Describing/Postgres/PostgresConnection.cs) answers `Npgsql cannot read the connection string` in its place, since the driver's exception quotes the value.  And every call after the one that found a connection ended answers `the connection to the server was lost`, where the driver would throw.  The container test `DescribeCommandTests.Describe_ConnectionRefusedWithLog_IsSqlsrc224AndNoDriverEventHoldsTheHost` shows the first: a connection to port 1 of the container's host is refused, and the `lines` of the `diagnostic` event hold `Failed to connect to 127.0.0.1:1`.  It asserts that the event has lines, and that no `postgres.driver` event holds the host: the driver's own messages are forwarded at levels that [TD-0048](TD-0048-driver-levels-trust-npgsqls-messages.md) records, and Npgsql 10.0.3 writes none for a refused connect.  [The tool's manual page](../manual/tool.md#logs) says, under logs, that a log holds what the server or the driver said of a database that could not be opened, which can name its host and its user.

## Why it exists

The tool does not read a connection string and so knows no part of one, and the first describer, PostgreSQL's, was not registered until sub-phase 3.6, so its driver's texts have been met in its tests and in no user's run.  What the tool could mend alone is mended: the descriptor of a failure is searched, a failure's server lines are searched joined, and a value that the sidecar holds without the describer is no fault.

## Impact

Low.  The released tool has PostgreSQL's describer since sub-phase 3.6, so the last hole reaches users: a database that cannot be opened prints its host or its user under `SQLSRC224` and writes it to the log, which [the tool's manual page](../manual/tool.md#logs) warns of.  A describer's rule is to put the value, or a part of it, in nothing it returns, and this is the net under that rule, with these holes.

## Proposed fix

Have the PostgreSQL describer hand the tool the parts of the connection that are secret, as its driver's connection-string builder knows them, and redact each in `Redaction`, `SessionRunLog` and `RunTrace`, and search for each in `EntrySecretCheck`.  That does not reach the case that matters most: a driver quotes a connection string mostly when it cannot read it, and then its builder gives no part either.  So study what the driver says of a string it cannot read, and either keep that text from the output whole or search it for the value as the driver changes it.  Search the message of a failure once it is made, and not its format and arguments alone.  For the message of a session that could not be opened, keep the SQLSTATE and write a fixed text of the describer's own in place of the driver's, as `PostgresConnection` does for a string it cannot read, or remove the host, the port and the user that the driver's builder reads from the string.  For a capture, before phase 10 writes one for a user: refuse to write a capture whose text holds the value or a secret part of it, as `EntrySecretCheck` refuses an entry, and decide with the first real describer what its `error` answers keep of a driver's message.

## Trigger

A user's report of a part of a connection in what the tool printed or logged.  Phase 5, whose release is the first a user can use, has closed, so the tool now describes `postgres` for users.  For a capture, phase 10's `sqlsource diagnose`, which writes one for a user.
