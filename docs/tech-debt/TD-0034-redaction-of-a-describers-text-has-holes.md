# TD-0034 - What the removal of a connection's value from a describer's text does not cover

## Problem

Before a text that a describer gave is printed, [`Redaction`](../../src/SqlSource.Tool/Describing/Redaction.cs) writes each whole form of the database's connection value as `***` wherever it stands, each secret part of it where it stands as a token, and each part too short or too common to be a token where it stands as a password key's value (`Password=pg;`).  [`ConnectionSecret`](../../src/SqlSource.Tool/Describing/ConnectionSecret.cs) holds all three.  The whole forms are the value, the value trimmed, and the value as the describer's driver writes it again, which `IQueryDescriber.RewriteOf` gives.  The parts are the passwords that the describer's `SecretsOf` gives: the PostgreSQL describer's `Password` and `SSL Password`, and, when the string has no `Password`, the `PGPASSWORD` of the host's environment, or else the passwords of the entries of the password file that Npgsql may use for the connection ([`PasswordFile`](../../src/SqlSource.Tool/Describing/Postgres/PasswordFile.cs)); the SQL Server describer's `Password`.  [`DatabaseRuns`](../../src/SqlSource.Tool/Describing/DatabaseRuns.cs) applies it, to a failure's message once it is formatted too.  The log of `--log`, through [`SessionRunLog`](../../src/SqlSource.Tool/Logging/SessionRunLog.cs), and the lines of `--verbose`, through [`RunTrace`](../../src/SqlSource.Tool/Logging/RunTrace.cs), have the same removal, and the log searches the strings of an event joined in order and every two of them joined in either order too ([`JoinedRedaction`](../../src/SqlSource.Tool/Describing/JoinedRedaction.cs)).  [`EntrySecretCheck`](../../src/SqlSource.Tool/Describing/EntrySecretCheck.cs) ends the run when a describer put a whole form into an entry of a sidecar.  [`CaptureJson.Write`](../../src/SqlSource.Tool/Describing/Capture/CaptureJson.cs), given the secret, refuses a capture whose strings hold a whole form, a part, or a short or common part as a password key's value, a query's own `password = 'pg'` included, searched alone and joined in order; the describers' fixtures are recorded through it, and `sqlsource diagnose` writes a user's capture only through it, inside `DatabaseRuns`, so the secret never leaves it ([describing](../architecture/tool.md#describing)).  A capture that holds the secret ends the run with `SQLSRC200`, and no bundle is written.  Both describers answer a session that could not be opened, or that ended, with the engine's code and a fixed text of their own (the `ConnectionErrors` of [PostgreSQL](../../src/SqlSource.Tool/Describing/Postgres/ConnectionErrors.cs) and of [SQL Server](../../src/SqlSource.Tool/Describing/SqlServer/ConnectionErrors.cs)), so no driver's message of a connection is passed on.  These are outside all of it:

- **A short or common password outside a password key.**  A part shorter than `ConnectionSecret.MinimumPartLength`, or equal to the database's logical name or the engine's canonical name, `postgres`, is found only after a key that ends in `password`, or is `pwd` or `psw`, and its sign.  A token of one to three characters matches too much ordinary text, and the run prints those words whatever the describer does: the password `postgres` would otherwise turn every error's `query:` line into `query: GetUser, database app, *** 16.4`.  A message that quotes such a password another way, `password 'pg' refused`, keeps it.
- **A login's name in a message of SQL Server.**  The SQL Server describer keeps the message of a server's error of a query verbatim, since it speaks of the query, and such a message can name the login: a query whose three-part name reaches a database that the login may not open is error 916 at `parameters`, `The server principal "app_login" is not able to access the database "billing" under the current security context.`, which `SQLSRC225` prints, the log writes and a capture holds.  The removal takes out the value and the password, and not the login's name, which is no secret and is still the user's.  That is the owner's decision.
- **A server's message in a raw bundle.**  The writer refuses a capture that holds the secret, and keeps the rest of what the server said, so the raw bundle of `diagnose --no-obfuscate` holds an `error`'s message, detail and hint, and `open`'s answer the server's version and settings.  A message that names the host, the database or the user is written, as the log writes it.  Such a bundle is the user's, which the tool says must not be posted, and goes to a maintainer privately, as a log does.  A renamed bundle keeps of an `error` its code, its other numbers (the class, state and type of a SQL Server error, and the position of a PostgreSQL error at `prepare`), and the query parameters it names, in a text the tool writes ([the renaming](../architecture/bundles.md#renaming)), so it holds none of the server's text.  `CaptureJson.Write(DescribeCapture)`, without the secret, writes whatever a capture holds; the renaming writes a renamed capture through it, made from one that was checked.
- **A value in pieces that no search of the log puts side by side.**  `SessionRunLog` searches the strings of an event alone, all of them joined in the order they were written, the names of members among them, the texts of the values joined without the names, and every two of them joined in either order.  A value in three or more strings in an order none of those follows is logged, and so is a short or common password whose key is in one string and whose value is in another, out of order, since the search of every two strings does not look for a key.  A capture is searched for each request and each answer apart, and the strings of one alone and joined in order, but not every two of them, so a value split between a request and its answer, between two calls, or over two strings of one in the reverse order, is written.  An answer holds a catalog's names, and two of them that make a password together would refuse a capture that holds none.  The describer's rule keeps the value out of all of them; the joined searches are for a describer that passes on a text cut in two.
- **A password file read for a user the tool does not know.**  When the string has no `Password` and `PGPASSWORD` is not set, the PostgreSQL describer gives the password of each entry of the file that may match the host, port, database and user, up to the first that surely matches, as Npgsql uses the first that matches.  When neither the string's `Username` nor `PGUSER` names the user, Npgsql takes one from Kerberos or from the system, which the tool does not ask, so every user's entry for that server may match, and each of those passwords is removed: one that equals a word of a message hides that word, as below.
- **A password file that can be read only once.**  A named pipe or the pipe of a shell's process substitution (`PGPASSFILE=<(...)`) is not read, since the describer asks for the secrets before the driver reads the file and would leave it nothing: its password is not removed.  Reading the pipe in the driver's place and handing the driver the tool's copy would take the connection's `ProvidePasswordCallback`, which Npgsql 10.0.3 marks obsolete, or a password provider of the data source, which is not told the host and the user that Npgsql resolves, so the tool would choose the entry in the driver's place.
- **A password that the driver takes from where the describer does not look.**  Npgsql also takes a password, before `PGPASSWORD`, from a provider of the data source, set with `NpgsqlDataSourceBuilder.UsePasswordProvider` or `UsePeriodicPasswordProvider`, and from the connection's `ProvidePasswordCallback`, a property of `NpgsqlConnection`.  The tool sets none of them, so no such password reaches a run today.
- **An entry is searched for the whole forms alone.**  `EntrySecretCheck` does not search for the parts.  An entry holds the names of a catalog and no driver's message, so a part found there would mostly be a name that equals a password, the password `password` beside a column `password` found through `SELECT *`, and `SQLSRC200` would end the run for a common schema.  The owner chose that over the search, so a describer that put a password into an entry would have it written to the sidecar, and printed under `--check`, in the line of `SQLSRC219` that says what the database says.
- **A value that the sidecar holds without the describer.**  `EntrySecretCheck` finds a whole form only when the entry's text holds it and the same text without the describer's part does not.  A value that equals a word of the format, the engine, or the name of the query, of its database or of a parameter is so never found in what a describer gave.  No real connection string has that shape, and the file holds such a value whatever the describer does.
- **A value that equals a word of the describer's part of an entry.**  The text without the describer's part has no column and no type, so a value that equals a key that only those have, `origin` or `nullableSource` for two, ends the run with `SQLSRC200` when a query has a column.  That fails closed, and it is what is left of a wider case: a dummy value of a test or a replay such as `postgres` does not end the run.
- **A password that equals a whole word of what is printed.**  A kept part is removed wherever it stands as a token, so a password that equals a name the server quotes, a column `password` in `column "password" does not exist` with the password `password`, prints that name as `***`.  In the log, two strings of an event that make a password together, the head of one and the start of another, are each written as `***` where they make it.  It leaks nothing and hides a word of the message.

## Why it exists

The tool does not read a connection string itself, so it knows of a value what the describer says: the passwords its driver reads from the value and from the environment, and the text its driver writes the value as.  A form of the value other than those three is found by its passwords alone.  The token rule, the shortest part, the words of the run and the key a keyed part needs trade a little cover for output a user can still read: a dev password such as `test` leaves `latest_orders` alone.  The search of every two strings is the log's alone, and takes no key, because a capture refused for a false find ends the run, and a key over two strings is not a shape any describer writes.  A password file is read for every user the tool cannot tell from another, because the user Npgsql finds is not the tool's to know, and a password too many only hides a word.  A pipe stays unread because the only ways to hand Npgsql the tool's copy are obsolete or would choose the entry in the driver's place.  The search of an entry for the whole forms alone, and a login's name left in SQL Server's messages, are the owner's decisions, for the reasons above.  What a server's message in a bundle keeps was decided by the owner on 2026-11-04, when phase 10 first wrote a capture for a user: its code and the query parameters it names, once renamed, and everything in a raw bundle, which is sent privately.

## Impact

Low.  A driver's message of a connection no longer reaches the output, and a driver quotes a connection string's password as a key's value, which the tool removes whatever its length.  The container tests of `tests/DatabaseTests/Postgres` hold it: `SessionTests` checks that the failure of a wrong password, a missing database, an unreachable host and a terminated backend names neither the host nor the user, and `DescribeCommandTests` that a refused connection and a wrong password leave them out of everything printed and logged.  What is left needs a short or common password that a message quotes without its key, a password file that is a pipe, or a describer that writes a value in pieces against its rule; the rest hides a word too many or keeps a name that is no secret.  The manual's [limit of a short password](../../site/reference/connections.md#limit-short-password) says to search a log for the password before sharing it.  A describer's rule is to put the value, or a part of it, in nothing it returns but `SecretsOf` and `RewriteOf`, and this is the net under that rule, with these holes.

## Proposed fix

For a value in pieces, search a capture's strings two by two, and a keyed part's key over two strings, if a describer is found to write one so.  For a password file read for an unknown user, give the user Npgsql would find, if Npgsql comes to expose it without a Kerberos call.  For a pipe, hand the driver the tool's copy if Npgsql gives a way that is not obsolete and that is told the resolved host and user.  For a password callback or provider, have `SecretsOf` give its password in the change that makes the tool set one.  Search an entry for the parts only if a describer is found to put a password in what it returns.

## Trigger

A user's report of a part of a connection in what the tool printed or logged, or of a word written as `***` that is no password of theirs.
